# Matryoshka: четыре системы CRC и XOR-шифрование

[English](solve.md)

## 0. План и сохранившиеся данные

В задании был stripped ELF64 PIE. При статической проверке бинарника найдены импорты `memfd_create` и `fexecve`, что соответствует описанной в отчёте схеме вложенных исполняемых файлов. Но точная последовательность снятия слоёв и все команды отладки не сохранились.

Главная математическая часть известна целиком: на 16-байтный пароль наложены **четыре CRC32-условия для четырёх последовательных слов по 4 байта**. CRC32 аффинен над GF(2), поэтому каждый четырёхбайтный фрагмент восстанавливается из системы 32 линейных уравнений. Затем полученный пароль повторяется и XOR-ится с 36 байтами внутреннего бинарника.

Порядок решения: изучение ELF → извлечение внутренней стадии → построение CRC-матриц → восстановление пароля → XOR-расшифровка → проверка флага.

## 1. Первичный анализ ELF

Статическая проверка присланного файла дала:

```text
ELF 64-bit LSB pie executable, x86-64, dynamically linked, stripped
interpreter /lib64/ld-linux-x86-64.so.2
```

Команды для проверки:

```sh
file assets/matryoshka
readelf -h assets/matryoshka
readelf -Ws assets/matryoshka | grep -E 'memfd_create|fexecve|write'
```

`memfd_create` создаёт анонимный файловый дескриптор, а `fexecve` позволяет запускать исполняемый файл по дескриптору. Это согласуется с многослойностью, но сами импорты не доказывают, сколько было слоёв и какими командами их извлекали. Придумывать отсутствующий trace не будем.

## 2. Данные из сохранённого решения

В оригинальном `evidence/solve_1.txt` указаны четыре цели:

```python
targets = [0x6d795f63, 0x30306c5f, 0x70343473, 0x77307264]
```

Обозначим `C(x) = zlib.crc32(x)` для четырёх байтов. Из-за начального и конечного преобразований CRC32 аффинен, поэтому сначала убираем константу:

```text
C0 = CRC32(00 00 00 00)
L(x) = CRC32(x) XOR C0
```

Полученная функция `L` линейна: `L(x XOR y)=L(x) XOR L(y)`.

Далее последовательно включаем каждый из 32 битов входного слова. Для бита `j` получаем 32-битный столбец влияния `cols[j]`. Любое слово равно XOR набора одноразрядных базисных векторов, поэтому:

```text
XOR( b[j] * cols[j] ) = target XOR C0
```

Для каждого из 32 выходных битов получаем отдельное уравнение с 32 бинарными неизвестными. Решаем исключением Гаусса над GF(2), где сложение и вычитание — XOR.

## 3. Восстановление четырёх слов

Реализация: [scripts/solve_crc.py](scripts/solve_crc.py).

```sh
python3 scripts/solve_crc.py
```

В отличие от исходного журнала, здесь расчёт перепроверен отдельно. Он даёт:

```text
password (hex): c667c58c3b02d6c91b8def4fdd1bc5f3
CRC[0:4]   = 6d795f63
CRC[4:8]   = 30306c5f
CRC[8:12]  = 70343473
CRC[12:16] = 77307264
```

Все четыре CRC совпали. Полученные байты **не являются текстовым паролем** — это 16 байт бинарного ключевого материала. Из каждого решения собирается little-endian 32-битное слово.

## 4. XOR с извлечённой стадией

Финал сохранённой команды:

```python
data = open('/tmp/gigatool/stage2.bin', 'rb').read()
encrypted = data[0x1b560:0x1b560+36]
flag = bytes(encrypted[i] ^ password[i % 16] for i in range(36))
```

Смещение `0x1b560` относится именно к **извлечённому** `stage2.bin`, не к исходному ELF. Длина — 36 байт, период XOR — 16 байт. Запуск с доступным `stage2.bin`:

```sh
python3 scripts/solve_crc.py --stage2 stage2.bin
```

## 5. Подтверждения и ограничения

По архиву подтверждаются CRC-цели, способ решения и формула XOR. Независимо перепроверены конкретные 16 байт и все четыре CRC. В итоговом отчёте агента указано, что флаг принят (`PP{...}`).

**Не сохранились** команды по снятию каждого слоя, сам `stage2.bin` и вывод финальной расшифровки. Важный момент: здесь это прямо сказано, а не подменено выдуманным логом.

## 6. Вывод

CRC32 — контрольная сумма, не криптографическая защита. Её аффинное преобразование можно выразить матрицей над GF(2) и обратить. Разделение ключа на четыре блока не усложняет восстановление, когда каждый блок проверяется независимо. Повторяющийся XOR тоже не подходит для защиты секретных данных.
