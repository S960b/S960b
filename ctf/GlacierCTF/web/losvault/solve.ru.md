# LosVault — восстановление внутреннего RSA-ключа методом Ферма

[English version](solve.md)

## Подтверждённый этап решения

В предыдущем диалоге **20 ноября 2026** был исследован внутренний TLS веб-сервиса LosVault. Для него использовался набор шифров `TLS_RSA_WITH_AES_128_GCM_SHA256`. Администраторские API `/api/admin/capture-tls`, `/api/admin/transparency/export` и `/admin/review/<id>` защищены ролью `vault-audit`; прямой экспорт отвечал HTTP 403. Очередь обращений к боту обрабатывалась медленно, XSS и traversal-пробы не дали рабочего обхода.

**Публичный TLS** обслуживался сертификатом Let's Encrypt **RSA-2048**, который здесь не уязвим. Нужен сертификат **внутреннего TLS-сервиса RSA-1024**.

## Факторизация

Генератор внутреннего RSA выбирал простые слишком близко: `q≈p+2^240`. Для `N=pq` вычисляем

```text
a=ceil(sqrt(N))
b=sqrt(a²-N)
p=a-b, q=a+b
```

Если `a²−N` полный квадрат, разложение найдено. При 512-битных простых указанное смещение делает метод Ферма чрезвычайно быстрым. Сохранённый из прошлого разговора [losvault_fermat.py](scripts/losvault_fermat.py) проверяет `p*q=N`, находит `d=e^(-1) mod lcm(p−1,q−1)` и сохраняет приватный PEM. Он специально отказывается работать не с RSA-1024, чтобы не атаковать внешний сертификат.

```sh
pip install cryptography
python3 scripts/losvault_fermat.py internal_tls_certificate.pem --out internal.key
```

Можно также передать десятичный или шестнадцатеричный `--modulus`.

## Граница восстановленных данных

В доступной истории сохранился **реальный скрипт слабого RSA** и выводы анализа, но не полный внутренний сертификат, не итоговое использование восстановленного ключа и не запрос с флагом. По списку пользователя задача **принята платформой**, но оставшиеся этапы исторического эксплойта восстановить точно не получилось.

Этот документ — честно обозначенный **частичный райтап**. Он не выдаёт факторизацию сама по себе за извлечение флага и не домысливает пропавшую часть цепочки.
