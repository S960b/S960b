# Нейропитомец: путь решения

## 0. План целиком

Зачем этот раздел: чтобы читатель видел цепочку до деталей и понимал, зачем нужен каждый
следующий шаг.

Дано: файл `neuropet.ab` на 359 458 байт и текст задания «Нейротамагочи в каждый дом, пароль
0000». Больше ничего.

Цель: найти флаг.

План получился такой:

1. Понять, что за формат у `.ab`, и распаковать его.
2. Посмотреть, что лежит внутри: это набор настроек или само приложение.
3. Найти в приложении всё, что похоже на скрытые данные: ресурсы и нативную библиотеку.
4. Разобрать строки библиотеки, чтобы понять, чем она занимается.
5. Прочитать формат приватного контейнера и снять с него шифрование.
6. Разобраться, что за программа лежит внутри, и выполнить её офлайн.
7. Собрать флаг из того, что эта программа выдаёт.

## 1. Что дано

Зачем этот шаг: зафиксировать входной файл и его хеш, чтобы все дальнейшие числа относились к
проверенной копии.

```
$ file neuropet.ab
neuropet.ab: Android Backup, version 1, Compressed, Not-Encrypted
$ sha256sum neuropet.ab
698a730af816cf91f324aeccbdde8ce66d5ca9acb2e367cb8f65d7b26a27eae9
```

Уже на этом шаге видно важное: бэкап **не зашифрован**. Значит подсказка про пароль `0000`
относится не к файлу, а к логике внутри приложения.

## 2. Android Backup: формат и распаковка

Зачем этот шаг: получить из бэкапа то, что внутри, не возясь с паролем, который здесь не нужен.

Формат `.ab` я погуглил, он описан в документации Android. Файл начинается четырьмя текстовыми
строками, и по ним всё понятно без догадок:

```
$ head -c 64 neuropet.ab | xxd
00000000: 414e 4452 4f49 4420 4241 434b 5550 0a31  ANDROID BACKUP.1
00000010: 0a31 0a6e 6f6e 650a 78da ecbb 7554 d64f  .1.none.x...uT.O
```

Строки означают: сигнатура `ANDROID BACKUP`, версия формата `1`, содержимое сжато `1`, то есть
zlib, и `none` вместо пароля шифрования. После четвёртого перевода строки начинается
zlib-поток, он и разжимается в обычный TAR.

Распаковывает мой скрипт `scripts/01_unpack_android_backup.py`. Свой, а не готовый `abe`, потому
что формат простой, а скрипт заодно проверяет заголовок, отказывается работать с шифрованным
бэкапом, распаковывает TAR с проверкой путей, находит внутри `base.apk`, распаковывает его и
печатает размеры нужных записей и хеш APK. Готовый `abe` на Java делает только первое и просит
пароль даже там, где его нет.

```
$ python3 scripts/01_unpack_android_backup.py neuropet.ab --out work
Android Backup: {'version': '1', 'compressed': True, 'encryption': 'none'}
TAR size: 378880
TAR: 1672 apps/com.solarlabs.neuropet/_manifest
TAR: 364193 apps/com.solarlabs.neuropet/a/base.apk
TAR: 71 apps/com.solarlabs.neuropet/f/rList
```

В архиве три записи, и главная из них это `base.apk` на 364 193 байта, то есть само приложение,
а не пользовательские настройки. Хеш полученного APK:

```
$ sha256sum work/base.apk
5c2f61f102bda136956e25867b4a4fa6b2f65592251e4c978ed86d9fbff9ee49
```

## 3. Что лежит в APK

Зачем этот шаг: понять, где искать логику, в Java-части или в нативном коде.

APK это обычный zip, я посмотрел его содержимое и выписал то, что относится к делу:

```
$ unzip -l work/base.apk
    24764  classes.dex
    11320  lib/arm64-v8a/libneurocore.so
    11960  lib/x86_64/libneurocore.so
     1865  assets/neuro/brain.bin
     5342  assets/neuro/skin.dat
   262154  assets/neuro/weights.bin
```

Что это значит. `classes.dex` это скомпилированный Java-код для Android. Файлы `.so` это
нативные библиотеки на C или C++, то есть обычные ELF-файлы под ARM64 и x86-64; версию под
x86-64 удобно разбирать на ноутбуке, потому что она совпадает с привычным `objdump`. Ресурсы в
`assets/neuro` названы как части нейросети: мозг, кожа, веса.

Здесь первая развилка. Названия намекают на нейросеть, но для анализа важнее другое: рядом с
ресурсами лежит своя нативная библиотека, а нестандартные форматы ресурсов почти всегда означают
свою логику чтения. Дальше я пошёл по нативной части.

## 4. Строки нативной библиотеки

Зачем этот шаг: до дизассемблирования узнать, чем библиотека занимается и за что можно
зацепиться.

Команда, которая показывает экспортируемые функции:

```
$ readelf -Ws libneurocore.so | grep Java_com_solarlabs_neuropet
```

Разбираю её по частям, потому что дальше такие команды встречаются постоянно. `readelf` читает
заголовки ELF-файла, то есть нативной библиотеки. Ключ `-W` включает широкий формат вывода, без
переносов длинных строк. Ключ `-s` печатает таблицу символов, то есть список функций и
переменных с адресами. Дальше `grep` оставляет только строки, в имени которых встречается
`Java_com_solarlabs_neuropet`.

Что такое JNI. Это Java Native Interface, механизм, которым код на Java вызывает код на C или
C++. Договорённость простая: если в Java объявлен метод, который должен исполняться нативно, то
в библиотеке обязана быть функция с именем из частей `Java_`, имени пакета, имени класса и имени
метода. Поэтому по имени функции сразу видно, откуда её вызывают, и искать соответствие в Java
не нужно.

В библиотеке нашлись четыре такие функции: `nInit`, `nMoodTick`, `nRun`, `nQuery`. Это методы
класса `com.solarlabs.neuropet.core.Q`: инициализация, тик настроения, запуск сценария и запрос
значения.

Второй заход это поиск строк:

```
$ strings -a -t x libneurocore.so | grep -Ei 'NEUROC|frida|xposed|maps'
     b60 NEUROC1!NEUROC2!NEUROC3!NEUROC4!xposed
     b87 frida
     b8d gum-js
     b9b substrate
    bac /data/local/tmp/re.frida.server
    bcc /proc/self/maps
   1b60 NEUROC1!I
```

`strings` вытаскивает из бинарника последовательности печатных символов, `-a` смотрит весь файл, а
не только секции данных, `-t x` печатает смещение каждого найденного куска в шестнадцатеричном
виде, чтобы потом можно было посмотреть это место в дизассемблере.

Что это даёт. Строка `NEUROC1!NEUROC2!NEUROC3!NEUROC4!` это заготовка сразу для четырёх
маркеров, то есть где-то в коде результаты будут помечаться этими четырьмя подписями. Остальные
строки это имена инструментов динамического анализа и путь к карте памяти процесса, значит в
библиотеке есть проверки на отладку.

Важная оговорка: наличие таких строк само по себе не доказывает, что проверки сработают.
Поэтому я не стал поднимать эмулятор и бороться с детектом, а выбрал офлайн-путь: прочитать
форматы и выполнить нужную часть самому.

## 5. Находим генератор в нативном коде

Зачем этот шаг: понять, как зашифрованы ресурсы, потому что без этого их не прочитать.

Честный порядок действий: сначала мы этого не знали. Была гипотеза, что ресурсы с именами
`brain` и `skin` как-то кодируются, но чем именно, было неизвестно. Поэтому я выгрузил весь
дизассемблер библиотеки в текстовый файл и стал смотреть, что необычного встречается в коде:
редкие константы, обращения к именам ресурсов, побайтовые циклы.

```
$ objdump -d -M intel libneurocore.so > neurocore_x86.asm
```

В районе `0x11a0` нашлось место, где подряд идут умножение на необычную константу, прибавление
второй константы, сдвиг вправо на 16 и исключающее или с байтом:

```
$ objdump -d -M intel --start-address=0x11a0 --stop-address=0x11d0 libneurocore.so
    11a0: 69 f5 6d 4e c6 41   imul   esi,ebp,0x41c64e6d
    11a6: 81 c6 39 30 00 00   add    esi,0x3039
    11ac: 69 ee 6d 4e c6 41   imul   ebp,esi,0x41c64e6d
    11b2: c1 ee 10            shr    esi,0x10
    11b5: 41 32 74 0d ff      xor    sil,BYTE PTR [r13+rcx*1-0x1]
    11ba: 40 88 34 08         mov    BYTE PTR [rax+rcx*1],sil
```

Такая последовательность означает потоковый шифр: число обновляется, из него берётся байт, этим
байтом складывается байт входных данных. То есть расшифровать ресурсы можно, если повторить ту
же арифметику в своём коде. Именно на этом шаге стало понятно, что ресурсы поддадутся разбору.

Что за генератор. Формула `state = (state * a + c) mod m` называется линейным конгруэнтным
генератором. Слово «конгруэнтный» от латинского congruens, «соразмерный»: в арифметике два числа
называют конгруэнтными по модулю, если при делении на этот модуль у них одинаковый остаток.
Генератор линейный, потому что формула линейная, и конгруэнтный, потому что на каждом шаге
берётся остаток по модулю. Здесь `a` это `0x41C64E6D`, `c` это `0x3039`, а `m` равно `2^32`.

Теперь про разрядность, и сначала зачем это вообще обсуждать. Если арифметику повторить в Python
«как есть», следующий байт ключа получится другим, и расшифровка превратится в мусор. Причина в
том, что процессор считает в ограниченных регистрах, а Python этого не делает.

Как это работает. У процессора регистры 32-битные, то есть в них помещается число от нуля до
`0xFFFFFFFF`. Когда два 32-битных числа перемножаются, точный результат занимает до 64 бит, но
процессор оставляет только младшие 32 бита, а старшие просто отбрасывает. Это и называют
переполнением. Например, `0xFFFFFFFF + 1` в 32 битах даёт `0x00000000`, потому что единица
уходит за разряд.

А в Python целые числа не ограничены: `0xFFFFFFFF + 1` честно даст `0x100000000`. Для
иллюстрации на наших числах: `0x41C64E6D * 0x19870419` в 64 битах равно `0x68F0E4986125CA5`, а
процессор оставит младшие 32 бита `0x86125CA5`. Поэтому в Python после каждого умножения и
сложения ставится маска `& 0xFFFFFFFF`: она отбрасывает всё, что вышло за 32 бита, и повторяет
поведение процессора.

## 6. Контейнер brain.bin

Зачем этот шаг: понять, что именно зашифровано и где лежат ключи.

Формат `brain.bin` придуман авторами задания, поэтому «узнать» его из документации нельзя, его
читают по байтам. Смотрю начало файла:

```
$ xxd -g 1 -l 48 brain.bin
00000000: 4e 52 42 43 01 00 02 00 04 6d 6f 6f 64 ad a6 db  NRBC.....mood...
00000010: 86 3e 00 00 00 3e 93 13 ad c3 6a 90 0c 0f 92 85  .>...>....j.....
```

Как это читается. Первые четыре байта `4e 52 42 43` это печатные символы `NRBC`, то есть
сигнатура формата, как у любого контейнера. Дальше `01 00` это версия 1, а `02 00` количество
записей 2, оба числа записаны младшим байтом вперёд, так же как в TAP и в других форматах.

Потом идёт первая запись. Байт `04` слишком мал для числа, зато похож на длину имени, и следом
действительно идут четыре печатных байта `mood`. Дальше четыре байта `ad a6 db 86` ни на что
печатное не похожи, но по смыслу это ключ, то есть seed. Следующие четыре байта `3e 00 00 00`
дают 62, и после них лежит ровно 62 байта, которые не читаются как текст. Значит схема записи
такая: длина имени, имя, seed, размер, шифротекст.

Проверка гипотезы простая: я написал разбор по этой схеме и посмотрел, где окажется указатель
после двух записей. Он встал ровно на конец файла, ни одного лишнего байта не осталось. Если бы
схема была неверной, остались бы или лишние байты, или нехватка. Второй признак: байты после
размера не читаются ни как текст, ни как числа, то есть это шифротекст, а не данные.

Разбор даёт две записи: `mood` с seed `0x86DBA6AD` и длиной 62 байта, и `devroom` с seed
`0xD2020289` и длиной 1766 байт. `mood` это обычное поведение питомца, `devroom` выглядит как
скрытая комната разработчика, поэтому дальше я работаю с ней.

## 7. Снимаем шифрование

Зачем этот шаг: получить байткод, то есть программу, которую останется выполнить.

Суть задачи в двух словах: внутри контейнера лежит не текст, а программа для внутренней машины,
и чтобы до неё добраться, надо снять шифрование тем же генератором, который мы нашли в
библиотеке.

Что делает решатель `scripts/02_solve_neurovm.py`. Он открывает APK, читает из него `brain.bin`,
разбирает контейнер по схеме из раздела 6, расшифровывает обе записи и сохраняет их. Расшифровка
это тот же цикл, что в машинном коде:

```python
state = seed
plain = bytearray()
for x in encrypted:
    state = (state * 0x41C64E6D + 0x3039) & 0xFFFFFFFF
    plain.append(x ^ ((state >> 16) & 0xFF))
```

Запуск на нашей сборке:

```
$ python3 scripts/02_solve_neurovm.py work/base.apk --out solved
NRBC[0]: name=mood seed=0x86dba6ad length=62
NRBC[1]: name=devroom seed=0xd2020289 length=1766
```

Расшифрованный `devroom` начинается байтами `6f 14 00 00 00 14 8c 2d 46 a3 5a 53 05 14 63 93`.
Это не текст и не исполняемый файл, а последовательность инструкций для внутренней машины. Именно
поэтому `strings` по `brain.bin` ничего не находил: до расшифровки там нет читаемых строк.

## 8. Что за виртуальная машина и как её нашли

Зачем этот шаг: понять правила, по которым исполняется байткод, иначе он останется набором чисел.

Виртуальная машина это программа, которая изображает процессор: у неё свой набор команд, свой
стек и свой счётчик инструкций. Байткод для такой машины нельзя запустить на настоящем
процессоре, его исполняет интерпретатор.

Искать интерпретатор логично от точки входа, которой пользуется Java, то есть от `nRun`. В ней
видно подготовку и вызов:

```
$ objdump -d -M intel --start-address=0x21f0 --stop-address=0x2210 libneurocore.so
    21fc: b9 80 f0 fa 02   mov    ecx,0x2faf080
    2201: e8 fa f0 ff ff   call   0x1300
```

Почему это похоже на интерпретатор. Во-первых, вызывается функция `0x1300`, внутри которой
дальше идёт большой блок сравнений и таблица переходов, а таблица переходов это обычный способ
разложить обработчики команд. Во-вторых, перед вызовом в регистр кладётся число `0x2faf080`: это
похоже на лимит шагов, чтобы программа не могла крутиться вечно. Внутри цикла это число
сравнивается со счётчиком исполненных инструкций.

Как устроен выбор команды. Интерпретатор читает байт по счётчику, но перед выбором обработчика
преобразует его арифметически:

```
$ objdump -d -M intel --start-address=0x1408 --stop-address=0x1420 libneurocore.so
    140f: 6b c0 b7         imul   eax,eax,0xffffffb7
    1412: 0f b6 c0         movzx  eax,al
    1415: 83 c0 b5         add    eax,0xffffffb5
    1418: 83 f8 11         cmp    eax,0x11
```

То есть байт умножается на `-0x49`, к результату прибавляется `-0x4B`, и только потом полученное
число сравнивается с `0x11`. Смысл такого преобразования в том, чтобы номера команд в байткоде не
совпадали с номерами обработчиков и код нельзя было прочитать глазами.

Откуда берётся число обработчиков. Сравнение с `0x11` означает: всё, что больше `0x11`,
отправляется в обработку ошибки. Ровно под эти значения в коде лежит таблица переходов, и в ней
восемнадцать адресов, то есть восемнадцать вариантов от нуля до семнадцати. Из них один адрес
ведёт на общий выход из функции, один на ошибку, а остальные шестнадцать это обработчики
команд.

## 9. Какие команды понадобились

Зачем этот раздел: без понимания команд байткод не выполнить, а переписывать машину целиком
незачем.

Нам нужно было не разобрать все команды, а исполнить один конкретный сценарий. Поэтому я брал
только те команды, которые в нём реально встречаются, и для каждой выяснял, что она делает со
стеком, то есть с рабочим списком значений.

Вот что понадобилось. `0x14` кладёт на стек 32-битную константу, это основной способ передать
данные. `0x6F` делает переход по абсолютному смещению, то есть задаёт циклы и ветвления.
`0x29`, `0x30`, `0x37` и `0x3E` это сложение, умножение и исключающее или. `0x22` и `0x1B`
дублируют и убирают значение со стека, без них не собрать выражение. `0x5A` делает один шаг
знакомого генератора над значением на стеке, то есть программа сама себя подмешивает к ключу.
`0x53`, `0x45` и `0x4C` это сдвиги. И `0x7D` выводит готовый фрагмент.

## 10. Что выдаёт программа

Зачем этот шаг: увидеть результат исполнения, ради которого всё и делалось.

Когда наш интерпретатор доходит до команды `0x7D`, он снимает со стека нужное число байтов и
кладёт результат в список вывода. Это не печать на экран, а внутренняя выдача: сценарий
формирует куски строки и отдаёт их наружу. Мой решатель печатает каждую такую выдачу и заодно
сохраняет её в файл `fragment*_encoded.bin`, поэтому результат можно проверить отдельно.

На `devroom` выдача происходит четыре раза:

```
Emit type=1 length=10 bytecode_pc=0x01ce: b'NEUROC1!SOLARCTF{F'
Emit type=2 length=10 bytecode_pc=0x037e: b'NEUROC2!P3f2...'
Emit type=3 length= 9 bytecode_pc=0x053c: b'NEUROC3!i_s3...'
Emit type=4 length= 9 bytecode_pc=0x06e1: b'NEUROC4!n\x00_\x00G\x00a\x00m\x00E\x00E\x00E\x00}\x00'
```

У каждой выдачи впереди маркер `NEUROC1!` и далее по порядку, ровно как обещала строка из
библиотеки. Сразу видно, что склеить куски подряд нельзя: второй не читается как текст, третий
читается, но задом наперёд, а в четвёртом между буквами стоят нулевые байты.

## 11. Разбираем четыре фрагмента

Зачем этот шаг: превратить четыре разных формата в одну строку.

Первый фрагмент самый простой: после маркера лежит обычный текст, начало флага `SOLARCTF{F`.

Второй фрагмент. Он не читается, и единственный параметр рядом, который может быть ключом, это
seed записи. Я предположил, что ключ это один байт из seed, и проверил: второй байт seed равен
`0x02`, а если сложить им каждый байт куска, получается читаемый текст. Проверка на глаз простая:
после преобразования все байты попадают в печатные символы и складываются в осмысленное
продолжение флага.

Третий фрагмент читается, но слова в нём выглядят перевёрнутыми: кусок начинается с буквы,
которая по смыслу должна стоять в конце. Поэтому я перевернул порядок байтов, и текст встал на
место.

Четвёртый фрагмент выглядит как текст с нулями между символами. Это признак двухбайтовой
кодировки: в UTF-16LE каждый символ занимает два байта, и для латинских букв старший байт равен
нулю. Я проверил это декодированием, и получился читаемый хвост флага вместе с закрывающей
скобкой.

Дальше четыре части склеиваются в порядке маркеров, и получается флаг:

```
SOLARCTF{FR1...EEE}
```

Начало и конец строки привожу специально, чтобы было видно, что флаг действительно получен.

## 12. Что не сработало и почему

- Подбор пароля к бэкапу. В заголовке написано `none`, шифрования нет, подбирать нечего.
- Поиск флага через `strings` по `brain.bin`. Сценарии зашифрованы, до расшифровки читаемых
  строк там нет.
- Попытка считать `weights.bin` нейросетью, которую надо запускать. Файл весов есть, но путь к
  флагу через него не идёт.
- Борьба с антиотладкой и запуск APK в эмуляторе. Строки про Frida и `/proc/self/maps` намекают
  на проверки, но офлайн-разбор оказался короче и надёжнее.
- Полная расшифровка `skin.dat`. По коду видно, что это отдельный слой с динамической загрузкой,
  но для `devroom` он не нужен.

## 13. Коротко, одним абзацем

`neuropet.ab` оказался незашифрованным бэкапом, внутри которого лежал настоящий APK. В ресурсах
приложения нашёлся контейнер `NRBC` с двумя зашифрованными сценариями, `mood` и `devroom`, а в
нативной библиотеке нашлись и схема шифрования на линейном конгруэнтном генераторе, и
интерпретатор собственного байткода. Я снял шифрование тем же генератором с маской `2^32`,
восстановил нужные команды интерпретатора и выполнил `devroom` офлайн. Программа выдала четыре
фрагмента с маркерами `NEUROC1` до `NEUROC4`, которые после XOR, реверса и декодирования
UTF-16LE склеились в флаг.

## 14. Выводы

- Формат файла стоит читать, а не угадывать: четыре строки в заголовке `.ab` сразу сняли вопрос
  про пароль.
- Имена ресурсов обманчивы: `brain`, `skin` и `weights` выглядят как нейросеть, а логика
  оказалась в нативной библиотеке и в маленьком контейнере.
- Дешёвая проверка строк по `.so` экономит время: по ним видно и назначение библиотеки, и
  наличие антиотладки, и заготовку маркеров.
- Численную модель надо повторять с той же разрядностью: без маски `2^32` расшифровка не
  сходится.
- Виртуальную машину не обязательно переписывать целиком: достаточно восстановить те команды,
  которые реально встречаются в нужном сценарии.
