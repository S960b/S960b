# Повторное ревью Hermes–ChatGPT bridge

Проверенный коммит: `adfe711c91cd35a1c1d5c4ca4ce572a52f8f19ef`, дата 2026-10-04.
Сравнение: исходный `3b082fe`, предоставленные ранее регрессии и новый REPORT_2.md.

## Вердикт

Основные исправления прошлого ревью приняты. Переписывать мост или менять модель Hermes не требуется. Однако обновлять публичный сервер и объявлять готовность пока рано: не работает внешнее управление отзывом доступа, ошибки events неправильно упакованы, а отмена подписки во время challenge не сохраняется.

Не нужно откладывать первый реальный обмен до построения многопроцессной системы. Ниже отделены обязательные исправления от ограничений, которые можно принять для первого однопроцессного пилота с синтетическими сообщениями.

Приоритеты здесь — порядок допуска: **P0** до публичного подключения, **P1** корректность жизненного цикла для пилота, **P2** дальнейшее укрепление/расширение. Это не оценка CVSS.

## Что исправлено и не требует повторной переделки

- Подпись содержит ID, время подписи и точные байты тела. Независимые проверки challenge/delivery проходят.
- Новая подписка не активируется после неуспешной проверки callback; последовательный повтор снова проверяется.
- HTML экранируется; внутренний login state отделён от клиентского OAuth state, имеет TTL и атомарно потребляется. Добавлен общий лимит входа, который новый state не сбрасывает.
- Адаптер discover/events встроен в factory. HTTP-ответ содержит tools и events; проверки авторизации сохранены.
- Обычная очередь сохраняет первый ответ атомарным условным UPDATE. Лимит UTF-8 и последовательная идемпотентность сохранены.
- Сохраняются байты события, сроки и конечный бюджет повторов; callback использует проверенный IP, TLS hostname/SNI и ограниченный пул; debug отключён и зависимости закреплены.

Исходные assertions предоставленных регрессий не ослаблены. Изменения fixture для реального auth context и перенос барьера гонки с SELECT перед UPDATE соответствуют новой реализации. Остался мёртвый `if False` в тесте гонки — это уборка кода, а не причина отклонять исправление.

## P0 — до включения публичного подключения

### P0.1. Реальный OAuth revoke не подключён и имеет несовместимую сигнатуру

Места: `make_mcp_server` / AuthSettings и `BridgeOAuthProvider.revoke_token`.

**Два воспроизведённых нарушения:**

1. POST `/revoke` возвращает **404**. В AuthSettings не включён `revocation_options`; SDK 2.3.0 по умолчанию не создаёт маршрут и не публикует его в OAuth metadata.
2. SDK вызывает `provider.revoke_token(AccessToken | RefreshToken)`. Реализация ожидает строку и передаёт объект в sqlite bind. Прямая проверка с обоими типами даёт `sqlite3.ProgrammingError: type 'AccessToken'/'RefreshToken' is not supported`.

Существующий тест агента вызывает метод напрямую со строкой. Он проверяет намерение функции, но не контракт SDK и не внешний endpoint. Просто включить маршрут недостаточно: затем проявится ошибка типа.

**Исправление:** объявить `RevocationOptions(enabled=True)` в AuthSettings; привести provider к сигнатуре SDK, извлекая `token.token`. Если нужны локальные строковые вызовы, сделать отдельный явно названный helper, а не подменять публичный контракт. Сохранить проверки клиента и идемпотентность отзыва.

**Приёмка:** настоящий ASGI/HTTP POST `/revoke` с access и refresh token возвращает 200; повтор — также 200; отозванный доступ не допускается к MCP, связанные подписки/доставки прекращены. Metadata содержит настоящий revocation endpoint. Наши проверки `test_real_revoke_endpoint_accepts_sdk_token_model`, `test_provider_revocation_accepts_sdk_object`.

### P0.2. Старое active=True нельзя переносить как доказательство проверки callback

Места: Store migration, `active_subscriptions`, `events_subscribe`.

В `3b082fe` active выставлялся даже после провала challenge. Новый Store сохраняет эти строки активными. При повторной subscribe активная непросроченная строка с тем же секретом также позволяет пропустить challenge. Новый корректный код не исправляет уже неверное состояние старой БД.

Тест создаёт только временную БД со схемой subs исходной версии и активной непроверенной строкой. После открытия новой версией она продолжает считаться активной. Production БД не читалась; существование таких строк именно у владельца **не утверждается**.

**Исправление для обновления старой БД:** одноразовая versioned migration делает старые подписки неподтверждёнными и прекращает их старые outbox-доставки до новой проверки. Зафиксировать schema version/verification generation, чтобы обычный последующий restart новой версии не отменял корректные подписки каждый раз.

**Более быстрый вариант для первого пилота:** новая явно выбранная БД только для синтетических задач; старую сохранить через SQLite backup. Добавить явный BRIDGE_DB_PATH и проверить путь перед стартом. Не удалять старую БД. При последующем переносе данных требование миграции остаётся.

Регрессия: `test_legacy_active_flag_is_not_proof_of_callback_verification`. При выборе пилота на новой БД этот migration-тест может оставаться в группе known limitations; нельзя заявлять безопасный upgrade старой БД.

## P1 — жизненный цикл подключения и доставки

### P1.1. Ошибка callback находится внутри result вместо JSON-RPC error

`events_subscribe` возвращает словарь `resultType=error`; для кастомного метода SDK сохраняет его как обычный успешный result. Реальный HTTP-ответ содержит `result.error.code=-32015`, а поле `error` верхнего уровня отсутствует.

Использовать штатный `MCPError(code=-32015, message='CallbackEndpointError', data=...)` либо поддерживаемый SDK ErrorData. Для invalid params тоже применять правильную ошибку. Нужен HTTP-тест формы ответа, а не поиск числа -32015 в произвольном месте. Предоставленный E2E принимает вложенную ошибку и поэтому этот дефект не обнаруживает.

Регрессия: `test_callback_failure_is_top_level_jsonrpc_error`. Контракт описан в [MCP Events](https://developers.openai.com/plugins/build/mcp-events).

### P1.2. Unsubscribe во время challenge проигрывает позднему результату

Один event loop: subscribe сохраняет pending и ждёт callback; unsubscribe успешно деактивирует строку; успешный поздний callback делает безусловный `save_sub(active=True)`. Подписка снова активна, хотя отмена уже подтверждена.

Нужно поколение/состояние операции и атомарный переход pending → active только для того же неотменённого поколения. Unsubscribe оставляет tombstone/новое поколение. Проверка owner после challenge уже есть, но она не заменяет проверку отмены подписки. Отдельно добавить проверки двух одновременных challenge и смены секрета с обратным порядком завершения.

Регрессия: `test_unsubscribe_during_pending_challenge_wins`. Не удерживать общий mutex через сетевой await так, чтобы unsubscribe вообще не мог отменить pending-запрос.

### P1.3. Поздняя HTTP-ошибка открывает терминальную доставку заново

`mark_delivery` безусловно заменяет done/reason. Даже при **одном** delivery loop: отзыв доступа завершает строку как access_revoked во время HTTP-запроса; поздний 503 меняет её обратно в pending с пустой причиной.

При двух одновременно вызванных delivery loops одна строка отправляется дважды; ответ 503 одного worker может отменить уже записанный delivered другого. Дубликаты HTTP сами по себе допустимы для at-least-once, но изменение завершённого состояния назад — отдельная ошибка.

**Минимум для одного процесса:** защитить вход в deliver_pending от перекрытия и обновлять результат условно, не перезаписывая уже терминальную строку. **Для нескольких процессов:** атомарный claim/lease и generation/fencing в UPDATE; lease должен восстанавливаться после истечения, если процесс упал. Exactly-once HTTP не заявлять.

Регрессии: `test_single_delivery_loop_cannot_reopen_revoked_row`, `test_overlapping_delivery_loops_claim_single_attempt`, `test_successful_delivery_cannot_be_rescheduled_by_stale_failure`.

Для первого пилота достаточно исправить терминальные переходы и явно обеспечить один сервер/один delivery loop; SQLite lease для нескольких процессов можно отложить.

### P1.4. Проверка доступа выполняется до TLS, а не перед записью запроса

`_post_pinned` проверяет allowed, затем вызывает `conn.request`. Если socket ещё не подключён, http.client внутри request выполняет connect/TLS. Между последней проверкой и отправкой тела могут пройти секунды. При отмене подписки в этом промежутке запрос всё равно отправляется.

Детерминированный тест отменяет подписку во время замоканного connect, до записи HTTP-байтов; запись всё равно происходит. Это проверка последовательности операций, не живая TLS-сессия.

Явно выполнить connect/TLS, затем повторно проверить актуальное поколение/active/expiry перед request. При отказе закрыть соединение без записи тела. Абсолютно отменить уже переданные байты невозможно; не обещать этого. Исправляется наблюдаемый длинный промежуток установления соединения.

Регрессия: `test_access_revocation_before_tcp_write_prevents_send`. При изменении транспорта адаптировать mock нового connect-пути, сохранив проверяемый порядок.

## P2 — ограничения расширенного режима

### P2.1. Обмен ранее загруженного OAuth grant не атомарен

Обычный **последовательный HTTP** повтор authorization code и refresh token отклоняется: обе проверки прошли. В текущем одном event loop provider load/exchange не содержат внутренних await, поэтому конкурентная HTTP-эксплуатация этой конфигурации не заявляется.

Однако exchange доверяет ранее загруженному объекту и не проверяет атомарное потребление существующей строки. Два exchange одного объекта дают два комплекта токенов, даже после удаления grant. Это воспроизведено на границе provider; актуально для нескольких процессов, отдельных соединений, задержки между load/exchange и последующей переработки кода.

Перед расширением режима делать DELETE/UPDATE RETURNING и выпуск токенов одной транзакцией; отсутствующий/просроченный grant даёт TokenError invalid_grant. Отдельно проверить межпроцессный повтор и revoke между load/exchange. Регрессии `test_stale_loaded_oauth_grant_cannot_be_exchanged_twice` предназначены именно для укрепления provider, а не доказательства дефекта одиночного HTTP-повтора.

Для первого ограниченного пилота допустимо оставить это ограничение, если принудительно обеспечен один процесс и оно явно записано в отчёте.

### P2.2. Документация и дальнейшая автономность

- Удалить мёртвый Cursor/if False из теста гонки; смысл assertions сохранить.
- Указать правильную модель вызова revoke и реальные endpoints; локальный вызов функции не называть проверкой UI-отключения.
- При реализации ротации секрета предусмотреть краткое совместное подписание старым/новым ключом и не перезаписывать актуальное поколение поздним callback. Это важно для непрерывного режима, но не требует ротации в первой синтетической задаче.
- CLI сначала фиксирует job, затем отдельно ставит event: между двумя commit возможен сбой. Для обещания автономности без потерь нужен общий transactional outbox либо восстановление pending jobs. В первой задаче наблюдать состояние job/outbox, не обещать гарантированную доставку при таком сбое.
- Системный DNS и socket timeout не дают общего конечного времени операции. Известное ограничение bounded pool описано честно; при дальнейшем укреплении добавить общий deadline, не освобождая slot раньше фактического завершения worker.

## Подтверждённые положительные проверки новых сценариев

1. Если существующий auth token удалён во время challenge, повторная require_owner не позволяет активировать подписку. Здесь использован локальный helper-путь текущей реализации со строкой; внешний revoke отдельно не прошёл.
2. После ошибки доставки, закрытия Store и открытия той же временной БД сохраняется тело события; повтор завершается delivered.
3. Повторный последовательный HTTP обмен code отклоняется invalid_grant.
4. Повторный последовательный HTTP обмен refresh token отклоняется invalid_grant.

Пункт 2 подтверждает восстановление состояния outbox, а не полное восстановление процесса/ChatGPT UI после перезагрузки Kali.

## Условия первого живого подключения

1. Исправлены P0.1 и P1.1–P1.4; выбран и проверен вариант P0.2: корректная миграция либо отдельная новая тестовая БД.
2. Сохранён исходный green suite; новые обязательные регрессии проходят. P2 тесты вынесены в явно обозначенную known-limitation группу, если исправление отложено; не выдавать выборочный прогон за все зелёные проверки.
3. Только один сервер и один delivery loop. Старый процесс действительно остановлен/заменён; health/build сообщает фактический git commit нового процесса. Обновление файлов на диске этого не доказывает.
4. Рабочая БД сохранена согласованным SQLite backup; для пилота используются только синтетические сообщения и отдельный сильный пароль. Торговые API-ключи этому мосту не нужны.
5. Реальный UI тест: добавить MCP → пройти OAuth → subscribe именно в нужном Work-чате → поставить одну задачу → получить и прочитать локально `BRIDGE_OK:<job_id>`. Затем один повтор события и одна отмена подписки; после отмены новые события не доставляются.
6. 2xx webhook и локальный OAuth-тест не заменяют ответ нужного чата. До успешного UI обмена сохранить unverified-флаги.

Публичный туннель пока оставить выключенным. SafeTrade не останавливать. Не повторять одинаковые ad-hoc прогоны вместо исправлений; после реальных изменений сделать одну полную приёмку и перейти к одной синтетической задаче.

## Как воспроизвести новые проверки

Распаковать пакет в `research/hermes_chat_bridge` checkout adfe711. В пакете нет замен production-кода. Нужны опубликованные tests/conftest.py и fixtures из test_review_3b082fe.py.

```sh
python3 -m venv .venv-review
.venv-review/bin/python -m pip install -r requirements.lock
PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 .venv-review/bin/python -m pytest tests/test_review_adfe711.py -q --tb=short
```

Для исходного adfe711 ожидается 13 failed / 4 passed, exit 1. Это воспроизведения, не исправления. После смены контракта provider revoke обновить старые строковые tests/helpers на настоящие SDK модели; это исправление тестового входа, а не ослабление assertions. После новых generation/claim механизмов можно адаптировать точки управления гонкой, сохранив смысл тестов.
