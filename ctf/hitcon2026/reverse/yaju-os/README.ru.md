# Yaju OS (reverse)

- **Платформа:** HITCON CTF 2026
- **Категория:** Reverse (встраиваемая / BLE firmware exploitation)
- **Очки / Решений:** 160 очков
- **Дата:** 2026-10-24
- **Remote:** `<host>:6402` (сырой HCI/H4 по TCP, не shell)
- **Флаг:** `hitcon{...}` (замаскирован)
- **Файлы:** `assets/yaju-os-e0b330b2a3740d63.tar.gz` (оригинальный архив), `assets/board_flash.bin` (256 КБ прошивка nRF51422)
- **Описание (официальное):** "My IOT homework_new folder（1）_ver.114514(final）"

Виртуальное устройство nRF51 (Cortex-M0), отдаваемое по TCP как BLE-контроллер
Rootcanal. Настоящий флаг лежит не в файле: секрет живёт в виртуальном MMIO GPIO-
регистре, который отдаёт байты при каждом чтении. Цепочка эксплойта:

1. Реверс скрытой maintenance-команды из прошивки (обфусцированные байты
   декодируются в `11 45 14 19 19 81 00`, то есть `11451419198100`), запись её в
   vendor-характеристику - устройство сбрасывается в загрузчик.
2. Nordic Legacy DFU: init-пакет (wildcard'ы устройства + CRC16) и образ, подпись
   не требуется; загрузчик принимает 176-байтовое неподписанное Thumb-приложение.
3. Нагрузка читает GPIO-секрет в SRAM и сама регистрирует GATT READ-характеристику
   через S130 SVC.
4. Переподключение (та же HCI/TCP-сессия), поиск характеристики
   `66551235-3322-1100-F0EE-CCAA88664422` и чтение флага.

Одна TCP/HCI-сессия должна пережить оба BLE-ресета, потому что каждое TCP-соединение
создаёт свежую изолированную сессию Rootcanal/Qiling.

Файлы:

- `solve.md` - полный райтрайт, включая тупики (английский)
- `solve.ru.md` - тот же райтрайт на русском (рабочая копия)
- `scripts/yaju_solve.py` - полный BLE/HCI эксплойт (Bumble)
- `scripts/yaju_payload.S`, `scripts/yaju.ld` - внедряемая прошивка Cortex-M0 Thumb
- `scripts/yaju_payload.bin` - готовый 176-байтовый ARM-фирмварь
- `scripts/magic_proof.py` - вывод maintenance-ключа из оригинальной прошивки
- `scripts/verify_bundle.py` - автономные офлайн-проверки (только stdlib)
- `scripts/rebuild_payload.sh` - пересборка и побайтовое сравнение пейлоада
- `evidence/remote_success_user.log` - захваченный успешный прогон на remote
- `evidence/local_verifications.log` - повторяемые офлайн-проверки
