# Yaju OS: ход решения

## 0. Общий план

Задача - виртуальный BLE-гаджет. Порт 6402 - не shell и даже не GATT поверх TCP: это
виртуальный Bluetooth-контроллер Rootcanal, говорящий сырым HCI/H4, так что «реверс» тут -
это весь беспроводной стек плюс ARM-прошивка. Флаг не в файле: эмулятор отдаёт его по
кусочкам через виртуальный MMIO GPIO-регистр. План был:

1. Прочитать выданный Python-проект и 256-КБ образ прошивки nRF51422.
2. Понять три фазы рантайма (приложение, maintenance, загрузчик, загруженное приложение)
   и модель HCI/TCP-сессий.
3. Восстановить скрытую maintenance-команду из байтов прошивки и переключить устройство в
   загрузчик.
4. Провести Nordic Legacy DFU, чтобы поставить неподписанное 176-байтовое
   Cortex-M0 Thumb-приложение.
5. Нагрузка читает GPIO-секрет в SRAM и регистрирует GATT READ-характеристику; клиент
   читает её по ATT и забирает флаг.

## 1. Что за бокс

Зачем этот шаг: транспорт и модель памяти определяют всё остальное.

`session_host.py` поднимает изолированные Rootcanal + Qiling для каждого TCP-соединения,
поэтому голого `nc` недостаточно; нужен host-стек (Bumble). Виртуальное устройство -
nRF51, Cortex-M0 / ARMv6-M Thumb, BLE-адрес `F6:F7:F8:F9:FA:FB`. Фазы прошивки:

```text
TCP 6402 / HCI-H4 -- Bumble Host -- Rootcanal -- виртуальный nRF51
                                               |
              1. обычное приложение -------> maintenance (скрытая write-команда)
                     -------------------------> загрузчик (Nordic legacy DFU)
                                          -----> наше Thumb-приложение в 0x1B000
                                                     | MMIO GPIO P0.IN
                                                     +-> GATT READ -> флаг
```

TCP/HCI-сессия должна пережить оба BLE-ресета: дисконнект при них нормален (это
перезагрузка устройства), но новое TCP-соединение создаст другую, чистую сессию
Rootcanal/Qiling и потеряет состояние DFU.

## 2. Секрет живёт в MMIO, а не в памяти

Зачем этот шаг: это отметает очевидные пути «выгрузить файл с флагом».

`hardware.py` задаёт:

```python
GPIO_P0_BASE = 0x5000_0000
GPIO_P0_IN = 0x5000_0000 + 0x510   # 0x50000510
```

`qiling_runtime.py` хукает `_SecretGpioP0`: каждое чтение `P0.IN` возвращает следующий
кусок удалённого секрета и двигает внутренний offset. Секрет никогда заранее не
мапится во flash/SRAM, поэтому кастомный ARM-код обязан сам выполнить MMIO-чтения.
Вторая половина: Qiling принимает только сервисы, которые загруженная прошивка
регистрирует настоящими S130 SVC-вызовами, так что нагрузка должна и прочитать GPIO, и
опубликовать результат как BLE-атрибут.

## 3. Фаза 1: реверс скрытой maintenance-команды

Зачем этот шаг: в прошивке обычного приложения спрятана обфусцированная 7-байтовая
команда; вход в загрузчик требует отправки её по GATT.

`command_handler` рантайма maintenance (символ по 0x1B008, то есть база 0x1B000 + 8)
проверяет 7-байтовую команду побайтовой обфускацией. Байты берутся прямо из образа
прошивки (`magic_proof.py`):

```python
code1 = flash[0x1b75b:0x1b762]   # 82 95 c1 37 4a b0 6e
code2 = flash[0x1b754:0x1b75b]   # 9d 8f 94 23 e8 a3 cd
for i in range(7):
    x = code1[i] ^ code2[i] ^ ((0x11 * i + 0x3d) & 0xff)
    b = ror8(x, (3 * i + 1) & 7)
```

что даёт точную команду:

```text
11 45 14 19 19 81 00   (= 11451419198100)
```

При её приёме оригинальная ARM-прошивка пишет `0xB1` в `POWER.GPREGRET`
(maintenance boot request), и эмулятор перезапускает устройство в загрузчик.
Используемая для отправки GATT-характеристика -
`5A1C0002-7C5D-4C8D-942C-A786C1D58B6D` (write).

## 4. Фаза 2: Nordic legacy DFU без подписи

Зачем этот шаг: загрузчик проверяет метаданные и CRC, но не подпись, значит
неподписанный образ поставить можно.

Загрузчик из `second_stage_runtime.py` вызывает настоящие скомпилированные
`prevalidate_metadata` / `postvalidate_image` - он не принимает любой байтовый поток.
Но это старый Nordic DFU: он проверяет подготовленные поля метаданных и CRC16 образа и
не требует цифровой подписи.

Init-пакет (14 байт):

```python
crc = binascii.crc_hqx(image, 0xffff)
init = struct.pack('<HHIHHH', 0xffff, 0xffff, 0, 1, 0xfffe, crc)
```

Для пейлоада (176 = 0xB0 байт, CRC16 = 0x11CC):

```text
init: ffffffff000000000100feffcc11
```

Последовательность DFU: включить уведомления на Control Point, `01 04` (start DFU,
application), пакет размеров `00 00 00 b0 00 00 00`, ждать `10 01 01`, затем
`02 00` + init-байты + `02 01` (init complete), `03` + пакеты образа по 20 байт,
`04` (validate), `05` (activate and reset). Небольшая задержка `--speed` не даёт
потоку WRITE-WITHOUT-RESPONSE переполнить эмуляцию.

## 5. Фаза 3: Cortex-M0 пейлоад

Зачем этот шаг: загруженное приложение - единственное, что умеет трогать MMIO и
регистрировать характеристику.

`yaju_payload.S` / `yaju.ld` задают raw-приложение в 0x1B000. Первые 8 байт - таблица
векторов (MSP = 0x20007F00, reset = 0x1B009). Ядро цикла:

```asm
ldr r0, =0x50000510      @ GPIO P0.IN
ldr r1, =0x20001000      @ SRAM buffer
movs r2, #64             @ 64 x 4-byte чтений = 256 байт
1:
    ldr r3, [r0]
    str r3, [r1]
    adds r1, #4
    subs r2, #1
    bne 1b
```

Эмулятор продвигает offset секрета при каждом 32-битном чтении; 256 байт хватает на
настоящий флаг. Затем приложение регистрирует primary service и READ-характеристику
через S130 SVC:

- `svc #0x63` - `sd_ble_uuid_vs_add` (vendor UUID base)
- `svc #0xA0` - `sd_ble_gatts_service_add`
- `svc #0xA2` - `sd_ble_gatts_characteristic_add`

со свойствами 0x02 (read), указателем на 0x20001000 и максимумом 256 байт. Итоговый
UUID - `66551235-3322-1100-F0EE-CCAA88664422`. Приложение крутится в вечном цикле,
чтобы GATT-таблица осталась живой.

Это не переполнение в классическом смысле DFU: загрузчик просто принимает
неподписанное контролируемое приложение, а Qiling честно выполняет его GPIO-чтения и
регистрацию GATT.

## 6. Фаза 4: чтение флага

Зачем этот шаг: секрет покидает устройство только через характеристику, которую
опубликовал пейлоад.

После `CTRL 05` клиент ждёт событие дисконнекта, переподключается к тому же BLE-адресу
на ТОЙ ЖЕ HCI/TCP-сессии, обнаруживает новую GATT-таблицу и читает
`66551235-3322-1100-F0EE-CCAA88664422` (для 256 байт продолжается ATT Read Blob).
Хвостовые NUL-байты срезаются, извлекается паттерн флага. Настоящий remote-лог
(`evidence/remote_success_user.log`) показывает строку флага, выходящую из GPIO-чтения.

## 7. Проверка

Зачем этот шаг: всё должно воспроизводиться офлайн после окончания CTF.

`tools/verify_bundle.py` (только stdlib) проверяет: SHA-256 оригинального tar.gz и
прошивки, обратный ключ из скомпилированной прошивки, совпадение пейлоада и солвера с
ранним exploit-zip, длину/выравнивание DFU-образа, таблицу векторов Cortex-M0, маркеры
S130 SVC, CRC16 образа и init-пакет. Вывод заканчивается `COMPLETE_PACKAGE_VERIFIED`.
`tools/rebuild_payload.sh` пересобирает прошивку clang/lld/llvm-objcopy и побайтово
сравнивает (`REBUILD_EXACT_MATCH`). `magic_proof.py` выдаёт `MAGIC_PROOF_PASS
11451419198100`.

## 8. Тупики (не повторять)

- **nc как клиент.** Порт 6402 - сырой HCI/H4, а не чат-линия; обязателен host-стек.
- **Дамп flash/SRAM ради флага.** Секрет генерируется на лету MMIO-чтениями и никогда
  не мапится заранее; дамп ничего не находит.
- **Перезапуск TCP-соединения между фазами.** Новое соединение даёт свежую изолированную
  сессию и DFU-состояние теряется; держи один HCI-транспорт.
- **Подпись образа.** В legacy DFU проверки подписи нет; prevalidate просит только
  валидные метаданные и CRC16.
- **Наивное «прочитать /flag.txt» из приложения.** Из ARM-кода гостя нет доступной ФС;
  единственный путь наружу - зарегистрированный GATT-атрибут.

## Короткая версия

Виртуальный nRF51 отдаёт BLE по HCI/TCP-сокету; флаг подаётся через виртуальный
GPIO-регистр. Скрытая maintenance-команда, восстановленная из прошивки, переключает
устройство в загрузчик; Nordic legacy DFU (без подписи, только CRC16-метаданные) ставит
176-байтовое неподписанное Thumb-приложение, которое читает GPIO-секрет в SRAM и само
регистрирует GATT READ-характеристику; клиент читает её по ATT в той же HCI-сессии и
извлекает флаг.

## Выводы

- Сырые транспорты (HCI по TCP) меняют инструменты: подбирай под протокол настоящий
  host-стек, а не сокетную библиотеку.
- «Прочитать флаг» в эмуляторе может быть MMIO-каналом вместо файла; смотри, какое
  железо захукано, а не какие строки лежат во flash.
- Загрузчик, проверяющий CRC, но не подпись, - примитив исполнения кода по дизайну;
  176-байтового Thumb-пейлоада, публикующего данные через зарегистрированный атрибут,
  достаточно для выноса всего, что отдаёт MMIO.
