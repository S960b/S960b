# Git Dialog: приёмка изолированного пилота

Дата фактической проверки: 27 октября 2026. Это код пилота, **не установленная
замена действующего моста**. Работающий `localhost:8787`, службы, их окружения,
OAuth, подписки, cron и старые задачи/БД не менялись. Нулевой риск не обещается.

Все компоненты и тесты находятся в PRIVATE `S960b/agent-dialogs`, существующей
ветке `implementation/git-dialog-v1`. Main менять нельзя. Commit пакета приёмки
сообщается отдельно после публикации: нельзя писать собственный SHA внутрь себя.
`ACCEPTANCE.json.source_base_commit` — проверенный родитель, не SHA нового пакета.

## Безопасная воспроизводимая проверка

Получить **точный согласованный SHA** через уже настроенный SSH в отдельную чистую
кодовую копию, без reset/force/потери чужих изменений. Использовать отдельное
тестовое окружение с Python3.12 или3.13 и pytest9.1.1, не venv служб. Не копировать
туда PAT, рабочие БД, конфигурацию моста или секреты.

Из корня копии:

```sh
git rev-parse HEAD
python --version
python -m pytest --version
PYTHONPATH=src python -m pytest tests -q
python -m compileall -q src
git status --short
```

Ожидается362 теста. Все они блокируют сеть/subprocess; SQLite только в tmp_path.
Никакого живого Git API или реального закрытия в suite нет. При необходимости
`APPDIR`/`APPIMAGE` убираются только из окружения тестового процесса, не служб.

При отдельном поручении и только после зелёного suite можно **один раз**:

```sh
timeout 25s env PYTHONPATH=src python -m git_dialog.preview_smoke --self-test
```

Это синтетическая виртуальная `task_preview_fixture`, не ветка/задача в Git.
Только127.0.0.1:0, фиксированные маркеры; no PAT/files/SQLite/GitAPI/grants/login.
Статусы `[200,200,405,405,404,403,400]`, security_headers passed, shutdown
joined_and_socket_closed, rootSHA256
`05f7537abe6f81a4ef34d1a3789c2a80dcd9fb1dc5a79ab5e78ade60fbf21e11`.
Тест сам завершится; служба, браузер, Funnel или постоянный preview не создаются.
Этот уже выполненный smoke не надо повторять ради очередного ACK.

## Что запрещено повторять и как реагировать на сбой

- Не запускать старые `live_probe`, `journal_probe`, `worker_probe` снова на
  выросшей истории. Их фиксированные seq/HEAD — исторические canary-поручения.
- Не сбрасывать журнал/attempted/consumed и не создавать новый ID для обхода
  неизвестного результата. `started`/`unknown` не разрешают новое исполнение.
- При `publication_unknown`/`closing_unresolved` — только точное read-only
  reconcile. Отсутствие ответа/ACK не означает, что записи не было.
- При исчезновении ref или опубликованного результата — остановить запись;
  не create-ref, не force, не восстанавливать удалённую ветку.
- При истёкшем/отозванном доступе — конкретная ошибка, без поиска другого токена,
  продления срока или расширения прав. PAT и его путь остаются локально у MT.
- Сохранить canary-БД отдельно. Не мигрировать/подключать их как рабочие БД моста.

## Граница переноса в рабочую систему

Это **не команда на установку**. Дальнейший production-перенос должен отдельно
определить разрешённую точку интеграции, неизменяемые резервные копии, отключённый
по умолчанию запуск и откат без потери истории. Нельзя менять защищённые действующие
службы/панель, OAuth/подписки/cron или доступы под видом обычного теста.

Реальная авторизация человека ещё не подключена. `AccessAuthority.issue()` —
только trusted host после проверенного login, не публичная выдача прав по строке
owner. Все cooperating writers, включая ChatGPT, должны проходить через одну
развёрнутую authority/registry; текущие прямые Git-клиенты этому не равны.
Постоянный Git-polling/исполнитель также не установлен.

Delete в HTML всегда disabled. `confirm_close` только готовит терминальный intent;
он не публикует barrier и не удаляет ref. Closing после явного подтверждения —
необратимое локальное прекращение публикаций, не отменяемое pending UI-намерение.
Ticket с expected_head **не является условным GitHub DELETE**. Удаление реальной
ветки требует подлинного пользовательского подтверждения и отдельно проверенного
общего пути всех writers. Пилотную ветку не использовать как тест удаления.
Даже удаление ref не обещает физического стирания объектов Git.
