# Куча дежавю (DejaHeap v10): путь решения

## 0. План целиком

Зачем этот раздел: чтобы читатель видел всю цепочку до деталей и понимал, зачем нужен
каждый следующий шаг.

Дано: сервис принимает на вход программу для своего интерпретатора и исполняет её. На
сервере рядом лежит файл с флагом, а доступ к файлам идёт через отдельный брокер по общей
памяти.

Цель: заставить сервис отдать содержимое файла с флагом.

План был такой:

1. Понять, что за файл перед нами и как с ним разговаривать.
2. Разобраться, из чего состоят значения интерпретатора: числа, объекты, буферы, хендлы.
3. Понять устройство кучи и сборщика мусора.
4. Найти в сборщике ошибку, из-за которой остаётся указатель на уже несуществующий объект.
5. Заставить интерпретатор скопировать данные по этому указателю в общую память, которую
   читает клиент.
6. Подделать запрос брокеру так, чтобы он открыл файл с флагом.
7. Прочитать файл штатным запросом и забрать флаг.

## 1. Что это за файл и как с ним говорить

Зачем этот шаг: не начинать реверс вслепую, а сначала выяснить тип файла и интерфейс.

Тип файла смотрю утилитой `file`:

```
$ file assets/dejaheap_v10
dejaheap_v10: ELF 64-bit LSB executable, x86-64, version 1 (SYSV), statically linked,
BuildID[sha1]=4ab208..., stripped
```

Что это значит по пунктам. `ELF 64-bit` это формат исполняемого файла для 64-битного
Linux. `statically linked` означает, что все библиотеки вкомпилированы внутрь, отдельных
`.so` рядом нет. `stripped` означает, что из файла удалены имена функций, поэтому в
дизассемблере не будет подсказок вроде `main` или `parse`. Тип `EXEC` (в отличие от `DYN`)
означает, что файл не перемещаемый: он всегда загружается по одним и тем же адресам, и
значит адреса глобальных переменных из дизассемблера совпадают с адресами в памяти. Это
важно, потому что дальше мы будем ссылаться на конкретные адреса.

Следующий шаг это спросить у самой программы, что она умеет. Запускаю её с ключом помощи:

```
$ ./assets/dejaheap_v10 --help
usage: ... [options] <program.vm>
  --trace            print every executed instruction (author build)
  --dump             disassemble and exit (author build)
  --stats            print engine counters on exit
  --flag=PATH        flag file (default flag.txt)
  --space-kb=N       bytes per semispace (default 64 KiB)
  --steps=N          abort after N instructions
  --test-hooks       enable the author-only test instructions
  -                  read the program from stdin
```

Из этой справки сразу берутся важные факты, и их не надо угадывать. Программа принимает
файл с расширением `.vm`, либо читает программу со стандартного ввода, если указан `-`.
Размер полупространства кучи по умолчанию 64 КиБ, это ключ `--space-kb`. Есть ограничение
на число инструкций `--steps`. Есть ключ `--flag`, который задаёт путь к файлу с флагом,
по умолчанию это `flag.txt`. Ключи `--trace`, `--dump` и `--stats` помечены как авторские,
и я проверил, что в этом бинаре они не работают:

```
$ ./assets/dejaheap_v10 --dump /tmp/mini.vm
vm: unknown option --dump
```

Теперь про язык. Строк с мнемониками в бинаре нет, я это проверил поиском по файлу, поэтому
список инструкций и их арность берутся из описания задачи, а не из самого файла. Зато
поведение каждой инструкции можно проверить запуском, и это я делал постоянно. Пример
минимальной программы:

```
.func main
 const r10 72
 putc r10
 const r10 105
 putc r10
 nl
 exit
.end
```

Что здесь что. `.func main` открывает функцию с именем `main`, точка в начале строки
означает директиву для интерпретатора, а не инструкцию. `const r10 72` кладёт число 72 в
регистр `r10`. `putc r10` печатает символ с кодом из регистра, 72 это латинская `H`.
Дальше `const r10 105` и `putc r10` печатают `i`, потому что 105 это код `i`. `nl` печатает
перевод строки. `exit` завершает программу. `.end` закрывает функцию.

Запускаю и смотрю результат:

```
$ printf '.func main\n const r10 72\n putc r10\n const r10 105\n putc r10\n nl\n exit\n.end\n' > /tmp/mini.vm
$ ./assets/dejaheap_v10 < /tmp/mini.vm
Hi
```

Программа напечатала `Hi` и вернула код 0, это я проверил через `echo $?`. Отсюда два
вывода. Первый: на вход идёт текст на собственном языке. Второй: это интерпретатор, то есть
программа не выполняет машинный код напрямую, а разбирает наш текст и исполняет его у себя.
Значит и атаковать надо не машинный код, а среду исполнения: память интерпретатора, его
объекты и его взаимодействие с брокером.

Насколько строг разбор, проверяю неизвестной инструкцией:

```
$ printf '.func main\n frobnicate r1\n exit\n.end\n' | ./assets/dejaheap_v10
vm: fault
```

Программа не подсказывает ни списка инструкций, ни позиции ошибки, а просто пишет `vm:
fault` и завершается с кодом 1. Поэтому единственный надёжный способ проверять гипотезы об
инструкциях это запускать маленькие программы и смотреть результат. Так я и делал дальше.

## 2. Числа, объекты, буферы, хендлы и регистры

Зачем этот шаг: вся атака состоит в подмене полей объектов, поэтому нужно точно знать, как
объект устроен и как отличить его от числа.

Сначала про регистры. Регистр здесь это не регистр процессора, а именованная ячейка внутри
интерпретатора, вроде `r0`, `r10`, `r31`. Программа обращается к ним по имени, а
интерпретатор хранит их значения в своей памяти. В регистре может лежать либо число, либо
ссылка на объект.

Почему нельзя путать число и ссылку. Инструкции вроде `getb`, `setb`, `hread` ожидают
ссылку на объект: они читают заголовок объекта, берут оттуда тип и длину и работают с
данными. Если подсунуть вместо ссылки число, интерпретатор пойдёт по этому числу как по
адресу и либо упадёт, либо прочитает мусор. Поэтому важно понимать, что именно лежит в
регистре.

Как они различаются технически. По разбору диспетчера видно, что целые хранятся с тегом:
значение записывается как `(n << 1) | 1`, то есть младший бит всегда единица. Ссылки
выровнены на 16 байт, поэтому их младший бит ноль. Отсюда правило: младший бит единица это
число, ноль это ссылка.

Теперь устройство объекта. Заголовок такой:

```
+0x00  type (u32)
+0x08  len  (u64)
+0x10  data
```

То есть первые четыре байта это тип, следующие восемь это длина, дальше идут данные. Тип
говорит, что это за объект. В коде встречаются четыре типа: 1 это строка или набор байт,
2 это буфер, 3 это хендл, 4 это корутина.

Буфер это объект типа 2: у него есть длина и область данных, в него можно писать по
индексу и читать из него. Хендл это объект типа 3, он описывает открытый ресурс: в `+0x08`
лежит дескриптор, то есть число, по которому операционная система или брокер различает
открытые ресурсы, а в `+0x0c` лежит тип ресурса или смещение. Корутина это объект типа 4,
в нём интерпретатор хранит состояние приостановленного выполнения, что-то вроде отдельного
потока; в этой задаче я его не использовал.

Что эти типы и раскладка не выдуманы, а проверены, я подтвердил отладчиком `gdb`.
Запускаю программу, которая создаёт буфер и завершается:

```
.func main
 const r1 16
 buf r0 r1
 exit
.end
```

Ставлю в `gdb` остановку на системном вызове завершения процесса и снимаю память:

```
$ gdb -q -batch -x /tmp/g2.txt ./assets/dejaheap_v10
Catchpoint 1 (call to syscall exit_group)
```

Дальше выгружаю отображённую область и ищу в ней заголовки. Нашёлся объект по адресу
`0x7ffff7fd3000` со значением типа 2 и длиной 16, дальше идут 16 байт данных. Кроме него в
памяти были объекты типа 1 и типа 3, то есть строки и хендлы. Так я получил подтверждение
раскладки заголовка и нумерации типов не из текста, а из живой памяти процесса.

## 3. Куча и сборщик мусора

Зачем этот шаг: ошибка, которую мы будем использовать, живёт в сборщике мусора, поэтому
надо понимать, как он устроен и где именно ошибается.

Куча состоит из двух полупространств, каждое по 64 КиБ, это значение по умолчанию из
`--help` (ключ `--space-kb`). Аллокатор простой, его называют bump: он выдаёт следующий
свободный кусок по возрастанию адреса и не ищет дырки.

Сборщик копирующий. Работает он так. Есть набор корней, то есть мест, откуда начинается
обход: регистры, стек вызовов, глобальные структуры, которые интерпретатор считает живыми.
Сборщик идёт от корней по ссылкам, находит все достижимые объекты, копирует их во второе
полупространство подряд и объявляет первое полупространство свободным.

Теперь определение, которое нам понадобится. Висячий указатель это указатель на объект,
которого уже нет: память по этому адресу либо освобождена, либо занята другим объектом.
Если такой указатель остался в каком-то месте, программа считает, что объект жив, а на
самом деле там уже что-то другое.

Откуда висячий указатель берётся в копирующем сборщике. Если ссылка на объект лежит в
месте, которое сборщик не считает корнем, то при копировании он про этот объект не знает:
не скопирует его и не обновит ссылку. Объект переедет или исчезнет, а ссылка останется
указывать на старое место. Это и есть use-after-free, использование после освобождения.

Как это приближает к флагу. Если у нас есть ссылка на место, где после сборки оказался
другой объект, то команда, которая читает данные по этой ссылке, прочитает не то, что мы
туда клали изначально, а то, что там лежит сейчас, включая заголовок и служебные поля.
А если интерпретатор умеет копировать содержимое такого объекта в общую память, то мы
получаем не только чтение, но и возможность подменить поля запроса к брокеру. Дальше
остаётся заставить брокер открыть файл.

## 4. Как я нашёл глобальную структуру экспорта

Зачем этот шаг: нужно найти конкретное место, где интерпретатор хранит ссылки на объекты
вне кучи, чтобы проверить, входит ли оно в корни сборщика.

Метод был такой. Во-первых, я посмотрел, какие глобальные области вообще есть у бинаря.
Во-вторых, искал в дизассемблере места, где в глобальные адреса записываются указатели на
объекты: это видно по инструкциям записи в память вида `mov [rip+смещение], rax` рядом с
кодом, который работает с объектами. Так нашлась область около `0x50cea8`, куда пишет
инструкция `hexport`.

Проверил я это не на глаз, а экспериментом в `gdb`: сравнил состояние глобалов у двух
программ, одна без `hexport`, вторая с ним. Сначала программа только создаёт буфер:

```
0x50cea0: 0x0
0x50cea8: 0x0
0x50ceb0: 0x0
```

Все три слова нулевые, то есть контейнер пуст. Потом программа создаёт буфер и вызывает
`hexport`:

```
0x50cea0: 0x00007ffff7fe2290
0x50cea8: 0x00007ffff7fe22b0
0x50ceb0: 0x00007ffff7fe22b0
```

Появились три указателя, это классическая тройка начало, конец, вместимость у вектора, то
есть динамического массива. Значит по этому адресу действительно лежит контейнер, куда
попадают ссылки на экспортируемые объекты.

Дальше я разобрал код самой сборки и увидел, с каких мест начинается обход кучи. Этот
контейнер в список корней не входит. Отсюда вывод: объект, зарегистрированный через
`hexport`, для сборщика не существует, и после сборки запись в контейнере становится
висячей.

Зачем нам это: это и есть вход в уязвимость. Мы сами регистрируем объект, сами вызываем
сборку, и после неё у нас на руках указатель на чужое место, которое мы можем подготовить
своим новым буфером.

## 5. Как экспорт превращается в копирование

Зачем этот шаг: висячий указатель сам по себе ничего не даёт, нужно, чтобы интерпретатор
что-то сделал с ним по нашей команде.

`hexport` устроен так: он регистрирует объект в контейнере и вызывает переданную функцию.
Когда эта функция завершается, то есть на инструкции `ret` её кадра, интерпретатор
выполняет копирование в общую память:

```
memcpy(ring + off, saved_object, min(saved_object->len, lim))
```

Что здесь что. `ring` это общая память, тот самый сегмент, который клиент отображает себе и
читает. `off` это курсор, накопленное смещение, оно хранится в глобале `0x50cf68`. `lim`
это ограничитель: он равен `0x1c8`, если флаг самопроверки по адресу `0x50ce8c` не ноль, и
`0x100000` в противном случае. Сам `hexport` не даёт курсору уйти дальше `0x80`, это видно
по сравнению в диспетчере около `0x409589`.

Как я убедился, что копирование действительно происходит на `ret` и действительно читает
данные по сохранённой ссылке: я собрал программу, где после `hexport` и возврата из
функции в общей памяти появились байты, которых там раньше не было, и они совпали с data
объекта. В конце концов это же и подтвердил рабочий эксплойт: он читает данные, которые
лежат в буфере, созданном уже после экспорта.

Зачем нам это: получился примитив чтения памяти. Мы подсовываем висячий указатель,
интерпретатор сам копирует содержимое того, что оказалось по этому адресу, в общую память, а
клиент читает её без всяких ограничений.

## 6. Почему большая копия невозможна: страница R+0x1000

Зачем этот шаг: я хотел копировать побольше, чтобы за один раз получить больше данных, и
надо было понять, есть ли такое ограничение.

Первая попытка была наивной: экспортировать объект побольше и получить длинную копию. Она
упала с `SIGSEGV` на адресе `ring + 0x1000`. Причина видна в дизассемблере: копирование
делается циклом побайтово, это участок около `0x4c9675`:

```
4c9678: and    edx,0x7
4c967b: je     0x4c9682
4c967d: movs   BYTE PTR [rdi],BYTE PTR [rsi]
```

Дальше я снял карту отображений своего процесса (для локального запуска это законно, это мой
собственный процесс) и увидел раскладку: `ring = R`, `spaceB = R + 0x2000`, `spaceA = R +
0x12000`. Страница `R + 0x1000` в момент копирования не отображена: там был временный
буфер брокера на 4096 байт, который к моменту копирования уже снят.

Вывод: любая копия длиннее `0x1000 - off` гарантированно падает. Поэтому идея «скопировать
много и сразу получить всё» отпадает, и дальше вся работа идёт в маленьком окне.

## 7. Мёртвый буфер и переиспользование места

Зачем этот шаг: окно копирования маленькое, значит нужен объект с нужной длиной и нужными
данными именно по старому адресу.

Сначала определение. Мёртвый буфер это объект, на который в программе больше нет ссылок.
Он создан, но никто им не пользуется, и для сборщика он мусор.

Какую ссылку он теряет: ссылку в регистре. В программе это выглядит так, что после создания
буфера мы затираем регистр нулём, и объект остаётся без ссылок.

```
buf r0 16
const r0 0        ; ссылка на буфер стёрта, объект стал мусором
buf r5 16         ; следующий буфер, его мы экспортируем
hexport r5 worker
```

В функции `worker` выполняется `gc; gc; buf N; ...; ret`, то есть две сборки, потом
создание нового буфера, потом возврат. После двух сборок новый буфер встаёт на то место,
где раньше лежал `r5`.

Почему адрес совпадает, и о каком адресе речь. Речь об адресе, который сохранён в
контейнере экспорта: это адрес объекта `r5` на момент `hexport`. Аллокатор выдаёт память
по возрастанию адреса, а сборка освобождает первое полупространство целиком. Поэтому
первый же буфер после сборки начинается с того же места, где начиналось полупространство, и
если перед сборкой это место занимал `r5`, новый объект встанет ровно туда же. На практике
пришлось подобрать паддинги 56 и 64 байта, чтобы выравнивание совпало и для внешней, и для
внутренней раскладки.

Зачем нам это: теперь мы управляем содержимым по старому адресу. Мы сами решаем, какая
будет длина и какие байты прочитает копирование.

## 8. Подпись запроса и ключ сессии

Зачем этот шаг: брокер принимает только запросы с правильной подписью, поэтому без неё
подменённые поля ничего не дадут.

Как я узнал, что подпись вообще есть. Первый поддельный запрос брокер не выполнил. Тогда я
посмотрел строки бинаря утилитой `strings` и нашёл служебные строки протокола: `HELLO`,
`FLUSH %d`, `DEJA_BROKER`, `%u %u %llu`. По ним видно, что есть рукопожатие и есть запрос с
форматом полей. Дальше в дизассемблере я нашёл функцию по адресу `0x408130`, которая
считает 64-битное значение по 32 байтам заголовка запроса, и именно это значение брокер
сверяет.

Как устроена подпись. Вход это 32 байта, они собираются из шести полей:

```python
data = struct.pack("<IIIIQQ", op, kind, fd, counter, key, length)
```

То есть два 32-битных поля, ещё два 32-битных, затем два 64-битных. Алгоритм это
собственная конструкция автора: четыре раунда по восемь байт входа, четыре 64-битных слова
состояния, перемешивание через сложения, исключающее или и циклические сдвиги. Я разобрал
его по инструкциям функции и перенёс в Python.

Ключ это последнее 64-битное поле. Он приходит в ответе на `HELLO`: клиент читает ответ,
берёт третье поле и хранит его по адресу `0x50cf58`, а кроме того кладёт его в общую память
по смещению `ring + 0x98`, откуда интерпретатор читает его инструкцией `ringpeek`. Это
видно и по коду, и по тому, что без чтения ключа из общей памяти подпись не сходится.

Ключ случайный на каждое соединение, поэтому подпись нельзя посчитать заранее на своей
машине. Значит её должна посчитать сама программа на языке интерпретатора.

Тут нужен был способ проверить, что моя реализация совпадает с нативной. Для этого я сделал
оракул. Оракул в данном случае это эталон: функция, которая для заданного входа выдаёт
правильный ответ, снятый с настоящего кода. Я взял у нативной функции несколько контрольных
значений на конкретных входах, а затем написал `scripts/dh_mac_exact.py`, который считает
то же самое на Python, и сравнил. Скрипт печатает результат сверки:

```
op=1, expected=0xc978e7a6ee7de9c7, actual=0xc978e7a6ee7de9c7, match=True
op=2, expected=0xb92f335964a4c1c8, actual=0xb92f335964a4c1c8, match=True
```

Совпадение на контрольных входах означает, что алгоритм перенесён верно, и теперь ему можно
доверять при генерации программы.

Как эту подпись считает генератор `scripts/dh_runtime_mac_vm.py`. В интерпретаторе нет
64-битной арифметики с нужными сдвигами, поэтому каждое 64-битное слово представлено парой
32-битных регистров: младшая половина и старшая половина. Генератор это обычный код на
Python, который печатает текст программы: он заводит буфер на 256 байт, читает ключ из
общей памяти по смещению `0x98` инструкцией `ringpeek`, выполняет четыре раунда
перемешивания на парах регистров через `add`, `xor`, `shl`, `shr` и `and`, а затем
записывает восемь байт результата обратно в заголовок запроса по смещению `0x88`
инструкцией `bset`. То есть генератор не считает подпись за нас, он создаёт программу,
которая считает её во время исполнения на сервере.

Зачем нам это: подпись перестала быть препятствием. Программа сама считает её правильной для
наших подменённых полей.

## 9. Раскладка общей памяти и протокол

Зачем этот шаг: чтобы знать, какие именно поля менять и откуда читать ответ.

Раскладку я собрал из двух источников: из формата строк, которые нашлись через `strings`
(там видно `FLUSH %d` и `%u %u %llu`), и из разбора кода, который эти поля заполняет.

```
+0x80  op            u32
+0x84  kind/offset   u32
+0x88  MAC           u64
+0x90  fd            u32
+0x94  counter       u32
+0x98  key           u64
+0xa0  length        u64
+0xa8  status        u32
+0xac  broker answer u64
+0xb4  count         u32
+0xc8  data
```

Дальше цепочка протокола по шагам, чтобы было видно, откуда каждое требование.

Рукопожатие. Клиент отправляет `HELLO`, получает ответ вида `1 <sid> <key>`, где `sid` это
идентификатор сессии, а `key` это ключ подписи. После этого клиент отображает сегмент
`/dev/shm/djv8_ring_<sid>`, это и есть общая память.

Открытие. Инструкция `hopen` формирует запрос на открытие и кладёт поля в общую память.
Инструкция `hflush` собирает строку `FLUSH %d`, отправляет её брокеру и делает один `read`
на 8 байт. Длину ответа она не проверяет, поэтому короткое чтение тоже принимается. Потом
она смотрит `status` по смещению `0xa8` и, если там ноль, переносит ответ из `0xac` в хендл
целиком, восемь байт.

Чтение. Инструкция `hread` требует, чтобы хендл был типа 3, а буфер типа 2, и падает, если
дескриптор в хендле равен `0xffffffff`. Она формирует запрос с `op=2`, `kind` берёт из
старших 32 бит ответа на открытие, `fd` из младших, увеличивает счётчик и подставляет
длину. Ответ брокер кладёт в общую память, и клиент читает его по смещению `0xc8`.

Зачем нам это: из этой раскладки видно, что для открытия файла достаточно подменить два
поля, `op` и `kind`, а чтение можно сделать штатной инструкцией.

## 10. Поддельный запрос на открытие

Зачем этот шаг: получить дескриптор файла, хотя штатной команды открыть произвольный файл у
нас нет.

Идея опирается на момент копирования. `hexport` внутри функции регистрирует запись, а
копирование происходит на `ret` этой функции, то есть уже после `hopen`, но до `hflush`.
Значит, если в висячем слоте к моменту `ret` лежат подготовленные байты, они перезапишут
поля запроса прямо перед отправкой. Вложенные вызовы `hexport` позволяют подготовить два
запроса за один запуск: сначала открытие, потом чтение.

Отдельная проблема это лимит инструкций. Справка говорит про ключ `--steps=N`, и на сервере
он задан. Чтобы измерить бюджет, я использовал пробную программу `scripts`-набора: она
печатает `B`, а дальше каждые сто инструкций `nop` печатает число. Когда бюджет
заканчивается, программа падает, и последнее напечатанное число даёт нижнюю оценку бюджета.
Локально тот же механизм проверяется ключом `--steps`:

```
$ ./assets/dejaheap_v10 --steps=300 dh_step_budget_probe.vm
B
100
200
vm: fault
```

Так я узнал, что бюджет на сервере с запасом покрывает примерно 3200 инструкций, и уложил
программу примерно в 2505 строк.

Результат первого поддельного открытия: брокер ответил `status=0` и выдал `fd=4`. Дескриптор
это число, которым операционная система нумерует открытые файлы; получив его, мы можем
ссылаться на открытый файл, не зная его пути. Именно это и нужно, чтобы добраться до флага:
файл открыт, осталось его прочитать.

Зачем нам это: у нас на руках номер открытого файла, и мы можем просить брокер прочитать из
него данные.

## 11. Штатное чтение и флаг

Зачем этот шаг: прочитать файл по полученному дескриптору, не подделывая второй запрос.

После открытия `hflush` перенёс ответ в хендл. Дальше штатная `hread` сама собрала запрос
`op=2`, `kind=0`, `fd=4`, счётчик 1 и правильную подпись, потому что ключ у неё есть, а
поля она берёт из хендла. Брокер вернул данные, и `ringpeek` прочитал их из общей памяти по
смещению `0xc8`.

Маркеры в выводе это наши собственные метки, а не сообщения программы. В программе перед
каждой стадией стоит пара инструкций вида `const r10 65` и `putc r10`, где 65 это код буквы
`A`. Я расставил их сам, чтобы по выводу понимать, до какой стадии дошло исполнение, если
что-то упадёт. Отсюда и порядок букв: `W` и `G` стоят внутри функции `worker`, поэтому
печатаются раньше, чем `C` и `D`.

```
A B W G M C D F 0 0 0 0 4 0 0 0 R S SOLARCTF{...}
```

Восемь чисел `0 0 0 0 4 0 0 0` это напечатанные побайтово значения из ответа брокера: статус
и дескриптор. `R` и `S` отмечают переход к чтению и успех чтения, после чего печатается
флаг.

Зачем нам это: это конец цепочки, от висячего указателя до конкретных байтов флага.

Готовый байткод лежит в `scripts/win_open0_full.vm`, отправка выполняется скриптом
`scripts/submit_remote.py`:

```
DH_HOST=<host> DH_PORT=<port> python3 scripts/submit_remote.py scripts/win_open0_full.vm
```

Перегенерировать программу под другое значение `kind` можно так:

```
python3 scripts/dh_op1_probe_gen.py --kind 0 -o /tmp/open0.vm
```

## 12. Что не сработало и почему

- `kind=8` в поддельном открытии. Ответ не приходил, чтение висело около тридцати секунд до
  таймаута обёртки. Похоже, такой ресурс ведёт себя как пайп, а не как файл. С `kind=0`
  сразу получился читаемый дескриптор 4.
- Перебор дескрипторов. Бессмысленно: читаемость канала определялась полем `kind` при
  открытии, а не номером дескриптора.
- Копия длиннее окна. Всегда падала на неотображённой странице `R + 0x1000`.
- Рассинхронизация подтверждения. Клиент читает подтверждение одним `read` на восемь байт и
  не сверяет длину. Теоретически это тоже ошибка, но на реальном брокере воспроизвести
  стабильно не удалось, в эксплойт это не пошло.
- Отладка под отладчиком. В строках бинаря есть `/proc/self/status` и `TracerPid`, то есть
  программа проверяет, не отлаживают ли её. Когда я запускал под `gdb`, флаг самопроверки по
  адресу `0x50ce8c` становился равен единице, ограничитель копирования падал до `0x1c8`, и
  уязвимость маскировалась. Часть проверок пришлось делать без отладчика, по маркерам.

## 13. Коротко, одним абзацем

Экспорт объектов не входит в корни сборщика, поэтому зарегистрированный объект становится
висячим после сборки, а его место занимает новый буфер. На возврате из функции, которой
принадлежит запись, интерпретатор копирует этот буфер в общую память, что даёт управляемую
подмену полей запроса. Подпись считается по случайному ключу сессии, поэтому её считает
сама программа на лету. Подделав открытие с `kind=0`, я получил дескриптор 4, затем штатное
чтение прочитало файл, и `ringpeek` забрал флаг.

## 14. Выводы

- Копирующий сборщик безопасен ровно настолько, насколько полон список корней. Любой
  глобальный контейнер с указателями, добавленный в обход корней, даёт use-after-free.
- Полезно сразу строить модель памяти: теги, типы объектов, раскладка кучи. Это окупается,
  когда нужно предсказать, что окажется в висячем слоте.
- Лимит инструкций измеряется пробной программой и ключом `--steps`, а не оценивается на
  глаз.
- Проверка на отладчик внутри программы меняет поведение, и это стоит обнаружить рано,
  иначе часть наблюдений окажется ложной.
