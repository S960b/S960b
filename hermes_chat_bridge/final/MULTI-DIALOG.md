# Отдельный диалог — отдельная ветка (P30)

> **Актуализация 6 ноября 2026:** ниже сохранены исторические сведения о P30. Для современных отправок обязательно начать с [CHATGPT_GIT_BRIDGE.md](CHATGPT_GIT_BRIDGE.md). Схемы MCP нужно проверять в каждом чате; текущий наблюдавшийся интерфейс не содержит `dialog_view`/`dialog_append`.

## Контракт

Один новый диалог моста получает новый `task_id` и **собственную корневую**
ветку `dialogs/<task_id>`. Ветка не ответвляется от пилотной переписки или кода:
исходный коммит содержит только `task.json` и `state.json`, `parents=[]`.
Сообщения другого диалога не наследуются. Пилот и прежняя история сохраняются.

Начать диалог могут обе уже авторизованные стороны: ChatGPT через MCP,
MT через существующий Unix CLI. Создатель получает первый ход. Идентичность
стороны определяется OAuth/Unix peer policy, не параметрами запроса.

Сервер не получает ID вкладки ChatGPT. Поэтому нет скрытого распознавания
«нового чата» и нет общего изменяемого `current_task`. При начале нового чата
без заданного ID клиент **один раз** вызывает создание. Для продолжения старого
диалога пользователь явно передаёт его ID. Во всех чтениях/записях ID обязателен.
Запрос без ID отклоняется, а не попадает в тестовую задачу.

## Инструменты обычного чата: фактически обнаруженный набор 06.11.2026

| Действие | Инструмент |
| --- | --- |
| Новый диалог | `dialog_create(request_id, title)` |
| Проверить неопределённое создание | `dialog_creation_status(request_id)` |
| Список диалогов без загрузки тел | `dialog_list(offset=0, limit=20)` |
| Индекс выбранного диалога без тел | `dialog_index(task_id, offset=0, limit=20, order="newest")` |
| Прочитать здоровье/ход | `dialog_health(task_id)` |
| Уведомить о **уже созданном** Git-коммите | `dialog_notice(task_id, head, message_id, seq)` |

`request_id` — новый случайный стабильный идентификатор **на диалог**, не на
сообщение. Сохранить его до вызова; затем сохранить возвращённый `task_id`.
Одинаковый request ID и инициатор обозначают тот же диалог. Другой title с тем
же ID — конфликт, а не новая ветка. Разные инициаторы не выдают себя друг за друга.
Нельзя автоматически создавать ещё один диалог из-за таймаута/ошибки.

Ответ создания `status="confirmed"` означает независимую проверку Git и локальную
регистрацию. Он содержит `task_id`, `branch`, `head`, `waiting_for`, `created`.
После создания первый текст нельзя передать через `dialog_notice`: он не принимает body. Если доступный текущий инструмент `dialog_append` отсутствует, действовать только по строго проверенному fallback-алгоритму в [CHATGPT_GIT_BRIDGE.md](CHATGPT_GIT_BRIDGE.md).

По умолчанию история — **новые сообщения сверху**, offset отсчитывается от
новейшего. `order="oldest"` сохраняет адресацию по возрастающим seq: сообщение
seq N читается с offset N-1 и limit 1. Чтение ограничено страницей, а также
256 KiB сериализованных тел; сообщения не обрезаются. Модель не получает весь
архив. Серверная проверка целостности выбранной ветки по-прежнему читает её
историю (до прежних 1000 сообщений/8 MiB), не истории остальных веток.

Список — локальные метаданные зарегистрированных диалогов, не обход Git/тел.
Для старой вручную зарегистрированной задачи title может быть null; это не
повод автоматически переименовывать, переносить или заново создавать её.

## MT: тот же существующий Unix CLI

В уже проверенной копии проекта, тем же интерпретатором/окружением, stdin JSON
для `python -m git_dialog.unix_authority cli`:

```json
{"op":"create_dialog","request_id":"UNIQUE_STABLE_REQUEST_ID","title":"Название новой задачи"}
```

Затем, подставляя **фактически возвращённый** task_id:

```json
{"op":"view","task_id":"RETURNED_TASK_ID","offset":0,"limit":20,"order":"newest"}
```

Запись: `op=append`, обязательные `task_id`, `head`, `message_id`, `kind`, `body`.
После неопределённого создания — только `op=creation_status` с тем же request ID.
Чужие actor/role/repository/path/credential параметры запрещены.
Текст переписки остаётся данными, не правом выполнять произвольные команды.

## Стойкость и ограничения

Новый private-файл `authority-creations.p30.sqlite` (600 в существующем STATE700)
хранит только метаданные намерений создания. Существующие lifecycle/append/worker/
event базы не сбрасываются и их схемы не изменяются. Намерение потребляется
durably ДО сетевой записи; кандидат сохраняется ДО единственного POST нового ref.
После потери ответа разрешена только GET-сверка точного кандидата; отсутствие
ветки не разрешает повторное создание. Обычный append никогда не создаёт ref.
Отменённые/закрываемые/tombstoned ID не оживают через повторное создание.

Это не изоляция от владельца PAT/UID, не внешнее fencing и не право на удаление.
Права/секреты/службы/панели/подписки не меняются данным модулем.

Автоматического запуска агента на новые ветки здесь нет. Обычный чат остаётся
полуавтоматическим: MT читает по ID по команде владельца. Старый native outbox
сохраняет прежнюю пилотную область; оповещения новых диалогов нельзя выдавать за
автоматически подключённые. Work-наблюдатель также не начинает обрабатывать все
новые задачи. Перед развёртыванием надо обновить его пилотное чтение на явный ID
и `order="oldest"` для точного seq. Это не перенос полномочий между чатами.

Фактический taskboard8789 не меняется этим патчем: его source binding пока
не получен. Новый `dialog_list`/`dialog_view` — API для отдельных карточек и
историй, не утверждение, что работающий старый интерфейс уже переключён на Git.

## Правило для нового обычного чата

Сначала открой [CHATGPT_GIT_BRIDGE.md](CHATGPT_GIT_BRIDGE.md) и сверь текущий набор инструментов. Если я передал task_id, продолжай только его: сначала
`dialog_index` и `dialog_health` с этим ID, затем чтение тела по точному Git HEAD через GitHub. Если task_id отсутствует и я начинаю новую задачу,
один раз вызови dialog_create с новым стабильным request_id и коротким title;
сохрани возвращённый task_id и покажи его мне. Каждую дальнейшую запись и
чтение адресуй этому ID. Не выбирай автоматически пилотную/последнюю задачу.
Историю читай начиная с последних сообщений. При неопределённом результате
не создавай новый ID и не повторяй запись: только проверка прежнего запроса.
