# Ревью первой версии Hermes Chat Bridge

Дата: 2026-10-04. Проверенный коммит: `3b082fee6b29b22d56b2bcc432dae5753040f0a5`.

## Решение

Разработку на этой основе продолжать можно. Подключать версию `3b082fe` к ChatGPT и передавать реальные сообщения пока рано. Обнаружены воспроизводимые ошибки доставки, авторизации формы входа и конкурентной записи. Проблема SDK существует, но устраняется небольшим адаптером: ждать следующего SDK или переписывать весь транспорт не требуется.

Если публичный мост уже запущен, временно остановить именно его публичный туннель до исправления формы входа. Сбор SafeTrade этим решением не затрагивается.

## Что действительно проверено

Исходники получены через git и проверены в отдельном checkout точного коммита. Рабочая копия владельца и действующие процессы на его Kali не изменялись. Тесты используют временные SQLite-базы, синтетические токены и локальный ASGI TestClient. Внешние callbacks, реальные пароли, торговые ключи и интерфейс подключения ChatGPT не использовались.

Это полезная основа. Сквозной обмен с настоящим ChatGPT пока не подтверждён.

## Обязательные исправления

### 1. Подпись webhook неверна — блокирует challenge и доставку

В `bridge_server.py`, `_sign_body`, подписывается `timestamp.body`. Для Standard Webhooks подписываемые байты должны иметь вид `webhook-id.timestamp.raw_body`. Отсутствует первый компонент. Независимый проверяющий код отклоняет подпись и при `verify_callback`, и при `deliver_pending`.

Изменить сигнатуру функции так, чтобы ID передавался явно; подписывать точные исходящие байты, без декодирования и повторной сериализации. Использовать проверенную библиотеку либо независимые эталонные векторы. Для нового challenge создавать новый ID. Проверка `sig.startswith('v1,')` в CLI не подтверждает правильность подписи.

Регрессии: `test_verification_accepted_by_independent_standard_webhooks_verifier`, `test_delivery_signed_with_id_and_exact_body`.

### 2. Непроверенная подписка становится активной

`events_subscribe` записывает `active=True` до проверки callback. При неуспешном challenge строка остаётся активной. Повтор того же запроса обнаруживает существующую строку, пропускает challenge и возвращает успешный результат. Обе ситуации воспроизведены.

Сначала хранить состояние pending/inactive; переводить в active только после успешной проверки. Наличие строки не равно успешной проверке. Повтор неуспешного запроса должен снова проверяться и оставаться ошибкой при отказе. Изменение секрета/callback требует корректной повторной проверки. Не заменять рабочую подписку непроверенными параметрами при неудачном обновлении.

Регрессии: `test_failed_challenge_leaves_no_active_subscription`, `test_failed_challenge_rechecked_on_repeat`.

### 3. Форма входа интерпретирует входные данные как HTML

`login_page` вставляет параметр `state` в HTML-атрибут без экранирования. Безвредный тестовый маркер превращается в настоящий HTML-элемент. Это подтверждённая HTML-инъекция и риск XSS; исполнение JavaScript или получение чужих данных не проверялось.

Экранировать значения атрибутов с учётом кавычек или использовать шаблон с autoescape. `/login` должен принимать только существующее непросроченное внутреннее состояние авторизации. Сейчас `load_state` не проверяет возраст: состояние возрастом 24 часа позволяет получить код после правильного пароля. Очистка при создании следующего состояния не обеспечивает TTL при чтении. Добавить явный срок, одноразовое атомарное потребление и ограничение попыток входа. Не считать переданный OAuth client state внутренним доверенным идентификатором сессии.

Регрессии: `test_public_login_does_not_interpret_state_as_html`, `test_old_login_state_rejected`.

### 4. SDK действительно теряет events; рабочий обход уже приложен

В `mcp==2.3.0` модель `ServerCapabilities` не содержит events. Runner сериализует core-ответ и удаляет неизвестное поле даже при возврате словаря из обработчика. Это подтверждено HTTP-тестом, а не только чтением моделей.

`discover_events_compat_poc.py` добавляет middleware, которое после `call_next` дополняет уже сериализованный результат `server/discover`. Действует только для протокола `2026-07-28` и успешного результата. HTTP-авторизация и валидация SDK остаются на обычном пути. Четыре проверки адаптера прошли: JSON содержит tools/events, без токена 401, с чужим resource 401, tools/list сохранён.

При интеграции вызывать `install_discover_events_compat(mcp)` внутри `make_mcp_server` перед возвратом сервера. Зафиксировать версии mcp/mcp-types и тестировать ответ после обновлений: используется внутренний атрибут `_lowlevel_server`. Это доказательство локального обхода SDK, а не доказательство подключения ChatGPT и не исправление остальных ошибок.

### 5. Сроки подписки и повторная доставка

Воспроизведено:

- `refreshBefore` возвращается числом epoch, а не строкой ISO8601 с часовым поясом;
- очередь отправляет ранее поставленное событие уже просроченной подписке;
- при 1000 накопленных попытках ошибка 503 всё ещё оставляет доставку бесконечно повторяемой;
- при повторе меняется timestamp внутри тела того же события.

Исправить формат срока, учитывать запрошенный ttlMs, проверять действительность подписки непосредственно перед отправкой. Задать конечный бюджет повторов по попыткам/возрасту и сохранять причину завершения. Сериализованное тело, eventId и время возникновения фиксировать при постановке события; время попытки в заголовке может обновляться. Отзыв доступа должен прекращать связанные доставки. Уникальность outbox по подписке и событию должна предотвращать случайное дублирование при повторном триггере.

Регрессии: `test_refresh_before_is_timezone_aware_iso_string`, `test_no_delivery_after_subscription_expiry`, `test_retries_eventually_become_terminal`, `test_body_and_occurrence_timestamp_stable_across_retry`.

### 6. Ответы могут молча перезаписываться при конкуренции

`Queue.put_reply` отдельно делает SELECT и безусловный UPDATE. Два соединения, прочитавшие пустой ответ, оба возвращают replied с разными ответами; последний UPDATE перезаписывает первый. Это воспроизведено управляемой гонкой двух соединений SQLite.

Нужна атомарная запись с условием `reply IS NULL`, проверкой числа изменённых строк и разбором повторного/конфликтующего ответа в корректной транзакции. Блокировка только внутри одного экземпляра Queue недостаточна: CLI и сервер могут использовать разные соединения/процессы. Сохранить первый принятый ответ; другой должен явно конфликтовать.

Регрессия: `test_queue_concurrent_reply_cannot_silently_overwrite`. При смене алгоритма допустимо адаптировать инструментирование гонки: текущий тест ставит барьер после SELECT. Смысл проверки сохранять — два разных ответа не могут оба успешно заменить пустое поле.

## Дополнительные проблемы, установленные чтением кода

Эти пункты не выдаются за результаты живой атаки или подключения ChatGPT.

1. `_validate_callback_url` проверяет DNS, затем urllib разрешает имя ещё раз при соединении. Это оставляет разрыв для DNS rebinding. Проверять и использовать фактический адрес соединения, сохраняя TLS-проверку исходного hostname. Запрещать credentials в callback URL и редиректы; явно учитывать поведение прокси. Добавить локальный детерминированный тест подмены DNS, не делать запросов к внутренним адресам реальной сети.
2. `_http_post` — async-функция с блокирующим urllib. Медленные callbacks блокируют обработку остальных запросов. Использовать неблокирующий клиент или ограниченный worker pool с таймаутами; не потерять проверку адреса при замене транспорта.
3. Principal подписок извлекается из `ctx.request_state`, которого нет в используемом контексте SDK; затем молча берётся owner. Получать подтверждённый AccessToken через механизм auth context SDK и проверять subject. Для однопользовательской версии явно разрешить только настроенного владельца во всех tools/events. Очередь не содержит owner, поэтому многопользовательскую изоляцию сейчас заявлять нельзя. Не заменять отсутствие principal значением по умолчанию.
4. У tools не объявлены явные securitySchemes и аннотации чтения/записи. Привести описание к реальному OAuth scope и поведению инструмента. Наличие глобальной защиты /mcp само по себе не доказывает нужное поведение UI.
5. В `bridge_cli.py` команды list/subs делают return внутри цикла: показывается только первая строка. Перенести return после цикла, включая случай пустой выдачи.
6. Отключить debug для публичного сервера. При отсутствии BRIDGE_PASS лучше отказывать в запуске, чем создавать неизвестный владельцу пароль. Добавить воспроизводимый requirements/lock и инструкции установки. Тестовый пароль в локальной фикстуре допустим; он не должен использоваться публичным сервером.

## Порядок следующей работы для Hermes

1. Ограничить публичный доступ к мосту на время ремонта формы входа. Остальные исследовательские процессы не трогать.
2. Исправить подпись, проверку/активацию подписки, форму входа и TTL состояния; интегрировать узкий обход SDK.
3. Исправить формат/сроки событий, конечные повторы, атомарную запись ответа, principal и соединение с callback. Дополнить сохранённые регрессии проверками изменённых путей.
4. Прогнать тесты после изменений один раз; повторять после новых правок или обнаруженной ошибки. Не заменять исправления одинаковыми отчётами о повторных ad-hoc прогонах. Не ослаблять смысл падающих проверок ради зелёного статуса.
5. Прислать коммит, сохранённые тесты, точные команды и их результаты. Не писать «11/11, один блокер» или «инструменты подключены», если UI ChatGPT не участвовал.
6. После локальных проверок выполнить один ограниченный реальный обмен: подключение в UI → OAuth → подписка → синтетическая задача → ответ `BRIDGE_OK:<job_id>` → чтение того же ответа локальной CLI. Отдельно проверить повтор события и перезапуск. Только этот обмен подтвердит мост к нужному чату; 2xx callback означает приём события, а не уже записанный ответ.

До такого обмена явно держать `chatgpt_connected`, `subscription_verified`, `same_chat_verified`, `roundtrip_verified` в состоянии unverified. Не менять модель Hermes и не подключать платный OpenAI API ради устранения этих дефектов.

## Воспроизведение

Распаковать пакет в `research/hermes_chat_bridge` проверяемого checkout. Исходные файлы из git пакет не заменяет.

Проверенное окружение: Python 3.12.14, mcp 2.3.0, mcp-types 2.3.0, pytest 9.1.1, httpx 0.28.1, starlette 1.7.0, pydantic 2.13.5, uvicorn 0.54.0. Транзитивные зависимости в этом ревью не зафиксированы; production lock требуется отдельно.

```bash
python -m venv .venv-review
.venv-review/bin/python -m pip install mcp==2.3.0 mcp-types==2.3.0 pytest==9.1.1 httpx==0.28.1 starlette==1.7.0 pydantic==2.13.5 uvicorn==0.54.0
PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 .venv-review/bin/python -m pytest tests/test_review_3b082fe.py -q --tb=short
PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 .venv-review/bin/python -m pytest tests/test_discover_compat_poc.py -q --tb=short
```

Первой команде pytest на исходном 3b082fe соответствует exit 1 и результат 12 failed/4 passed. Второй — exit 0 и 4 passed. При интеграции адаптера в исходный factory тесты PoC не должны добавлять тот же middleware повторно: обновить fixture под новый production путь.
