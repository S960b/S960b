# SafeTrade Research

Сбор публичных котировок Binance, OKX, Bybit и SafeTrade, анализ опережения цены и
виртуальные сделки. API-ключи не нужны. Реальные заявки программа не отправляет.
Это исследовательская версия, а не готовый торговый бот.

## Установка

Из каталога `research/safetrade`:

```bash
python3 -m venv venv
./venv/bin/python -m pip install -r requirements.lock.txt
./venv/bin/python -m pytest tests -q
```

`requirements.lock.txt` фиксирует проверенные версии. `requirements.txt` задаёт диапазоны.
Старые вспомогательные скрипты и `reference/` не входят в основной запуск.

## Запуск

```bash
./venv/bin/python cli.py doctor
./venv/bin/python cli.py collect --minutes 60 --symbols BTCUSDT
./venv/bin/python cli.py replay --symbol BTCUSDT
./venv/bin/python cli.py analyze --symbol BTCUSDT
./venv/bin/python cli.py paper --symbol BTCUSDT
./venv/bin/python cli.py dashboard --port 8501
```

Панель открывается по адресу **http://127.0.0.1:8501** на том компьютере, где запущена команда.
Сборщик и панель запускаются в отдельных терминалах. Панель обновляется каждые 5 секунд;
анализ и paper запускаются отдельными командами. Публичного размещения нет.

По умолчанию используется одна последняя запись по метаданным времени её начала.
Можно выбрать `analyze --run-id st_...` или `paper --run-id st_...`.
Разные run/boot не соединяются по монотонным часам.
Глобальные `--config` и `--data-root` указываются **перед** командой.

### Ограничение памяти (длинные сессии)

Один час сбора по одной паре даёт ~1.9 млн событий. Полный анализ такой сессии
(построение стаканов по каждому событию) требует ~10 ГБ RAM и на многих машинах
завершается по нехватке памяти. Для работы с длинными сессиями добавлен честный
срез: `replay/analyze/paper --window-min N` анализирует только последние N минут:

```bash
./venv/bin/python cli.py analyze --symbol BTCUSDT --window-min 10
./venv/bin/python cli.py paper --symbol BTCUSDT --window-min 10
```

Без флага команды работают по полной сессии и могут упасть по памяти (OOM) —
в этом случае повторите с `--window-min`. Разбиение полной сессии на
последовательные окна и потоковая обработка без хранения всего run в памяти
пока не реализованы.

## Проверка без бирж

```bash
./venv/bin/python scripts/make_demo.py --out /tmp/safetrade-demo
./venv/bin/python cli.py --config /tmp/safetrade-demo/config.yaml --data-root /tmp/safetrade-demo analyze
./venv/bin/python cli.py --config /tmp/safetrade-demo/config.yaml --data-root /tmp/safetrade-demo paper
./venv/bin/python cli.py --config /tmp/safetrade-demo/config.yaml --data-root /tmp/safetrade-demo dashboard
```

Это **искусственные** данные с задержкой SafeTrade 10 секунд. Они проверяют программу,
но не доходность стратегии. Сокращённый разогрев премии в demo не меняет рабочий конфиг.

## Что считается

- `R(t)` — медиана **трёх внешних** свежих mid, SafeTrade не входит. Нужны 3/3.
  Используется отдельный BBO-канал каждой биржи, а не смесь BBO и глубины.
- `b(t)` — медиана прошлых пар `log(SafeTrade(u)/R(u))`. Каждая пара относится к одному
  моменту получения; текущая пара не участвует в собственной оценке.
  По умолчанию окно 30 минут, минимум 10 пар и 15 минут истории, максимальный возраст b 60 секунд.
- `F0=R0*exp(b)` фиксируется в момент сигнала. Без разогрева F0 недоступна.
- Положительный lead/lag означает: SafeTrade повторяет внешнее движение позднее.
  Корреляция измеряется ретроспективно; она не является прогнозом.
- Достижение R0/F0 — первый **наблюдаемый** hit, не точное время пересечения в тишине.
  Пробелы дают `unknown`; уже достигнутая цель и отсутствующая премия имеют отдельные статусы.
  `message_bin_occupancy` — частота наблюдений, не работоспособность соединения.
- W — окно движения внешней цены; D — проверка сохранения движения перед решением;
  L — моделируемая задержка заявки; H — время до решения о выходе, отсчитываемое от входа.
  Нет основания выбирать их только по одному удачному прогону.

## Что ограничивает SafeTrade

REST-снимки сохраняются независимо от WS, с временем отправки, получения и RTT.
WS-дельты сохраняются, но **не добавляются к REST-снимкам**: общая последовательность
для синхронизации пока не подтверждена. REST даёт редкие наблюдения, а не непрерывный стакан.

Поэтому эти снимки доступны на панели и в информационном анализе, но не допускают
paper-входы. Виртуальный счёт при таких данных должен показывать отказы, а не выдуманную прибыль.
Для реального исследования исполнения нужно сначала подтвердить протокол WS-снапшота,
дельт, переподключения и последовательности либо подобрать другой проверяемый источник.

## Виртуальные счета

Каждая комбинация гипотезы, L и бюджета получает **свой** счёт со стартовыми $100.
Результаты вариантов не складываются. На счёте разрешена одна позиция; комиссия входит в бюджет.
Фильтр входа использует стакан в момент решения. На момент прихода заявки проверяется исполнение
по заранее выбранному ограничению цены и полному объёму. Неисполненная заявка отклоняется.
Это условная модель полного исполнения, а не утверждение о поддержке FOK биржей.

Выход в этой версии — по H, с задержкой L и полной глубиной bid. Стопы, очередь maker-заявок,
частичные исполнения и переводы между биржами не моделируются. Неизвестный выход остаётся
`open_unknown`, уменьшает доступные деньги и запрещает следующие входы; equity может быть неизвестной.
Если неизвестно исполнение уже выбранной заявки на вход, её бюджет резервируется,
счёт получает `entry_unknown` и прекращает новые входы.
Строки сделок сохраняются в CSV, отдельные счета и отказы — в JSON.
Комиссия 10 bps пока является допущением; точность объёма и минимальный ордер требуют проверки.

## Файлы и длительный сбор

`data/raw` — исходные ответы JSONL/gzip; `data/parquet` — нормализованные события;
`data/state.db` — статус и текущие данные панели. Ссылки `raw_ref` используют байтовые смещения
в распакованном JSONL. Отчёты в `reports/` имеют run_id; короткое имя — последняя версия.
Прежние отчёты в репозитории относятся к старому коду и не подтверждают прибыльность.

Писатель работает последовательно вне цикла получения данных, закрывает буферы и при тишине,
а при остановке добивает очередь. Ошибка записи, переполнение или нехватка диска прекращают run
с состоянием `failed`. Такой run требует проверки качества перед использованием.

`scripts/collector_watchdog.sh` использует `flock` именно для процесса сборщика.
Для остановки создайте `logs/COLLECTOR_STOP` и завершите запущенный процесс Ctrl+C либо SIGTERM.
После аварийного выхода маркер предотвращает автоматическое возобновление до проверки причины.

## Следующий этап

1. На компьютере пользователя проверить live-доступ, здоровье потоков и сохранение raw/Parquet.
2. Подтвердить пригодный для исполнения стакан SafeTrade; редкие REST-снимки этого не доказывают.
3. Собрать несколько дней событий и выбрать рынки по спреду, глубине и фактической активности.
4. Зафиксировать гипотезы и провести отдельные хронологические dev/validation/holdout прогоны.
   Автоматическое разбиение и статистическая проверка преимущества ещё не реализованы.
5. Рассматривать реальную торговлю только после измерения издержек и устойчивого результата.

Binance/OKX/Bybit пока зафиксированы как диагностические источники. Исторический выбор «из топ-5»
в `reports/exchange_selection.md` требует перепроверки: Pionex имеет публичный WS `/wsPub`.
Сбой сети или обращение к приватному endpoint не доказывает отсутствия публичного API.
