# Sticker Booth - разбор (pwn: путаница счётчика ссылок, UAF, чтение файла)

## Знакомство: что за программа

Описание: "A place where you can safely customize your stickers and print them out!" (Место, где можно безопасно кастомизировать стикеры и распечатать их!)

В архиве: бинарь `chall`, `recipe_docs.md` (мануал), `sample.recipe` и папка `assets/` с тремя крошечными файлами (`heart.txt`, `star.txt`, `smile.txt` - по несколько байт).

Программа - «конструктор стикер-листа». Она читает команды из стандартного ввода, по одной на строку. Из мануала:

- `photo NAME W H RGBA_HEX` - добавить фото, пиксели это W*H*4 hex-байт (RGBA)
- `caption NAME TEXT` - добавить текстовую подпись
- `builtin NAME heart|star|smile` - добавить встроенный стикер
- `mono NAME` - применить монохромный фильтр к фото
- `remove NAME` - удалить элемент
- `upload NAME HEX` - загрузить свой стикер как сырые hex-байты
- `print` - напечатать лист

Сначала я скормил программе простой рецепт (фото + print), чтобы увидеть формат вывода. Потом стал разбираться в устройстве: уязвимости в таких бинарях ищутся по коду, а не перебором, поэтому первым делом - статический анализ.

## Как я читал бинарь (какими программами)

- `file chall` - x86-64 ELF, статически слинкован, без PIE, **не stripped**.
  Статически слинкован - вся программа в одном файле, без внешних библиотек. Без PIE - адреса фиксированные (это потом пригодится для gdb). Не stripped - в файле остались имена функций и глобальных переменных, то есть читать его можно по именам, а не угадывать.
- `nm chall` (то же даёт `readelf -s`) - список символов с адресами. Я выписал глобальные данные, которые по именам выглядят важными:

  ```text
  booth_ticket @ 0x4acb20   (8 случайных байт из /dev/urandom, читаются при старте)
  top          @ 0x4acb28   (верх аллокатора)
  nblocks      @ 0x4acb30
  items[]      @ 0x4acb40   (32 слота по 0x28 байт)
  blocks[]     @ 0x4ad040   (метаданные блоков, по 0x18: {offset, size, used})
  pool         @ 0x4ad640   (пул на 16 КиБ)
  ```

  Почему они важные: `booth_ticket` по названию - секрет (позже выяснится, что он запирает чтение файла); `items`, `blocks`, `pool`, `top` - это устройство памяти, куда программа складывает все данные. Без понимания этого плана дальше не сдвинуться.
- `objdump -d -M intel chall` - дизассемблер. По именам функций я нашёл обработчики команд (`photo`, `caption`, `builtin`, `mono`, `remove`, `upload`, `print`) и функцию раздачи памяти `xalloc` (0x402340) - и прочитал их по очереди.
- `strings chall` - полезные строки: "[broken sticker]", "assets/heart.txt" и т.д. Это первая зацепка, что встроенные стикеры как-то связаны с файлами.
- gdb - когда я хотел убедиться, что правильно понял структуру данных, ставил брейкпоинты и смотрел память (примеры ниже).

## Память программы: что такое аллокатор (простыми словами)

Программа не вызывает malloc для каждого объекта - у неё свой раздатчик памяти, `xalloc`. В BSS зарезервирован один большой кусок - **пул на 16 КиБ** (`pool @ 0x4ad640`), и `xalloc` выдаёт из него куски по запросам.

Что такое «bump-аллокатор»: простейшая схема раздачи. Рядом с пулом лежит счётчик `top` - сколько пула уже выдано. Новый кусок «отрезается от верхушки»: кладём его на адрес `pool + top` и сдвигаем `top` вверх на размер. Дёшево и быстро, но память не переиспользуется, пока кто-то явно не освободит блок.

Здесь `xalloc` чуть умнее. Рядом с пулом лежит список блоков `blocks[]` (по 0x18 байт: offset, size, used - смещение, размер, занят ли). Я прочитал `xalloc` в objdump, по шагам:

1. округлить запрошенный размер вверх до 8;
2. пройтись по `blocks[]`: если есть блок с `used = 0` и `size >= нужного` - переиспользовать его (первый подходящий по списку, схема first-fit): пометить `used = 1` и **занулить весь пул от этого блока до конца** (memset);
3. если свободного подходящего нет - отрезать новый кусок сверху (`top += size`) и добавить блок в список.

Как я это проверил, а не просто поверил дизассемблеру: в gdb освободил блок, запросил кусок того же размера - `xalloc` вернул тот же адрес, и байты после него оказались нулями. Поведение подтвердилось.

Почему это важно для атаки:
1. **Расположение предсказуемо**: новые куски ложатся подряд, сверху.
2. **Освобождённый блок можно выпросить снова**: запросив кусок нужного размера, получишь ровно тот блок, который мы освободили.
3. **Переиспользование зануляет хвост пула**: поля объекта «сбрасываются», и мы можем сформировать их заново своими байтами (этим воспользуемся в фазе 2).

## Что такое item и data

Программа хранит объекты как **элементы**: фиксированная структура 0x28 байт в `items[]` (в BSS), а сами данные объекта лежат в пуле, и на них указывает поле `data` (смещение +0x20); тип объекта - поле `type` (+0x18). Я выяснил это из objdump: `print` и функции создания обращаются к `items[i]+0x18` и `items[i]+0x20`.

Типы объектов:
- **1 - фото**: `[W][H][stride][?][пиксели RGBA]`, выделяется 0x10 + 4*W*H байт;
- **2 - подпись или встроенный стикер**;
- **3 - upload**: произвольные байты, которые мы выбираем, максимум 0x100.

Что лежит в `data` у типа 2. Я создал `builtin x heart` и посмотрел байты блока в gdb (`x/40bx` по указателю data):

```text
data[0..1]    счётчик ссылок (у подписей; про него - в баге 2)
data[2]       подвид: 1 = текстовая подпись, 2 = стикер-из-файла
data[3]       флаг (у builtin = 1)
data[4..7]    длина (текста или пути)
data[8..15]   booth_ticket, 8 байт
data[0x10..]  путь к файлу, например "assets/heart.txt"
```

Тикет - 8 случайных байт, программа читает их из `/dev/urandom` при старте в `booth_ticket` и хранит в BSS.

## Ветки print: какая первая, какая вторая

`print` обходит все элементы и печатает каждый. Для типа 2 в дизассемблере `print` видна цепочка сравнений - три ветки:

- **первая**: `data[2] = 1` - «подпись»: вывести `data[4]` байт из `data+0x10` (`fwrite`) - это просто текст подписи;
- **вторая**: `data[2] = 2` И `data[3]` не ноль И 8 байт на `data+8` равны `booth_ticket` - открыть файл по пути `data+0x10` (длина `data[4]`) и вывалить его содержимое;
- иначе - "[broken sticker]".

Вторая ветка - это **легальный механизм**: так печатаются встроенные стикеры. Программа кладёт в блок путь вида `"assets/heart.txt"` и тикет, а `print` при встрече такого элемента открывает файл и печатает его содержимое (сами стикеры - это файлы в `assets/`; строки путей видны в `strings`). Осталось понять, что нам это даёт: если я смогу подложить в `data` свои байты, прошедшие проверку, и путь `"flag.txt"` - программа сама откроет и напечатает нужный файл. Чтение файла, по сути LFI (local file inclusion).

Загвоздка: проверка требует 8 случайных байт тикета, которых мы не знаем. Значит, сначала нужен способ тикет вытащить (утечка), а уже потом пользоваться второй веткой. Так и вышло: фаза 1 сливает тикет, фаза 2 использует его для чтения флага.

## Баг 1: фильтр `mono` рисует на одну строку больше

Я искал, какой командой можно повлиять на **чужие** данные - это самый частый источник багов в таких программах. `photo` и `upload` пишут ровно столько, сколько просят; `caption` читает существующие данные (дедупликация - про неё ниже); а вот `mono` пишет **в существующее фото** - там, где программа вычисляет границы, стоит посмотреть внимательнее.

В objdump цикл `mono` такой:

```text
row = 0
loop:
  ... записать 4*W байт в строку row (RGB каждого пикселя занулить, альфу не трогать) ...
  row += 1
  cmp row, H
  jae loop        ; переход, пока row < H, т.е. обрабатываются строки 0..H включительно
```

Меня насторожило: сравнение с H стоит **после** инкремента `row`, и цикл продолжается, пока `row < H`. Раз `row` начинает с 0 и доходит до H включительно - обрабатывается H+1 строка, а не H. Классический off-by-one. (Для сравнения, правильный цикл проверял бы `row < H` до обработки строки или сравнивал с H-1.)

Проверка гипотезы, а не вера в глаза: фото 2×1 (H = 1). Строка 0 - легитимная, а строка 1 уже за пределами фото: она пишет 4*W = 8 байт в следующий блок пула. В gdb я создал фото, за ним подпись, применил `mono` - и увидел, что первые байты подписи обнулились. Гипотеза подтвердилась.

Характер перезаписи:
- **только зануляющая**: из каждых 4 байт (RGBA) три (RGB) становятся нулями, альфа остаётся. Произвольные значения записать нельзя;
- попадает в блок, идущий сразу за фото в пуле;
- максимум 4*W байт за границу (W ограничено, так что немного).

На первый взгляд бесполезно - нули! Но именно нули нам и нужны: счётчик ссылок - это два байта в начале чужого блока. Занулить счётчик - превратить «общий» буфер в «освобождаемый», пока на него кто-то ещё ссылается. Это мостик к UAF (use-after-free - использование памяти после освобождения).

## Баг 2: одинаковые подписи делят один буфер (счётчик ссылок)

Читая `caption`, я заметил дедупликацию: если подпись с таким текстом уже есть, команда НЕ выделяет новый буфер - она создаёт новый элемент, указывающий на **тот же** блок, и увеличивает счётчик ссылок в `data[0..1]`.

Откуда я узнал про счётчик - из `remove`. Логика там:

```text
если data[0..1] не нули: уменьшить счётчик; если стал 0 - освободить блок (used = 0) и очистить слот элемента
если data[0..1] = 0:     освободить блок и очистить слот
```

То есть буфер «жив», пока счётчик больше нуля; `remove` освобождает его, только когда счётчик падает до нуля. Две одинаковые подписи `a` и `b` - один блок со счётчиком 2; удаление одной даёт счётчик 1, и блок остаётся живым.

Опасность в том, что счётчик лежит в данных блока, в пуле, прямо рядом с фото - а `mono` умеет писать нули в соседний блок. Два бага складываются в один примитив.

## Собираем всё: путаница счётчика, UAF, утечка тикета

План:
1. Создать фото так, чтобы лишняя строка `mono` попала ровно в начало блока подписи.
2. Занулить счётчик - общий буфер перестанет быть «общим».
3. Удалить одну подпись - блок освободится, хотя вторая подпись всё ещё на него указывает (висячий указатель, UAF).
4. Перевыделить блок через `upload` (свои байты) и посадить `builtin` сразу после него - тогда `print` по висячей подписи сольёт память за блоком, включая тикет.

Рецепт фазы 1 (лик тикета):

```text
photo p 2 1 0102030405060708   # блок фото = 0x10 + 4*2*1 = 24 байта; строка 1 mono
                               # начинается ровно со следующего блока
caption a AAAAAAAAAAAAAAAA     # блок D1 = 32 байта, счётчик 2 (a и b)
caption b AAAAAAAAAAAAAAAA
mono p                         # лишняя строка зануляет D1[0..2]: счётчик и data[2] = 0
remove a                       # счётчик 0, D1 освобождается; b всё ещё указывает на D1
upload c 000001002000000000... # xalloc(32) отдаёт D1; наши байты: data[2]=1, data[4]=0x20
builtin x heart                # новый блок ложится сразу после D1: заголовок + тикет + путь
print b                        # b: тип 2, data[2]=1 - ветка «подпись»:
                               # fwrite(D1+0x10, 1, 0x20) - сливает 32 байта
```

Почему фото именно 2×1: `mono` пишет строки по 4*W байт. У фото 2×1 блок = 24 байта, строка 1 начинается с offset 24 - ровно с первого байта следующего блока D1. А из 8 байт строки зануляются байты 0,1,2,4,5,6 (RGB-позиции) - в том числе счётчик ссылок `D1[0..1]` и `data[2]`.

Что происходит на последнем `print`:
- `b` - тип 2, `data[2] = 1`, значит срабатывает ветка «подпись»: `fwrite(D1+0x10, 1, 0x20)` - печать 32 байт, начиная с 16-го байта D1.
- D1 (32 байта) сейчас занят upload'ом `c`: первые 8 байт наши (00 00 01 00 20 00 00 00), остальные 24 - нули. Байты 16..31 D1 - нули.
- `builtin x heart` выделился сразу после D1, с байта 32: заголовок `01 00 02 01 10 00 00 00` (8 байт), затем 8 байт тикета, затем путь.
- Итого в выводе: 16 нулевых байт, паттерн `01 00 02 01 10 00 00 00`, и сразу за ним 8 байт - это и есть booth_ticket. Скрипт ловит паттерн и вытаскивает тикет.

(Математика: `fwrite(D1+0x10, 1, 0x20)` печатает байты 16..47 D1 - то есть хвост D1 и начало следующего блока. Следующий блок - builtin: заголовок 8 байт + тикет 8 байт. Тикет появляется в выводе ровно после паттерна заголовка.)

## Фаза 2: пересобираем блок под «стикер-из-файла»

Тикет есть. Нужен снова висячий указатель на D1 - он уже есть: `b` всё ещё указывает на D1. Сейчас D1 занят upload'ом `c`, поэтому:

```text
remove c           # у c data[0..1] = 0, D1 освобождается; b всё ещё указывает на D1
upload d <payload> # payload = 00 00 02 01 | 08 00 00 00 | тикет | "flag.txt\0"
print b            # b: data[2]=2, data[3]=1, data[8..15] = тикет -
                   # проверка пройдена, срабатывает вторая ветка:
                   # open("flag.txt") - флаг в stdout
```

Байты payload:

```text
00 00 02 01                  data[0..1] = 0 (счётчик), data[2] = 2 (стикер-из-файла), data[3] = 1
08 00 00 00                  data[4] = 8 - длина пути "flag.txt"
<тикет 8 байт>               data[8..15] - слитый тикет
"flag.txt\0" + паддинг       путь на data+0x10
```

Момент с проверкой: вторая ветка требует `data[2] = 2`, `data[3]` не ноль и `data[8..15] = тикет`. У нас `data[3] = 1` - подходит. Всё происходит в одном процессе, поэтому тикет тот же, что мы слили в фазе 1.

## Почему обе фазы должны быть в одном процессе

`booth_ticket` генерируется один раз при старте процесса из `/dev/urandom`. Новое подключение/процесс - новый тикет. Поэтому эксплойт интерактивный: отправить фазу 1, прочитать слитый тикет из вывода, отправить фазу 2 с этим тикетом - всё в одной сессии. Скрипты делают ровно это.

## Проверка локально, до remote

Я создал тестовую папку с оригинальным `chall`, синтетическим `flag.txt` = `FortID{LOCAL_TEST_ONLY_ue4f}` и запустил proof-скрипт (он подаёт фазу 1, парсит тикет, подаёт фазу 2):

```text
ticket: a222e7f2ce978a8b
flag found: FortID{LOCAL_TEST_ONLY_ue4f}
RESULT: FILE SUBSTITUTION OK
```

Затем тот же скрипт с неверным тикетом дал "[broken sticker]" - подтверждение, что проверка тикета реально запирает вторую ветку (негативный контроль).

## Remote

Тот же двухфазный обмен по TLS против инстанса (`sticker-booth-<...>.inst18.ctf.fortid.com:1337`). Баннер сервиса - "Sticker Booth recipe runner"; после фазы 2 флаг напечатался: `FortID{I_h0p3_Y0u_W1ll_Pu7_Th15_5t1ck3r_0n_Y0ur_L4p70p_<хэш>}` (здесь замаскирован).

## Что я пробовал сначала (тупики)

1. **Прямая подмена пути через mono.** Первая идея: использовать off-by-one, чтобы перезаписать путь builtin напрямую. Не работает: mono зануляет только 3 из 4 байт, значит никогда не запишет подряд байты "flag.txt"; и он зануляет `data[2]` (превращая builtin в "broken"), а не ставит 2. Только-зануляющая запись не может подделать нужные поля.

2. **Upload как примитив чтения файла.** Upload-объекты - тип 3, а `print` для типа 3 печатает только "[custom sticker]" - до ветки открытия файла (тип 2) он не доходит. Один upload не читает файлы.

3. **Тикет, переживающий переиспользование.** Сначала я надеялся, что освобождённый builtin можно переиспользовать «как есть» и он сохранит тикет. Но `xalloc` зануляет хвост пула при переиспользовании, стирая тикет. Тикет выживает только внутри нетронутого builtin-блока - поэтому мы сливаем его с живого.

4. **LFI без лика.** Вторая ветка проверяет `data[8..15] = booth_ticket` (8 случайных байт). Угадывать бессмысленно; лик (фаза 1) - то, что делает всю цепочку возможной. Хореография «подписи алиасят + mono зануляет счётчик + remove освобождает + upload переиспользует + соседний builtin + контролируемая длина fwrite» - минимальная, которая и сливает тикет, и позже его воспроизводит.

## Итоговые скрипты

- `scripts/proof_sb.py` - локальный proof: интерактивный двухфазный (фаза 1 сливает тикет, фаза 2 подменяет путь), печатает найденный флаг.
- `scripts/solve.py` - та же цепочка по TLS для remote-инстанса.

## Версия в один абзац

Sticker Booth - бинарь без PIE с пулом на 16 КиБ. Комбинируются два бага: фильтр `mono` рисует H+1 строк (только-зануляющий off-by-one в соседний блок пула), а `caption` дедуплицирует одинаковые тексты, из-за чего два элемента делят один буфер под счётчиком ссылок. Мы зануляем счётчик через mono, удаляем одну подпись, чтобы освободить общий буфер, пока другая подпись всё ещё указывает на него (UAF), затем перевыделяем этот блок upload'ом с контролируемыми полями и устраиваем builtin-блок сразу после. `print` тогда сливает 32 байта за пределы переиспользованного блока - включая 8-байтовый booth_ticket. С тикетом в руках освобождаем блок снова и загружаем поддельный builtin-заголовок (тип 2, валидный тикет, путь "flag.txt"); висячая подпись теперь попадает во вторую ветку `print`, и бинарь вываливает flag.txt. Всё в одном процессе, потому что тикет привязан к процессу.

## Уроки

1. Только-зануляющая смежная перезапись (off-by-one) поначалу кажется бесполезной, но она блистает, когда цель - счётчик ссылок: занулив его, превращаешь разделяемый буфер в освобождаемый, пока остаётся устаревший указатель (UAF).
2. Дедупликация - это фича с точки зрения безопасности: «два объекта делят один буфер» плюс счётчик ссылок - богатый примитив.
3. Когда случайное значение запирает специальный путь (здесь тикет), ищи лик этого значения ПЕРЕД планированием основного эксплойта; хореография лика часто - более сложная половина.
4. First-fit аллокаторы с занулением при переиспользовании предсказуемо сбрасывают поля объектов - используй зануление как фичу (нам и так нужны нули в большинстве полей заголовка).
5. Всегда доказывай затвор: неверный тикет даёт "[broken sticker]" (негативный контроль), верный - флаг.
6. Одно-сессионные сценарии важны: пер-процессная случайность означает, что лик и payload должны делить одну сессию; пиши скрипт как интерактивный двухфазный обмен, а не два независимых запуска.
