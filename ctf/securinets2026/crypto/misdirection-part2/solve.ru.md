# Misdirection: Part 2 (crypto): путь решения

## 0. План целиком

Зачем этот раздел: чтобы читатель видел цепочку до деталей и понимал, зачем нужен каждый шаг.

Дано: исходники сервиса с ботом (`bot.js`, `authenticator.js`, `auth-flow.js`, `config.js`,
`admin.rs`), публичный эндпоинт `/report`, которым можно попросить бота открыть ссылку, и
шифротекст подсказки на 64 байта. Сайт с интерфейсом регистрации и входа по WebAuthn закрыт,
но исходники бота открыты.

Два уточнения по названиям, чтобы не путаться. На портале задача значится как
`Misdirection: Part 2` в категории Cryptography, при этом архив исходников называется
`misdir.zip`, а в некоторых материалах задачу называют просто Misdirection. Шифротекст
подсказки пришёл вместе с условием: в `misdir.zip` его нет, я проверил поиском по всем
исходникам.

Цель: получить флаг, который лежит в зашифрованной подсказке.

План получился такой:

1. Понять, как бот подписывает данные и что в этой подписи можно вычислить заранее.
2. Заставить бота подписать нашу страницу, обойдя проверку ссылки в `/report`.
3. Из подписи восстановить приватный ключ администратора.
4. Проверить ключ по публичному ключу из базы.
5. Расшифровать подсказку этим ключом и получить флаг.

## 1. Что дано

Зачем этот шаг: зафиксировать материалы и понять, где вообще искать ошибку.

В комплекте исходники бота. `bot.js` поднимает headless-браузер, открывает переданную ссылку,
регистрирует случайного пользователя и логинится. В `authenticator.js` лежит самодельная
реализация WebAuthn: регистрация и вход. `admin.rs` это серверная часть на Rust, там же
обработчик `/report`, который запускает бота.

В сервисе есть и другой путь к флагу, чисто прикладной: маршрут `/api/flag` отдаёт флаг
пользователю, у которого баланс не меньше пяти миллионов, а пополнение `/api/admin/add_funds`
доступно только администратору. Этот путь мы не использовали, флаг получен из подсказки, но
упомянуть его стоит: в сервисе было два разных способа добраться до флага, и админский ключ
нужен обоим.

Плюс к этому в задании был шифротекст подсказки. Он лежит в `assets/hint_ciphertext.hex`, это
64 байта, то есть четыре блока AES.

## 2. Как устроен вход по WebAuthn

Зачем этот шаг: без понимания подписи не видно, что именно сломано.

WebAuthn это стандарт входа без пароля. У клиента есть ключевая пара, приватный ключ хранится у
него, публичный знает сервер. При входе сервер присылает случайную строку, challenge, клиент
собирает из неё и данных аутентификации сообщение и подписывает его, а сервер проверяет подпись
публичным ключом.

Подпись здесь ECDSA на кривой P-256. В ECDSA подпись это пара чисел `r` и `s`, которые
считаются так: выбирается случайное число `k`, называемое nonce, потом вычисляется точка `k*G`,
из неё берётся `r`, а `s` считается по формуле `s = k^-1 * (z + r*d) mod n`, где `z` это хеш
сообщения, `d` приватный ключ, `n` порядок кривой. Сервер, зная `r`, `s`, `z` и публичный ключ,
проверяет, что подпись сходится.

Ключевое свойство: если `k` известно, приватный ключ вычисляется из одной подписи. Формула
получается простым преобразованием: `d = (s*k - z) * r^-1 mod n`. Поэтому в ECDSA nonce и
называют одноразовым: его нельзя повторять и нельзя делать предсказуемым.

## 3. Где ошибка

Зачем этот шаг: найти, что именно делает nonce вычислимым.

В `assets/authenticator.js` подпись собирается вручную, и nonce берётся не случайным:

```js
const rpIdHash = sha256(rpId);
...
const signature = keyPair.sign(msgHash, { k: () => ec.keyFromPrivate(rpIdHash, 'hex').getPrivate() });
```

То есть `k` равен SHA-256 от `rpId`, а `rpId` это домен, на котором проходит вход. Домен не
секрет, хеш от него считается за микросекунды. Значит `k` известен заранее.

Вторая половина ошибки в том, как бот отдаёт подпись. `bot.js` выставляет функцию
`forgeAuthentication` в страницу:

```js
await page.exposeFunction('forgeAuthentication', forgeAuthentication);
```

Такая функция становится доступна любому JavaScript на открытой странице. И первым аргументом
она принимает `rpId`, то есть страница сама выбирает, какой домен подписывать. Вдобавок
`forgeAuthentication` подписывает произвольный challenge, который тоже приходит со страницы.

Итого: страница атакующего может попросить бота подписать два разных `rpId`, и для каждого
nonce будет известен.

## 4. Заставляем бота открыть нашу страницу

Зачем этот шаг: подпись можно получить, только если бот зайдёт на наш сайт.

Обработчик `/report` в `admin.rs` принимает ссылку и проверяет её так:

```rust
if !payload.url.starts_with(&frontend_url) {
    return reply("error", format!("URL must start with {frontend_url}"));
}
```

Дальше ссылка переписывается заменой префикса на адрес бота:

```rust
let bot_url = payload.url.replacen(&frontend_url, &var("BOT_FRONTEND_URL"), 1);
```

Проверка смотрит только начало строки, а сама ссылка может содержать символ `@`, который в URL
отделяет данные пользователя от хоста. Поэтому подходит такая строка: сначала настоящий адрес
фронтенда, потом `@`, потом наш хост. Проверка видит знакомый префикс и пропускает, а после
замены префикса получается ссылка, где данные пользователя это фронтенд, а хост наш:

```text
https://frontend.example@attacker.example/auth
```

Хост здесь `attacker.example`, поэтому бот открывает наш сайт. Чтобы у бота был настоящий HTTPS
адрес, я поднял локальный сервер и вывел его наружу через `cloudflared`:

```bash
python3 scripts/solve_misdir.py --listen --port 8877
./cloudflared tunnel --url http://127.0.0.1:8877
python3 scripts/solve_misdir.py --trigger --base 'https://<host>' --tunnel 'https://<tunnel>.trycloudflare.com'
```

Перед этим решатель отправляет в `/report` заведомо неподходящую ссылку, чтобы сервер сам
назвал ожидаемый префикс в тексте ошибки, и уже из ответа берёт `FRONTEND_URL`. Придумывать его
не нужно, он приходит от самого сервиса.

Страница, которую открывает бот, вызывает в его браузере `forgeAuthentication` дважды: с
`rpId` `example.com` и `example.org`. Обе подписи вместе с `authenticatorData` и
`clientDataJSON` уходят на наш сервер, который их и разбирает.

## 5. Восстанавливаем ключ

Зачем этот шаг: из двух подписей получить приватный ключ администратора.

Сервер разбирает `authenticatorData`, проверяет, что первые 32 байта это SHA-256 от `rpId`,
достаёт `r` и `s` из подписи, считает `z` как SHA-256 от `authenticatorData` вместе с хешем
`clientDataJSON`, и применяет формулу:

```python
k = int.from_bytes(hashlib.sha256(rp.encode()).digest(), 'big') % N
d = ((s*k - z) * pow(r, -1, N)) % N
```

Зачем два разных `rpId`: с одним и тем же `k` и одним сообщением получилась бы одна и та же
подпись, и проверять было бы нечего. Два разных домена дают два независимых уравнения, и если
формула верна, оба дают один и тот же `d`. Совпадение и есть проверка.

Второй контроль сильнее: из восстановленного `d` можно вывести публичный ключ и сравнить с тем,
что лежит в базе задания. В миграции `init.sql` для админского passkey записаны координаты
`x = ax-gywE6mENnh-AHn4wRoEgrmC772tSG2jCRCKJQoZc` и `y =
8YKWhWAp0RnCeXjFWXWXvXYhlmz9WIEO3FwHWYvOD2M`. Мой `scripts/verify_offline.py` считает точку по
восстановленному `d` и сравнивает: обе координаты совпадают.

## 6. Расшифровываем подсказку

Зачем этот шаг: собственно получить флаг.

В подсказке 64 байта, то есть ровно четыре блока AES, значит режим без IV, то есть ECB. Ключ не
сам `d`, а SHA-256 от его шестнадцатеричной записи в нижнем регистре, без префикса:

```python
key = hashlib.sha256(f'{d:064x}'.encode()).digest()
```

Эту деталь пришлось подбирать, и она же объясняет сообщение из комплекта решателя. В нём ключ
брался как `d.to_bytes(32, 'big')`, а выравнивание снималось стандартным PKCS7, поэтому скрипт и
печатал `PKCS7 padding invalid`: с самими байтами `d`, с обратным порядком байтов и с обычным
PKCS7 расшифровка не сходится.

Выравнивание тоже нестандартное. После расшифровки в конце лежат 28 байт со значением `0x1c`,
то есть 28. Для AES блок 16 байт, и обычный PKCS7 больше 16 байт добавить не может, поэтому
автоматическое снятие выравнивания падает. Правило здесь проще: последний байт говорит, сколько
байт добавлено, и все они равны этому числу. Убираем их вручную, и остаётся строка:

```
Securinets{sm0l...AMS}
```

Начало и конец строки привожу специально, чтобы было видно, что флаг действительно получен.

Офлайн цепочку можно проверить одной командой:

```bash
python3 scripts/verify_offline.py
public x matches init.sql: True
public y matches init.sql: True
scalar recovered for example.com : True
scalar recovered for example.org : True
padding bytes: 28
flag: Securinets{sm0l...AMS}
```

## 7. Что не сработало и почему

- Ключ из байтов `d`. Первая попытка взять `d.to_bytes(32, 'big')` даёт мусор: авторы задачи
  вывели ключ как SHA-256 от hex-строки, а не из самих байтов.
- Обычное снятие PKCS7. 28 байт выравнивания больше размера блока AES, поэтому стандартная
  функция отказывается, и это не баг скрипта, а другая схема выравнивания.
- Один `rpId` вместо двух. С одним доменом нельзя проверить, что восстановленный ключ
  стабилен, а ошибка в формуле осталась бы незамеченной.
- Попытка обойтись без туннеля. Бот запускается на сервере задания и до localhost не дойдёт,
  поэтому нужен публичный HTTPS адрес.

## 8. Коротко, одним абзацем

Бот подписывал WebAuthn-вход с nonce, равным SHA-256 от домена, и выставлял функцию подписи в
страницу вместе с аргументом `rpId`. Через `/report` с обходом проверки префикса получилось
заставить бота открыть нашу страницу, которая попросила подписать два разных домена. Из каждой
подписи по формуле `d = (s*k - z) * r^-1 mod n` восстановился приватный ключ, оба значения
совпали, а выведенный из ключа публичный совпал с ключом из базы. Подсказка расшифровалась
AES-256-ECB ключом SHA-256 от hex-записи `d`, после снятия нестандартного выравнивания получился
флаг.

## 9. Выводы

- В ECDSA nonce нельзя выводить из публичных данных: если `k` известен, ключ восстанавливается
  из одной подписи.
- Опасна не только сама формула, но и то, что функция подписи отдана странице: она даёт выбрать
  и домен, и challenge.
- Проверка префикса строки не заменяет разбор URL: символ `@` меняет хост, хотя строка
  начинается с ожидаемого адреса.
- Восстановленный ключ надо проверять независимо, по публичному ключу из базы, а не только по
  совпадению двух подписей.
- Схему шифрования и выравнивание нужно подтверждать экспериментом: ключ и режим подбираются,
  а не берутся из общего правила.
