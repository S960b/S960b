# LinkedIn Daily Posting - Full Restoration Guide

**Owner:** S960b
**Repo path (this doc):** `linkedin/`
**Live workspace:** `~/linkedin/` on the Kali host (`/home/kali`)
**Written:** 2026-10-14 (source of truth for rebuilding the whole system from zero)

This document is the **complete disaster-recovery guide** for the LinkedIn daily
posting automation. If the OS/host dies and the agent has to rebuild everything
from scratch, follow this file top to bottom. It is intentionally verbose and
kept in sync with the live state of `~/linkedin/` and the Hermes cron jobs.

---

## 0. What this system does (one paragraph)

Every day at 20:00 MSK an OS cron entry runs a resilient wrapper that triggers a
Hermes cron job (`9fc7abfe87a3`, agent task with the `linkedin-content-research`
skill attached). The agent researches cybersecurity/mining/AI-security topics,
applies strict personal-fact and fact gates, writes ONE English LinkedIn post
(700-1400 chars), publishes it via the **official LinkedIn Posts API**
(OAuth, `w_member_social`), logs it, and sends a short Telegram report.
The whole design assumes the host is powered on 16:00-22:00 MSK.

Key constraint: **no browser automation, no cookie reuse, no scraping** - the
official API only. If the API is unavailable, the post is queued to
`~/linkedin/QUEUE/YYYY-MM-DD.md` and a failure is logged - the system never
bypasses to unofficial channels.

## 2. Rebuild checklist (fresh OS)

Order matters. Do NOT skip the "check" steps.

### 2.1 Install prerequisites

```bash
# Kali/Debian base + hermes agent (user-level install)
curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash
# ensure hermes is on PATH: ~/.local/bin/hermes
hermes --version
```

### 2.2 Restore the workspace

```bash
mkdir -p ~/linkedin
# copy the scripts from this repo
cp -r <repo>/linkedin/scripts/. ~/linkedin/
chmod +x ~/linkedin/*.sh ~/linkedin/*.py
```

### 2.3 Install the skill into Hermes

```bash
# create ~/.hermes/skills/social-media/linkedin-content-research/SKILL.md
# from <repo>/linkedin/skill/SKILL.md (see RESTORE_GUIDE.md)
# then verify it loads:
hermes chat -q "load skill linkedin-content-research and confirm readiness"
```

### 2.4 Recreate the cron jobs (in Hermes)

```bash
hermes cron create \
  --name "LinkedIn daily post cycle" \
  --schedule "0 20 * * *" \
  --skill linkedin-content-research \
  --deliver local \
  --workdir /home/kali/linkedin \
  --prompt "$(cat /tmp/cron_prompt_9fc7abfe87a3.txt)"
```

The **full prompt text** for both jobs is stored in
`linkedin/cron/prompt_9fc7abfe87a3.txt` and
`linkedin/cron/prompt_1693af0de3c1.txt` in this repo.

**CRITICAL - pin the model/provider** (the whole "JOB MUST BE PINNED" saga):

```bash
hermes cron edit <job_id> --schedule "0 20 * * *"  # if needed
# then pin via the cronjob tool OR config; the job MUST have
# model=deepseek-v4-flash, provider=custom:multitool-deepseek
# (see the "Model pinning" section below)
```

Second job - **LinkedIn token re-auth reminder** (once at 2026-11-17 18:00):

```bash
hermes cron create \
  --name "LinkedIn token re-auth reminder" \
  --schedule "once at 2026-11-17 18:00" \
  --deliver local \
  --prompt "$(cat /tmp/cron_prompt_1693af0de3c1.txt)"
```

### 2.5 Set up OAuth + credentials

1. Create `~/linkedin/.credentials` with:
   ```
   CLIENT_ID=...
   CLIENT_SECRET=...
   ACCESS_TOKEN=...
   TOKEN_EXPIRES_AT=2026-11-22
   TELEGRAM_BOT_TOKEN=...
   TELEGRAM_CHAT_ID=...
   ```
2. If the access token is expired/missing, run the callback server:
   ```bash
   python3 ~/linkedin/oauth_callback.py   # listens on :8444 (IPv6 dual-stack)
   ```
   Open the URL from `auth_url.txt` in `/home/kali/firefox/firefox-bin`
   (the standalone Firefox build; system default is Chromium).
   Ports 8443/9443 are occupied on this host - use 8444.
3. Verify with a read-only call:
   ```bash
   curl -s -H "Authorization: Bearer $ACCESS_TOKEN" \
     https://api.linkedin.com/v2/userinfo
   # expect 200 + {"sub":"<member-sub>", ...}
   ```

### 2.6 Wire the OS cron (the resilient wrapper)

```bash
crontab -l > /tmp/ct
# keep all existing lines; REMOVE any old "hermes cron tick" 20:00 line
# ADD:
echo '0 20 * * * /home/kali/linkedin/linkedin_resilient.sh >> /home/kali/.hermes/cron/os_cron.log 2>&1' >> /tmp/ct
crontab /tmp/ct
```

The wrapper does NOT rely on the Hermes gateway being up. It force-runs the job
(`hermes cron run <job>`) and, if the day is not covered yet, retries:
immediate, +4 min, +10 min, +25 min (all inside the 16-22 MSK window).

### 2.7 Post-restore checks

```bash
# 1) Skill loads
hermes chat -q "load skill linkedin-content-research and confirm readiness"
# 2) Cron job list shows the job with pinned model/provider
hermes cron list | grep -A3 9fc7abfe87a3
# 3) Wrapper is executable and syntactically valid
bash -n ~/linkedin/linkedin_resilient.sh && echo OK
# 4) Dry-run a publish (no network call)
python3 ~/linkedin/publish_queued.py ~/linkedin/QUEUE/2026-09-28.md --dry-run
# 5) First posts manually via the API before trusting the auto-cycle
python3 ~/linkedin/publish_queued.py ~/linkedin/QUEUE/<date>.md
```

## 3. How publishing works (API contract, verified)

- **Endpoint:** `POST https://api.linkedin.com/rest/posts`
  (NOT `/v2/rest/posts` - that returns 404 RESOURCE_NOT_FOUND).
- **Headers:** `Authorization: Bearer <token>`,
  `X-Restli-Protocol-Version: 2.0.0`, `LinkedIn-Version: 202609`,
  `Content-Type: application/json`.
- **Body:**
  ```json
  {
    "author": "urn:li:person:<member-sub>",
    "commentary": "<post text, LinkedIn little-format escaped>",
    "visibility": "PUBLIC",
    "distribution": {"feedDistribution":"MAIN_FEED","targetEntities":[],"thirdPartyDistributionChannels":[]},
    "lifecycleState": "PUBLISHED",
    "isReshareDisabledByAuthor": false
  }
  ```
- **Success:** HTTP 201, post URN in `x-restli-id` header
  (e.g. `urn:li:share:7510387200140693504`).
- **Author URN:** `urn:li:person:<member-sub>` (from GET /v2/userinfo, sub).
- **Scopes:** `w_member_social + openid profile email` (OpenID Connect product
  must be added to the LinkedIn app; "unauthorized_scope_error: openid" = the
  product is missing). `offline_access` is REJECTED for this app
  ("Unknown scope") - so **no refresh token**, access token lives ~60 days,
  re-auth needed ~2026-11-17.

### LinkedIn "little" text format (critical, causes truncation)

The `commentary` field uses LinkedIn's `little` format, NOT plain text.
Reserved chars that break display unless backslash-escaped:
`| { } @ [ ] ( ) < > \ * _ ~`
(`#` is intentionally NOT escaped so hashtags stay hashtags).
`publish_queued.py` handles this automatically via
`escape_linkedin_little()`. ALWAYS dry-run before publishing:
`python3 publish_queued.py <file> --dry-run`.

## 4. The 2026-10-13 incident (why the resilient wrapper exists)

- **Symptom:** yesterday's 20:00 run produced no post, no research log, no
  Telegram report.
- **Evidence:** the cron job FIRED (output file
  `~/.hermes/cron/output/9fc7abfe87a3/2026-10-13_20-01-55.md` created, `## Error`
  block) and the tick log showed:
  `RuntimeError: HTTP 502: prefill leg failed`
  (upstream `https://gw2.gigatool.app/deepseek`, error `prefill_failed`).
- **Root cause:** the DeepSeek router/upstream was momentarily down; the single
  20:00 tick did ~3 fast retries in ~9 seconds, ALL against a dead upstream,
  then gave up. The day silently had no post.
- **What it was NOT:** NOT a model-change skip. The job is PINNED to
  `deepseek-v4-flash / custom:multitool-deepseek` and that matched the active
  model at the time. "Make the job adopt the active model" would NOT have
  prevented this.
- **Fix:** the OS cron now runs the resilient wrapper
  (`linkedin_resilient.sh`) with backoff re-triggers instead of a bare
  `hermes cron tick`. It is idempotent: it stops as soon as TODAY appears in
  `PUBLISHED.md` or `QUEUE/<date>.md`, so it can never double-post.

## 5. Model pinning - the "JOB MUST BE PINNED" rule

- **Why:** a Hermes cron job whose model/provider is NOT pinned refuses to run
  after the global model changes (it will NOT auto-adopt the new model). The
  error is:
  `RuntimeError: Skipped to prevent unintended spend: global inference config drifted since this job was created ...`
- **Rule:** after ANY `hermes config set model ...` (or provider change), check
  `hermes cron list` / `~/.hermes/cron/jobs.json` and re-pin the job's model if
  it drifted. Current pin: `deepseek-v4-flash` / `custom:multitool-deepseek`.
- **Diagnostic path for ANY cron failure:**
  1. `~/.hermes/cron/jobs.json` -> `last_status` / `last_error`
  2. `~/.hermes/cron/output/<job>/<date>.md` -> "## Error" block
  3. `~/.hermes/cron/os_cron.log` -> tick-level retries
  4. `~/.hermes/cron/os_linkedin_resilient.log` -> wrapper retries

## 6. Account restriction incident (2026-09-27) - summary

The account was restricted after the 4th API-published post in 4 days
(identity verification requested). Likely signals: datacenter egress IP
(Frankfurt AS215730), new/low-activity account publishing only via API, country
mismatch, automated side traffic. Resolved 2026-09-28 the same day (appeal on
the user side). Full record + re-entry checklist:
`linkedin/incidents/ACCOUNT_RESTRICTED.md` (copy of the live file).

Rules learned (also in the skill):
1. On restriction: PAUSE the cron job immediately, never retry into a
   restricted account, never fall back to browser/cookie automation.
2. Do not upload an ID as the first move; use the Help Center appeal path.
3. On restore: verify via read-only GET /v2/userinfo -> 200, then resume.
4. Risk hygiene for new accounts: residential-like IP, browser activity
   between posts, fewer posts in the first weeks.
