# Crypto Wallet - разбор (Reverse/Android: BIP39-фраза из what3words, затем AES-GCM флаг)

## Знакомство с задачей

В раздатке один Android APK, `crypto_wallet.apk`. Приложение - «крипто-кошелёк»: просит 12-словную recovery-фразу, и если фраза правильная, показывает флаг. Никакого remote и сети нет - вся задача в одном APK.

Первый вопрос всегда такой: что эта штука вообще делает? Для APK это значит - заглянуть внутрь.

## Как я заглядывал внутрь (какими программами)

- `file crypto_wallet.apk`, `sha256sum` - это zip (APK всегда zip), ~2.9 МБ.
- `unzip -l` - структура. Сразу бросаются в глаза две вещи:
  - `assets/bip39_english.txt` - стандартный список слов BIP39 (2048 слов). Значит, приложение действительно работает с recovery-фразами.
  - `lib/arm64-v8a/libwalletverify.so` и `lib/x86_64/libwalletverify.so` - НАТИВНАЯ библиотека. Маленькая (4-5 КБ), то есть это не криптодвижок, а скорее маленький помощник.
- `jadx` (поставил 1.5.3) - декомпилирует dex-байткод обратно в читаемую Java. Это главный инструмент для этой задачи: вся логика приложения в `MainActivity`.
- `nm -D` / `readelf -Ws` по .so - экспортируемые нативные символы (см. раздел про нативную часть).
- `objdump -s -j .rodata` по .so - константные данные (координаты).
- `strings` по .so - быстрый скан читаемых констант.
- Python `zipfile` - чтобы прочитать конкретный asset (список слов) без распаковки.

Альтернативы для той же работы: `apktool` (ресурсы + smali), `dex2jar` + декомпилятор Java, `jeb`, `Ghidra` для .so. Для этой задачи хватило jadx + objdump.

## Что делает MainActivity (весь поток), и откуда каждый факт

Декомпилированный `MainActivity` (jadx, метод восстановления кошелька) - это одна прямая линия криптографии. По шагам, с источником каждого пункта:

1. **Строит 4 тройки слов в формате `///w1.w2.w3`.** Источник: jadx. В декомпилированном коде введённая фраза режется на подсписки по 3 слова (`subList(3*i, 3*i+3)`) и к каждой добавляется префикс-строка `"///"` - и нарезка, и префикс видны прямо в декомпилированном методе.

2. **Каждая тройка уходит в `NativeVerifier.checkObjectVicinity` вместе с парой координат; собираются 4 результата.** Источник: jadx (вызов метода и его аргументы). Пары координат приходят из `NativeVerifier.targetCoordinates()` - за этим я и пошёл в нативную часть (следующий раздел).

3. **4 результата проходят через `NativeVerifier.hasPerfectMatching` - ворота, которые должны вернуть true.** Источник: jadx (вызов). Запирают ли эти ворота что-то на самом деле, я проверил отдельно - оказалось, что нет (раздел про нативную часть).

4. **12 слов переводятся в индексы списка BIP39 и проверяется BIP39-checksum.** Источник: jadx (вызов хеша) + asset. Приложение читает `assets/bip39_english.txt` (я прочитал тот же файл через `zipfile`; он байт-в-байт совпадает с официальным списком BIP39), сопоставляет слова с индексами, берёт SHA-256 от первых 16 байт энтропии и сравнивает первые 4 бита - стандартный BIP39-checksum, виден как JCA-вызовы в декомпилированном коде.

5. **Выводится мастер-сид: PBKDF2-HMAC-SHA512(фраза, salt="mnemonic", 2048).** Источник: jadx. В коде вызывается `PBKDF2WithHmacSHA512` с итерациями 2048 и солью `"mnemonic"` - обе величины константы в методе.

6. **HMAC-SHA512 со строкой "Bitcoin seed" даёт мастер-приватный ключ + chain code.** Источник: jadx - константа `"Bitcoin seed"` в коде; это стандартный шаг BIP32 от сида к мастер-ключу.

7. **BIP32-деривация по пути m/44'/60'/0'/0/0.** Источник: jadx. В декомпилированном коде массив индексов: `{0x8000002c, 0x8000003c, 0x80000000, 0, 0}` = hardened 44, hardened 60, hardened 0, потом 0, 0 - стандартный путь деривации для Ethereum.

8. **secp256k1-публичный ключ, keccak256 от (x || y), последние 20 байт - Ethereum-адрес, сравнение с фиксированной константой.** Источник: jadx. Операции EC - JCA-вызовы; целевой адрес `0xdc7d8b278af5f31fed5fe68f50be6d02404fb522` - строковая константа, сравнение через `equalsIgnoreCase`.

9. **При совпадении: key = sha256(байты_приватного_ключа + "FortID/cryptocurrency-wallet/flag/v1"), AES-GCM-расшифровка, печать флага.** Источник: jadx - все константы в коде: label `FortID/cryptocurrency-wallet/flag/v1`, nonce `NaY6LHeKYbf9abvi` (base64), ciphertext `7ue/WCpa...` (base64), AAD `wallet-recovery`.

То есть вся защита сводится к одному: нужно знать 12 слов, которые деривируются в этот один адрес. Флаг зашифрован ключом, выведенным из приватного ключа, так что обойти AES нельзя - нужно найти фразу.

## Нативная библиотека: что это на самом деле (и как я это прочитал)

- `nm -D lib/x86_64/libwalletverify.so` (или `readelf -Ws`) перечисляет ЭКСПОРТИРУЕМЫЕ символы. Выделяются две JNI-функции: `targetCoordinates` и `hasPerfectMatching`. Именно так я узнал, что библиотека экспортирует ровно эти две и больше ничего примечательного.
- Сверка с jadx: Java-класс `NativeVerifier` объявляет два `native`-метода с теми же именами - значит, экспорт .so и Java-объявления совпадают 1:1.
- `objdump -s -j .rodata libwalletverify.so` (после нахождения символов) показывает константные данные `targetCoordinates`: 4 пары (широта, долгота) double:
  - (41.99175, -87.889806)  - это ORD, Chicago O'Hare, аэропорт
  - (33.941589, -118.40853) - LAX, Лос-Анджелес
  - (44.884755, -93.222284) - MSP, Миннеаполис-Сент-Пол
  - (40.641311, -73.778139) - JFK, Нью-Йорк

  (Аэропорты я узнал по координатам: это широко известные центральные точки этих аэропортов. Первое диагностическое предположение было «сначала LAX»; реальный порядок в нативной библиотеке - ORD, LAX, MSP, JFK - и это важно для порядка слов.)

- **А это реальные ворота? Я проверил - нет:**
  - `checkObjectVicinity` - декомпилирован в jadx: тело всегда возвращает `new VicinityResult(true, "Vicinity verification is not implemented yet...")`. Это заглушка, которая всегда говорит «да».
  - `hasPerfectMatching` - я разобрал нативную реализацию (совершенное паросочетание 4x4 по фиксированной таблице перестановок), затем прошёлся по всему dex в поисках вызова - она НИКОГДА не вызывается из dex.

То есть оба нативных слоя - декорация: они НИЧЕГО не запирают. Решающее - из какой строки `MainActivity` строит тройки.

## Зацепка: what3words (и откуда я взял этот формат)

`MainActivity` строит строки вида `///w1.w2.w3`. Я погуглил формат («///» + три слова через точку) и нашёл what3words - систему геокодирования, где каждый квадрат 3x3 м имеет уникальный адрес `///слово.слово.слово`. Источники: статья в Википедии (https://en.wikipedia.org/wiki/What3words) и официальный сайт (https://what3words.com). Приложение строит ровно этот формат и проверяет каждую тройку против пары координат - это reverse-геокодинг what3words.

Значит, задуманный поток такой: взять четыре аэропорта - получить их what3words-адреса - 12 слов (4 x 3) И ЕСТЬ recovery-фраза. Это и есть зацепка «как получить 12 слов», спрятанная в нативной библиотеке в виде координат.

## Поиск адресов аэропортов (сначала тупик: центры карты через API)

Сначала я попробовал точные ячейки центров карты: сделал reverse-lookup четырёх координат центров через what3words (маленький Python-HTTP-клиент к их публичному reverse-geocoding-эндпоинту; тот же результат виден на их карте-виджете). Тройки вернулись для ячеек центров карты - и выведенный из них Ethereum-адрес НЕ совпал с целевым. Тупик: автор использовал опубликованные ОБЪЕКТНЫЕ адреса аэропортов, а не ячейки центров.

Правильными оказались ПУБЛИЧНЫЕ what3words-адреса объектов аэропортов (опубликованы на страницах аэропортов / в what3words):

```text
ORD: ///slot.escape.oven
LAX: ///dice.ticket.path
MSP: ///sport.glue.survey
JFK: ///reason.manual.myself
```

Склеив в порядке нативной библиотеки (ORD, LAX, MSP, JFK - именно в этом порядке `checkObjectVicinity` их получает):

```text
slot escape oven dice ticket path sport glue survey reason manual myself
```

Это и есть 12-словная recovery-фраза.

## Верификатор: зачем скрипт, а не ввод в UI? (аргумент)

Честный ответ сразу: если бы APK запускался на эмуляторе или телефоне, быстрейший путь был бы - ввести 12 слов в UI приложения и прочитать флаг с экрана. Это валидно, и в реальном CTF часто это правильный ход.

Почему я всё же использовал скрипт:

1. **В окружении не было готового эмулятора.** Поднять его (скачать образ системы, загрузить, поставить APK) дольше, чем написать верификатор на 30 строк. Скрипт делает ту же криптографию за секунды, полностью офлайн.
2. **Скрипт доказывает, что фраза верна, а не просто «приложение приняло».** Он печатает выведенный адрес и точное совпадение с целевым, затем AES-GCM-проверку тега. UI показывает успех/флаг, но не адрес; `match=True` у скрипта - это доказательство, и именно оно нужно перед сдачей.
3. **Он мгновенно отбрасывает BIP39-невалидные фразы** - защита от опечаток. Опечатка в UI просто молча не проходит.
4. **Он оставляет воспроизводимый артефакт** - верификатор это та же цепочка, что и приложение, пригодится как доказательство в writeup и для любой фразы-кандидата потом.

Моё мнение: UI-first - быстрейший путь для человека, когда приложение реально запускается; скрипт был эквивалентом, продиктованным окружением, и заодно дал проверяемое доказательство. Будь эмулятор готов - я бы тоже ввёл фразу в UI.

## Проверка (офлайн, end-to-end)

Верификатор (`scripts/wallet_candidate_check.py`, stdlib + `cryptography`) воспроизводит ровно ту же цепочку, что и приложение: BIP39 checksum - PBKDF2 - "Bitcoin seed" - BIP32 m/44'/60'/0'/0/0 - secp256k1 - keccak256 - сравнение с `0xdc7d8b...`, и при совпадении расшифровывает AES-GCM-блоб ключом `sha256(privkey + label)`.

Результат:

```text
$ python3 wallet_candidate_check.py --apk crypto_wallet.apk --mnemonic "slot escape oven dice ticket path sport glue survey reason manual myself"
address=0xdc7d8b278af5f31fed5fe68f50be6d02404fb522 match= True
CHALLENGE FLAG: FortID{Jus7_H0DL_70_7h3_M00n_Br0}
```

Точное совпадение адреса, AES-GCM принял, флаг расшифрован. Флаг затем отправлен на портале - ПРИНЯТ.

## Тупики, которые я прошёл по пути

1. **Брутфорс / угадывание фразы.** 12 слов BIP39 = 2^132 с фильтром по checksum. Бессмысленно, и задача явно прячет фразу в другом месте.

2. **Поиск фразы внутри APK.** Проверил strings, resources.arsc (все UI-строки: "Enter your 12-word recovery phrase...", "Wallet recovered" и т.д.), layouts, zip-комментарий, длинные dex-строки. Ничего: ни кластера из 12 слов, ни суженного списка слов, ни дефолтной фразы. Список слов в assets байт-в-байт совпадает с официальным списком BIP39.

3. **Точные what3words-ячейки центра карты.** Сделал reverse-lookup точных координат центров ORD/LAX/MSP/JFK через публичный what3words-эндпоинт. Получил другие тройки, которые не деривируются в целевой адрес. Правильные тройки - это опубликованные ОБЪЕКТНЫЕ адреса аэропортов, а не ячейки центров.

4. **Нативное perfect-matching как реальные ворота.** Полностью разобрал `hasPerfectMatching` (совершенное паросочетание 4x4 по фиксированной таблице перестановок) - потом выяснил, что она не вызывается из dex, а `checkObjectVicinity` всегда возвращает true («not implemented yet»). Оба нативных слоя - декорация.

5. **Расшифровка AES без фразы.** AES-ключ = `sha256(privkey + label)`; без приватного ключа (то есть без фразы) его не вычислить, а AES-GCM аутентифицирован - нельзя даже перебирать ключи-кандидаты.

## Версия в один абзац

APK - это цепочка BIP39 + BIP32 + Ethereum + AES-GCM: 12 слов - сид - m/44'/60'/0'/0/0 - проверка адреса против фиксированного значения - AES-GCM флаг. 12 слов не перебираются, но нативная библиотека хранит координаты четырёх аэропортов (ORD, LAX, MSP, JFK), а `MainActivity` строит what3words-тройки `///w1.w2.w3` и прогоняет их через два декоративных нативных «верификатора», которые всегда проходят. Опубликованные what3words-адреса объектов четырёх аэропортов (`slot.escape.oven`, `dice.ticket.path`, `sport.glue.survey`, `reason.manual.myself`) в порядке нативной библиотеки и есть 12-словная фраза. Локальный верификатор воспроизводит всю цепочку офлайн: точное совпадение адреса, AES-GCM расшифровывает флаг, флаг принят.

## Уроки

1. APK-задача - это три слоя, и для каждого нужен свой инструмент: dex - jadx, нативный .so - nm/objdump/strings, ресурсы - apktool/таблица ресурсов. Не гадай по UI.
2. Когда путь в коде - односторонняя криптоцепочка (фраза - адрес), фраза ОБЯЗАНА быть спрятана где-то в артефакте. Ищи необычную константу, а не очевидную строку. Координаты в .so - это замаскированная подсказка.
3. what3words-адреса (`///слово.слово.слово`) могут быть «словами» фразы в стиле BIP39 - аккуратный кроссовер геолокационного API и формата кошелька.
4. Нативные «защитные» слои могут быть чистой декорацией: проверь, вызывается ли ворота из dex, прежде чем им доверять. Здесь `hasPerfectMatching` не вызывался вообще, а `checkObjectVicinity` всегда возвращал true.
5. Подбирай инструмент под окружение: с готовым эмулятором быстрейший путь - ввести фразу в UI; без него - офлайн-верификатор на 30 строк делает то же и печатает доказательство (`match=True`, флаг). Оба валидны; скрипт вдобавок защищает от опечаток и оставляет воспроизводимый артефакт.
6. Разница «точная ячейка vs опубликованный объект» важна: задача использовала ОБЪЕКТНЫЕ адреса аэропортов, а не ячейки центров карты. Когда догадка не сработала, попробуй другую интерпретацию той же подсказки.
