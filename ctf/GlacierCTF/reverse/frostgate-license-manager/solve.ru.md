# Русская версия

## 1. С чего начали

В архиве находились два файла: `virt/virt.exe` и `virt/sha256sum`. Второй файл содержал контрольную сумму исполняемого файла. `virt.exe` — 64-битная консольная PE-программа для Windows. Строки в бинарнике показывали, что перед нами менеджер лицензий: программа предлагает ввести ключ и сообщает, что правильный ключ является флагом.

Первичная проверка:

```bash
tar -tzf virt.tar.gz
tar -xzf virt.tar.gz
file virt/virt.exe
sha256sum virt/virt.exe
strings -a -n 5 virt/virt.exe | grep -E 'Frostgate|Enter license|Access granted'
objdump -x virt/virt.exe | less
```

Характерные строки:

```text
Frostgate License Manager  v3.1
Enter license key:
[+] Access granted. The key you entered is the flag.
```

PE-заголовок и таблица секций дали несколько важных ориентиров:

| Свойство | Значение |
| --- | --- |
| Архитектура | Windows PE32+, x86-64 |
| Предпочтительная база образа | `0x100000000` |
| Размер образа в памяти | `0x2d000` |
| Точка входа программы | `0x1000016a0` |
| Необычная исполняемая секция | `.frost0`, RVA `0x29000` |
| Длина настоящего ключа | `40` символов |

В бинарнике присутствуют строки рантайма Delphi; кроме обычных секций (`.text`, `.data`, `.rdata` и др.) есть секция `.frost0`. Она и оказалась связана с защитой основной проверки.

## 2. Ложный след: «флаг», который не подходит

Помимо настоящей проверки в программе имеется отдельная функция по адресу **RVA `0x125c0`**. Её легко принять за решение, потому что она сравнивает ввод с зашифрованными байтами, но проверяет длину **`0x27` (39)**, а не 40.

Для каждого символа этой ветки сравнение эквивалентно:

```python
input[i] == decoy_table[i] ^ ((0x2f * i + 0xa7) & 0xff)
```

Массив лежит по **RVA `0x19890`**, то есть в оригинальном файле, в данном PE, по смещению `0x18290`. Его легко расшифровать одним циклом. Полная команда приведена в разделе «Проверка ложной ветки» ниже.

Результат:

```text
wrong{f1n4l1z3r_d3c0y_n0t_th3_r34l_0n3}
```

Это не `gctf{...}` и сама строка прямо обозначена как decoy. В программе есть условная логика выбора между функциями проверки; нельзя считать первую найденную проверку правильной. Поэтому мы перешли к ветке длиной 40 символов.

## 3. Нашли реальную проверку

Основной проверяющий код расположен по **RVA `0x12490`** (VA `0x100012490`). Его цикл читается даже в обычном дизассемблере, несмотря на защиту вызываемых функций.

Ключевые места:

```asm
; RVA 0x124a4: корректная длина = 0x28 = 40
cmp dword ptr [rip+...], 0x28

; RVA 0x124b8: начальное состояние
mov eax, [input_length]
xor eax, 0xdeadbeef

; RVA 0x124ef: проверка очередного символа
call 0x100012340

; RVA 0x12501–0x1250b: накапливание ошибки
xor eax, [vm_result]
or  eax, [error_accumulator]

; RVA 0x12523: обновление состояния
call 0x100012410

; RVA 0x1252b: цикл до индекса 39 включительно
cmp dword ptr [index], 0x27
```

Из цикла видно, что программа **не сравнивает вход с обычной строкой**. Она выполняет две защищённые функции для каждого байта, причём вторая функция изменяет состояние, необходимое для проверки следующего символа.

Обнаруженные адреса:

| Назначение | RVA | Виртуальный адрес (VA) |
| --- | --- | --- |
| Функция проверки символа `vm_check` | `0x12340` | `0x100012340` |
| Функция обновления состояния `vm_next` | `0x12410` | `0x100012410` |
| Реальный проверяющий цикл | `0x12490` | `0x100012490` |
| Входной буфер | `0x260d0` | `0x1000260d0` |
| Длина ввода | `0x26110` | `0x100026110` |
| Таблица ожидаемых значений | `0x19860` | `0x100019860` |
| Защищённый диспетчер | `0x29000` | `0x100029000` |

Важное различие: **RVA — это адрес относительно ImageBase**, а не смещение в файле. Например, `.data` начинается с RVA `0x19000`, но физически — со смещения `0x17a00`. Поэтому нужная таблица по RVA `0x19860` находится по файловому смещению:

```text
0x17a00 + (0x19860 - 0x19000) = 0x18260
```

В оригинальном файле это ровно 40 байтов:

```text
2e 85 73 e8 b6 9b 94 0e 49 1a 6c 7d 91 3f 57 1e
11 b7 50 9e 43 66 64 f4 81 d3 58 44 49 ea 26 42
ec ca 3b 19 42 65 d1 f7
```

## 4. Почему обычная дизассемблировка не сработала

По RVA `0x12340` и `0x12410` находятся обёртки виртуализированного кода. Они выполняют подготовку стека и обращаются к общему диспетчеру в `.frost0` (VA `0x100029000`), передавая разные селекторы виртуальной программы, например `0` и `0x241`.

При прямом последовательном дизассемблировании после переходов видны бессмысленные инструкции, случайные байты и даже недопустимые опкоды. Это не значит, что выполнение действительно попадает на все эти байты: диспетчер интерпретирует защищённое содержимое, а часть своего кода меняет на лету.

В `.frost0` нашлись повторяющиеся последовательности самоперезаписи. Их схема:

```asm
pushfq
mov dword ptr [rip+1], IMM32
popfq
; следующие четыре байта перезаписываются значением IMM32
```

Есть аналогичные конструкции для записи 1 и 2 байт. При статическом анализе мы применили эти замены к копии секции. Для исходного файла найдено **413** таких записей: **339 четырёхбайтовых, 43 двухбайтовых и 31 однобайтовая**. Это позволило осмысленно изучать код диспетчера, но для восстановления флага **не требовалось полностью переписывать виртуальную машину на Python или C**.

Скрипт, воспроизводящий применение этих замен к копии секции, находится в общем приложении ниже. Он не модифицирует `virt.exe`.

## 5. Главная идея: использовать оригинальные VM-функции как оракул

Решение оказалось проще полной деобфускации. Мы уже знаем аргументы вызовов из цикла, а также можем извлечь таблицу ожидаемых значений. Вместо перевода всей VM в высокоуровневый код можно вызвать её оригинальные функции из собственного процесса.

В Windows x64 первые три целочисленных аргумента передаются через `RCX`, `RDX`, `R8`. Для функций из `virt.exe` интерфейс выглядит так:

```c
uint32_t vm_check(uint32_t character, uint32_t state, uint32_t index);
uint32_t vm_next (uint32_t character, uint32_t state, uint32_t index);
```

В Linux GCC для такого вызова используется атрибут `__attribute__((ms_abi))`, иначе регистры аргументов будут неправильными.

Идея следующая:

```python
length = 40
state = length ^ 0xDEADBEEF
result = ""

for i in range(length):
    expected = target[i]
    # Восстанавливаем символ для уже известного состояния.
    candidates = [
        c for c in range(0x20, 0x7f)
        if vm_check(c, state, i) == expected
    ]
    assert len(candidates) == 1
    c = candidates[0]
    result += chr(c)
    state = vm_next(c, state, i)
```

**Почему перебор посимвольный, а не `95^40`?** Потому что состояние для позиции `i` зависит только от уже восстановленного префикса. Сначала проверяем 95 печатных ASCII-кандидатов для первого символа, затем обновляем состояние с найденным символом, и так далее. Получается всего **`40 × 95 = 3800`** проверок `vm_check` плюс 40 вызовов `vm_next`.

Критично не обновлять `state` во время проверки *неверных* кандидатов: оригинальная программа обновляет его только после проверки текущего символа, а при решении мы должны перейти к следующему индексу с правильным кандидатом.

## 6. Как вызвали функции Windows PE из Linux

Мы не запускали Windows-приложение целиком под Wine и не вызывали его точку входа. Вместо этого написали небольшой нативный C-harness:

1. Открыть исходный `virt.exe` и прочитать PE-заголовки.
2. Проверить, что это ожидаемый 64-битный PE с ImageBase `0x100000000`.
3. Выделить приватный участок памяти по этой базе с правами `READ | WRITE | EXEC` (запись нужна, потому что `.frost0` самомодифицируется).
4. Перенести каждую секцию файла из `PointerToRawData` по её `VirtualAddress` (RVA), сохранив ожидаемую карту памяти.
5. Взять указатели на функции по RVA `0x12340` и `0x12410`, используя Windows x64 ABI.
6. Прочитать таблицу из отображённого образа по RVA `0x19860` и восстановить флаг.

В этой части кода вызовы WinAPI не понадобились: мы обращаемся непосредственно к двум вычислительным функциям и их диспетчеру, а не к интерактивному вводу/выводу программы. Образ не изменяется на диске. Это также означает, что код привязан к **Linux x86-64**, к конкретному PE и к доступности фиксированного адреса памяти.

Безопаснее выполнять такое воспроизведение в изолированной CTF-VM/контейнере: даже если запускается только часть кода, в памяти выполняются машинные инструкции из анализируемого бинарника.

# Воспроизведение / Reproduction

## Требования / Prerequisites

- Linux on **x86-64** (или Linux VM/WSL2 с доступным отображением памяти по `0x100000000`).
- `gcc` и стандартные заголовки Linux; `python3` — только для дополнительных статических проверок.
- Своя копия исходного `virt.tar.gz` — **не приложена к этому райтапу**.

Начальные команды / Initial commands:

```bash
mkdir -p virt-repro && cd virt-repro
# Скопируйте сюда свой virt.tar.gz / Place your own archive here.
tar -xzf virt.tar.gz
sha256sum virt/virt.exe
# expected:
# ec5620b986ee7102054e676998dedcea7e25f101b0def8d7366f83010bf16ce2
```

## A. Проверка ложной ветки / Verify the decoy

Команда читает таблицу по RVA из PE и расшифровывает её без сторонних библиотек / The command extracts and decodes the decoy table from the PE without external libraries:

```bash
python3 - <<'PY'
from pathlib import Path
import struct
b = Path('virt/virt.exe').read_bytes()
pe = struct.unpack_from('<I', b, 0x3c)[0]
s = pe + 24 + struct.unpack_from('<H', b, pe + 20)[0]
for i in range(struct.unpack_from('<H', b, pe + 6)[0]):
    h = s + i * 40
    name = b[h:h+8].rstrip(b'\0')
    if name == b'.data':
        rva = struct.unpack_from('<I', b, h + 12)[0]
        file_offset = struct.unpack_from('<I', b, h + 20)[0]
        start = file_offset + (0x19890 - rva)
        encoded = b[start:start + 39]
        decoded = bytes(x ^ ((i * 0x2f + 0xa7) & 255)
                        for i, x in enumerate(encoded))
        print(decoded.decode('ascii'))
        break
PY
# wrong{f1n4l1z3r_d3c0y_n0t_th3_r34l_0n3}
```

## C. Полный решатель / Complete native solver (`solve_virt.c`)

Сохраните приведённый ниже исходный код как `solve_virt.c`. Он сам читает секции PE, таблицу ожидаемых значений и вызывает настоящую VM в памяти. **Флаг в программе не захардкожен.** / Save the following as `solve_virt.c`. It reads the original PE, maps its sections, extracts the real target table and invokes the VM in memory. **The flag is not hardcoded.**

The complete original, flag-independent C solver is preserved as [`scripts/solve_virt.c`](scripts/solve_virt.c).

## D. Сборка и результат / Build and verify

```bash
gcc -O2 -Wall -Wextra -o solve_virt solve_virt.c
./solve_virt virt/virt.exe
```

Для короткой проверки вывода / For a short output check:

```bash
./solve_virt virt/virt.exe | tail -3
```

Ожидаемый вывод / Expected output:

```text
39  }  state=14792a50
FLAG: gctf{...}
final state: 14792a50
```

При успехе решатель завершается с кодом `0`. Если на какой-либо позиции число подходящих ASCII-символов не равно единице, он останавливается и выводит состояние и ожидаемый байт. Если фиксированная база `0x100000000` недоступна, `mmap` сообщит об ошибке; используйте изолированную x86-64 Linux-среду с доступной памятью по этому адресу. На ARM или Windows этот Linux-харнесс напрямую не рассчитан.

Воспроизведение проверено на оригинальном файле с указанным SHA-256: все 40 позиций восстановлены единственным образом, начальное состояние `0xdeadbec7`, конечное — `0x14792a50`. В результате не использовались заранее известные символы флага, кроме проверки формата `gctf{...}` **после** полного восстановления.

## Итог / Takeaway

В задаче сочетались **ложная проверка**, **виртуализация контрольных функций** и **самомодифицирующийся диспетчер**. Главное решение — отделить внешний алгоритм сверки от скрытой реализации операций, затем использовать доступные бинарные функции как точный оракул. Это позволило восстановить все 40 символов без полной ручной деобфускации VM.

The key insight was to separate the visible validation loop from the virtualized primitives. Once the comparison table and state dependency were known, **the original VM could serve as its own oracle**. A short native harness recovered all 40 characters exactly, without reproducing the entire VM interpreter.
