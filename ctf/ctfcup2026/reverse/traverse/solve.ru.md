# Traverse: флаг из битстрима iCE40

[English](solve.md)

## 0. Постановка

В архиве `traverse.zip` лежали два файла: `traverse.bin` (32 220 байт) и `run.py`. Расширение `.bin` тянет к реверсу обычной программы, но обвязка говорит об обратном: она собирает тестбенч вокруг конфигурации ПЛИС. Это битстрим Lattice iCE40 HX1K. Здесь нет опкодов, есть только таблицы LUT, триггеры и биты маршрутизации.

План получился такой:

1. Прочитать обвязку и понять, как вход попадает в устройство и какой байт считается ответом.
2. Превратить битстрим в гейт-лист.
3. Восстановить автомат, который формирует байт ответа.
4. Дойти по нему до принимающего состояния и сдать строку, которая туда ведёт.

## 1. Что задаёт обвязка

`run.py` делает весь инструментарий сам: распаковывает битстрим, конвертирует его в Verilog с файлом ограничений, компилирует UART-тестбенч и гоняет его на 12 МГц, 115200 8N1. Вход это строка, завершённая `\n`, выход один байт. В скрипте же лежит карта выводов `chip.pcf`, а пример строки в нём это заглушка, а не флаг.

Практическая деталь того дня: на машине не было `sudo` и пакетов IceStorm. И то и другое обходится:

```bash
apt-get download fpga-icestorm iverilog yosys
dpkg-deb -x fpga-icestorm_*.deb /tmp/gigatool/tools
dpkg-deb -x iverilog_*.deb     /tmp/gigatool/tools
```

Обёртки для `iverilog` и `vvp`, которые передают `-B` и `-M` в `tools/usr/lib/x86_64-linux-gnu/ivl`, позволяют запускать `run.py` без изменений.

Зачем этот шаг: без гейт-листа битстрим это 32 КБ безымянных битов. С ним появляются имена ячеек и связей, и только так можно рассуждать о проверке.

## 2. Из битов в схему

```bash
iceunpack traverse.bin chip.asc
icebox_vlog -s -p chip.pcf chip.asc > chip.v
```

Получается 693 LUT и 69 триггеров, блочная RAM не задействована. Полезная проверка: `icepack chip.asc` воспроизводит `traverse.bin` побайтово, значит ничего важного вне конфигурационной памяти нет.

Зачем этот шаг: отсутствие BRAM исключает заранее записанный флаг или таблицу ожидаемых байтов. Проверка обязана вычисляться логикой и состоянием.

## 3. Ловушка: на любой вход отвечает `f`

Симулятор на любом входе возвращает ровно один байт `0x66`, то есть букву `f`. Так на всех 256 одиночных символах, на длинах от 1 до 300 и при разных паузах между байтами. От длины зависит только время ответа, значит триггер это `\n`, а не результат сравнения.

Полное сравнение трасс всех 69 регистров для `A\n` и `B\n` даёт различия только в регистрах приёма. При наивном чтении схема выглядит независимой от входа, и именно здесь умирает перебор.

Зачем этот шаг: понимание, что видимый выход постоянен, заставляет искать скрытое состояние, а не угадывать строки.

## 4. Где спрятано состояние

Важны две группы регистров:

- Принятый байт: `n54` (бит 0), `n56`, `n58`, `n55`, `n51`, `n57`, `n53`, `n52` (бит 7).
- Байт состояния: `n436`, `n439`, `n440`, `n441`, `n530`, `n531`, `n532`, `n534`. Он перезаписывается на каждом принятом символе по сигналу `n146`, значение при сбросе `0xA0`.

Байт ответа собирается в момент `n106` (конец строки) из трёх битов `led`, `n117`, `n114`, а те приходят из комбинационной логики по текущему состоянию и текущему символу:

- `(0, 1, 1)` даёт `0x66`, буква `f`
- `(1, 1, 0)` даёт `0x73`, буква `s`

То есть автомат действительно двигается на каждом символе, но ответ выдаёт только на переводе строки, и этот байт зависит от достигнутого состояния, а не от текста напрямую. Поэтому одиночные символы и любой мусор всегда заканчиваются на `f`.

## 5. Модель и поиск

Нетлист достаточно регулярный, чтобы его разобрать. Небольшой вычислитель на Python обрабатывает `assign`-выражения с `?:`, `!`, `&` и `|` и точно воспроизводит комбинационную часть; сверка с Icarus на 2768 тактах дала 100 процентов совпадения.

Когда есть `s' = F(s, c)`, остаётся поиск по графу:

- стартовое состояние `0xA0`
- переходы по всем 256 возможным символам
- достижимо 139 состояний
- ровно одно состояние, `0x7f`, даёт `(1, 1, 0)` при приходе перевода строки

Обход в ширину даёт кратчайший путь из `0xA0` в `0x7f`, и именно эта строка сдаётся. Тут стоит разделить, что поиск доказывает, а что нет:

- принимающее состояние единственно среди 139 достижимых, значит любая принятая строка заканчивается в `0x7f`;
- обход в ширину гарантирует, что первый найденный путь кратчайший, то есть строка минимальна по длине;
- он не доказывает, что принятая строка единственна. Более длинный маршрут может вернуться в `0x7f` до перевода строки и тоже быть принят. Тесты с мутациями ниже согласуются с единственным коротким путём, но в общем случае этого не исключают.

Для этой задачи кратчайшего пути хватило, и его длина совпадает с ожидаемым форматом флага.

Зачем этот шаг: пространство состояний 256 на 256 достаточно мало для полного перебора, а условие успеха это одно состояние, поэтому поиск кратчайшего пути здесь и дешёвый, и достаточный.

## 6. Проверка на оригинальном битстриме

Найденная строка прогнана через нетронутые `run.py` и `traverse.bin`:

- верная строка - `s` (`0x73`)
- изменена последняя hex-цифра - `f` (`0x66`)
- убран последний символ - `f`
- изменена первая hex-цифра - `f`
- `hello` - `f`

Любая мутация, включая изменение длины, отклоняется, значит совпадение не по префиксу. Сама линия UART отдаёт `0x73` на верном входе и `0x66` на любом другом.

Флаг в репозитории скрыт как `ctfcup{...}`, воспроизведение в `scripts/solve_traverse.py`:

```bash
iceunpack traverse.bin chip.asc
icebox_vlog -s -p chip.pcf chip.asc > chip.v
python3 scripts/solve_traverse.py chip.v
```

Скрипт печатает число достижимых состояний и строку с флагом.

## 7. Тупики, которые стоит помнить

- Поиск `ctfcup{` в битстриме, в ASCII-дампе и в таблицах истинности LUT ничего не дал, при любом порядке бит и смещении.
- Гипотеза «это ROM, разложенный на восемь битовых плоскостей» не подтвердилась: таблицы истинности оказались обычной логикой с popcount 1, 3 и 9.
- Форсирование регистров приёма и перебор входных байтов дают ровно описанную картину, потому что ответ не является сравнением.
- Ранний архив `traverse_analysis_scripts.zip` воспроизводит только предварительную разведку, поиска автомата в нём нет.

## 8. Выводы

- Формат файла определяет инструменты. Битстрим это не бинарник для дизассемблера.
- Постоянный выход не означает мёртвую проверку: результат может лежать в состоянии, которое наблюдается только на разделителе.
- Когда пространство состояний конечно и мало, полный обход по честной модели надёжнее угадывания.

Одним абзацем: задача это схема на iCE40, чья проверка на любой строке отвечает `f` и раскрывается только на переводе строки; после пересборки нетлиста через IceStorm и моделирования восьмибитного автомата на Python обход в ширину по 139 достижимым состояниям находит единственное принимающее состояние `0x7f`, а кратчайший путь до него и есть флаг; единственность самой строки поиск не доказывает, но для сдачи хватает кратчайшей.
