# thin-ice — извлечение Git-объектов через receive-pack oracle

[English version](solve.md)

## 1. Устройство задачи

Оригинальный `thin_ice.tar.gz` содержит небольшой сервис Alpine с `git-daemon`. Скрипт `entrypoint.sh` создаёт временный Git-репозиторий, записывает содержимое `/flag.txt` в `flag.txt`, коммитит его с сообщением `test.`, фиксированными датой `2004-10-04T00:00:00Z`, автором и коммиттером `losfuzzys`, затем клонирует репозиторий в bare-формате как `/srv/git/shared.git`.

Запуск демона устроен так:

```sh
git daemon --reuseaddr --base-path=/srv/git --strict-paths --export-all \
  --listen=0.0.0.0 --port=1337 --enable=receive-pack \
  --disable=upload-pack --disable=upload-archive /srv/git/shared.git
```

У bare-репозитория есть `hooks/update` с `exit 1`. Поэтому `git clone` не работает (выключен `upload-pack`), а попытка push не может обновить refs. Цель — извлечь **содержимое** объекта, имея лишь интерфейс приёма Git-паков.

Исторический сервис `13372` выдавал kCTF PoW, а после ENTER — новый инстанс на 600 секунд. Git-доступ проходил через общий маршрутизатор на `13360`.

## 2. Первая проблема: маршрутизация Git

Первые запросы возвращали однотипный отказ:

```text
ERR access denied or repository not exported
```

Проверка путей, вариантов `git-upload-pack`, протоколов v0/v2 и попыток инъекции в путь результата не дала.

Реальное решение: запрос `git-receive-pack` в формате pkt-line должен включать `host=<uuid>`, где `uuid` — первые 32 hex из имени инстанса, без `--thin-ice`. Путь должен соответствовать баннеру:

```text
git-receive-pack /<uuid>--thin-ice/shared.git\0host=<uuid>\0
```

Перед этой строкой ставится четырёхсимвольная шестнадцатеричная длина pkt-line. Удалённый маршрутизатор срабатывал приблизительно в четверти попыток, поэтому транспорт делал до **45 повторов**.

После правильного подключения `receive-pack` сам раскрывал SHA HEAD при объявлении refs:

```text
refs/heads/main = 2c7c30925427d63273b2fb14c7b81c6fe4197074
```

Это уже известный ID коммита, хотя скачать сам коммит нельзя.

## 3. Что даёт отклонённый push

Локально обнаружили: `git-receive-pack` мигрирует объекты из карантина при разборе pack раньше, чем `hooks/update` отклоняет изменение refs. Получается возможность передавать объекты в объектную базу, хотя сам push отвечает ошибкой.

Далее используются **thin pack** и `REF_DELTA`. База дельты может находиться в существующем репозитории, не присутствуя внутри переданного PACK. Если базовый объект найден, Git применяет дельту; если нет — она остаётся неразрешённой.

Дополнительный оракул позволяет узнать **размер объекта**: поле `base_size` внутри дельты должно точно равняться реальной длине базы. Разница ответов `unpack ok` и `failed to apply delta` показывает правильное значение.

Первый вариант оракула через `duplicate base <oid>` тестировался локально, но оказался ненадёжным для Git 2.56.1. Финальный солвер использует **количество неразрешённых дельт**, которое сообщает `index-pack`.

## 4. Математика счётного оракула

Пусть известны Git OID секретного объекта `H`, его размер `L`, тип `kind`, и требуется узнать байт `S[i]`.

Берём свежий nonce `r` длиной 7 байт. Первый `REF_DELTA` с базой `H` преобразует секретный объект в:

```text
P = r || S[i]
```

В Git-дельте сначала вставляется nonce, затем командой COPY копируется ровно один байт исходного объекта по заданному смещению.

Для каждого кандидата `c` заранее считаем OID:

```text
candidate_oid = SHA1(kind + " " + len(r||c) + "\0" + r||c)
```

Добавляем `w(c)` дочерних `REF_DELTA`, которые **ссылаются** на этот OID в качестве базы, но сам кандидат в pack не включаем. Каждая дочерняя дельта должна скопировать 8 байт кандидата и добавить `!`.

Все кандидаты, кроме реального `c=S[i]`, остаются неразрешёнными: только в одном случае родительская дельта создала объект с нужным OID. Если суммарно было `T=Σw(c)` таких детей, а сервер сообщает `N` неразрешённых, то:

```text
N = T - w(S[i])
S[i] = inverse_weight(T - N)
```

Вес каждого кандидата внутри набора уникален. Для маленьких алфавитов достаточно одного Git-запроса на байт: `0123456789abcdef` при чтении tree-OID из коммита, ASCII `32..126` при чтении флага.

Для произвольных двоичных байтов используем два запроса: сначала старший полубайт с весами `1+(c>>4)`, затем младший с 16 вариантами.

**Важно правильно указать тип Git-объекта:** commit=1, tree=2, blob=3. Дочерний OID должен вычисляться для того же типа, что и исходная база; иначе даже правильный кандидат не разрешится.

Чтобы запустить именно `index-pack`, к паку добавлялись filler-объекты, пока общее число записей не достигало **110**. Для предотвращения ложных совпадений при серии запросов каждый раз создавался новый nonce.

## 5. Практическая цепочка

Финальный драйвер `run_flag.py` сохранял чекпоинт после каждого успешно найденного байта:

| Этап | Исходный объект | Метод | Результат |
| --- | --- | --- | --- |
| SHA tree | HEAD commit, 166 байт | 40 hex-символов с offset 5 | `6fe60ef3d25dd3e8bccec929a4b44297e80e41a0` |
| SHA blob | tree, 36 байт | 20 двоичных байт с offset 16, по 2 запроса | `5c5955cf03e044090e9db2f2280fe08acdb1c5e1` |
| Длина | blob | перебор `base_size` от 16 | **27** |
| Флаг | blob | 27 байт из printable ASCII | `gctf{...}` |

Полные OID:

```text
commit 2c7c30925427d63273b2fb14c7b81c6fe4197074
tree   6fe60ef3d25dd3e8bccec929a4b44297e80e41a0
blob   5c5955cf03e044090e9db2f2280fe08acdb1c5e1
```

В формате commit поле начинается с `tree `, поэтому ASCII-hex SHA занимает байты с 5 по 44. В однозаписном дереве `100644 flag.txt\0` занимает 16 байт, затем идёт сырая 20-байтная SHA blob.

## 6. Подтверждённый результат

Фактический `evidence/run_flag.log` показывает успешный PoW, извлечение 40/40 символов tree-OID, 20/20 байт blob-OID, длину 27 и 27/27 байт флага. Последние строки — `[+] FLAG` и `DONE` с одним и тем же результатом.

В отчёте зафиксированы **118 Git-запросов и примерно 150 секунд** в одном 600-секундном инстансе. `flag_state.json` совпадает с логом.

Пользователь отдельно подтвердил **принятие флага платформой**. В публичных файлах принятое значение маскируется как `gctf{...}`.

## 7. Независимая проверка Git SHA-1

Для объекта Git:

```text
OID = SHA1("<type> <size>\0" || содержимое)
```

`entrypoint.sh` записывает флаг без завершающего перевода строки (`printf '%s'`). Tree содержит ровно одну запись `100644 flag.txt\0` и 20 сырьевых байт blob-OID. Из фиксированных даты, автора, коммиттера, дерева и сообщения `test.` восстанавливается точное тело коммита длиной 166 байт.

[scripts/verify_git_chain.py](scripts/verify_git_chain.py) принимает значение флага **в момент запуска локально**, считает три SHA-1 и сопоставляет с удалёнными OID. При подготовке текста все три значения были отдельно пересчитаны и совпали. В файле скрипта настоящего флага нет.

## 8. Неудачные ветви и ограничения

Сначала пробовали `clone`/`ls-remote`, `upload-pack` v0/v2, разные пути, варианты host, shell-метасимволы, поиск других портов, десятки повторов запроса и словарный перебор 2,39 млн leet-фраз. Все эти попытки не дали чтения объекта.

Ранний `duplicate base` оракул работал в локальном эксперименте, но **не** стал успешным удалённым методом. Финальный счётный oracle v2 проверялся локально на Git 2.47.3 и затем использовался в удалённом драйвере против Git 2.56.1.

В первоначальном чате описан локальный успех с фейковым флагом, но удалённый результат тогда ещё отсутствовал. Последующий архив агента содержит оригинальный успешный удалённый лог — именно на него опирается итоговый райтап.

Оригинальный архив, солвер и сырой лог доступны в частном `glacierctf_thin-ice_materials.zip`; в GitHub они не дублируются с реальными флагами и адресами инстансов.

## 9. Вывод

Даже если запретить `fetch` и изменение refs, интерфейс `receive-pack` может оставлять **побочные каналы через диагностику разбора Git-паков**. Здесь ответ о числе неразрешённых дельт превратился в побайтовое чтение Git-объектов, вплоть до полного флага.
