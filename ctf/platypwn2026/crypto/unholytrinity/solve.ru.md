# Unholy Trinity: ход решения

[English](solve.md)

## 1. Условие и данные

В самодельной RSA-аутентификации было две независимые ошибки: модульный хэш пароля и доказательство знания короткого секрета. Исходные материалы: `server.py`, Dockerfile, compose; изначально только команда запуска, но позднее восстановлен оригинальный `scripts/solve_unholytrinity.py`.

## 2. Анализ

Сервер задаёт `e=17`, RSA-модуль `N` примерно на 2674 бита и хранит `hash_pw(pw) = int(pw)^17 mod N`. Разные числа, сравнимые по модулю N, дают одинаковый хэш. У `admin` секрет всего 19 байт: для такого `m` выполняется `m^17 < N`. Сервер печатает `pw_hash` до раундов, значит точный целочисленный корень степени 17 раскрывает секрет без факторизации N.

## 3. Как получен результат

1. Прочитать из приветствия публичные `N` и `e`.
2. Построить два разных пароля длиной `NLEN`: числа `x+N` и `x+2N` (или пару с разницей N); оба должны пройти странную проверку символов в `str(bytes)`.
3. Зарегистрировать двух пользователей: совпадение RSA-хэша откроет первый флаг.
4. Начать вход `admin`, получить опубликованный `pw_hash` и извлечь точный целочисленный корень степени 17 — исходный 19-байтный секрет.
5. На каждом раунде выбрать ненулевое `r`, отправить `announcement=r^17 mod N`, получить `c`, ответить `response=r*m^c mod N`. Проверка сервера выполнится.
6. Пройти все раунды и получить второй флаг.

## 4. Подтверждение

Математика обеих ошибок напрямую видна в приложенном `server.py`. В первоначальном ZIP есть только команда запуска, но позже оригинальный код солвера восстановлен в `scripts/`. Полного терминального вывода всё ещё нет. Результат с двумя флагами подтверждён отчётом.

Результат: **2 флаг(а) принято**, содержимое замаскировано `PP{...}`.

## 5. Ограничения воспроизведения

Исходный код солвера теперь сохранён и показывает фактически использованное `r=1` и 52 раунда. Не сохранились лишь случайные вызовы сервера и полный живой терминальный вывод.

## 6. Защита и вывод

Для хранения паролей нужен KDF, например Argon2id, а не RSA-степень. Самодельный протокол идентификации с коротким секретом и малым показателем опасен.


## Оригинальный решающий скрипт

Найден оригинальный солвер двух флагов: два пароля одинаковой длины с совпадающим RSA-хэшем по модулю N, точный целочисленный корень степени 17 от хэша admin и прохождение 52 раундов идентификации.

```bash
python3 scripts/solve_unholytrinity.py <host> <port>
```

Код: [scripts/solve_unholytrinity.py](scripts/solve_unholytrinity.py). Параметры и проверки находятся в файле, адрес инстанса в него не встроен.


## 7. Алгоритм солвера: точные формулы

В исходнике две проверки, и каждая имеет собственную математическую уязвимость.

**Регистрация.** Публичный модуль `N=pq` имеет примерно 2674 бита, а `e=17`. Сервер принимает пароли длиной `NLEN=ceil(bit_length(N)/8)` и сравнивает одновременно сырые байты и RSA-«хэш» `h(x)=x^17 mod N`. Для любых допустимых `x`:

```text
a = N + x
b = 2N + x
a != b
a mod N = b mod N = x
a^17 mod N = b^17 mod N
```

Это даёт разные байтовые пароли с одинаковым хэшем. В настоящем `scripts/solve_unholytrinity.py` начальное `x` берётся из `b"Aa1+"` и постепенно увеличивается, пока оба числа не помещаются в `NLEN` байт и проходят серверный фильтр. Проверка пароля написана необычно: символы ищутся в `str(password)`, то есть в текстовом представлении объекта `bytes`, а не непосредственно в пароле. Солвер воспроизводит **именно эту проверку**, поэтому не теряет время на отклонённые регистрации.

Сервер при совпадении хэша с другой ранее зарегистрированной записью печатает `FLAG0`, но затем всё равно продолжает регистрацию. Имена, записанные солвером, — `player0` и `player1`. Пользователя `admin` регистрировать не требуется.

**Администратор.** Сервер заранее выбрал 19 случайных байт `m`. При входе он публикует десятичное `h=m^17 mod N`. Поскольку максимум 19-байтного числа имеет 152 бита, `m^17` занимает не более 2584 бит, меньше `N`, и взятие остатка ничего не меняет:

```text
h = m^17  (as an ordinary integer)
m = exact_integer_root(h, 17)
```

Солвер ищет точный корень бинарным поиском и проверяет обратным возведением в степень. Это **не факторизация RSA**.

Далее идёт 52 раунда (`ROUNDS = 256 // 5 + 1`). Проверка сервера:

```text
response^17 == announcement * h^challenge   (mod N)
challenge in {0, ..., 16}
```

В реальном скрипте выбран максимально простой `r=1`: `announcement=1`, `response=m^challenge mod N`. Обе величины ненулевые, взаимно просты с модулем с подавляющей вероятностью и удовлетворяют равенству. Это точнее описывает успешную реализацию, чем абстрактный вариант с произвольным `r`.

Почему этот способ работает: схема подтверждения знания секрета не защищает его от восстановления из уже опубликованного `h`, если исходный секрет слишком короток для выбранного малого показателя степени.

## 8. Воспроизведение и проверки

```bash
python3 scripts/solve_unholytrinity.py <host> <port>
```

Скрипт сначала выводит размер `N` и `NLEN`, потом результат обеих регистраций и `FLAG0`. Перед аутентификацией admin он проверяет `pow(m,e,N)==admin_hash`. После последнего из 52 раундов ищет `FLAG1` в ответе.

Для проверки офлайн можно независимо убедиться, что у пары `N+x` и `2N+x` совпадает RSA-хэш. Скрипт не содержит адреса стенда или готовых значений секретов. Само по себе знание флага в этом разборе не подставляется в решение.

## 9. Какие ошибки здесь важнее всего

1. Криптографическая функция `pow(password, 17, N)` не является безопасным хэшем пароля: её значение зависит только от остатка password по модулю N.
2. Ограничение длины `NLEN` не делает отображение инъективным: есть несколько допустимых чисел, сравнимых по модулю N.
3. Вывод `pw_hash` до проверки входа не безопасен для короткого `admin_secret` при маленькой степени.
4. 52 итерации интерактивного протокола не компенсируют утечку самого секретного `m`.
