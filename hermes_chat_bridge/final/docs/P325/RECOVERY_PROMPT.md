### 3. Архитектура, которую требуется восстановить

Актуально обнаруженный путь ChatGPT: `dialog_index/health` → GitHub по pin HEAD → preflight → Git commit и CAS → `dialog_notice` → Unix authority → private GitHub `dialogs/<task_id>` → MT Inbox plugin → MT session.prompt → MT append(report) → ChatGPT `dialog_index` + GitHub `fetch_file`. Исторический путь с `dialog_view/dialog_append` действует лишь если эти операции вновь обнаружены и авторизованы.

Панель на localhost:8787 предоставляет историю, управление и возврат только последнего хода. Старый Hermes queue с bridge_put_message/job_id — **отдельный механизм**, не используемый как скрытая замена Git-протоколу. Прямые GitHub create_file/commit **не дают гарантий `dialog_append`**: это ограниченный fallback из памятки, допустимый только с проверкой полного snapshot до Git, candidate до ref и fast-forward CAS, без утверждения exactly-once.

Одна беседа = одна отдельная ветка dialogs/<task_id>, файлы task.json, state.json, messages/<seq>.<actor>.json; основной branch main не является диалогом. Git сохраняет историю, но не реальный процесс исполнения.

Пишущий актор предъявляет актуальный head, постоянный message_id и право хода. Append делает fast-forward без force. При неизвестном результате **не менять message_id и не создавать повторно**, только читать и сверять. Для создания нового диалога dialog_create(request_id,title) вызывается один раз; если результат неизвестен, dialog_creation_status с **тем же** request_id.

MT inbox примерно каждые 60 секунд читает Git через CLI. Межэкземплярная файловая блокировка сериализует отправку. Durable локальный seen подавляет повтор уже подтверждённого seq, inflight резервирует неизвестный результат до prompt. Для существующей session_id обязательно выбрать её собственный directory из opencode.db; если каталог неизвестен, не выполнять prompt.

Вернуть ход = отдельная owner-only операция return_turn для последнего сообщения, она не удаляет Git-коммиты и не должна исполняться MT как новое задание. Удаление ветки требует отдельного подтверждения владельца; никогда не удалять реальный диалог для диагностики.

### 4. Выбери сценарий восстановления

**A. Git и MCP работают, MT молчит.** Проверь waiting_for, inbox.log, плагин и процесс, seen/inflight и сессию. При inflight неизвестно, выполни read-only reconcile с MT-чатом. Нельзя уменьшать seen, удалять inflight или отправлять старую задачу повторно без подтверждения отсутствия эффекта.

**B. MT получает задачи в неправильную вкладку.** Сверь установленный SHA и реально загруженную версию, сохранённую sessions[task_id], актуальный session_id/directory. Версия P32.5 896e189 использует durable session binding как приоритет; при неизвестном каталоге остановит отправку. Изменение привязки допустимо только при остановленном MT, пустом inflight, резервной копии и атомарной смене одного ключа.

**C. Hermes/Unix authority сломан, Git жив.** Восстанови общую authority и MCP на основании repository source/runbook, не редактируя разговоры напрямую в GitHub. Сохрани SQLite registry, append/outbox/event журналы, authority sockets, настройки bridge и владелец OAuth. Не запускай новую пустую state DB как замену без оценки дублей.

**C1. Hermes Bridge не запускается, но Git и панель доступны.** Проверить отдельный P33-постмортем: Git-диалог `task_58deb02895d43f1548bdf265fe118bd8` (MT №1 и №3). После краша в `/home/kali/agent-dialog-beta/state` оставались `authority-cg.sock` и `authority-mt.sock` без живого процесса. `src/git_dialog/unix_authority.py` запрещал bind на существующий path, а `gateway_lifespan.py` маскировал ошибку кодом `authority_host_failed`; systemd `Restart=no` оставлял службу выключенной. MT восстановил её вручную после тщательной проверки, но исправление исходников для автоматического безопасного восстановления **ещё не было развёрнуто** в отчёте P33 №3. Сначала read-only `systemctl status`, `ss -xlp`, `ss -ltnp`, `lstat` socket path. **Никогда не удалять Unix socket только потому, что он существует**: нельзя трогать живой listener или неизвестный inode. Любая очистка — отдельное согласованное операторское действие после строгой проверки uid/type/mode/inode и отсутствия listener. Production HEAD моста на дату аудита P33 `4b309cbeeffc7c090f5fc40155062ecdba81bb03`, не путать с SHA плагина P32.5.

**D. Утрачен компьютер и остался только Git.** Git сам по себе НЕ восстанавливает токены, пароли, авторизацию, opencode.db, local inbox seen/inflight, SQLite-журналы, установленные плагины и PID. Попроси защищённые резервные копии и ручное восстановление OAuth/токенов через локальный безопасный способ. Клонируй приватный репозиторий отдельно, проверь SHA и исходники, изолированно проверь тесты, восстанови инфраструктуру. При потере местного state нельзя гарантировать exactly-once, поэтому сначала сверяй Git-историю и фактические ответы/эффекты MT; старую задачу не запускать повторно автоматически.

**E. ChatGPT получает «вызов инструмента заблокирован».** Различай отказ платформы, ошибку MCP и Git. Проверяй commit через `dialog_index` и GitHub по точному HEAD; если неясно, не придумывай новую цепочку message_id. Статистика наблюдений велась в private issue #4; внутренние правила блокировки платформы недоступны. Не пытайся обходить проверки безопасности.

### 6. Контролируемая установка и критерии STOP

Сначала проверь, не установлен ли уже релиз (аудит MT №82 его подтвердил). Если мост исправен, не переустанавливай. При реальной необходимости покажи владельцу точный выбранный SHA, установленную версию, служебные состояния и план rollback. Не выполняй незапрошенный restart MultiTool/bridge/taskboard, не трогай OAuth/секреты/порты и не удаляй беседы.

Если хозяин разрешил обновление, останови MT, убедись в отсутствии действующего prompt/inflight, сохрани plugin и state backups с режимом 0600. Атомарно установи подтверждённый plugin; переустановку кода выполняй только в проверенном релизном процессе. Привяжи один task_id к подтверждённой Chat-45 после остановки MT, без изменения seen, inflight, других sessions. Не копируй старый state.json целиком в rollback после новых доставок: откат seen вызывает дубли.

Smoke-test: новый task по правильному head доставляется один раз и только в Chat-45; directory совпадает с session database, seen становится равен seq и inflight исчезает; ответ MT записан в ту же ветку. Затем отдельный тест кнопки «Вернуть ход» без повторной отправки return к MT. Если одна из проверок не проходит, остановись и предложи обратимое устранение конкретного блокера.

Незакрытые, **не блокирующие** улучшения (классификация любых 404 как вероятного удаления сессии, сообщения host plugin loader о path) записать в backlog, не задерживать рабочий релиз.

### 7. Как отчитываться владельцу

Коротко: что прочитано в Git и конкретный SHA; что действительно работает (Git/MCP/authority/inbox/чат), что сломано; waiting_for и последний seq; seen/inflight; тесты с реальными результатами; **один** следующий безопасный шаг; откат и приёмка. Не называй отчёт MT независимой проверкой, если сам не проверял.

Если мост уже работает и обе стороны обмениваются сообщениями — **ничего не переделывай**, сохрани checkpoint и возвращайся к CTF.
