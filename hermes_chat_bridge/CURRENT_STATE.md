# Hermes Chat Bridge — состояние на 10 ноября 2026 года

## Схема работы

Текущая архитектура использует **Git-диалоги**, а не SQLite-очередь старой реализации. Каждая задача имеет `task_id` и отдельную ветку `dialogs/<task_id>`, содержащую `task.json`, `state.json` и `messages/<seq>.<actor>.json`.

Взаимодействие включает MCP-инструменты ChatGPT, Git-журнал, локальную authority, MT Git Inbox, локальную сессию MultiTool и Taskboard.

| Компонент | Роль |
| --- | --- |
| MCP `dialog_*` | Создание и просмотр задач, получение статуса, уведомление о публикации |
| Git-диалог | Неизменяемая история сообщений и порядок ходов в ветке задачи |
| Локальная authority | Проверка состояния, разрешений и очередности действий |
| MT Git Inbox | Передача нового поручения в закреплённую сессию; учёт `seen` и `inflight` |
| Taskboard | Локальная панель задач и истории, обычно порт `8787` |
| MCP bridge transport | Локальный транспорт, обычно порт `8765`; доступ снаружи зависит от конфигурации машины |

## Последняя подтверждённая приёмка

**8 ноября 2026** была подтверждена установка P36.2: тестовый двусторонний обмен ChatGPT → MT → ChatGPT прошёл, плагин MT загружался после перезапуска, Taskboard отвечал, контроль неотправленных `inflight` прошёл. Это исторический результат проверки, а **не** непрерывное подтверждение, что все процессы сейчас запущены.

**10 ноября 2026** обмен через Git-диалоги использовался в исследовательских и инфраструктурных задачах. Временные ошибки `authority_unavailable` нельзя автоматически трактовать как отключение службы: причиной может быть и некорректный Git-снимок.

## Инструменты, доступные в проверенной конфигурации

- `dialog_create(request_id, title)` — новый диалог, только когда существующая задача не задана.
- `dialog_creation_status(request_id)` — проверка неоднозначного создания с тем же идентификатором запроса.
- `dialog_list` — список задач без тел сообщений.
- `dialog_index(task_id, ...)` и `dialog_health(task_id)` — HEAD, последовательность, состояние и текущий ход.
- `dialog_notice(task_id, head, message_id, seq)` — подтверждение наблюдения **уже опубликованного** сообщения.

Названия и сигнатуры необходимо сверять с реально доступными инструментами перед использованием. Методы старой очереди `bridge_get_message`, `bridge_put_reply`, а также `job_id` не используются в текущем обмене.

Для чтения отчёта нужен точный `task_id`, актуальный HEAD ветки и файл сообщения на этом HEAD. Подтверждение `observed:true` не означает, что MT уже получил или выполнил задачу.

## Важные ограничения

1. При ручной публикации обязательна полная проверка Git-снимка **до** записи. Формат `created_at_utc`: `YYYY-MM-DDTHH:MM:SSZ`, без миллисекунд; ограничение тела сообщения — 64 KiB.
2. Не переписывать опубликованные сообщения, не делать `force`/`reset`, не повторять операцию при неизвестном исходе.
3. `seen` и `inflight` MT Inbox — отдельное локальное состояние. Не восстанавливать старый snapshot поверх нового: это может привести к повторной доставке задачи.
4. Наличие исторического `bridge_server.py` не означает, что старая SQLite-очередь продолжает использоваться. Он может участвовать в локальном MCP-транспорте, поэтому его нельзя удалять без проверки служб.
5. Перенос файлов в Git не изменял запущенные процессы, ключи, сокеты, сессии и системные службы на Kali.
