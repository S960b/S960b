# Carbon: портал, граница RSC и два полученных флага

[English](solve.md)

## 0. Условие и границы доказательств

Platypus Freight предлагает клиентам портал отчётов об эмиссии CO2. По условию, команда Ops «почистила окружение под SOC2», а паролей якобы больше нигде нет. Нужно было получить пользовательский файл `/home/operator/user.txt` и root-файл `/root/root.txt`.

**Оба флага были получены.** Но исходный архив CTF **не содержит образ Carbon, финальный эксплойт, журнал команд на сервере и лог повышения прав**. Сохранилось первоначальное техническое обследование в Git-мосте и итоговое подтверждение обоих флагов. Ниже разделены наблюдения, рабочие гипотезы и подтверждённые результаты.

## 1. Разведка: только портал

При разведке проверены порты: доступен портал на `3000`, а 22, 80, 443, 5432, 6379, 8080 и 9000 закрыты. В футере страницы:

```text
Carbon portal 2.4.1 · built with Next.js 15.5.6
```

Приложение построено на Next.js 15.5.6 и React 19. Главный маршрут `/portal` содержит форму **Request an emissions report** с серверным действием `queueEmissionsReport`.

Три поля проверяются сервером:

| Поле | Допустимое значение |
|---|---|
| `account` | `^PF-\d{6}$` |
| `quarter` | `^\d{4}-Q[1-4]$` |
| `kind` | `scope1`, `scope2`, `scope3`, `full` |

Пример успешного заполнения формы:

```text
Report CR-<id> queued for PF-123456 (2026-Q3, full).
You will get an e-mail once it is ready.
```

Комбинации вроде `2026-Q3;id`, `2026-Q3$(id)`, вариантов с обратными кавычками и `|` отбрасывались валидатором. Дополнительные поля `is_admin`, `role` и `name` игнорировались. Это исключило самый простой вариант инъекции через параметры формы.

## 2. Как исследовали React Server Components

Клиентский JavaScript содержал `createServerReference(...)` и форму, без явного скрытого API.

Прямой запрос к Server Action отправляли как `POST /portal` с заголовками `Next-Action` и `Content-Type: application/json`. В ответ получали HTTP 500 и digest:

```text
1:E{"digest":"1786758220"}
```

Multipart-варианты тоже не раскрыли stack trace. Digest говорит только об ошибке обработки запроса, не об исполнении кода.

Заголовки обычной страницы:

```text
x-nextjs-prerender: 1
x-nextjs-cache: HIT
cache-control: s-maxage=31536000
```

Другие проверенные пути `/admin`, `/api`, `/healthz`, `/internal` и прочие — 404. Заголовок `x-middleware-subrequest` не помог.

Важный переход в рассуждении: если все три поля формы нормально валидируются, нужно смотреть не на `account` или `quarter`, а на **сериализацию React Flight / RSC до выполнения логики самого приложения**.

## 3. Гипотеза React2Shell и её статус

В ранней переписке Next.js **15.5.6** и React 19 сопоставили с классом ошибок десериализации React Server Components, известным как React2Shell / CVE-2025-55182.

Однако точного успешного multipart-payload в архиве **нет**. Поэтому фиксируем отдельно:

- **Прямо наблюдалось:** версия фреймворка, серверное действие, ограничения полей, поведение RSC и ответы приложения.
- **Гипотеза из исследования:** возможность первичного выполнения кода при обработке специально построенного React Flight-запроса.
- **Подтверждённый итог:** получены оба флага, user и root.
- **Не сохранилось:** точное тело запроса, вывод первого выполнения команды и последовательность повышения до root.

Названия флагов `c4rb0n_c4ch3d_s3ss10n_r3pl4y` и `0p3r4t0r_3nv_1s_r00t` намекают на кэшированную сессию и окружение оператора, но **название флага — не лог эксплуатации**. По одному имени нельзя достоверно восстановить источники токенов и команды повышения привилегий.

## 4. Что реально было получено

Пользовательский файл находился в `/home/operator/user.txt`, root-файл — в `/root/root.txt`. Итоговый отчёт и подтверждение пользователя фиксируют оба флага как полученные.

Оригинальная папка `writeups/fullpwn_carbon` содержит лишь краткий README, без скриптов и истории SSH/команд. Поэтому я не подменяю пробел красивым, но неподтверждённым «шагом 4: sudo».

## 5. Проверенные тупики

- Командная инъекция через `quarter` с `;`, `$(...)`, обратными кавычками и `|` отвергнута регулярным выражением.
- Некорректный `kind` отвергнут.
- Дополнительные поля `is_admin`, `role`, `name` проигнорированы.
- Прямой JSON к Server Action даёт digest без полезного вывода.
- Угаданные служебные URL дают 404.
- `x-middleware-subrequest` не меняет доступ.

## 6. Вывод и оставшиеся материалы

Хорошая серверная проверка полей не защищает от возможной ошибки самого RSC-фреймворка. Сессии из кэша должны быть изолированы по пользователям и срокам, секреты оператора — недоступны веб-процессу, а root-ресурсы — отделены от непривилегированного приложения.

Этот райтап содержит честную разведку, гипотезу и подтверждённые два флага. **Полным воспроизводимым эксплойтом он станет только после восстановления оригинального multipart-запроса и команд получения root** из сохранившейся истории команд.
