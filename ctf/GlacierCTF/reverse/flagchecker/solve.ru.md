# Flagchecker: путь решения

[English version](solve.md)

## 0. Общий план

Это задача по обратной разработке, а не перебор всех возможных флагов. Главный вопрос: содержит ли исполняемый файл информацию, достаточную для восстановления правильного входного значения?

Сохранённая запись решения от 20 ноября 2026 года подтверждает следующую цепочку:

1. Исследовать предоставленный ELF-бинарник.
2. Обнаружить набор из 1337 строк, закодированных XOR, и однобайтовый ключ 0x12.
3. Декодировать строки-кандидаты.
4. Определить правильное значение, связанное с записью №706.
5. Проверить его оригинальной программой.

Восстановленный флаг имел форму `gctf{<64 шестнадцатеричных символа>}`. Оригинальная программа ответила `The flag is valid!`. Полное значение не публикуется.

## 1. Исследование задачи

Организаторы предоставили архив `flagchecker.tar.gz`, исполняемый файл назывался `challenge`. ELF (Executable and Linkable Format) — формат исполняемых и объектных файлов, используемый в Linux. Обычно такой файл содержит машинный код, служебные сведения и данные, используемые программой. Проверяющая программа может содержать закодированные константы, даже если их открытый текст не виден в обычном списке строк.

Для воспроизведения предлагаем распаковать исходный архив в отдельной одноразовой Linux-VM и найти исполняемый файл:

```sh
tar -tzf flagchecker.tar.gz
tar -xzf flagchecker.tar.gz
find . -type f -name challenge
file ./challenge
readelf -h ./challenge
readelf -S ./challenge
strings -a ./challenge | head
```

Это рекомендуемые команды для повторного исследования, а не журнал исходного запуска. Если архив создаёт подкаталог, следует изменить путь. Точная архитектура ELF, адреса секций и исходный дизассемблерный листинг не сохранились.

При наличии бинарника полезно найти ссылки на сообщение об успехе и исследовать код обработки ввода в Ghidra или с помощью `objdump -d ./challenge`. Так можно выяснить, какие именно данные участвуют в проверке. Нельзя считать любую интересную строку правильным ответом только по её внешнему виду.

## 2. Как работает XOR

В сохранившемся решении установлен постоянный однобайтовый ключ `0x12` (18 в десятичной системе). XOR, или исключающее ИЛИ, сравнивает биты двух значений и устанавливает единицу там, где они различаются.

Обозначим исходный байт через P, ключ через K и закодированный байт через C:

```
C = P XOR K
P = C XOR K
```

Второе равенство следует из обратимости операции: повторное применение XOR с тем же ключом возвращает исходный байт. После определения ключа и способа кодирования перебирать все возможные флаги не требуется.

Для известного начала флага преобразование выглядит так:

| Символ | ASCII (hex) | XOR 0x12 (hex) |
| --- | --- | --- |
| g | 67 | 75 |
| c | 63 | 71 |
| t | 74 | 66 |
| f | 66 | 74 |
| { | 7b | 69 |

Таким образом, закодированный префикс имеет байты `75 71 66 74 69` (ASCII `uqfti`). Закрывающая фигурная скобка 0x7d превращается в 0x6f.

Даже если ключ изначально неизвестен, гипотезу можно проверить по известному открытому тексту: если первый байт закодированного префикса равен 0x75, а ожидаемый символ g равен 0x67, то 0x75 XOR 0x67 = 0x12. Остальные четыре байта позволяют независимо проверить согласованность предположения. Это объясняет способ распознавания кодировки; точные исходные команды обнаружения ключа не сохранились.

## 3. Извлечение строк-кандидатов

В исходном исследовании зафиксирован набор из 1337 строк, закодированных XOR. Правильный флаг содержал 64 шестнадцатеричных символа между скобками. Полная длина такого кандидата составляет 70 байт: пять байт префикса, 64 символа и закрывающая скобка.

В восстановленном скрипте мы применяем XOR с ключом 0x12 ко всем байтам файла и ищем в полученном буфере совпадения с регулярным выражением:

```
gctf\{[0-9a-fA-F]{64}\}
```

Декодирование выполняется в памяти и не изменяет исходный файл. Большинство полученных байтов не несут полезной информации, поэтому регулярное выражение отбирает только строки ожидаемого формата. XOR не изменяет длину или позицию байтов, значит смещение найденной строки соответствует смещению её закодированного представления в исходном файле.

Этот способ предполагает, что закодированные строки хранятся в файле непрерывными последовательностями байтов. Для извлечения не требуется запускать ELF и устанавливать сторонние библиотеки Python. Если же строки разделены, хранятся в другом представлении или формируются во время выполнения, необходимо изучить реальный код проверяющей программы.

Восстановленный экстрактор перечисляет найденные совпадения в порядке файловых смещений и удаляет дубликаты при проверке. Этот порядок необязательно совпадает с порядком внутреннего массива программы.

## 4. Почему нельзя остановиться на извлечении кандидатов

Совпадение с форматом флага ещё не доказывает, что перед нами правильный ответ. При наличии 1337 закодированных строк внешний вид кандидата сам по себе не позволяет установить, какое значение будет принято.

Сохранившаяся запись указывает на правильный элемент №706. Однако из неё неясно, начиналась ли исходная нумерация с нуля или единицы, имели ли все 1337 элементов одинаковый формат и каким способом был выбран нужный элемент. Поэтому нельзя просто взять 706-е совпадение регулярного выражения и объявить его решением.

Оригинальная программа выступает в качестве локального оракула проверки: передаём ей кандидата и проверяем наличие сообщения об успехе. Так мы проверяем фактически принимаемое значение, а не только правильность его формата. Если бинарник использует особый протокол ввода, его необходимо изучить перед применением автоматической проверки.

## 5. Воспроизведение восстановленным скриптом

Нужен Python 3. Дополнительные зависимости не требуются. Из каталога задачи в репозитории:

```sh
python3 scripts/solve.py /path/to/challenge
python3 scripts/solve.py --self-test
```

По умолчанию скрипт показывает количество совпадений и их файловые смещения, не выводя полные флаги.

Если исследование бинарника подтвердит, что программа читает одну строку из стандартного ввода, можно запустить локальную проверку в изолированной виртуальной машине:

```sh
python3 scripts/solve.py /path/to/challenge --verify stdin
```

Если программа принимает кандидата первым аргументом командной строки:

```sh
python3 scripts/solve.py /path/to/challenge --verify argv
```

Точный интерфейс исходного бинарника не сохранился. Это два альтернативных режима, а не утверждение о том, какой из них использовался в первоначальном решении. Скрипт запускает отдельный процесс для каждого уникального кандидата, ищет зафиксированное сообщение об успехе и ограничивает время выполнения каждой попытки. Сетевых запросов и запуска через оболочку нет. Для локального вывода полного кандидата можно добавить параметр `--show`.

Самотестирование использует два синтетических значения формата флага, включая дубликат, и проверяет декодирование и файловые смещения. Оно не заменяет проверку на оригинальном ELF, который пока отсутствует.

## 6. Итог и доказательства

В сохранившейся записи решения во время соревнования зафиксированы полный флаг, запись №706 и сообщение оригинальной программы:

```text
The flag is valid!
```

Это сохранённый результат из переписки, а не новый терминальный лог. Флаг замаскирован как `gctf{...}`. На момент подготовки райтапа оригинальный ELF недоступен, поэтому повторный запуск восстановленного скрипта на нём не выполнен. Отдельное подтверждение принятия флага платформой не найдено.

## 7. Вывод

Слабость схемы заключается в использовании постоянного обратимого преобразования для сокрытия данных. Это обфускация, а не защита секрета от человека, имеющего исполняемый файл. Известный префикс флага помогает распознать способ кодирования, а сама проверяющая программа позволяет отличить правильный ответ от ложных кандидатов.

Важно разделять извлечение возможных значений и доказательство того, что одно из них действительно принимается. Статическое декодирование и локальная проверка решают эти две разные задачи.
