# compuuuter: граф, который меняется между проверкой и использованием

[English](solve.md)

## 0. Что за сервис

Flask-сервис держит числовые dataflow-графы в памяти. У узла есть `id`, `type` и `args`; у константы ещё `value`. Граф загружается, узлы правятся по одному, затем `compute` считает результаты.

В таблице операций спрятан `T_FLAG = 1337`, чей выход это байты флага, прочитанные как little-endian целое:

```python
FLAG = _load_flag()
FLAG_INT = int.from_bytes(FLAG.encode(), "little")
```

`/api/ops` его не показывает, а загрузка и вычисление отклоняют графы с таким типом. Значит задача в том, чтобы вычислитель увидел `type == 1337` у узла, который проверку прошёл.

Зачем этот шаг: флаг здесь не файл, который надо прочитать, а значение, которое вычислитель умеет выдать, поэтому цель это дойти до этой ветки.

## 1. Где происходит проверка

```python
def guard(nodes):
    for node in nodes:
        if node["type"] == T_FLAG:
            raise GraphError("the flag operation (type 1337) is not available")

def compute(nodes):
    guard(nodes)                      # момент проверки
    nmap = {}
    for node in nodes:
        nmap[node["id"]] = node       # индекс тех же объектов
    ...
        t = node["type"]              # момент использования
        if t == T_FLAG:
            val = FLAG_INT
```

Уязвимость дают два свойства. Словари узлов не копируются и не замораживаются, поэтому `nmap` хранит ссылки на живые объекты. И тип читается заново гораздо позже, внутри `evaluate`.

Роут правки завершает картину:

```python
patch = parse_node(body)              # здесь нет guard()
for node in graph["nodes"]:
    if node["id"] == patch["id"]:
        node["type"] = patch["type"]  # на месте, тот же объект
        node["args"] = patch["args"]
        break
```

`PATCH` не проверяет флаг, приложение работает с `threaded=True`, а `GRAPHS_LOCK` защищает только вставку нового графа, но не использование существующего списка узлов. Значит один запрос может быть внутри `compute`, пока другой переписывает узел.

Зачем этот шаг: вся уязвимость это отсутствие фиксации между проверкой и использованием, а не ошибка разбора.

## 2. Как сделать окно пригодным

Гонка в несколько микросекунд по сети не выигрывается. Сервер помогает:

```python
nmap = {}
for node in nodes:
    nmap[node["id"]] = node
```

и в коде есть assert, который выдаёт задумку:

```python
assert sys.hash_info.modulus == 2 ** 61 - 1
```

В 64-битном CPython `hash(n)` для неотрицательного целого это `n mod (2^61 - 1)`. Значит id, кратные `2^61 - 1`, имеют одинаковый хеш:

```python
MOD = (1 << 61) - 1
ids = [i * MOD for i in range(1, count + 1)]
```

Идентификаторы различны, поэтому проверка на дубликаты проходит, но вставка в словарь деградирует: все ключи попадают в один слот, и стоимость вставки резко растёт. Это превращает построение словаря между `guard` и `evaluate` в задержку, которую можно поймать по сети.

Целевой узел получает `id = 1` и добавляется последним, поэтому вычисление доходит до него после всех наполнителей. Сами наполнители это обычные константы.

Зачем этот шаг: усиление коллизиями превращает гонку в микросекундах в управляемую паузу.

## 3. Сама гонка

1. Загрузить граф из `count` коллизирующих констант плюс целевой узел `id = 1, type = 1`.
2. Запустить `POST /api/graph/<gid>/compute` в отдельном потоке.
3. Подождать `delay`, затем `PATCH` узла `1` на `type = 1337`.
4. Если правка попала после `guard`, но до чтения типа в `evaluate`, результат для `"1"` это `FLAG_INT`.
5. Раскодировать: `value.to_bytes((value.bit_length() + 7) // 8, "little")`.

Между попытками узел возвращается к легальному типу, иначе следующий `compute` упадёт на собственном guard. Именно эту дисциплину тайминга и реализует скрипт: сброс, старт вычисления, пауза, правка, чтение.

Зачем этот шаг: правка сама по себе бесполезна, граф должен быть легальным в момент проверки и запрещённым в момент чтения.

## 4. Размер графа

Больше коллизий означает более длинное окно, но и более медленную загрузку: `parse_nodes` строит множество `seen` для поиска дубликатов, и оно страдает от той же проблемы. Граф на 12 001 узел заметно тормозит ещё до гонки, а на одном инстансе загрузка сама по себе привела к обрыву соединения.

Прогон, записанный 2 ноября 2026 года, использовал 6 001 узел и задержку 0.3 секунды, и первая попытка прошла:

```text
[*] Uploading 6001 nodes ...
[*] Graph id: ae1597a76f254296bb3e08e3ca9bce26
[*] Attempt 1: compute -> wait 0.3s -> PATCH(type=1337)
[+] Decoded output: ctfcup{...}
[FLAG] ctfcup{...}
```

Флаг в репозитории скрыт. Полезно помнить диагностику: ошибка guard означает, что правка пришла слишком рано, а обычный числовой результат означает, что поздно.

Зачем этот шаг: размер графа это ручка для обеих фаз, и одно значение задержки не универсально.

## 5. Чтение результата

`results["1"]` это десятичная строка числа, в которое сервер упаковал байты флага как little-endian целое. Это не хеш и не hex. Обратное преобразование даёт текст.

```bash
python3 scripts/exploit_compuuuter.py https://<host> --count 6000 --delay 0.3
```

Скрипт сбрасывает целевой узел, устраивает гонку, декодирует и повторяет; сырой вывод лежит в `evidence/compuuuter_run.log`.

## 6. Тупики

- Загрузить узел с `type = 1337` напрямую: отклоняется и при загрузке, и при вычислении.
- Поставить `1337` и вызвать compute: следующий guard отклоняет граф, потому что на момент проверки он нелегален.
- Взять гигантский граф: путь загрузки тоже квадратичный, поэтому соединение может умереть до гонки.
- Локальная проверка на заглушке: она доказывает ветку вычислителя, а не удалённый флаг, потому что `_load_flag` возвращает тестовую строку.

## 7. Выводы

- TOCTOU это про идентичность объектов: словарь ссылок не является снимком.
- Коллизии хешей это примитив тайминга: они дают окно, не трогая сетевой стек.
- Если гонке нужно окно, искать работу, которую сервер делает между проверкой и использованием по данным атакующего.

Одним абзацем: `compute` проверяет типы узлов, а затем вычисляет те же изменяемые словари, при этом `PATCH` переписывает узел на месте без проверки флага, поэтому конкурентная правка превращает константу в опкод 1337 уже после guard; тысячи id, коллизирующих по правилу `n mod (2^61 - 1)`, замедляют построение словаря настолько, что окно ловится по сети, а полученный `FLAG_INT` декодируется обратно в флаг.
