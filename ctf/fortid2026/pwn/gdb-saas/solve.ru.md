# GDB SaaS - writeup (pwn, чтение файла через DWARF)

## Знакомство с задачей

Сервис называется GDB SaaS: "Get your `main`s disassembled for free" (дизассемблируем ваши main бесплатно). Ты отправляешь ему бинарь и имя функции, он запускает gdb от твоего имени, дизассемблирует функцию и печатает результат.

Вложение - один файл, `server.py`. Прочитал его целиком, сверху вниз. Он делает примерно так:

1. Просит байты ELF в base64. Ограничение - меньше 30 КиБ.
2. Просит имя функции. Ограничение - меньше 30 символов, и в нём не должно быть ни одного символа из длинного списка "плохих": NUL, перевод строки, таб, `; | & \` $ < > \ ' " ! # , ( ) [ ] { }`.
3. Создаёт временную директорию внутри рабочей директории сервера.
4. Копирует `flag.txt` в эту временную директорию.
5. Пишет наш бинарь как `<tmpdir>/a.out`.
6. Запускает: `gdb -ex "disassemble <function_name>" -ex quit <tmpdir>/a.out`.

Ключевая деталь - в шаге 4: `flag.txt` копируется в ту же директорию, которая является рабочей для нашего бинаря. А gdb запускается с рабочей директорией сервера как cwd, не temp-директории.

## Идея: заставить gdb самому напечатать флаг

Мне не нужен шелл, и мне не нужно ничего "ломать". Сервис и так запускает gdb на бинаре, который я контролирую. Мне нужно только заставить gdb показать содержимое файла, которого нет в моём бинаре.

Когда gdb дизассемблирует функцию, скомпилированную с отладочной информацией (`-g`), он может показать строку исходника рядом с ассемблером. Для этого он вычисляет путь к исходнику из отладочной информации. Путь хранится двумя частями: директория компиляции (`DW_AT_comp_dir`) и имя файла.

Значит, план такой: написать крошечную C-программу, чья отладочная информация утверждает, что её исходный файл - это `flag.txt`, а директория компиляции - `.` (точка, то есть "текущая директория"). Тогда gdb, запущенный в рабочей директории сервера, будет искать `./flag.txt` - а сервер уже скопировал настоящий `flag.txt` прямо туда.

Если это сработает, `disassemble /s main` напечатает флаг как "строку исходника" функции main.

## Сборка payload

Нужны два трюка компилятора.

Первый - заставить записанное имя исходного файла быть `flag.txt`. gcc поддерживает директивы строк: `#line 1 "flag.txt"` говорит компилятору "с этого места считай, что исходный файл называется flag.txt". Поэтому исходник начинается с этой директивы:

```c
#line 1 "flag.txt"
int main(void) {
    int x = 1;
    x += 1;
    return x;
}
```

Второй - заставить директорию компиляции быть `.`. По умолчанию gcc записывает как `DW_AT_comp_dir` директорию, из которой он был вызван (его cwd). Флаг `-fdebug-prefix-map=<builddir>=.` переписывает записанный путь: каждое вхождение директории сборки заменяется на `.`. Поэтому компилировать нужно изнутри директории сборки:

```bash
cd /tmp/gdb_build
gcc -g -O0 -fdebug-prefix-map=/tmp/gdb_build=. -o elf.bin main.c
```

Прежде чем идти дальше, проверил результат через `readelf` (утилита из GNU binutils, печатает заголовки ELF и отладочные секции DWARF). Это легко испортить, а неправильный `DW_AT_comp_dir` означает, что gdb будет искать не там. Команда:

```bash
readelf --debug-dump=info elf.bin
```

показывает дерево отладочной информации. Две строки, которые важны:

```text
<17>   DW_AT_name        : (indirect line string, offset: 0x2): main.c
<1b>   DW_AT_comp_dir    : (indirect line string, offset: 0): .
```

`DW_AT_name` - записанное имя исходного файла (`main.c`), `DW_AT_comp_dir` - записанная директория компиляции. Значения лежат в строковой таблице `.debug_line_str`, поэтому readelf печатает их как `(indirect line string, offset: N): <значение>`. Важное - после второго двоеточия: директория компиляции разрешилась в `.` - ровно то, что нужно. (`DW_AT_name` остаётся `main.c`; когда gdb не находит `main.c`, он идёт по пути от comp_dir - это мы и используем.)

Теперь проверка размера. gdb-saas отклоняет вход длиной `len(contents) >= 30*1024` символов, значит base64 должен быть меньше 30720 символов. Я измерил оба значения:

```bash
ls -la elf.bin
base64 elf.bin | wc -c
```

```text
-rwxrwxr-x 1 kali kali 16720 ... elf.bin     (размер файла: 16720 байт = 16.7 КиБ)
22590                                        (длина base64: 22590 символов)
```

base64 кодирует каждые 3 байта как 4 символа, поэтому 16720 байт превращаются в 22590 символов (~22 КиБ). 22590 меньше лимита 30720 с запасом около 8 КиБ - payload влезает.

## Выбор имени функции

Имя функции должно пройти фильтр символов, и оно подставляется в команду gdb как `disassemble <name>`. Список плохих символов запрещает метасимволы шелла и разделители команд gdb, но НЕ запрещает пробел и слэш. В этом вся суть.

`disassemble` в gdb принимает модификатор `/m` или `/s` перед адресом/именем - подмешивать строки исходника. Поэтому имя функции `/s main` превращается в команду `disassemble /s main` - "дизассемблируй main и покажи исходник". Ни `/`, ни пробел, ни `main` не входят в плохой список, а длина строки 8 символов, меньше 30.

## Проверка локально, до remote

Я воспроизвёл окружение сервера у себя: директория с `flag.txt`, поддиректория с `a.out`, и запустил ровно ту команду gdb, которую запускает сервер:

```bash
gdb -ex 'disassemble /s main' -ex quit a.out
```

Вывод:

```text
Dump of assembler code for function main:
./flag.txt:
1   FortID{SIM_FLAG_gdb_77ab}
   0x0000000000001129 <+0>  push   %rbp
   ...
```

Флаг появляется как первая "строка исходника" main. Цепочка подтверждена локально.

## Что я пробовал сначала (dead ends)

1. **Искать способ читать файлы через команды gdb.** Очевидная идея: сделать из имени функции саму команду gdb, например `disassemble; shell cat flag.txt`. Умерла сразу: пробел-то допустим, но `;` входит в BAD_CHARS, как и метасимволы шелла `$`, `|`, `&`. Склейки команд через точку с запятой здесь нет.
2. **Пробовать другие команды gdb как "имя функции".** Даже без `;`, `-ex` выполняет только то, что идёт после `disassemble ` - как единый аргумент-локацию. Фильтр убивает всё, что могло бы превратиться в новую команду. Чтение файла должно было произойти *внутри* самого дизассемблирования - что и даёт модификатор `/s`.
3. **Абсолютный путь в ELF вместо `.`.** Сначала я пробовал `-fdebug-prefix-map` на абсолютный путь, например `/`, чтобы gdb искал `/flag.txt`. Такого файла на сервере нет. Правильное место - рабочая директория сервера, куда копируется `flag.txt`: это `.` с точки зрения gdb. Проверка через `readelf` поймала это на раннем этапе.
4. **Компиляция не из той cwd.** gcc записывает как `DW_AT_comp_dir` свою собственную рабочую директорию, а не директорию исходного файла. Первая сборка запускала gcc снаружи директории сборки, поэтому `DW_AT_comp_dir` оказался абсолютным путём, и `-fdebug-prefix-map` не сработал. readelf показал проблему, а запуск компиляции изнутри директории сборки её решил.

## Итоговые скрипты

- `scripts/build_payload.py` - создаёт вредоносный ELF. Пишет исходник с директивой `#line 1 "flag.txt"`, компилирует через `gcc -g -O0 -fdebug-prefix-map=<tmp>=.`, печатает путь к результату. Запуск: `python3 build_payload.py elf.bin`.
- `scripts/solve.py` - клиент. Подключается по TLS, отправляет base64 ELF, затем имя функции `/s main`, печатает всё, что вернул сервер. Запуск: `python3 solve.py elf.bin` (хост/порт в скрипте; remote-инстанс закрыт после события).

## Версия в один абзац

Сервис запускает `gdb -ex "disassemble <наша_строка>"` на загруженном бинаре, в рабочей директории, где лежит flag.txt. Фильтр символов блокирует шелл-символы, но не пробел и слэш, поэтому мы передаём `/s main`, и gdb дизассемблирует main с исходником. Путь к исходнику берётся из отладочной информации, поэтому мы компилируем крошечную программу, у которой файл записан как `flag.txt` (`#line 1`), а директория компиляции - `.` (`-fdebug-prefix-map`), и проверяем readelf. gdb резолвит `./flag.txt` от своего cwd - где сервер положил настоящий флаг - и печатает его как строку исходника main. Одна загрузка, одно имя функции, флаг печатает сам gdb.

## Уроки

1. Когда сервис запускает инструмент на твоём вводе, думай, что инструмент можно *уговорить* сделать через его же конфигурацию, а не только о том, как из него вырваться. gdb читает файлы через резолв исходников - шелл не нужен.
2. Фильтр символов настолько хорош, насколько хороши символы, которые он покрывает. Здесь пробел и слэш оказались разрешены, и дальше всё сделали модификатор `/s` и путь в отладочной информации.
3. Отладочная информация - это контролируемые атакующим данные: `#line` и `-fdebug-prefix-map` позволяют посадить в ELF произвольное имя файла и директорию.
4. Проверяй промежуточные артефакты (здесь `DW_AT_comp_dir` через readelf), прежде чем тратить прогон на remote: неправильная директория компиляции - и gdb ищет не там.
5. Всегда сначала воспроизводи окружение сервера локально (скопируй flag.txt в рабочую директорию, запусти ровно ту команду) - вся цепочка доказана здесь, до касания инстанса.
