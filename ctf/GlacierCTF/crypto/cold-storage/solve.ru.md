# Cold Storage — повтор nonce AES-GCM из-за високосной секунды

[English version](solve.md)

## 1. Архитектура сервиса

Организаторы выдали Node.js/Express-приложение с `src/server.js`, `src/archive.js`, `src/record-crypto.js`. При каждом запуске создаётся новый случайный **16-байтовый ключ AES** и 32 зашифрованные архивные записи. Благодаря `node --random-seed=1337` архив детерминирован по метаданным, но криптографический ключ от этого **не предсказуем**.

Основные маршруты: `GET /archive` выдаёт 32 записи в `application/x-www-form-urlencoded`; `POST /api/import` один раз шифрует пользовательский объект с принудительным `classification=open`; `POST /api/open` расшифровывает запись и возвращает флаг, только если поля равны `restricted` и `Ice-VII`.

Запись кодируется ровно в **32 байта**:

```javascript
Buffer.from(`${classification.padEnd(10)}|${sample.padEnd(21)}`)
```

Шифрование — AES-128-GCM без AAD. Nonce длиной 12 байт получается из:

```javascript
sha256(Temporal.Instant.from(recorded).epochNanoseconds.toString()).subarray(0,12)
```

## 2. Ошибка на границе двух представлений времени

Публичный архив содержит запись `1972-12-31T23:59:59Z` / `ice-e1512db7`. Импорт принимает `1972-12-31T23:59:60Z` / `ice-eaaa`.

Проверка дубликата в `server.js` использует **строковое сравнение**:

```javascript
archive.some(record => record.recorded === recorded)
```

Строки различаются — импорт разрешён. Но `Temporal.Instant.from` преобразует високосную секунду `:60` в `:59`, поэтому обе строки дают один `epochNanoseconds` и **одинаковый nonce**. В следующую минуту `:00` значение не переносится: это отдельно проверено неудачным тестом `1988-03-04T08:30:60Z` → `08:31:00Z` (HTTP 403).

Успешный `/api/import` разрешён только один раз на инстанс, не создаёт запись в `archive`. Неверный формат даты (`:560Z`) даёт 400 и не расходует импорт.

## 3. Алгебра AES-GCM

Две записи шифруются одним ключом и nonce. Формат каждого открытого текста: `classification.padEnd(10) + "|" + sample.padEnd(21)`, общая длина 32 байта.

Выбираем импортируемый `sample=ice-eaaa`, чтобы совпали первые 16 байт с записью `ice-e1512db7`. Тогда первые блоки шифртекстов также совпадают, а вся разность находится во втором 16-байтовом блоке.

Для GCM над GF(2¹²⁸) (неприводимый полином `x^128+x^7+x^2+x+1`):

```text
Tag = E_K(J0) XOR GHASH_H(C1,C2)
H = AES_K(0^128)
GHASH_H(C1,C2)=((C1·H XOR C2)·H XOR L)·H
L=256 бит (AAD пустой)
```

Из двух тегов при одном nonce:

```text
ΔTag = ΔC_second · H²
H² = ΔTag / ΔC_second
H = (H²)^(2^127)
```

Обращение элемента поля выполняется степенью `2^128-2`, квадратный корень — степенью `2^127`. В сохранённом успешном запуске получен:

```text
H = 8ac7c6018c46310301929f354247b6f0
```

Проверка `GHASH_H(C1) XOR T1 == GHASH_H(C2) XOR T2` прошла. Это `H` только **конкретного инстанса**, не общий ключ.

## 4. Поддельный ciphertext и тег

Из известной пары `P1,C1` получаем гамму CTR: `KS=P1 XOR C1`. Формируем целевой текст:

```python
P_target = ("restricted" + "|" + "Ice-VII".ljust(21)).encode()
assert len(P_target) == 32
```

Далее:

```text
C_target = P_target XOR KS
E        = Tag1 XOR GHASH_H(C1)
Tag_target = E XOR GHASH_H(C_target)
```

Отправляем `POST /api/open` с **исходной** датой архива `1972-12-31T23:59:59Z`, вычисленными `ciphertext` и `tag`. Проверка GCM проходит, объект содержит `restricted / Ice-VII`, сервер добавляет поле `flag`.

Реальный сохранённый журнал фиксирует:

```text
records 32
target record 1972-12-31T23:59:59Z ice-e1512db7
alias 1972-12-31T23:59:60Z
import 200
H 8ac7c6018c46310301929f354247b6f0
H verified
FORGED OPEN: 200 ... classification=restricted&sample=Ice-VII&...&flag=gctf%7B...%7D
```

Участник подтвердил принятие полученного флага платформой. В публичном GitHub он скрыт в соответствии с принятой договорённостью.

## 5. Какие гипотезы не сработали

- Перебор ключей из публичных timestamps, sample и температур, десятки миллионов вариантов: без результата. Ключ создаётся `randomBytes(16)`.
- Анализ 496 пар и 4 960 троек **архивных** записей не показал повторов nonce. Ошибка требует **импорта новой записи**, а не столкновения внутри архива.
- Перебор URL, параметров, HTTP-методов и заголовков не открыл скрытую запись.
- Разница таймингов успешного/неуспешного `/api/open` не давала полезного оракула.
- Гипотеза переноса `:60` в следующую минуту `:00` оказалась неверной.
- Ошибочное построение алиаса `:560Z` было отфильтровано regex до шифрования.

## 6. Воспроизведение и сохранённые материалы

Оба пользовательских ZIP идентичны. В них есть исходный архив и его распакованная копия, оригинальный `scripts/solve.py` с `session.py`, `exploit.py`, скрипты прежних проверок, архивные ответы десяти инстансов и реальный `evidence/03_successful_run.log`.

В GitHub опубликован переносимый [scripts/solve.py](scripts/solve.py), без жёсткого пути `/tmp/gigatool/cold`, и [scripts/test_offline.py](scripts/test_offline.py) для проверки GF-арифметики по сохранённым данным. Оригинальный инстанс истёк, новых запросов во время создания райтапа не выполнялось.

## 7. Выводы для защиты

Уникальность nonce нужно гарантировать **внутри одной криптографической области**, а не по исходным текстовым представлениям меток времени. Сначала следует канонизировать timestamp и контролировать повтор уже по нормализованной величине; более надёжный вариант — генерировать независимый уникальный nonce и хранить его вместе с ciphertext. Публичный chosen-plaintext endpoint под тем же ключом, что и секретные записи, усиливает риск.
