# Пропавший архив: путь решения

Флаг в конце: `SOLARCTF{...}`.

## 0. План целиком, до всех подробностей

Чтобы читатель понимал, к чему мы идём, сразу опишу цепочку. Перехожу к деталям.

Дано: четыре модуля `n`, четыре шифртекста `c` и по куску информации о ключе. Нужно
получить байты флага.

Мой план был таким:

1. Понять из кода, что именно зашифровано и какая информация о ключе известна.
2. Восстановить по этой информации один простой множитель `p` каждого модуля.
3. Из `p` получить `q = n / p`, затем закрытую экспоненту `d` и расшифровать `c`.
4. В расшифрованном сообщении взять младшие 8 байт, это и есть кусок флага.
5. Склеить четыре куска по порядку и получить `SOLARCTF{...}`.

Главная сложность в шаге 2, и почти весь текст ниже именно про него. Остальные шаги
механические.

## 1. Запуск генератора: что вообще в выводе

Зачем этот шаг: до чтения кода я хотел увидеть сами данные, чтобы понять их форму и
проверить, что я правильно сопоставляю числа с ролями.

Я открыл терминал в папке с задачей и запустил генератор на тестовом флаге нужной длины:

```
FLAG='SOLARCTF{0123456789abcdefghijkl}' python3 generate.py > demo_out.txt
```

В файле оказалось 15 строк. Первые три числа:

```
4
65537
32
```

Дальше шли двенадцать больших чисел, то есть по три числа на инстанс, четыре инстанса.

Затем я измерил длины, чтобы не доверять глазу:

```python
vals=[int(x) for x in open('demo_out.txt').read().split()]
ns, cs, hs = vals[3::3], vals[4::3], vals[5::3]
# bits(n): 2047 2047 2048 2048
# bits(h): 518  518  518  518
```

Получилось: модули по 2047 или 2048 бит, третье число каждой тройки ровно 518 бит.

Как я понял, что эти три числа означают именно это, а не что-то ещё: сверил с кодом.
В `generate.py` строка 90 собирает заголовок вывода:

```python
values = [N_INSTANCES, E, len(flag)]
```

а строка 87 добавляет по одному кортежу на инстанс:

```python
records.append((n, pow(message, E, n), h))
```

То есть порядок такой: сначала число инстансов, экспонента и длина флага, затем
четырёхкратный повтор тройки модуль, шифртекст, утечка. Измеренные длины это
подтверждают.

## 2. Что именно шифруется: разбор функции make_messages

Зачем этот шаг: нужно точно знать, в каком месте расшифрованного числа лежат байты
флага, иначе после восстановления ключа мы не поймём, что из результата брать.

Смотрю строки 60 - 67:

```python
base, extra = divmod(len(flag), N_INSTANCES)
for index in range(N_INSTANCES):
    chunk_size = base + (index < extra)
    chunk = flag[offset:offset + chunk_size]
    offset += chunk_size
    messages.append(secrets.token_bytes(SHARE_BYTES - chunk_size) + chunk)
```

Разбираю по-человечески. Флаг делится на четыре части максимально ровно: если длина не
делится на четыре, первые части получают на байт больше. У нас длина 32, делится ровно,
поэтому все части по 8 байт.

Каждая часть дополняется слева случайными байтами до 32 байт. Сложение идёт так, что
случайные байты оказываются старшими, а часть флага младшими. В коде это видно по
порядку склейки: `token_bytes(...) + chunk`.

Отсюда прямое следствие для шага расшифровки: когда мы получим число `m`, младшие 8
байт этого числа и есть кусок флага. В Python это `m & (2**64 - 1)`.

Проверка, что длина действительно 32: третье число в выводе, которое по строке 90 равно
`len(flag)`, было 32.

## 3. Откуда известна информация о ключе: строки 84 - 85

Зачем этот шаг: именно эта информация определяет, каким методом можно атаковать. Если
бы утечки не было, задача была бы нерешаемой, а если бы утекало другое поле, метод был
бы другим.

Две строки решают всё:

```python
leaked = p if secrets.randbelow(2) == 0 else q
h = leaked >> (PRIME_BITS - LEAK_BITS)
```

Разбираю. Сначала случайно выбирается один из двух простых множителей, `p` или `q`.
Поэтому по файлу нельзя сказать, какой именно множитель нам достался, и алгоритм должен
работать для любого из них.

Затем число сдвигается вправо на `PRIME_BITS - LEAK_BITS`, то есть на `1024 - 518 = 506`
бит.

Теперь по-человечески, что такое сдвиг вправо и что такое старшие биты. Любое число в
компьютере хранится в двоичном виде, набором нулей и единиц. Старшие биты это те, что
стоят слева, они задают порядок величины, а младшие это правый хвост, они задают точное
значение внутри этого порядка. Сдвиг вправо на 506 отбрасывает 506 младших бит и
оставляет только старшие.

Что это значит практически. Множитель `p` примерно равен `h * 2^506` плюс неизвестный
хвост `x`, который меньше `2^506`. То есть мы знаем `p` грубо, с точностью до хвоста в
506 бит:

```
p = h * 2^506 + x,   где 0 <= x < 2^506
```

Почему это называется утечкой старших бит: генератор сам сообщает нам `h`, а это и есть
старшие биты множителя.

Почему это важно: у нас появилось уравнение на `p` с одним небольшим неизвестным `x`.
Именно с ним и будет работать метод из следующего раздела.

## 4. Почему нельзя решить в лоб

Зачем этот шаг: убедиться, что простые подходы не подходят, и понять, какие именно
свойства задачи можно использовать.

Три очевидные идеи отпадают сразу.

Перебор хвоста. В хвосте 506 бит, вариантов `2^506`. Даже при миллиарде проверок в
секунду это на много порядков больше возраста Вселенной.

Прямое деление. Мы не можем посчитать `gcd(n, h * 2^506)`, потому что настоящий множитель
это `h * 2^506 + x`, а не `h * 2^506`. Хвост неизвестен, и без него число не делит `n`.

Атака через общий делитель двух модулей. Она была бы возможна, если бы два модуля имели
общий простой множитель. Но генератор это исключает, строка 82:

```python
if any(math.gcd(n, old) != 1 for old in moduli):
    continue
```

Каждый новый модуль проверяется на взаимную простоту со всеми предыдущими, поэтому
общих множителей нет по построению.

Вывод: нужен метод, который находит маленькое неизвестное `x` из уравнения
`h * 2^506 + x` делит `n`, не зная `n`-множителя.

## 5. Класс задачи и метод Копперсмита простыми словами

Зачем этот шаг: назвать метод, который умеет находить малое неизвестное по модулю
неизвестного делителя, и понять, откуда берётся ограничение на размер этого
неизвестного.

Такие задачи называют partial key exposure, то есть частичное раскрытие ключа: известна
часть секрета, и по ней нужно восстановить секрет целиком. Здесь известны старшие биты
множителя.

Метод Копперсмита простыми словами работает так. Есть многочлен, у которого есть корень
по модулю неизвестного делителя `n`. Если этот корень мал, его можно найти, не зная
делитель, с помощью специально построенной решётки. Слово "малый" здесь ключевое: метод
гарантированно работает только до некоторой границы.

Задача поиска малого корня формулируется так. Дан многочлен `f` и модуль `N`, про который
известно, что у него есть делитель `p`. Нужно найти `x0`, для которого `f(x0)` делится
на `p`, при условии, что `x0` не превосходит известной границы `X`. Мы ищем именно
малый корень, потому что больших корней в диапазоне слишком много и они неотличимы от
случайных чисел.

Граница метода для делителя `p`, который составляет долю `beta` от `N`, равна `N` в
степени `beta` в квадрате. У нас `p` примерно равен корню из `N`, то есть `beta = 0.5`,
значит граница это `N^0.25`.

Считаю числа, потому что дальше на них всё держится:

- `N` около `2^2048`;
- `N^0.25` это `2^512`;
- наш хвост `x` меньше `2^506`;
- запас равен `512 - 506 = 6` бит.

Вот откуда взялись те 6 бит, о которых речь идёт дальше. Запас есть, но он маленький.

Что такое решётка, если совсем по-простому. Это множество точек, полученных целочисленными
комбинациями заданных векторов. Алгоритм редукции ищет в этом множестве самый короткий
вектор. Короткий вектор ценен тем, что его коэффициенты дают новый многочлен, у которого
наш `x0` является обычным целым корнем, и тогда корень находится без всякой модульной
арифметики.

Как это ведёт к флагу: находим `x0`, получаем `p = h * 2^506 + x0`, делим `n` на `p`,
получаем `q`, считаем `d`, расшифровываем `c`, берём младшие 8 байт, склеиваем четыре
куска.

## 6. Первый подход: одна большая решётка

Зачем этот шаг: попробовать прямолинейную конструкцию, чтобы увидеть её стоимость и
понять, что именно надо оптимизировать.

Я погуглил, как строят решётку для задачи Копперсмита с делителем модуля, а не с самим
модулем, и выбрал схему Хаугрейва - Грэма. Она мне подошла потому, что это стандартная
конструкция именно для случая, когда корень нужен по модулю делителя `N`, а не по модулю
самого `N`.

Схема простыми словами. Мы строим семейство многочленов, каждый из которых при подстановке
`x0` делится на достаточно высокую степень `p`. Затем коэффициенты этих многочленов
записываются в матрицу, и редукция ищет короткую целочисленную комбинацию строк. Строки
задаются так:

```
g_i = N^(m-i) * f(x*X)^i,   i = 0 .. m-1
h_j = x^j * f(x*X)^m,       j = 0 .. t-1
```

Размерность матрицы равна `m + t`. Множитель `X` здесь нужен, чтобы коэффициенты остались
целыми и одновременно корень перешёл в целые числа.

Дальше арифметика, и она неутешительная. Чтобы покрыть 506 неизвестных бит при запасе
всего 6 бит, нужна размерность порядка 131, то есть `m` около 65. Элементы матрицы при
этом вырастают примерно до 120 тысяч бит.

Редукцию выполняет алгоритм LLL, это сокращение от фамилий Ленстра, Ленстра и Ловас.
Он ищет короткие векторы в решётке за полиномиальное время, но полиномиальное не значит
быстрое: на числах такого размера одна редукция идёт часами. Реализацию я взял из
библиотеки fplll.

Я честно попробовал. При параметре качества `delta = 0.75` и размерностях 80 и 95 корень
не находился, редукция слабовата. При `delta = 0.99` качество становилось достаточным, но
время уходило в неприемлемое.

Вывод: уменьшать надо размерность, а не подкручивать параметры.

## 7. Идея, которая сработала: угадать несколько старших бит

Зачем этот шаг: снизить размерность решётки до значений, где редукция занимает секунды,
ценой небольшого перебора.

К идее я пришёл из арифметики предыдущего раздела. Запас был всего 6 бит, а размерность
росла именно из-за этого. Значит, если уменьшить число неизвестных бит, размерность
упадёт.

Как уменьшить, если хвост неизвестен. Можно угадать несколько следующих старших бит
хвоста. Если угадать `g` бит, неизвестных остаётся `506 - g`, граница становится
`2^(506-g)`, а запас относительно `N^0.25` вырастает до `6 + g` бит.

Плата за это: нужно перебрать `2^g` вариантов. При `g = 5` это 32 варианта, что вполне
подъёмно.

Выигрыш: вместо одной решётки размерности 131 получаем 32 решётки размерности 59 (`k = 29`,
`t = 30`) с запасом 11 бит. Каждая такая редукция идёт секунды.

Стартовая точка для конкретного варианта:

```
P = ((h << g) | guess) << (506 - g)
```

Здесь `h << g` дописывает `g` нулей, `| guess` подставляет угаданные биты, а сдвиг
влево на `506 - g` ставит их на своё место в числе.

Проверку гипотезы я начал не с боевого файла, а с синтетического примера: сгенерировал
маленькие множители с частичной утечкой и прогнал солвер в режиме самопроверки. Он
восстановил множитель и расшифровал сообщение на размерности 7. Только после этого
запустил на настоящих данных.

## 8. Инструменты и настройка окружения

Зачем этот шаг: нужна быстрая редукция решётки и предсказуемое использование ядер,
иначе полный прогон растягивается на часы.

LLL я уже назвал, это алгоритм поиска коротких векторов. Его быстрая реализация это
fplll, библиотека с открытым кодом, в которой кроме LLL есть и более сильный BKZ. Ставить
её напрямую неудобно, поэтому я взял `flatn` версии 0.3.5: это тонкая Python-обёртка над
flatter, а flatter это оптимизированная реализация, которая поставляется готовым бинарём
внутри wheel. Плюс `sympy` для работы с многочленами.

Установка в локальную папку:

```
python3 -m pip install --target ./deps 'flatn==0.3.5' 'sympy>=1.12'
export PYTHONPATH="$PWD/deps${PYTHONPATH:+:$PYTHONPATH}"
```

Теперь про потоки, это важная деталь. BLAS это набор базовых операций линейной алгебры,
а OpenBLAS одна из его реализаций. OpenMP это механизм распараллеливания циклов. По
умолчанию обе библиотеки создают столько потоков, сколько ядер, причём в каждом процессе
отдельно. Когда я запускаю восемь воркеров, каждый поднимает по восемь потоков, и на
восемь ядер приходится шестьдесят четыре потока. Это и есть переподписка: потоки
постоянно вытесняют друг друга, кэш промахивается, и суммарно становится медленнее, а не
быстрее.

Поэтому на каждый воркер я оставил по одному потоку:

```
export OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 MKL_NUM_THREADS=1
```

Про это я узнал из документации flatn и OpenBLAS и проверил по времени: с ограничением
прогон ускоряется.

Видеокарту я не использовал. LLL на больших целых почти последовательный, зрелых
реализаций на GPU нет, так что выигрыша тут не будет.

## 9. Как из результата редукции получается корень

Зачем этот шаг: редукция выдаёт короткие векторы, но не сам `x0`. Нужно превратить
векторы в число, то есть закрыть последний разрыв между математикой и множителем `p`.

Беру два самых коротких вектора, которые дала редукция. Каждый вектор это набор
коэффициентов, по ним строю многочлен:

```
H(x) = sum v_d * X^(n-1-d) * x^d
```

Множители `X` нужны, чтобы коэффициенты были целыми и корень сохранился. Теперь у меня
два многочлена, у которых `x0` является общим корнем по модулю `p`.

Чтобы найти общий корень, я считаю наибольший общий делитель этих двух многочленов. Делаю
это не над целыми числами, а над конечными полями по нескольким небольшим простым числам
порядка 31 бита. Так надёжнее: над целыми коэффициенты огромные, а над малым полем
вычисления быстрые, и результат не вырождается.

Каждый такой счёт даёт остаток `x0` по своему простому модулю. Собираю остатки по
китайской теореме об остатках, пока произведение модулей не превысит `X`. После этого
`x0` известен точно.

Дальше `p = P + x0`, и проверка: делится ли `n` на `p`. Если делится, множитель настоящий.

## 11. Расшифровка и сборка флага

Зачем этот шаг: превратить найденный множитель в байты флага и проверить, что всё
сходится.

По найденному `p` считаю `q = n / p`, затем функцию Эйлера `phi = (p - 1) * (q - 1)`,
закрытую экспоненту `d` как обратный элемент к `e` по модулю `phi`, и сообщение
`m = c^d mod n`.

Из сообщения беру младшие 8 байт, как договорились в разделе 2:

```python
chunk = (m & (2**64 - 1)).to_bytes(8, 'big')
```

Первые 24 байта при этом случайные, и это хороший признак: если они выглядят как
случайный мусор, а хвост как осмысленный текст, значит ключ восстановлен верно.

Четыре куска склеиваются по порядку инстансов. Первый дал префикс `SOLARCTF`, остальные
три дали тело и закрывающую скобку. Итог: `SOLARCTF{...}`.

## 12. Что не сработало

- Одна большая решётка размерности около 131. На элементах по 120 тысяч бит редукция
  идёт часами, практического результата это не дало.
- Параметр `delta = 0.75` при размерностях 80 и 95. Редукция слишком слабая, корень не
  находится.
- `delta = 0.99` при большой размерности. Качество достаточное, время неприемлемое,
  отсюда и переход к угадыванию старших бит.
- Атака через общий делитель модулей. Исключена генератором на строке 82.
- Видеокарта. Зрелых реализаций LLL для больших целых на GPU нет, вычисление почти
  последовательное.

## 13. Коротко, одним абзацем

Генератор сообщает 518 старших бит одного из множителей, поэтому `p` имеет вид
`h * 2^506 + x` с неизвестным хвостом `x` меньше `2^506`, а граница метода Копперсмита
для такого делителя около `2^512`. Одной решёткой это решается слишком долго, поэтому я
угадываю ещё 5 старших бит и получаю 32 решётки размерности 59 вместо одной размерности
131. Редукция идёт на flatter через `flatn`, корень извлекается через НОД многочленов над
малыми полями и китайскую теорему об остатках, множитель проверяется делением модуля.
Расшифровка даёт четыре куска, из которых собирается `SOLARCTF{...}`.

## 14. Выводы

- Перед выбором атаки стоит посчитать запас: 6 бит сверх границы означают, что метод
  применим, но требует контроля размерности.
- Разбиение одной большой решётки на много маленьких за счёт угадывания нескольких бит
  часто выгоднее, чем подбор параметра редукции.
- Ограничение потоков важнее числа ядер: один поток на воркер даёт больший суммарный
  выигрыш, чем переподписка.
- Точное деление модуля и осмысленный текст после расшифровки это достаточный критерий,
  что найден настоящий множитель, а не артефакт решётки.
