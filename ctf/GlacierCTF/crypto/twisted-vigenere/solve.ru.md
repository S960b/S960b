# Twisted Vigenere — восстановление XOR-ключа через переход состояния MT19937

[English version](solve.md)

**GlacierCTF 2026 · Crypto · 50 баллов · Решено**

## 1. Что находится в исходном архиве

Оригинальный `twisted-vigenere (1).tar.gz` содержит `gen.py`, `output.txt`, `pyproject.toml`, `uv.lock` и `sha256sum`. Все записи контрольных сумм прошли проверку.

Критическая часть кода организаторов:

```python
flag = Path("flag.txt").read_bytes().strip()
pt = random.randbytes(2536)
keystream = np.tile(np.frombuffer(flag, dtype=np.uint8),
                    (len(pt) + len(flag) - 1) // len(flag))[:len(pt)]
ct = np.frombuffer(pt, dtype=np.uint8) ^ keystream
output = base64.b64encode(ct)
```

Здесь нет классического Виженера: **флаг — это циклический XOR-ключ**, накладываемый на псевдослучайную последовательность:

```text
C[i] = R[i] XOR K[i mod 48].
```

`R` сгенерирован `random.randbytes()` из Python, то есть MT19937, который не предназначен для криптографии. Base64 в `output.txt` — только представление результата. После декодирования получается **2536 байта**.

Важно: запуск `gen.py` без оригинального `flag.txt` запишет **новый** ciphertext с демонстрационным флагом и новой случайностью. Восстанавливать нужно именно оригинальный `output.txt`.

## 2. Почему длина 2536 критична

`random.randbytes(2536)` выдаёт 634 слова MT19937 по 32 бита в порядке little-endian:

```text
2536 / 4 = 634 = 624 + 10.
```

Первые **624 слова** позволяют восстановить внутренний массив MT, если предположить конкретный XOR-ключ; **следующие 10 слов** обязаны соответствовать преобразованию `twist` этого массива.

Выход генератора — `temper(state_word)`:

```text
y ^= y >> 11
y ^= (y << 7)  & 0x9d2c5680
y ^= (y << 15) & 0xefc60000
y ^= y >> 18
```

Эти битовые операции обратимы. Скрипт `untemper` обращает их в обратном порядке. Для предполагаемого ключа расшифровываем `R[i]=C[i] XOR K[i mod 48]`, затем отменяем temper для первых 624 слов.

## 3. MT19937 даёт линейные ограничения на биты флага

Десять выходных слов после границы состояния должны получаться из первых 624 по правилу:

```python
y = (state[j] & 0x80000000) | (state[j+1] & 0x7fffffff)
next_state[j] = state[j+397] ^ (y >> 1) ^ (
    0x9908b0df if (y & 1) else 0)
output[j] = temper(next_state[j])
```

Пусть `F(K)` — XOR предсказанных десяти слов и тех, которые фактически прочитаны в конце ciphertext после вычитания повторяющегося ключа.

Все преобразования MT19937 — **линейные по GF(2)**. Условный XOR константы `0x9908b0df` при установленном младшем бите тоже является линейным отображением. Поэтому `F` — аффинная функция **384 бит ключа**.

Находим `b=F(0)`, затем по очереди переключаем каждый из 384 бит:

```text
column_i = F(1<<i) XOR b
A*K = b над GF(2).
```

Получаем **320 битовых уравнений** для 384 бит ключа. Это не эвристика и не подбор слов по словарю, а точные отношения между выходами MT.

## 4. Ограничения формата и метод Гаусса

В решённом экземпляре флаг имеет **48 байт**. Добавляем известное начало `gctf{`, закрывающую `}` и тот факт, что флаг состоит из ASCII-символов (старший бит каждого байта равен нулю).

```text
320 уравнений перехода MT
 48 бит известных gctf{ и }
 48 нулевых старших битов ASCII
----------------------------------
416 записанных уравнений, 384 переменные
ранг = 363, свободных битов = 21
```

Решаем двоичным Гауссом, храня каждую строку одним большим числом Python. Получаем **воспроизведённый на оригинальном архиве результат**:

```text
ciphertext bytes: 2536
key length assumption: 48
equations: 416 rank: 363 free bits: 21
recovered: gctf{from_rand0m_!mpor+_n0+_s0_r4nd0m_af+3r_???}
unknown byte positions: [44, 45, 46]
```

Это и есть важнейшая техническая тонкость: **45 байт определяются однозначно, а три позиции (44–46, отсчёт с нуля) криптоанализом исходного output.txt не определяются**. На них приходится 21 свободный бит (7 на байт). Даже если требовать читаемые символы, неоднозначность полностью не исчезает.

Поэтому утверждение, будто MT-восстановление само по себе однозначно извлекает все 48 байт, было бы неверным.

## 5. Как найдено реальное окончание

Ранее в диалоге решения был получен флаг, который **прошёл проверку на платформе**. Его три последние символа внутри фигурных скобок — `al1`. Это **не байты, доказанные исходным ciphertext**, а окончание, установленное по исторически принятому ответу.

Подстановка **всего 48-байтного принятого ключа** в проверку текущего скрипта даёт:

```text
MT19937 next-state mismatched bits: 0
Candidate passes all 320 MT checks.
```

Тем самым подтверждена криптографическая согласованность известного флага с подлинным `output.txt`. Но **не утверждается**, что иных последних трёх символов не могло бы быть: эта часть выбирается внешней проверкой площадки.

Знаки `+` и `!` в ключе — буквальные, их нельзя заменять пробелами.

## 6. Пошаговое воспроизведение

Распаковать handout, взять оригинальный `output.txt`:

```sh
tar xf twisted-vigenere.tar.gz
python3 scripts/solve_mt.py twisted-vigenere/output.txt
```

Новый [scripts/solve_mt.py](scripts/solve_mt.py) не содержит зашитого флага и обходится **стандартным Python 3.10+**, без NumPy/Z3/SageMath. Он строит 384 столбца с помощью побитовых возмущений, выполняет метод Гаусса над GF(2), выводит фиксированные байты и позиции `?`.

Вторым аргументом можно указать **известный 48-символьный кандидат**: программа проверит его по всем десяти пост-переходным словам MT. Это верификация, а не способ магически определить последние три байта.

## 7. Почему шифр сломан

Ошибку образуют вместе два решения авторов: использовать **флаг как циклический XOR-ключ** и брать открытый текст из **предсказуемого линейного PRNG**. Нельзя считать такой поток криптостойкой одноразовой гаммой. Граница из 624 слов MT и лишние десять слов раскрывают сильные линейные связи.

Частотный анализ обычного Виженера или попытки угадывать псевдослучайный открытый текст здесь не нужны. Условия MT дают точные ограничения; последняя тройка символов остаётся за их пределами и разрешается принятой на платформе строкой.
