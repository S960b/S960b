# Proto Prism — RCE через @response-file в protoc

[English version](solve.md)

## 1. Первичные проверки

Временный веб-инстанс создавался лаунчером на порту 13376, время жизни — 600 секунд. Форма POST /generate принимала multipart-поле bundle с ZIP, а /example.zip возвращал эталонные protobuf-исходники. В ответе Insomnia v4 JSON есть ресурсы proto_file с полем protoText.

**Исходники сервиса организаторы не выдавали**: механизм определён по реакции на запросы. Сначала выяснилось, что ZIP-записи должны иметь Unix-атрибуты обычного файла: create_system=3, external_attr=(0o100644 << 16). Обычный zipfile.writestr без этих атрибутов давал 400. Допускались имена до 127 символов, рекурсивный обход protos/, дополнительные не-proto файлы.

Проверка protos/-x.proto показала, что ведущий дефис интерпретируется самим protoc как опция, в отличие от protos/sub/-x.proto. Следовательно, сервис передавал компилятору **имена без префикса protos/ и без разделителя --**. Инъекция метасимволов shell в имена ничего не дала.

## 2. Ключ: response-файл

Protoc обрабатывает аргументы, начинающиеся с @, через ExpandArgumentFile: файл открывается **относительно текущего рабочего каталога**, а не proto_path, и каждая строка преобразуется в полноценный argv-аргумент. Для атаки в ZIP помещены:

    args.proto                      (корень распаковки)
    protos/@args.proto              (имя становится аргументом @args.proto)
    protos/service.proto

Файл args.proto содержит:

    --plugin=protoc-gen-x=/bin/sh
    --x_out=<parameter>:.

Таким образом, ограниченное имя *.proto превращается в подмену параметров компилятора. Через встроенный механизм плагинов запускается настоящий /bin/sh.

## 3. Превращение бинарного protobuf в shell-программу

Protoc передаёт плагину бинарный CodeGeneratorRequest через stdin. При обычных именах shell завершался ошибкой синтаксиса из-за бинарных полей и кавычек. Локальный дамп запроса объёмом 764 байта дал ключевой приём.

Поле file_to_generate начинается с 0x0a (перевод строки), далее — длина имени. Для имени **ровно 35 байт** длина кодируется 0x23, то есть знаком #. Подготовленное имя:

    #AAAAAAAAAAAAAAAAAA<LF>BBBBBBBBB.proto

даёт начало 0a 23 23 41...: shell воспринимает # как начало комментария, а перевод строки внутри имени — как его окончание. Аргумент плагина добавляет команду и завершение:

    ;echo RUNOK-MARKER > protos/service.proto;exit 0;#

Это гибрид protobuf/shell, а не просто вызов /bin/sh. Локально на protoc 25.1 и 29.3 он создал файл pwned.txt с PWNED.

## 4. Получение флага

Полный отправленный ZIP:

    args.proto
    protos/@args.proto
    protos/#AAAAAAAAAAAAAAAAAA<LF>BBBBBBBBB.proto
    protos/service.proto

Первый реальный запрос выполнил echo RUNOK-MARKER > protos/service.proto. Сервер ответил **HTTP 200, 2503 байта**, а поле service.proto.protoText содержало RUNOK-MARKER. Это доказывает и выполнение команды, и повторное чтение исходника после protoc.

Второй запрос выполнил:

    cat /flag > protos/service.proto

Ответ **HTTP 200** вернул настоящий флаг в protoText. В публичном репозитории его значение скрыто как gctf{...}; полный текст находится в частном FLAG.txt из архива.

## 5. Что не сработало

Обычные метасимволы в имени, прямые флаги --fatal_warnings и --descriptor_set_out, новая опция --<lang>_prefix, пользовательский скрипт-плагин в ZIP, перезапись через *_out и попытки отправки на webhook не привели к успеху. Коллизии basename в Insomnia JSON не ломали связи ресурсов.

Эти отрицательные результаты объясняют, почему потребовалось именно сочетание **response-файла**, **плагина /bin/sh** и **35-байтового имени**.

## 6. Доказательства и оговорки

Прежний чат "Proto Prism Analysis" фиксировал лишь неудачные пробы. Более поздний архив агента содержит REPORT.md, восстановленный solve.py, оригинальный local_repro.sh, файлы example.zip/index.html, результат PWNED и журнал извлечения флага.

Сырой финальный HTTP-ответ не был сохранён, только перенесённый из терминала текст. solve.py восстановлен по успешному inline-прогону. Исходники сервиса и точная версия protoc неизвестны; дамп CodeGeneratorRequest сделан **локально**, а не снят с веб-инстанса.

**Флаг действительно извлечён с сервиса, но сдача на платформе отдельно не подтверждена.** Это различие сохраняем в write-up.
