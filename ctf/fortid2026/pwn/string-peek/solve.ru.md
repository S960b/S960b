# String Peek & Poke - writeup (pwn: OOB-индекс на std::string, порча ctype, execve)

## Знакомство с задачей

Сервис «заметки»: программа читает команды из стандартного ввода и хранит строки. К ней прилагался исходник и набор библиотек, а на remote крутился такой же бинарь.

В архиве (handout):
- `chall` - сам бинарь (x86-64 ELF, PIE, full RELRO, NX);
- `chall.cpp` - исходник (редкость, сразу видно всё устройство);
- `libc-2.39.so`, `libstdc++.so.6.0.33` - библиотеки, которые стояли на сервере.

Вся программа целиком:

```cpp
string notes[8];   // глобальный массив строк

int main() {
    while (true) {
        // "> "
        getline(cin, line);
        if (command == "put") { int idx; string val; cin >> idx >> val; notes[idx] = val; }
        else if (command == "get") { int idx; cin >> idx; cout << notes[idx] << endl; }
    }
}
```

`put IDX VAL` записывает строку в заметку, `get IDX` печатает её. Индекс НИГДЕ не проверяется: `notes[idx]` - это просто арифметика указателей. `notes[0..7]` - нормальные заметки, а `notes[-1]`, `notes[-2]`, `notes[16]` - это уже память, которая лежит ДО или ПОСЛЕ массива. Вопрос только в том, что там лежит и можно ли этим воспользоваться. Именно так я и начал: сначала посмотрел, что рядом с массивом, потом карту «какие индексы что делают».

## Как я читал код (какими программами)

- `cat chall.cpp` - исходник прилагался, с него и начал. Сразу видно: `notes[idx]` без проверок, массив глобальный (в BSS).
- `file chall` - x86-64 ELF, статически не слинкован (использует системные .so), PIE, динамический.
- `readelf -h chall`, `checksec`-стиль чтение заголовков - PIE, full RELRO (GOT помечен read-only), NX. Важно сразу: перезапись GOT не сработает, нужно что-то другое.
- `nm -C chall`, `readelf -s` - символы: `notes` на PIE-смещении 0x203260, размер 256 байт (8 строк по 32).
- `objdump -d` - куда обращаются `put` и `get` (по смещениям от main), как устроен ввод (istringstream, getline).
- gdb - когда нужно было посмотреть, что реально лежит в памяти по конкретному индексу, и что именно ломается при записи. Брейкпоинт на `main+0x319` (после `notes[idx] = val`) и смотрю слот до/после.

## Что такое std::string в памяти (важно, дальше всё на этом)

`std::string` - это объект фиксированного размера (32 байта), который хранит либо саму строку, либо указатель на неё. Устройство (упрощённо, это libstdc++ SSO - small string optimization):

```text
[0..7]   указатель на данные (для коротких строк - на самого себя, внутри объекта)
[8..15]  длина (size)
[16..23] ёмкость (capacity)
[24..31] сами байты строки для коротких строк (SSO-буфер)
```

Если строка короткая (меньше 16 байт) - байты лежат прямо в объекте, `data` указывает на себя. Если длинная - `data` указывает на кучу, а в объекте лежат указатель/длина/ёмкость.

Ключевой момент для утечки: `cout << s` печатает ровно `s.size()` байт из `s.data()`. Если прочитать «строку», которой на самом деле нет (мусор в BSS или чужие данные), то `size` интерпретируется из мусорных байт - и может оказаться огромным числом. Программа напечатает большой кусок памяти, даже не упав. Это и есть read-примитив.

## Разведка: карта индексов (probe_oob.py)

Не хотелось ронять процесс на каждом шаге, поэтому я сделал простой скан: для каждого индекса запускается ОТДЕЛЬНЫЙ процесс, ему подаётся `get IDX` (или `put IDX ...`), и смотрится код возврата и вывод. Так и процесс не портится, и видно сразу, какие индексы читают, какие пишут, какие падают.

Итог по чтению (get даёт ~4096 байт):

```text
-26..-21   GOT/.got.plt - указатели на функции libstdc++.so (.text)
-18        cout (объект std::cout в BSS)
-10        cout + 0x100
-2         cin + 0xE0
-1         cin + 0x100  < -- самое интересное
```

Итог по записи (put):

```text
пишется без краха: -16..-13, -7..-4, -1, и все 0..64
крах (SEGV/abort): -32..-17, -12..-9, -3, -2
```

Почему put в часть слотов падает: `notes[idx] = val` вызывает `assign`, а `assign` для «длинной» строки сначала освобождает старый буфер (`free(ptr)`) - если `ptr` в мусоре битый, будет `free(): invalid size` или `double free`. А вот если у «строки» ёмкость огромная и `assign` может писать по существующему указателю без освобождения - тогда запись проходит. Об этом ниже.

## get -1: главный лик

Слот `-1` - это не строка, а байты поля `cin+0x100`. Там лежит структура locale (facet) - данные, которыми iostream пользуется для классификации символов. Внутри - несколько указателей:

```text
[0]    ptr в libstdc++ (r-- данные, +0x2a0a90)
[1]    0x2
[2]    ptr в libc    (r-- данные)
[3]    0
[4..6] ptr в libc (r-- данные, это ctype-таблицы)
...
```

`get -1` печатает 4096 байт, начиная с этой структуры. Из первых qword'ов считаются базы:

```text
libstdc++ база = qword[0] - 0x26fe98
libc база      = qword[2] - 0x202de0   (для glibc 2.39; 0x202de0 - смещение ctype-указателя в libc)
```

То есть одна команда `get -1` даёт обе базы - и libstdc++, и libc. Это ровно то, что нужно для ROP. (В скрипте эти смещения - таблица CONFIG, потому что они версионно-зависимые; для glibc 2.42 на локальной машине они другие.)

## put -1: примитив записи

Почему запись именно в `-1` безопасна, а в другие - крах: `assign` смотрит на ёмкость «строки». У слота `-1` ёмкость огромная (мусорные байты), поэтому `assign` НЕ освобождает и НЕ выделяет ничего - он копирует наши байты прямо по существующему указателю. А этот указатель ведёт в структуру locale (libstdc++-контекст + 0x2acae0, рядом с rw-картой libstdc++). Получается:

```text
put -1 <payload>  -  пишем payload по фиксированному адресу (locale-структура),
                       содержание и длина - наши, адрес - нет (он зашит в слоте)
```

Более того, в payload можно класть NUL-байты: getline читает строку до перевода строки, NUL внутри значения переживает (проверено: `put 0 A\x00BB` - `get 0` печатает `A\x00BB`). Нельзя только перевод строки (0x0a) - он заканчивает команду. Это важно для сборки бинарного payload.

## Что триггерить: istream sentry и ctype-таблица

Запись в locale-структуру сама по себе ничего не даёт - нужно, чтобы программа ПОТРЕБИЛА испорченные данные. Здесь пригодилась диагностика в gdb (стадии 6-7):

- При чтении следующей команды `std::istream::sentry` проверяет пробельные символы. Для этого он обращается к таблице классификации символов (ctype) через указатель, который лежит в нашей locale-структуре (7-й qword, база+0x30).
- Если перезаписать этот указатель «в мусор» (записать 52+ байта 'A'), следующий же `get 0` падает в sentry: `testb $0x20, 0x1(%rdx,%rax,2)` с rdx = испорченная база таблицы. Это НЕ косвенный вызов, а просто чтение из таблицы по индексу символа - но адрес таблицы мы контролируем.
- Если сдвинуть указатель на ±2 (не ломая совсем) - парсинг ломается («unknown command»), процесс жив. Значит, указатель реально потребляется на каждом ходе.

Вывод: слот `-1` даёт запись в структуру, один из указателей которой разыменовывается при чтении следующей команды. Осталось сделать так, чтобы разыменование привело к исполнению кода.

## Финальная цепочка: поддельный setcontext-фрейм

Мы пишем 0x510 байт в locale-структуру (назовём её базу `ctype` - это адрес, куда указывает слот `-1`). Внутри этого куска собираем поддельный контекст для `setcontext`-стиля:

```text
[0x00..0x37] первые 56 байт восстановлены из утечки (чтобы остальные проверки структуры не сломались),
             но первый qword переписан на адрес нашего fake-фрейма: ctype + 0x150
[0x150 + 0x38] - libc + gadget (0x5ef84 для 2.39): переключает регистры из памяти (setcontext-стиль)
[0x150 + 0x68] - ctype + 0x3e0   (rsp: указывает на строки)
[0x150 + 0x70] - ctype + 0x430   (rbp)
[0x150 + 0xa8] - libc + execve   (0xef030 для 2.39)
[0x150 + 0x1c0] - 0x1f80 (rflags)
[0x360]        - "\x7f\x03" (значение, похожее на xmm/мусор, не критично)
[0x3e0]        - "/bin/sh\0"
[0x3f0]        - "-c\0"
[0x410]        - команда (например, "cat flag.txt")
[0x430]        - argv: { ctype+0x3e0, ctype+0x3f0, ctype+0x410, 0 }
[0x488]        - libc + exit (0x47ba0 для 2.39)
```

Механика (упрощённо): gadget в libc (это фактически setcontext или его аналог) берёт из памяти значения регистров - включая указатель стека и адрес возврата - и переключает выполнение на них. Мы кладём туда `rsp` на наши строки и `execve` как точку входа: получается `execve("/bin/sh", ["/bin/sh", "-c", "cat flag.txt"], ...)`.

Когда это срабатывает: после `put -1 <payload>` отправляем `get 0`. Программа начинает читать `get 0`, sentry идёт в ctype-таблицу по указателю из locale-структуры, а указатель теперь ведёт в наш fake-фрейм. Разыменование превращается в исполнение поддельного контекста - `execve`, и вместо ответа сервиса мы получаем вывод команды - `cat flag.txt`.

Ограничения:
- payload не должен содержать пробельные символы (` `, `\r`, `\n`, `\t`, `\v`, `\f`): значение `put` читается через `iss >> val`, пробел обрежет payload на середине; перевод строки закончит команду.
- ASLR меняет базы при каждом запуске, поэтому каждый try заново: `get -1` - считаем базы - собираем payload - проверяем на «плохие» байты - `put -1` - `get 0`. Если в payload попал пробельный байт - просто переподключаемся (вероятность мала, ретраев обычно хватает).

## Скрипт solve.py

`scripts/solve.py` делает ровно эту цепочку:

1. Коннект (TLS к remote или локальный процесс), ждём баннер `> `.
2. `get -1`, читаем 4096 байт утечки.
3. Из утечки: `libstd = u64(leak) - 0x26fe98`, `libc = u64(leak, 0x10) - CONFIG[glibc]['locale']`, `ctype = libstd + 0x27ba20`.
4. Собираем payload 0x510 байт (как выше), проверяем на пробельные байты; если есть - `continue` (новый try).
5. `put -1 <payload>`, затем `get 0`.
6. Читаем ответ, ищем `FortID{`.

Таблица CONFIG содержит оффсеты для двух конфигураций: `host` (локальная glibc 2.42) и `2.39` (remote). Для remote запуск был `--glibc 2.39`.

## Проверка локально, до remote

Локально стояла системная glibc 2.42 + bundled libstdc++ 6.0.33. Оффсеты другие (execve 0xe1cf0, exit 0x43450, locale 0x1e7de0), и локальный прогон `--glibc host` умирал тихо (процесс падал, ответ пустой) - ожидаемо, версии не совпадают с remote. Это нормально: скрипт параметризован по версии, и для remote брались оффсеты glibc 2.39 из CONFIG.

## Что я пробовал сначала (тупики)

1. **GOT-указатели из get -26..-21.** Утечки из GOT дают только адреса функций libstdc++ (.text), и GOT в full RELRO read-only - ни записать, ни дотянуться до libc через них. Для execve нужен libc, он появляется только в утечке `-1`.

2. **Коррупция cout/cin (индексы -16..-13, -7..-4).** `put` туда создаёт настоящую heap-строку (assign аллоцирует новый буфер), но эти поля НЕ потребляются обычным циклом «ввод-вывод»: после порчи всё работает, вывод корректный. Мёртвые поля - управление не получить.

3. **Управление адресом записи.** `put -1` пишет по фиксированному указателю (зашит в слоте), адрес мы не выбираем - только содержимое и длину. Поэтому цель должна быть «потребляемой по этому адресу», а не произвольной.

4. **Собрать payload «как есть» из утечки.** Восстановить первые 48 байт структуры дословно нельзя: среди них есть байт 0x0a (перевод строки) - getline оборвёт значение. Поэтому payload собирается заново, а не копируется.

5. **Сдвиг ctype-указателя на ±2 (gdb-эксперимент).** Ломает парсинг («unknown command») без краша - это read-lookup, а не косвенный вызов. Управление потоком даёт только полный поддельный фрейм, а не маленький сдвиг.

6. **Локальный прогон с host-оффсетами.** Процесс умирал молча, ответ пустой - версии libc разные, оффсеты не сходятся. Вывод: всегда параметризовать скрипт по версии glibc.

## Версия в один абзац

Программа хранит 8 строк в глобальном массиве `std::string notes[8]` и не проверяет индекс. `get` с отрицательным индексом печатает память перед массивом как строку: слот `-1` - это структура locale (cin+0x100), полная указателей на libstdc++ и libc, и одна команда `get -1` выдаёт 4096 байт, из которых считаются обе базы. `put -1` пишет наши байты прямо в эту структуру (у «строки» огромная ёмкость - assign копирует по существующему указателю без переаллокации). Внутри payload мы собираем поддельный setcontext-фрейм: указатель ctype-таблицы, который istream::sentry разыменует при чтении следующей команды, перенаправляем на этот фрейм - и вместо классификации символов программа исполняет `execve("/bin/sh", ["/bin/sh", "-c", "cat flag.txt"])`. Всё в одной сессии, на каждый try заново из-за ASLR, и payload обязан быть без пробельных байт.

## Уроки

1. OOB-индекс на C++-объекте - это и чтение, и запись, но семантика `assign` решает: при огромной ёмкости строка пишет по существующему указателю (безопасно, фиксированный адрес), при маленькой - освобождает/аллоцирует (крах на мусоре).
2. Мусорный `std::string` - готовый read-примитив: длина интерпретируется как есть, и `cout << s` печатает сотни байт чужой памяти.
3. Full RELRO закрывает GOT, но не закрывает «легитимные» указатели в данных (locale/ctype), которые сам код разыменует на каждом ходе.
4. Объекты iostream в BSS (cout/cin) - соблазнительная цель, но бесполезная, если их поля никто не потребляет; ищи то, что реально читается (sentry), а не то, что красиво выглядит.
5. Оффсеты зависят от версии libc/libstdc++: скрипт обязан быть параметризован по версии, иначе локальный прогон молча не сойдётся.
6. Ограничения канала (пробелы, перевод строки) превращаются в условия на payload; проверяй «плохие» байты и переподключайся - ASLR даёт новый шанс каждый try.
