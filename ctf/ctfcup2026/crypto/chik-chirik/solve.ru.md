# Chik Chirik: демодуляция чирп-передатчика

[English](solve.md)

## 0. Что было в аудио

`capture.wav` это не речь. Сигнал представлял собой последовательность частотных чирпов с фиксированной длиной символа 2048 отсчётов, то есть цифровую модуляцию, а не запись флага голосом. Передатчик из того же архива (`transmitter FLAG OUTPUT.wav`) это подтвердил: он синтезирует запись из флага и отказывается работать с payload вне диапазона 8..4096 байт.

Цепочка, которая в итоге сработала, по слоям:

1. Демодулировать чирпы в октальные символы.
2. Снять блоковый код, которым оказался Рид-Соломон RS(7,3) над GF(8).
3. Описать скремблер, это линейный xorshift128.
4. Восстановить его 128-битное состояние из линейных уравнений над GF(2).
5. Снять перемешивание, разбить payload и проверить CRC32.

Зачем такой порядок: помехоустойчивый код и скремблер решают разные задачи. Пока символы грязные, скремблер выглядит случайным; пока он не обращён, корректность декодирования кода не проверить.

## 1. Символы из осциллограммы

Каждый чирп использует четыре наклона частоты и две фазы, итого восемь состояний, один символ на 2048 отсчётов. Запись начинается преамбулой `24355342`, дальше символы идут группами по семь.

Демодулированный поток хранился как текст из октальных цифр (`capture.wav.octal.txt`), чтобы отлаживать аудио и декодирование отдельно. `scripts/decode_capture.py` это демодулятор, `scripts/solve_from_octal.py` принимает уже готовый октальный поток.

## 2. Блоковый код это RS(7,3), а не Хэмминг

Первое прочтение было «блоки по семь с избыточностью Хэмминга». Это неверно, и ошибка стоит времени: при Хэмминге разбиение не сходится на всей записи.

Кодер около `0x211ac0` в передатчике работает над GF(8) с многочленом `x^3 + x + 1`. Семь символов несут три информационных и четыре избыточных.

Именно на учёте бит легко ошибиться, поэтому сформулируем точно. Одно кодовое слово это семь октальных символов, то есть 21 бит на линии. Три информационных символа содержат 9 бит закодированных данных, а четыре избыточных их защищают. Но полезных бит сообщения среди этих девяти только 3. Остальные 6 это биты, которые передатчик в этой позиции payload отдаёт из своего потока xorshift128, и они нужны ровно для того, чтобы приёмник восстановил состояние генератора. Значит скорость полезной нагрузки 3 бита на кодовое слово, и закон `ceil(8 * (L + 4) / 3)` берётся именно отсюда: делитель 3 это число бит сообщения на кодовое слово, а не число информационных бит.

`scripts/solve_chirp.py` строит таблицу кодера для всех 512 троек и обращает её по первым трём значениям.

Закон кадра следует из той же процедуры: число блоков

```text
B = ceil(8 * (L + 4) / 3)
```

где `L` это длина payload в байтах, а четыре лишних байта это CRC32. Для захваченного файла `B = 144`, значит `L = 50`. Это вычислено, а не угадано, и это важно дальше, потому что длину payload нужно знать до обращения скремблера.

## 3. Скремблер линейный, значит состояние решается

Перемешивание находится около `0x220b29`..`0x220de3`, обновление состояния около `0x210f80`. Это xorshift128: четыре 32-битных слова, только XOR и сдвиги. Значит каждый выходной бит линейно выражается через 128 начальных бит состояния, а запись даёт два из трёх выходных бит на каждый информационный символ.

Восстановление ключа превращается в линейную алгебру:

```text
A * s = b  (mod 2)
```

Гаусс над GF(2) дал ранг 128 из 128, то есть состояние единственно, а не одно из многих. `scripts/gf2_gauss.py` это небольшой помощник для исключения, им проверялся ранг по мере сборки уравнений.

Зачем этот шаг: перебор 128 бит безнадёжен, а линейная система ранга 128 это рутинная задача. Вся задача держится на том, чтобы заметить линейность генератора.

## 4. Декодирование записи

Сначала два контрольных теста, оба сделаны исходным передатчиком:

- 22 байта `A`: 70 блоков, восстановленное состояние `00000001 00000000 00000000 00000000`, payload из 22 букв `A`, CRC32 `c0bb810c`.
- payload 43 байта с seed `00112233445566778899aabbccddeeff`: восстановлен полностью, CRC32 совпал.

Затем реальный захват:

```text
chirps: 1016  preamble: 24355342
FEC blocks: 144  invalid: 0
raw symbols: 432
probable length: 50
xorshift rank: 128 of 128
PRNG state: 8bf31bf8 886c0791 8d3e0dc3 1557904c
CRC32 (LE): 2a2617cc
```

`invalid: 0` означает, что каждое кодовое слово декодировалось без остаточной ошибки, а текст payload это корректный `ctfcup{...}` с совпавшим CRC32. Флаг в тексте скрыт как `ctfcup{...}`; внутри есть `$` и `?`, так что алфавит шире, чем у чисто hex-флагов этого же события.

Запуск:

```bash
python3 scripts/solve_chirp.py capture.wav
python3 scripts/solve_from_octal.py capture.wav.octal.txt
```

Первый вариант требует numpy и scipy для чтения WAV, второй обходится стандартной библиотекой.

## 5. Тупики

- Избыточность, принятая за Хэмминг, давала стройное разбиение на коротких тестах и рассыпалась на реальном файле.
- Попытка вытащить 16 случайных байт seed из шума тупиковая по простой причине: seed в аудио не присутствует, он только управляет генератором. Правильный ход был решать состояние, а не искать его.
- Дифференциальные приёмы (сравнить два прогона одного флага или два флага с одним изменённым символом) не работают, потому что перемешивание зависит от данных, и один байт даёт лавину по всему потоку.

## 6. Выводы

- Сначала проверять блоковый код, потом атаковать псевдослучайный слой.
- Линейный генератор с утечкой выходных бит это линейная система, а не поиск ключа.
- Длину payload надо выводить из закона кадра, это убирает одно неизвестное из всей цепочки.

Одним абзацем: запись это чирп-модуляция кода RS(7,3) над GF(8) с последующим линейным скремблером xorshift128; демодуляция даёт 144 чистых кодовых слова, закон кадра фиксирует payload в 50 байт, утёкшие биты дают линейную систему ранга 128 для состояния генератора, и после обращения перемешивания payload вместе с CRC32 воспроизводит флаг.
