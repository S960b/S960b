# Stage 38C — точечное завершение ранее выполненного задания seq=5

Причина: stage37b2c создал fsync-журнал claim-intent **до** попытки SQL claim; агент ранее выполнил только GET диагностику и получил HTTP 401, но истёк agent gate. Поэтому журнал остался, а PostgreSQL показывает `seq=5 pending attempts=0`.

**530_recover_seq5_once.sh** верифицирует текущую базу, старый журнал, конфиг, watchdog и отсутствие активных разрешений. Скрипт создаёт устойчивый личный checkpoint **до** выдачи временных разрешений, открывает строго scoped permit/gate, выполняет SQL `claim` (без SDK), сохраняет секретный lease token локально с fsync, отправляет **один** уже известный отчёт с прежним `message_id`, ACK-ает `seq=5` тем же lease. При любой ошибке не повторять: снимет разрешения и оставит checkpoint и journal для диагностики. Временное разрешение ChatGPT оставляется только при успехе для ACK seq6.

После успеха ChatGPT читает seq6, проверяет точный body/SHA, ACK-ает seq6 и отключает dispatch. Затем агент выполняет независимый emergency revoke Stage37A. Только после подтверждения ACK и отзыва обоих разрешений **531_finalize_after_chatgpt_ack.sh** архивирует исходный блокирующий journal. Этот скрипт read-only для БД, но **переименовывает один локальный журнал**, иначе следующая задача будет зависать. Новый отчёт не создаёт. При STOP не повторять.

Примечание: Сценарий не даёт универсального восстановления crash-window и не исправляет общий SQL lease-протокол; это операторская одноразовая процедура, строго ограниченная данным task_id, seq=5, delivery_id=21, известным телом уже выполненного GET-задания. SQL claim/ACK используются исключительно для восстановления квитанции доставки, не для запуска SDK. Максимум 20 минут для agent gate, 60 минут для MCP-permit; watchdog активен.
