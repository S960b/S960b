# Stage 40 — оптимизация обновления Taskboard v2 (8789)

Назначение: убрать повторное установление TCP/SCRAM-соединений для каждой строки и повторную загрузку истории каждой строки в браузере. **Никаких SQL DDL, изменений схемы, conninfo, авторизации, pg MCP, managed worker, Stage39 или systemd unit.** Единственное обслуживание службы: `systemctl --user restart bridge-pg-v2-taskboard.service` после установки трех файлов.

## Исходные факты

Live root `/home/kali/bridge-pg-v2`, порт 8789; user unit `bridge-pg-v2-taskboard.service`. По read-only обследованию: 5 диалогов, обновление 18.8 секунд, база на VPS по SSH и одно подключение 0.62 секунды; до патча 1+5N DB connections на полное обновление.

## Изменения

1. `bridge_pg/store.py`: `ContextVar` с изолированным `taskboard_read_batch` на каждый *HTTP-запрос*. Каталог и все другие клиенты по-прежнему получают короткие соединения. Внутри batch используется отдельная `psycopg` transaction на каждую операцию, чтобы SQL исключение в одном диалоге не блокировало остальные.
2. `bridge_pg/taskboard_v2.py`: один batch для `/api/dialogs`, добавлена компактная карта `row_details`, где последнее сообщение *без поля body* (только метаданные для таблицы). Basic Auth / Origin / CSRF и операции записи не изменяются.
3. `bridge_pg/static/taskboard.js`: таблица берет `row_details` из того же ответа, больше не запрашивает `/api/history` для каждой строки. История по кнопке продолжает использовать отдельный запрос и текущий браузерный кэш. «Обновить» сразу показывает «Обновляем…» и блокирует повторный клик до завершения.

Ожидаемое число DB connect при `/api/dialogs` с пятью диалогами: одно, вместо 16. Истории при refresh: ноль, вместо пяти. Остальные SQL-вызовы внутри одной DB-сессии выполняются последовательно; скорость **не гарантирована** и будет измерена после установки.

## Ограничения безопасности

Инсталлятор остановится до изменений, если любой из пяти исходных SHA256 не совпадает, код отличается от присланного агентом, службы нет/она неактивна, либо нет Node для проверки JS. Сверяет AST Python и Node `--check` JS, делает приватные byte-exact бэкапы и сохраняет состояние для отката. Обновляет файлы атомарно; при сбое после патча пробует восстановить источники и службу. Перед и после перезапуска проверяет `401` на запрос без авторизации (без чтения паролей). При STOP **не запускать повторно** без изучения причин. Никаких запросов с учетными данными автоматически не выполняется.

## Установка

Выполнять **без sudo**, под `kali`, только по команде оператора:

```bash
bash /home/kali/Downloads/stage40/400_install_once.sh
```

После успешного запуска открыть `http://127.0.0.1:8789/` в браузере, авторизоваться обычным способом и измерить время кнопки «Обновить». Проверить пятёрку диалогов, статусы передачи, «История», «Вернуть ход», «Удалить» (только отображение кнопки, НЕ удалять), сортировку.

Скрипт печатает `STAGE40_BACKUP_DIR`, например `/home/kali/.local/state/bridge-pg-v2/stage40/backup-...`.

При необходимости откат:

```bash
bash /home/kali/Downloads/stage40/401_rollback.sh \
  /home/kali/.local/state/bridge-pg-v2/stage40/backup-<...>
```

## Критерии приемки

Сервер возвращает `/api/dialogs` с ключами `dialogs`, `csrf`, `mt_delivery`, `row_details`. При пяти диалогах список показывает последнее событие и `waiting_for` сразу, история открывается отдельным запросом только по клику. Кнопка блокирует повторный клик. Служба слушает только loopback 8789; доступ без Basic Auth даёт 401. Сохранено старое поведение остальных Store потребителей. Время refresh замерить отдельно с действующей авторизацией; при ухудшении — откат.
