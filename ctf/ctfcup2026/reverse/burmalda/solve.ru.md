# Burmalda: флаг лежит в клиентском пакете

[English](solve.md)

## 0. Как выглядит задача

Инстанс отдаёт браузерную игру: рулетка с балансом, полем ставки, кнопками красного и чёрного и отдельной панелью, которая должна показывать флаг. Очевидное прочтение это «выиграть игру», и оно неверное.

Страница это экспорт Godot 4.4.1 в HTML5. Браузер не запустит игру Godot, не скачав её целиком, значит всё нужное, включая скрипты, приходит на клиент. Вопрос в том, что в этих скриптах.

Зачем этот шаг: распознать движок означает сразу сменить цель. Экспорт игры в веб это статический пакет, а не серверный сервис.

## 1. Достаём пакет

Экспорт грузит файл `.pck`, пакет ресурсов Godot. Он виден в сетевой панели как `/Burmalda.pck` и скачивается напрямую:

```bash
curl -O https://<host>/Burmalda.pck
sha256sum Burmalda.pck
```

Файл весит 43 760 байт и начинается сигнатурой `GDPC`, версия формата 2.

Игра пытается мешать осмотру: собственный обработчик клавиатуры съедает `F12`. Это косметика, потому что меню браузера всё равно открывает инструменты разработчика, а отдельный профиль Chrome с `--auto-open-devtools-for-tabs` обходит страницу целиком.

Зачем этот шаг: блокировка `F12` намекает, что автор ждал взгляда в клиент, а ответ лежит именно в пакете.

## 2. Восстанавливаем скрипты

`GDRE Tools` (проект `gdsdecomp`) распаковывает PCK и декомпилирует байткод GDScript:

```bash
gdre_tools --headless --recover=Burmalda.pck --output=bur_out
```

Восстановление сообщает о 18 файлах и даёт читаемые `main.gd` и `wheel.gd`. Интересен `main.gd`: там логика рулетки, проверки баланса и в конце две важные вещи:

```gdscript
const _EF: = [178, 199, 143, ...]  # 151 байт
func _decode_flag() -> String:
```

`strings` по сырому `.gdc` ничего не даёт, потому что скомпилированный GDScript это контейнер `GDSC` со сжатым содержимым. Декомпиляция здесь единственный практичный путь, а версия движка в заголовке подсказывает инструменту нужный диалект байткода.

Зачем этот шаг: флаг не лежит открытым текстом, но процедура, которая его собирает, поставляется каждому игроку.

## 3. Процедура декодирования

В скрипте есть ЛКГ с четырьмя константами и побайтовое восстановление текста:

```gdscript
const _SA: = 3405691582   # 0xCAFEBABE
const _SB: = 322376503    # 0x13371337
const _LC: = 1664525
const _LA: = 1013904223

var state: int = (_SA ^ _SB) & 4294967295
for i in range(_EF.size()):
    state = (_LC * state + _LA) & 4294967295
    var kb: int = (state >> 13) & 255
    out[i] = ((_EF[i] ^ kb) - i) & 255
return out.get_string_from_utf8()
```

При переносе важны три детали:

- состояние 32-битное, поэтому на каждом шаге нужен `& 0xffffffff`; целые Python растут вместо переполнения;
- байт ключа это биты с 13 по 20 состояния, а не младший байт;
- индекс вычитается после XOR, и это легко потерять при быстром чтении.

Если всё сохранено, байты декодируются в строку UTF-8. В ней 151 байт, она начинается с `ctfcup{` и представляет собой шутливую фразу про бесконечные дэпы.

Зачем этот шаг: алгоритм самодостаточен, поэтому флаг вычисляется, не трогая ни игру, ни сервер.

## 4. Проверка

Сделаны две проверки:

1. Пакет, который отдаёт живой инстанс, побайтово совпадает с разобранным локально (`sha256 255728bebc0358f7aebe6038f25b646050316200043a2d2b34c5313cab5048e0`, `cmp` различий не находит).
2. Декодер `scripts/decode_flag.py` воспроизводит строку из `_EF` и четырёх констант, и вывод совпадает с флагом из исходного райтапа символ в символ.

```bash
python3 scripts/decode_flag.py
```

Флаг в репозитории скрыт как `ctfcup{...}`.

Зачем этот шаг: совпадение хешей доказывает, что инстанс отдаёт те же данные, а независимое декодирование доказывает, что процедура понята, а не скопирована.

## 5. Почему рулетка не нужна

Дойти до целевого баланса означало бы обыграть колесо с фиксированной последовательностью вращений и зашифрованным балансом. К флагу это не относится: `_show_flag()` только показывает панель, а текст берётся из `_decode_flag()`, то есть локально.

То же про шифрованный баланс. `_key` генерируется при старте и не покидает процесс, а `_balance_enc` и `_target_enc` замаскированы им через XOR, поэтому подмена чисел в памяти браузера откроет панель, но панель не является секретом.

Зачем этот шаг: понимание, что интерфейс это театр, удерживает работу на клиентском пакете.

## 6. Тупики

- Честно выигрывать в рулетку: последовательность фиксирована, баланс замаскирован, но флаг от этого не зависит.
- `strings` по `main.gdc`: скомпилированный байткод, читаемого ничего нет.
- Искать эндпоинт, который отдаёт флаг: инстанс отдаёт только статические файлы.
- Бороться с обработчиком `F12` внутри страницы: не нужно, работают и меню браузера, и свежий профиль.

## 7. Выводы

- Всё, что экспорт Godot в HTML5 не хочет отдавать, всё равно приходит клиенту; пакет и есть источник правды.
- Замаскированные константы это не секрет: ЛКГ, лежащий в одном файле со своим шифротекстом, это декодер, а не замок.
- Сначала формат контейнера и версия движка, потом декомпиляция; угадывание смещений отнимает больше времени, чем установка нужного инструмента.

Одним абзацем: инстанс это веб-экспорт Godot 4.4.1, поэтому вся игра вместе со скомпилированными скриптами уходит в браузер; после скачивания `Burmalda.pck` и восстановления `main.gd` через GDRE Tools локальная процедура `_decode_flag` превращает массив `_EF` из 151 байта в флаг с помощью 32-битной ЛКГ, чей байт ключа берётся из битов 13..20, и всё это воспроизводится без единого вращения рулетки.
