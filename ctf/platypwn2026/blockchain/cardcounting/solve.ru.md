# Card Counting: шесть карт из одного 32-битного числа

[English](solve.md)

## 0. Что известно и что осталось в архивах

`PlatyJack` — казино с blackjack и рулеткой; контракт начинает со 100 ETH, нужно опустить его баланс **ниже 10 ETH**. Python-бэкенд обслуживает обе игры из одного `random.Random`.

Задача отмечена решённой в итоговых данных и флаг принятым. Однако в приложенном ZIP **нет оригинального предсказателя PRNG**, трассы восстановления состояния и истории выигрышей. Поэтому здесь подробно разобраны исходный алгоритм, математическое преобразование карт, условия выплат и способ проверять гипотезу. Мы не пишем, будто исполнили солвер, которого в материалах нет.

## 1. Ошибка в dealer.py

`service/dealer.py`:

```python
rng = random.Random()

def deal_hand():
    number = rng.getrandbits(32)
    cards = []
    for _ in range(6):
        number, card = divmod(number, 52)
        cards.append(card)
    return cards

def spin_wheel():
    return rng.randrange(37)
```

На **шесть карт** выбирается только **одно** число `X` длиной 32 бита. Каждый `divmod` достаёт очередную цифру в системе счисления с основанием 52:

```text
X = c0 + 52*c1 + 52²*c2 + 52³*c3 + 52⁴*c4 + 52⁵*c5
0 <= ci <= 51
0 <= X < 2³²
```

Карты видны из `HandDealt` и `getHand(id)`. Поэтому из одной законченной раздачи можно восстановить **точное 32-битное слово генератора**, а не просто догадаться о колоде.

## 2. Какую информацию дают старшие карты

Нужные степени:

```text
52^4 =    7 311 616
52^5 =  380 204 032
52^6 = 19 770 609 664
2^32 =  4 294 967 296
```

Следовательно:

```text
c5 = floor(X / 52^5) = 0..11
```

Утверждение «последняя карта всегда 0» **неверно**: её значение ограничено 0–11, причём распределение сильно перекошено. `P(c5=0)≈8.85%`, `P(c5=11)≈2.62%`, тогда как равномерная карта из 52 значений имела бы `1/52≈1.92%`.

Шесть независимых карт хранили бы `6 log2(52)≈34.20` бит. Здесь ровно 32 бита, а значения связаны арифметически. Для восстановления слова:

```python
def recover_word(cards):
    assert len(cards) == 6 and all(0 <= c < 52 for c in cards)
    x = sum(card * (52 ** i) for i, card in enumerate(cards))
    assert x < 2**32
    return x
```

Это **точное обратное преобразование**, без перебора. Оно ещё не означает автоматического восстановления всего состояния Mersenne Twister. Для этого требуется достаточно последовательных выходов и учёт вызовов рулетки от того же PRNG.

## 3. Зачем blackjack, если он убыточен

`Chal.sol` требует за руку:

```solidity
HAND_BET = 0.005 ether;
DEALER_TIP = 0.006 ether;
MAX_HANDS = 16;
```

Покупка одной руки стоит **0.011 ETH**. За победу начисляется только `2*HAND_BET=0.010 ETH`, за ничью 0.005, за проигрыш 0. Даже при **100% побед** сам blackjack приносит игроку чистый убыток 0.001 ETH на руку.

Его ценность в задаче — **публичный источник наблюдений** за генератором через `HandDealt` и `getHand`. На каждой руке до шести цифр, но все они составляют одно целое 32-битное значение.

Порядок карт: у игрока `c0,c2,c4`, у дилера `c1,c3,c5`. Функция `score` считает туза как 11 с переводом в 1 при переборе; после двух карт останавливается при сумме от 17.

## 4. Где настоящая выплата: рулетка

Для рулетки:

- `number` от 0 до 36;
- ставка `0.1..0.5 ETH`;
- правильный результат платит `36*bet`;
- результат выбирается через **тот же** `rng.randrange(37)`.

Максимальная ставка 0.5 ETH при попадании даёт выплату 18 ETH. Из контрактного баланса на таком спине: сначала поступает 0.5 ETH, затем при `cashOut` выходит 18 ETH, чистое изменение **−17.5 ETH**. Несколько предсказанных побед позволяют опустить фонд с 100 ETH до порога задачи.

Случайно угадывать номер с шансом 1/37 — не то же самое, что восстановить состояние RNG. Нам нужен прогноз, сверяемый с реальными следующими значениями, прежде чем делать ставки.

### Важное условие: `cashOut()` ограничивает выплату остатком казны

Исходный контракт использует `amount = min(winnings[msg.sender], address(this).balance)`. Поэтому последняя выплата **не отменяется**, даже если накопленный выигрыш превосходит остаток казино: `cashOut()` перечислит все имеющиеся ETH и может обнулить контракт. При ставке 0.5 ETH пять выигрышных спинов уменьшают казну на `5 × 17.5 = 87.5 ETH` (без учёта оплаченных наблюдений за картами), оставляя примерно 12.5 ETH. Шестой спин начислит 18 ETH, но `cashOut()` выдаст только доступный остаток. Это принципиальная деталь реального механизма; историческая последовательность транзакций и восстановление состояния генератора в архиве не сохранились.

## 5. Как проверять гипотезу

Контракт публикует:

```solidity
event HandDealt(uint256 indexed id, address indexed player, uint8[6] cards, uint256 payout);
event SpinSettled(uint256 indexed id, address indexed player, uint8 result, uint256 payout);
function getHand(uint256 id) external view returns (uint8[6] memory);
function cashOut() external;
```

Проверяемая последовательность в отдельном тестовом инстансе:

1. Вызвать `play(count)` с числом рук до 16 и правильной оплатой.
2. Дождаться `HandDealt` / изменения `nextUnsettledHand`.
3. Для каждой руки вычислить `X` по формуле выше и получить полный 32-битный выход MT19937.
4. Накопить достаточно **последовательных** слов для модели состояния и учесть, что `randrange(37)` тоже потребляет генератор и может делать rejection sampling.
5. Проверить предсказание на новых ещё не использованных раздачах.
6. Только после контрольной проверки предсказывать `spin`, дожидаться `SpinSettled`, выводить `winnings` через `cashOut` и проверять `Setup.isSolved()`.

Пункты 4–6 описывают **методику воспроизведения**, а не сохранённый исторический эксплойт: полного журнала предсказаний и ставок нет. Его поиск проводится отдельно.

## 6. Независимая проверка восстановления MT19937

Теперь алгоритм прогноза подтверждён **отдельным локальным тестом**, а не только предположением о генераторе. Добавленный [`scripts/recover_mt.py`](scripts/recover_mt.py) — **новая реконструкция по исходнику**, не обнаруженный исторический эксплойт. Скрипту нужен только стандартный Python, к серверу соревнования он не подключается.

У MT19937 624 внутренних 32-битных слова. В `dealer.py` на одну руку тратится ровно один `rng.getrandbits(32)`. По **624 последовательным раздачам** сперва обращаем запись числа в системе с основанием 52, а затем снимаем четыре операции tempering генератора:

```text
y ^= y >> 11
y ^= (y << 7)  & 0x9d2c5680
y ^= (y << 15) & 0xefc60000
y ^= y >> 18
```

Полученные 624 слова образуют состояние, которое загружается через `random.Random.setstate((3, state_words + (624,), None))`. Для рулетки важно **не** подменять `randrange(37)` формулой `getrandbits(32) % 37`: Python берёт шесть бит и отбрасывает значения от 37 до 63, иногда расходуя дополнительные выходы генератора. Восстановленный объект `Random` сам учитывает этот механизм.

```bash
python3 scripts/recover_mt.py --selftest
python3 scripts/recover_mt.py --hands hands.json --predict 10
```

Файл `hands.json` содержит минимум 624 раздачи в порядке обработки, например `{"hands": [[c0,c1,c2,c3,c4,c5], ...]}`, где в настоящем файле указаны целые ID карт от 0 до 51. Тест намеренно пропускает перед сбором 137 случайных слов, после чего получает **100 правильных прогнозов из 100**. Отдельно проверен разбор JSON с десятью совпавшими прогнозами. Это результаты **новых синтетических испытаний**, не исторический лог блокчейна.

Для 624 рук можно провести 39 транзакций `play(16)`. Их суммарная начальная стоимость: `624 × 0.011 = 6.864 ETH` до учёта выплат по blackjack; наличие необходимого баланса зависит от условий стенда. Все 624 значения должны быть последовательными **в общем потоке PRNG**. Между ними нельзя пропускать вызовы рулетки или других участников; даже после сбора лишние раздачи изменяют положение генератора. Локальная математическая проверка не доказывает, что победный исторический сеанс проходил именно так.

## 7. Что подтверждено

Оригинальные `Chal.sol` и `dealer.py` однозначно показывают общую PRNG, обратимое кодирование рук, работу выплат и проверку баланса. Итоговая запись о результате подтверждает принятый флаг. **Не подтверждён отдельным архивным доказательством только конкретный путь восстановления MT-состояния и последовательность сделок**, поэтому его нельзя придумывать.

## 8. Защита и вывод

Нужно применять верифицируемую случайность, фиксировать итог до реакции игрока и не раскрывать состояние общего генератора в публичных результатах другой игры. Надёжная на вид рулетка перестаёт быть надёжной, если соседний интерфейс отдаёт полные выходы того же PRNG.
