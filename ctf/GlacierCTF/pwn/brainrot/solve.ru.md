# brainrot — эксплуатация форматной строки внутри SWEB

[English version](solve.md)

## 1. Устройство задачи

Это **brainrot**, а не **brainrot-revenge**. Организаторы выдали `bf.c`, бинарник `bf.sweb`, сжатый диск SWEB, `exe2minixfs` и `run.sh`. Гость — x86-64 SWEB под QEMU с 8 МиБ RAM; `/usr` — MinixFS, `/` — ramfs. Локальный запуск использует `-cpu qemu64,+smep`.

Удалённый сервис сначала требовал SHA-1 hashcash PoW (в архиве сохранён расчёт токена с `-mb29`), затем принимал **одну строку base64**. Внутри декодированного файла первая строка — Brainfuck-программа размером до 4096 байт, вторая — её фиктивный stdin до 16384 байт. Файл размещался в госте как `/usr/prog`, запускался `/usr/shell.sweb`.

В `bf.c` есть статические буферы `code[4097]`, `input[16384]`, `tape[30000]`, `outbuf[1024]`, `filebuf[0x18000]`. По логам статический `input` расположен на `0x08025a80`.

## 2. Уязвимость

Функция вывода содержит:

```c
static void flush_out(void)
{
  if (out_pos == 0)
    return;
  outbuf[out_pos] = '\0';
  printf(outbuf);
  out_pos = 0;
}
```

Форматная строка берётся **не из константы, а из пользовательского вывода Brainfuck**. Никаких аргументов для директив `%u`, `%c`, `%s` нет. Это CWE-134. Исправление — `printf("%s", outbuf)` или `fwrite(outbuf, 1, out_pos, stdout)`.

Интерпретатор выводит через `.`, читает через `,`, а `flush_out` вызывается при переводе строки, заполнении выходного буфера или окончании программы.

## 3. Как подаётся payload

Фактическая атака использует 1423-байтовый файл. Первая строка генерируется так:

```python
code = (b",." * 512 + b",").ljust(1280, b"Z")
```

Каждая пара `,.` копирует очередной байт фальшивого stdin на экран без изменения значения. Дополнительная `,` поглощает следующий байт, символы `Z` Brainfuck игнорирует. Когда выполнение завершается, `outbuf` передаётся `printf`.

Вторая строка (141 байт) начинается с `%0256u%0119u`, затем включает машинный код, директивы `%c`/`%s`, двоичные значения адресов, NOP-площадку и нулевой байт. После нуля находится `/usr/flag\0`: путь остаётся в глобальном `input[]`, но не входит в строку для `printf`.

Для архива подтверждены:

```text
полный payload       1423 байта
Brainfuck-строка      1280 байт
строка input           141 байт
SHA-256               745f6801de6bfacad34cdc0cd3c97fc1da2eadbc452d51983b341a2da01e941e
```

## 4. Перехват исполнения

Ключевой эффект зависит от конкретного `printf` в SWEB и устройства его стека. Поля ширины `%0256u%0119u` расширяют вывод, следующие директивы потребляют непереданные аргументы, а подготовленные литеральные байты приводят к повреждению управляющих данных стека.

В исходном payload присутствуют последовательности:

```text
47 ff ff ff ff 7f
7a ff ff ff ff 7f
```

Они соответствуют высокому диапазону адресов стека SWEB; в исторических заметках упомянут пивот на `0x7fffffffff7a`. Есть также 56-байтовая область для shellcode и NOP-площадка.

Важно: этот эксплойт **не использует `%n`**. Он опирается на вывод нужной длины и специфическое поведение форматтера/стека SWEB. Сам захват управления подтверждён успешным чтением флага. Полной пошаговой трассы падения/повреждения внутренностей `printf` в архиве нет, поэтому отдельные детали стека не выдаются за независимо воспроизведённые.

## 5. Shellcode и системные вызовы SWEB

В рабочем коде используются `int 0x80`, EAX — номер вызова, EBX/ECX/EDX — аргументы. В первоначальном отчёте агента было краткое описание ABI с ошибочно повторённым RBX; фактические байты и реконструированный солвер подтверждают **EBX, ECX, EDX**.

```text
open("/usr/flag", O_RDONLY)        eax=5, ebx=path, ecx=1
read(fd, 0x08025a80, 127)          eax=3, ebx=fd, ecx=buf, edx=127
write(1, 0x08025a80, 127)          eax=4, ebx=1, ecx=buf, edx=127
exit(0)                            eax=1, ebx=0
```

После `open` инструкция `mov ebx,eax` передаёт дескриптор на `read`, поэтому его номер не угадывается. Буфер `input[]` уже отображён в процессе. Выводится 127 байт фиксированной длины, так что после текста флага могут оказаться лишние байты.

В прежнем чате локально получали тестовую строку `gctf{LOCAL_TEST_SUCCESS}` из `/tmp/flag`. Это отдельно от настоящего соревновательного флага.

## 6. Удалённый результат

Порядок был следующим:

```text
TCP → challs.glacierctf.com:13370
получение параметров hashcash и уникального resource
локальный подбор токена для 29 нулевых бит SHA-1
отправка токена
приглашение "program> "
отправка base64(двухстрочный payload)
получение debug-console SWEB и флага
```

Сохранённый `brainrot_remote.log` начинается так:

```text
[*] Proof of Work passed
=== brainrot ===
Send your Brainfuck program as ONE base64 line:
  line 1 = Brainfuck code, line 2 = fake stdin (base64 the whole file).
program> [*] booting SWEB (debug console follows; grep for the flag)...
```

В том же логе размером **21 273 байта** найден флаг `gctf{...}` со смещением 18894. Позже SWEB сообщает о нарушении assert в `File::~File` при размонтировании файловой системы и переходит в kernel panic. **Флаг уже выведен**, поэтому сбой при завершении сессии не опровергает успех.

Отдельного скриншота принятия флага платформой нет. Не смешиваем это с достоверно сохранённым ответом удалённого сервиса.

## 7. Исходные материалы и воспроизведение

В частном архиве `glacierctf_brainrot_materials.zip` находятся оригинальный handout, окончательный payload (1423 байта), удалённый лог (21 273 байта), `hc.c`, реконструированный `brainrot_solve_reconstructed.py` и восстановленный локальный QEMU-скрипт. Оригинальный `brainrot_solve.py` потерян, поэтому реконструкция прямо помечена как реконструкция.

В публичном репозитории генератор payload работает **офлайн**. Он не подключается к старому сервису и не выдаётся за заново проверенный удалённый солвер.

Историческая локальная схема: распаковать `brainrot.vmdk.gz`, скопировать образ, выполнить `exe2minixfs <disk> 10321920 <payload> prog`, затем загрузить QEMU через `run.sh`. Эти шаги описаны по логу и отчёту; при написании данного текста бинарник не запускался.

## 8. Вывод

- Учебная ОС не исправляет ошибки в приложениях, которые в ней работают.
- Безопасный tape Brainfuck не спасает от `printf(user_text)`.
- Для эксплуатации важно учитывать реализацию форматтера и стек именно SWEB, а не переносить механизмы glibc вслепую.
- При анализе нужно различать фактический файл, реконструированный солвер и подтверждённый результат удалённой сессии.
