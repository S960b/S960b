# Fortune Teller - writeup (pwn, format string)

## Знакомство с задачей

Нам выдали архив `fortune_teller_public.zip`. Первым делом распаковал и посмотрел, что внутри:

```bash
unzip fortune_teller_public.zip
ls -la
```

Внутри три файла: `chall.c` (исходник), `fortune` (ELF x86-64), `README.md`. Прочитал README - там сказано, какие включены защиты: Full RELRO, stack canary, NX, PIE. Это значит: перезапись GOT не пройдёт (RELRO), вставлять шеллкод в стек нельзя (NX), адреса функций в рантайме плавают (PIE). Запомнил это, но не стал зацикливаться - сначала читаем код.

## Как мы нашли уязвимость (анализ, а не диагноз)

Открыл `chall.c` и читал его по функциям, без спешки. Меню: спросить у оракула (1), получить благословение (2), выйти (3). Функция `ask_oracle()`:

```c
void ask_oracle() {
    char question[256];
    read_line(question, 256);
    printf(question);
}
```

Вот тут я остановился. `printf` вызывается с ОДНИМ аргументом - и этим аргументом является мой ввод. А по своей сути `printf` - это функция с формат-строкой: первый аргумент описывает, что печатать, а остальные - значения, которые подставляются. Если я введу `%p`, printf попытается напечатать «очередной аргумент» - которого ему не передали. Он возьмёт его из того места, откуда функция достаёт аргументы, то есть со стека. А ещё есть спецификатор `%n`, который не печатает, а ЗАПИСЫВАЕТ число уже выведенных символов по адресу из аргумента.

Это не какая-то новая магия - это классическая уязвимость «format string» (формат-строка). Я раньше с ней сталкивался: пользовательский ввод нельзя передавать в printf как формат. Если бы я не помнил - достаточно погуглить «printf user input format string vulnerability», это одна из базовых тем по pwn.

Гипотезу проверил сразу: запустил бинарь локально и ввёл `%p` в качестве вопроса. Сервис напечатал указатель - то есть формат-строка реально работает, и это не теория, а факт, который видно глазами.

## Что нам нужно сделать, чтобы получить флаг

Раз есть примитив чтения/записи - надо понять, что записывать и куда. Читаю исходник дальше. Вижу `receive_blessing()`: она вызывает `win()`, но только при условии

```c
if (blessing == 0x1337) { win(); }
```

А `win()` печатает `flag.txt`. То есть вся цепочка: записать в глобальную переменную `blessing` значение `0x1337` - нажать menu 2 - получить флаг. Никакого переполнения буфера, никакого ROP - просто аккуратная запись в одну переменную.

## Как мы узнали адреса (инструменты)

Бинарь с PIE, значит абсолютные адреса в рантайме = база + смещение. Смещения символов смотрим утилитой `nm`:

```bash
nm -n fortune
```

Интересные строки из вывода:

```text
00000000000012a9 t win
00000000000014ff t receive_blessing
000000000000404c B blessing
0000000000003d68 d .fini_array
```

- `win` на смещении 0x12a9,
- глобальный `blessing` - в секции B (неинициализированные данные) на 0x404c,
- `.fini_array` на 0x3d68 (пригодится позже для лика базы).

Для надёжности заглянул и в дизассемблер (`objdump -d fortune` / gdb), чтобы убедиться, что `win()` действительно открывает flag.txt, а не что-то другое - да, там fopen/чтение файла. Факты подтверждены двумя инструментами, а не взяты из воздуха.

## Почему буфер стал «таблицей аргументов» printf

Ключевой вопрос: как формат-строка добирается до НАШИХ данных? Отвечаю по шагам, как я это понял:

1. `char question[256]` - это локальная переменная функции `ask_oracle()`. Локальные переменные в C лежат на стеке. Не в куче, не в глобальной памяти - именно на стеке, рядом с адресом возврата.
2. `printf` берёт свои аргументы так: первые 6 - из регистров, все остальные - со стека. У нас у printf реально передан только один аргумент (формат-строка). Значит всё, что он читает через `%2$p`, `%3$p` и дальше, он читает со стека.
3. А на стеке в этот момент лежит наш буфер `question`. Получается, printf при разборе `%N$p` гуляет прямо по нашему вводу. Если я положу в начало буфера байты `ABCDEFGH`, то `%6$p` должен напечатать их как qword.

Это была гипотеза - проверил экспериментом. Написал короткий python-скрипт: подключается к сервису, отправляет вопрос `ABCDEFGH` + `%6$p`, печатает ответ. Увидел `0x4847464544434241` - это ровно `ABCDEFGH` в little-endian (буква A = 0x41, H = 0x48, идут задом наперёд). Гипотеза подтвердилась: первые 8 байт буфера видны как аргумент 6, следующие 8 байт - аргумент 7, и так далее.

```text
buffer[0..7]   - arg 6
buffer[8..15]  - arg 7
buffer[16..23] - arg 8
...
```

Это и есть фундамент всего эксплойта: мы контролируем «аргументы» printf.

## Как мы узнали базу PIE (лик)

Теперь нужно понять, где в памяти лежит бинарь (база PIE), чтобы вычислить адрес `blessing`. План: найти в стеке указатель, который ведёт внутрь нашего ELF.

Скриптом прогнал подряд `%6$p`, `%7$p`, ..., `%72$p` и собрал все напечатанные значения. Несколько из них попали в диапазон 0x55..-0x56.. - это типичный диапазон адресов бинаря под Linux (в отличие от libc, который живёт выше, 0x7f..). Теперь важный трюк: у PIE-бинаря младшие 12 бит адреса равны младшим 12 битам смещения (база выровнена по странице 0x1000). Поэтому я сравнил младшие 12 бит каждого подозрительного указателя с известными смещениями символов:

```text
0x...d68  = .fini_array (0x3d68)  - нашлось в 4 аргументах
0x...441  = return-site в read_choice (0x1441)
0x...664  = return-site в main (0x1664)
0x...570  = указатель на текст main (0x1570)
0x...1c0  = _start (0x11c0)
```

Совпадение младших бит - сильный признак, что это указатели на наш бинарь. Дальше для каждого такого указателя вычислил кандидата в базу: `base = указатель - смещение`. Правильная база обязана быть выровнена по 0x1000 (младшие 12 бит = 0). И главное: у ВСЕХ девяти указателей получилась ОДНА И ТА ЖЕ база. Девять независимых указателей не могут случайно сойтись в одну точку - база найдена. Это делал скрипт: перебирает аргументы, собирает кандидатов, считает совпадения, выбирает самого подтверждённого.

## Как мы узнали, через какой аргумент писать (слот записи)

Для записи `%N$hn` потребуется, чтобы в аргументе N лежал адрес `blessing`. Мы уже знаем раскладку «смещение буфера - аргумент», но проверить её на целевом адресе нельзя (он бинарный, обрежет строку). Поэтому сделал так: положил в буфер на смещение 16 известный маркер-число (qword `0x4b4a494847464544` - просто байты "DEFGHIJK") и скриптом перебрал `%6$p`..`%18$p` - какой аргумент напечатает ровно маркер. Напечатал `%8$p` - значит байты на смещении 16 попадают в аргумент 8.

Вывод: если положить на смещение 16 адрес blessing, то `%8$hn` запишет по этому адресу. Слот найден.

## Финальный шаг: пишем 0x1337

Спецификатор `%hn` пишет 16-битное число, равное количеству символов, которые printf уже вывел. Нам нужно записать 0x1337 = 4919. Значит: сначала заставляем printf вывести 4919 символов, потом вызываем `%8$hn`.

`%4919c` печатает 4919 пробелов (ширина поля). Дальше `%8$hn`. Собираем payload:

```python
fmt = b"%4919c%8$hn"                      # 4919 пробелов, потом запись
payload = fmt + b"\x00" * (16 - len(fmt)) # добить до 16 байт нулями
payload += struct.pack("<Q", blessing)    # и адрес на смещении 16
```

Почему нули: printf обрывает разбор строки на первом `\0`. Но к этому моменту спецификаторы уже отработали - запись произошла до обрыва. Адрес на смещении 16 как раз попадёт в аргумент 8.

Про старшие байты: `blessing` - глобальная переменная, при старте программы она нулевая (секция B). Значит старшие 2 байта уже 0, `%hn` (2 байта) полностью решает задачу.

Отправляем payload как вопрос, затем menu 2. Сервис отвечает "The stars are aligned." и печатает флаг.

## Что я пробовал сначала (dead ends)

1. **Фиксированные индексы для лика и записи.** Первый вариант скрипта использовал конкретный `%34$p` как лик и arg 8 для записи. На том инстансе, где я это тестировал, сработало. Но я задумался: раскладка аргументов на стеке - это дело случая конкретной сессии, а ASLR меняет базу при каждом подключении. Если инстанс или версия бинаря чуть другие - `%34$p` может оказаться мусором. Поэтому переписал скрипт так, чтобы он каждый запуск заново сканировал аргументы и сам находил базу и слот (это и есть итоговый solve.py). Тупиковая ветка с фиксированным `%34$p` осталась только как repro.py для локальных прогонов.
2. **Перезапись GOT ради `system`.** Подумал: может, переписать какую-нибудь запись GOT на system и получить исполнение команд? Быстро отбросил: Full RELRO делает GOT read-only, а главное - нам это не нужно. Цель - простая записываемая переменная, один `%hn` достаточен.
3. **Каскад `%hhn` по байтам.** В сложных формат-строковых задачах пишут по одному байту несколько раз. Здесь не понадобилось: значение 0x1337 влезает в 2 байта, а старшие и так нулевые.

## Итоговые скрипты

- `scripts/solve.py` - рабочий эксплойт, которым брали флаг. Что он делает по шагам:
  - `find_pie_base()` - шлёт `%N$p` для N = 6..72, ловит указатели в диапазон ELF, сравнивает младшие 12 бит с известными смещениями, выбирает базу по числу совпадений;
  - `find_write_arg()` - кладёт маркер на смещение 16, ищет `%N$p`, который его печатает (находит arg 8);
  - `run()` - считает `blessing = base + 0x404c`, шлёт `%4919c%8$hn` + адрес, жмёт menu 2 и печатает ответ.
  - Запуск: `python3 solve.py` (remote) или `python3 solve.py ./fortune` (локальный бинарь).
- `scripts/repro.py` - упрощённый вариант с фиксированными `%34$p`/`%8$hn` для быстрого локального воспроизведения, когда раскладка заведомо та же.

Примечание: в адресе `blessing` не должно быть байта перевода строки (0x0a), потому что `read_line()` на нём останавливается. ASLR рандомизирует базу при каждом подключении, поэтому скрипт просто повторяет попытки, пока адрес не окажется чистым.

## Версия в один абзац

Мы прочитали исходник и заметили, что `printf(question)` передаёт пользовательский ввод как формат-строку - классическая format string уязвимость. Рядом в коде нашли цель: `win()` печатает флаг, но только если глобальная переменная `blessing` равна 0x1337. Так как буфер вопроса лежит на стеке, printf читает его байты как свои аргументы - мы проверили это, положив в буфер известные байты и увидев их через `%N$p`. Скриптом просканировали аргументы, нашли указатели на бинарь и по совпадению младших 12 бит со смещениями символов (nm) восстановили базу PIE; маркером нашли, что через `%8$hn` можно писать по адресу из буфера. Положили туда `blessing = base + 0x404c`, вывели `%4919c` (4919 символов) и записали `%8$hn` значение 0x1337, затем нажали menu 2 - сервис вызвал `win()` и напечатал флаг.

## Уроки

1. Начинай с чтения исходника, а не с поиска эксплойта: подозрительное место (ввод в printf) находится глазами, а цель (win + условие) - рядом в коде.
2. Любую гипотезу подтверждай экспериментом: ввёл `%p` - увидел лик; положил `ABCDEFGH` - увидел `0x4847464544434241`. Формат-строка доказана, а не постулирована.
3. Смещения символов - через `nm`, защищённость - через README/checksec. Два инструмента для одного факта - нормальная практика.
4. Помни, откуда printf берёт аргументы (регистры, потом стек): локальный буфер на стеке автоматически становится таблицей аргументов - это не магия, а механика вызова.
5. При PIE база восстанавливается по совпадению младших 12 бит указателей с известными смещениями + выравниванию кандидата по 0x1000; девять совпавших указателей - это уже не случайность.
6. `%hn` пишет счётчик выведенных символов, а не «значение из аргумента»: управляй шириной (`%4919c`), и запись сама станет нужным числом.
7. NUL в payload не страшен: printf обрывается на нём, но спецификаторы к этому моменту уже отработали - адреса смело клади в хвост.
