# End of Life - writeup (pwn, 16-битный DOS, переполнение стека)

## Знакомство с задачей

Описание задачи: "MS Windows 10 has reached its (endoflife.date), but MS DOS is still going strong" (Windows 10 доживает последние дни, а MS DOS до сих пор работает).

Распаковал архив. Внутри четыре файла:

- `CHALL.CPP` - исходник программы на C (Borland C++ 3.0, старый компилятор для DOS)
- `CHALL.EXE` - скомпилированная 16-битная DOS-программа (14 КиБ)
- `RUN.BAT` - командный файл, который просто запускает CHALL.EXE
- `server.py` - сервер, который крутит эту программу на удалённой стороне

Первым делом я прочитал `server.py` - это спецификация того, как работает задача. Он делает вот что:

1. Принимает одну строку: наш файл, закодированный в base64.
2. Создаёт временную папку внутри `./run`.
3. Копирует туда секретный `flag.txt` (переименовав в `FLAG.TXT`), плюс `RUN.BAT` и `CHALL.EXE`.
4. Декодирует нашу base64-строку и записывает как `INPUT.TXT` в ту же папку.
5. Запускает эмулятор DOS: `dosbox -c "MOUNT C <папка>" -c "C:\RUN.BAT"` (то есть DOS-программа видит эту папку как диск C:).
6. Если программа создала файл `OUTPUT.TXT` - сервер возвращает его содержимое в base64. Если нет - пишет "Program did not produce OUTPUT.TXT".

Ключевые выводы из этого:

- Секретный флаг лежит рядом с нашей программой на диске C:, как обычный файл `FLAG.TXT`.
- Единственный способ вытащить данные наружу - заставить программу записать что-то в `OUTPUT.TXT`.
- На всё про всё сервер даёт 10 секунд (`signal.alarm(10)`).

## Чтение исходника: ищем, где программа может ошибиться

`CHALL.CPP` короткий, читается за минуту. Главное - две функции.

Первая, `check_input()`, проверяет входной файл:

```c
int check_input() {
    FILE* input = fopen("input.txt", "rt");   // открыли в ТЕКСТОВОМ режиме
    ...
    while ((c = fgetc(input)) != EOF) {
        if (c < 'a' || c > 'z') return 0;      // только строчные буквы
        if (length >= 16) return 0;            // и не больше 16 штук
    }
    ...
}
```

Вторая, `process_input()`, обрабатывает тот же файл:

```c
void process_input() {
    FILE* input = fopen("input.txt", "rb");   // открыли в БИНАРНОМ режиме
    FILE* output = fopen("output.txt", "wb");
    char name[17];                            // буфер на 17 байт
    fscanf(input, "%[^ ]s", name);            // читаем "слово" в буфер
    fprintf(output, "%d\n", strlen(name));    // печатаем длину
}
```

Смотрите, что я заметил: одна и та же программа открывает ОДИН И ТОТ ЖЕ файл ДВАЖДЫ - один раз как текст (`"rt"`), второй раз как бинарь (`"rb"`). Это редко бывает просто так. Я задался вопросом: а эти два режима вообще эквивалентны? Не может ли быть, что одна функция увидит файл одним образом, а другая - другим?

## Баг 1: текстовый и бинарный режимы по-разному видят байт 0x1A

Я вспомнил, что в старых DOS-системах текстовые файлы имели особенности, и решил проверить. Погуглил "fopen text mode binary mode difference" и нашёл документацию:

- cppreference, fopen: https://en.cppreference.com/c/io/fopen - там написано, что в текстовом режиме `fgetc` читает по одному символу и "на некоторых системах байт 0x1A (Ctrl-Z, символ конца файла DOS) рассматривается как конец файла";
- Stack Overflow, "Difference between files written in binary and text mode": https://stackoverflow.com/questions/229924 - там прямо сказано, что при чтении в текстовом режиме DOS-библиотеки останавливаются на Ctrl-Z (символ 26 = 0x1A), а в бинарном - читают его как обычный байт.

Вот он, логический мостик: `check_input()` открывает файл как текст и потому ОСТАНОВИТСЯ на первом байте 0x1A, решив, что файл закончился. А `process_input()` открывает тот же файл как бинарь и спокойно читает всё, включая байты ПОСЛЕ 0x1A.

Что это даёт? Проверка (`check_input`) видит только кусок до 0x1A, а обработчик (`process_input`) - весь файл. Если я положу в начало 16 строчных букв (чтобы проверка пропустила), потом байт 0x1A, а потом что угодно - проверка пропустит файл, а обработчик прочитает и мой хвост.

## Баг 2: fscanf читает в буфер без ограничения длины

Теперь смотрю на `process_input()`: `fscanf(input, "%[^ ]s", name)`.

Что такое `%[^ ]`? Это спецификатор "набора символов" (scanset) из scanf-семейства. Квадратные скобки задают набор разрешённых символов, а `^` в начале означает отрицание: "любой символ, КРОМЕ перечисленных". То есть `%[^ ]` читает символы, пока не встретит ПРОБЕЛ (0x20). Документация: cppreference, fscanf: https://en.cppreference.com/w/c/io/fscanf (раздел про scanset).

Важные следствия:

- Ограничения длины в формате НЕТ (не `%16[^ ]`), а буфер `name` всего 17 байт. Значит, если во входном файле "слово" длиннее 17 символов, `fscanf` запишет его целиком и выйдет за границы буфера в память дальше - переполнение стека.
- Останавливает чтение ТОЛЬКО пробел. Байты 0x00 (NUL), перевод строки, всё остальное - просто копируются в буфер.

Вот и схема атаки: 16 букв + 0x1A + хвост без пробелов. Проверка пропускает (видит 16 букв, потом "конец файла"), обработчик читает всё, и хвост переполняет `name[17]`. В хвосте нельзя использовать только пробел.

## Эксперимент: проверяю, какие байты реально доходят (по шагам)

Прежде чем строить эксплойт, я убедился на практике, как программа обращается с разными байтами. Эксперимент простой: программа печатает в OUTPUT.TXT длину прочитанного слова (`strlen`), так что по числу видно, где остановился `fscanf` и что дошло.

Делал так, по шагам:

1. Создал папку, положил в неё `CHALL.EXE` и `RUN.BAT`.
2. Создал в ней `INPUT.TXT` с нужными байтами.
3. Запустил DOSBox с той же командой, что и сервер: `dosbox -c "MOUNT C ." -c "C:\RUN.BAT"`. Так как у меня нет прав root, DOSBox я поставил без root: скачал .deb-пакеты и распаковал их в свою папку (`apt-get download`, `dpkg-deb -x`), запускаю с переменными окружения `LD_LIBRARY_PATH=... SDL_VIDEODRIVER=dummy SDL_AUDIODRIVER=dummy`.
4. Открыл `OUTPUT.TXT` и посмотрел, что напечатано.

Проба 1: INPUT.TXT = `aaaa` + байт 0x1A + `BBBB`. Проверка видит `aaaa` (4 буквы, потом "конец файла") и пропускает. Обработчик в бинарном режиме читает `aaaa` + 0x1A + `BBBB` - 9 байт до пробела/конца. OUTPUT.TXT = `5`? Нет, на самом деле вывод был `9` - то есть `fscanf` прочитал всё 9 байт. Это подтверждает баг 1: 0x1A не остановил обработчика.

Проба 2 (NUL): INPUT.TXT = `aaaa` + 0x1A + байт 0x00 + `BBBB`. OUTPUT.TXT = `5`. Вывод: NUL ДОХОДИТ до буфера (иначе длина была бы 9), и он обрывает C-строку (`strlen` считает до первого нуля) - то есть NUL можно использовать в payload, но он закончит строку.

Проба 3 (перевод строки): INPUT.TXT = `aaaa` + 0x1A + 0x0A + `BBBB`. OUTPUT.TXT = `10` - LF дошёл и НЕ остановил чтение.

Проба 4 (пробел): INPUT.TXT = `abc` + 0x1A + ` def`. OUTPUT.TXT = `4` - fscanf остановился на пробеле (прочитал `abc` + 0x1A = 4 байта).

Выводы для payload: 0x1A - разделитель для проверки; 0x00 доставляется (и обрывает строку); LF доставляется; 0x20 (пробел) - единственный запрещённый байт.

## Что такое стековый кадр (объяснение для новичка)

Чтобы понять, куда именно переполняется буфер, надо знать, как программа раскладывает локальные переменные.

Когда функция в C вызывается, процессор использует стек - область памяти, которая растёт "вниз". Для каждой вызванной функции на стеке выделяется блок - стековый кадр - в котором лежат: адрес возврата (куда вернуться после завершения функции), сохранённый указатель кадра, и локальные переменные. В 16-битных программах обычно два регистра указывают на кадр: BP (base pointer - начало кадра) и SP (stack pointer - вершина стека). Локальные переменные лежат по отрицательным смещениям от BP.

"Разметить кадр" - значит выяснить, где именно относительно BP лежит каждая локальная переменная (и адрес возврата). Это нужно, чтобы понять, сколько байт переполнения потребуется, чтобы дойти от буфера до адреса возврата.

Чем я размечал: дизассемблером. Дизассемблер - это инструмент, который превращает машинные байты программы обратно в инструкции ассемблера. Я использовал `ndisasm` (из пакета nasm): сначала выяснил, что MZ-заголовок у этого файла 512 байт, и запустил `ndisasm -b16 -e512 CHALL.EXE` (пропустить заголовок, разбирать как 16-битный код). В разобранной `process_input` я увидел:

```text
push bp              ; сохранить старый BP
mov bp, sp           ; BP = начало нашего кадра
sub sp, 0x12         ; выделить 18 байт под локальные переменные
...
lea ax, [bp-0x12]    ; вычислить адрес name
push ax
push 0xD2            ; адрес строки "%[^ ]s"
push si              ; FILE* input
call fscanf
...
```

Инструкция `lea ax, [bp-0x12]` - это ключ: она вычисляет адрес буфера `name`. Значит `name` лежит на 18 байт ниже начала кадра, то есть `name` занимает `[bp-0x12] .. [bp-0x12+17]`. Сразу за ним (выше по стеку): сохранённый BP на `[bp]` (2 байта), а адрес возврата на `[bp+2]` (2 байта). Итого от начала `name` до адреса возврата - 20 байт (0x12 = 18 + 2). Значит, если записать в `name` больше 17 байт, 18-й и 19-й байты затрут сохранённый BP, а 20-й и 21-й - адрес возврата.

Ещё один важный факт я узнал про эту программу: у неё необычный стек. В MZ-заголовке указан свой сегмент стека, но Borland-рантайм при старте делает явный переключатель: `mov ss,dx; mov sp,di`, где DX = сегмент данных (DGROUP). То есть в рантайме стек лежит В ТОМ ЖЕ сегменте, что и данные (`SS == DS`). Это потом окажется ключевым для эксплойта.

## Как я узнал BP и SS без отладчика

Чтобы точно посчитать адреса в payload, мне нужны были живые значения двух регистров в момент вызова `process_input`: BP (начало кадра) и SS (сегмент стека).

Отладчика под DOSBox у меня не было (а тот, что был - не скриптовался). Я пошёл обходным путём: заставил САМУ ПРОГРАММУ напечатать эти регистры. В конце `process_input` стоит `fprintf(output, "%d\n", strlen(name))` - то есть в стек перед вызовом пушится результат `strlen`. В машинных байтах это инструкция `push ax` (код 0x50), она находится на смещении 512+0x32F в файле (0x32F - смещение внутри кода, 512 - размер MZ-заголовка).

Как патчил: простым скриптом на Python - прочитал файл как байты, заменил ОДИН байт на нужном смещении, записал новую копию. Никаких сложных инструментов не нужно. Две копии:

- `CHALL_BP.EXE` - заменил 0x50 на 0x55 (`push bp`): теперь fprintf печатает BP вместо длины
- `CHALL_SS.EXE` - заменил 0x50 на 0x16 (`push ss`): теперь печатает SS

Запустил каждую в DOSBox с INPUT.TXT = `hello`, прочитал OUTPUT.TXT. Число там знаковое десятичное, привожу к 16 битам через `& 0xFFFF`:

```text
CHALL_BP: -14   = 0xFFF2
CHALL_SS:  993  = 0x03E1
```

Важно: эти патченые копии нужны только для измерений. На сервер они никогда не уходят - там работает оригинальный CHALL.EXE, а простое число BP используется для расчёта payload.

## Эксплойт: как переполнение превратить в выполнение кода

Теперь главное. У нас есть переполнение, которое затирает адрес возврата. Когда функция завершается, инструкция `ret` забирает со стека адрес возврата и прыгает на него. Если мы записали туда своё значение - мы управляем, куда прыгнет программа.

Но тут есть тонкость 16-битной архитектуры: адрес в DOS состоит из ДВУХ частей - сегмента и смещения (CS:IP). Обычный `ret` (near return) прыгает ТОЛЬКО в пределах того же сегмента кода: он берёт со стека 2 байта и кладёт их в IP, а CS оставляет как был. А есть `retf` (far return) - он берёт со стека 4 байта и загружает и IP, и CS, то есть может прыгнуть в ДРУГОЙ сегмент.

Почему near return не годится: наш шеллкод лежит на стеке, а стек (мы выяснили) находится в сегменте данных DGROUP. Смещение внутри этого сегмента считается от начала DGROUP, и при высоко расположенном стеке это число близко к 0xFFFF или больше. IP у нас 16-битный, максимум 0xFFFF, поэтому адрес "заворачивается" - переполняется и превращается в маленькое число, мимо нашего кода. Простыми словами: near-`ret` может прыгнуть только "внутри" текущего 64-килобайтного окна кода, а наш код лежит в другом окне - он туда физически не дотягивается.

А `retf` умеет прыгать в другой сегмент: мы сами задаём и CS (= SS = 0x3E1, сегмент стека), и IP (смещение шеллкода). Так что план: записать в адрес возврата адрес существующей в программе инструкции `retf`, а сразу за ней - наши значения CS и IP.

В файле CHALL.EXE есть готовые `retf`-инструкции (машинный код CB) - я нашёл их поиском по байтам: на смещениях 0x986, 0x1141, 0x14DC. Возьмём 0x986.

Что такое "позиционно-независимый код"? Это код, который одинаково работает, где бы его ни загрузили: он не использует жёсткие адреса, а вычисляет своё положение на лету. Первая инструкция нашего шеллкода - `call $+5; pop si`: `call` (короткий, 2 байта) прыгает на следующую инструкцию, положив на стек адрес этой самой следующей инструкции, а `pop si` забирает его в регистр SI. Теперь SI = адрес, где мы находимся в памяти, и все обращения к строкам идут как "SI + смещение". Поэтому мне не нужно знать заранее, по какому адресу ляжет шеллкод - он сам себя найдёт.

Шеллкод делает ровно то, что сделала бы DOS-команда "скопировать FLAG.TXT в OUTPUT.TXT", только через системные вызовы INT 21h:

1. Открыть `FLAG.TXT` (INT 21h, функция 3Dh)
2. Прочитать до 256 байт (3Fh)
3. Создать `OUTPUT.TXT` (3Ch)
4. Записать туда прочитанное (40h)
5. Закрыть (3Eh), выйти (4Ch)

Строки "FLAG.TXT" и "OUTPUT.TXT" лежат сразу после кода, адресуются через SI+смещение. И ни одного байта 0x20 (пробела) во всём payload, иначе fscanf остановится раньше времени - это я проверил скриптом.

Полная раскладка payload (INPUT.TXT):

```text
байты 0..15    'a' x 16          проходят проверку (16 букв)
байт 16        0x1A              разделитель: проверка останавливается
байт 17        'Z'               заполнение
байты 18..19   'QQ'              портим сохранённый BP (не важно, что там)
байты 20..21   0x86 0x09         адрес возврата = retf-гаджет (0x986, little-endian)
байты 22..23   младшие 2 байта IP шеллкода (считается от BP)
байты 24..25   0xE1 0x03         CS = SS = 0x3E1
байты 26..31   'Z' x 6           заполнение до шеллкода
байт 32 и далее                 сам шеллкод
```

Смещение шеллкода считал так: `name` начинается на `[bp-0x12]`, шеллкод начинается на `where=32` байт от начала переполнения, значит его адрес = `bp - 0x12 + 32` = `0xFFF2 - 0x12 + 32 = 0x10000 - 0x12 + 32`... на самом деле `0xFFF2 - 0x12 + 32 = 0x10010`, что обрезается до 16 бит = `0x0010`? Нет, стоп: 0xFFF2 - 0x12 = 0xFFE0, +32 = 0x10000, то есть ровно 0x10000, обрезается до 0x0000. Да, формально IP оборачивается в 0. И тем не менее шеллкод ВЫПОЛНЯЕТСЯ корректно - я проверил многократно, результат детерминированный. Это странное место: модель "линейный адрес = сегмент*16 + смещение" объясняет это тем, что при таком обороте мы всё равно попадаем на тот же линейный байт. Я не стал это досконально объяснять - эмпирика надёжнее теории, а цепочка работает стабильно.

## Локальная проверка: по шагам

Прежде чем идти на сервер, я проверил всё локально, шаг за шагом:

1. Создал тестовую папку.
2. Положил в неё оригинальный `CHALL.EXE`, `RUN.BAT`, собранный `INPUT.TXT` (payload).
3. Положил рядом синтетический флаг: файл `FLAG.TXT` с содержимым `FortID{LOCAL_SYNTHETIC_dos_7e21}` - так же, как это делает сервер.
4. Запустил DOSBox той же командой, что и сервер: `dosbox -c "MOUNT C ." -c "C:\RUN.BAT"`.
5. Открыл `OUTPUT.TXT`.

Результат: `OUTPUT.TXT` = `FortID{LOCAL_SYNTHETIC_dos_7e21}` - точная копия флага. Шеллкод сработал, прочитал FLAG.TXT и записал его в OUTPUT.TXT.

Потом негативный контроль - те же шаги, но БЕЗ файла FLAG.TXT. `OUTPUT.TXT` получился ПУСТЫМ. Это важно: значит, надпись в OUTPUT.TXT - не случайный мусор и не "фантом", а результат именно чтения файла. Если бы шеллкод писал что-то всегда, пустого вывода бы не было.

И финальная локальная проверка - весь цикл через НАСТОЯЩИЙ server.py с платформы (я лишь заменил в нём путь к dosbox на локальный, потому что мой dosbox стоит без root в /tmp):

1. Положил `server.py`, `CHALL.EXE`, `RUN.BAT` в папку, создал там `flag.txt` с синтетическим флагом.
2. Запустил сервер, отправил ему base64(payload) одной строкой.
3. Сервер ответил `Your OUTPUT.TXT: <base64>`.
4. Декодировал - получил синтетический флаг.

Цепочка доказана локально целиком.

## Remote

Запускаем ту же нагрузку на удалённом инстансе (`end-of-life-<...>.inst20.ctf.fortid.com:1337`, TLS). Скрипт-клиент подключается, отправляет base64(payload), получает ответ. Сервер ответил `Your OUTPUT.TXT: <base64>`, декодировал - флаг: `FortID{3oF_15_JU57_4_5u993571On_<хэш>}` (в этом райтапе замаскирован).

## Что я пробовал сначала (тупики)

1. **Думал, что это формат-строка.** При больших переполнениях (250+ байт) OUTPUT.TXT начинал эхоить мои байты по странному закону (длина вывода = N-249, печать начинается со смещения 197). Я посадил в эти места безобидные маркеры `%c`/`%x`: они НЕ раскрылись, значит это не формат-строка, а порча внутренностей структуры FILE (её буфер/поля длины) - fprintf просто печатал сырые байты. Это важный отрицательный результат: он отвёл меня от записей через `%n`.

2. **Прямой near-return в шеллкод.** Логичный первый вариант - просто записать в адрес возврата адрес шеллкода. Но near-`ret` не может прыгнуть в другой сегмент (а стек в сегменте данных), и из-за оборота 16-битного адреса он никогда не попадал в код. Сотни прогонов с разными значениями BP - ноль попаданий. Именно это подтолкнуло искать far-путь (retf).

3. **ret2code: прыжок в существующий fopen.** Можно прыгнуть не в шеллкод, а в уже существующую функцию `fopen` и скормить ей аргументы со стека. Но для точных смещений аргументов нужен числовой BP, который зависит от верха памяти (PSP:2), прочитать который в рантайме я не мог. Патч-калибровка решила ту же задачу проще.

4. **Эмулятор Unicorn как отладчик.** Пытался эмулировать 16-битный код на Unicorn, чтобы смотреть регистры. Он загрузил MZ и перехватывал INT 21h, но Borland-стартап так и не дошёл до `main` (крутился в цикле вызовов и выходил). Задокументировал как блокер; в итоге он стал не нужен - программу заставили печатать свои регистры.

## Итоговые скрипты

- `scripts/calibrate.py` - патчит CHALL.EXE (меняет один байт через Python), чтобы fprintf печатал BP или SS; запускаем в DOSBox с INPUT.TXT = hello, читаем OUTPUT.TXT, переводим & 0xFFFF. Для этой сборки: BP=0xFFF2, SS=0x3E1.
- `scripts/build_payload.py` - собирает INPUT.TXT: берёт BP и SS, перебирает позиции шеллкода и retf-гаджеты, пока не найдёт раскладку без пробела; дописывает PIC-шеллкод; пишет INPUT.TXT и INPUT.TXT.b64.
- `scripts/solve.py` - клиент: TLS, отправляет base64(payload), печатает ответ сервера и декодированный OUTPUT.TXT.

## Результат

Лог remote-прогона: сервер прислал `Enter contents for INPUT.TXT (base64):`, мы отправили одну base64-строку, сервер ответил `Running /usr/bin/dosbox ...` и `Your OUTPUT.TXT: <base64>`. Декодированное - флаг.

## Версия в один абзац

Сервер запускает наш файл как INPUT.TXT под DOSBox рядом с FLAG.TXT и возвращает base64 того, что программа записала в OUTPUT.TXT. У DOS-программы два бага: текстовый валидатор останавливается на байте 0x1A (так устроены текстовые файлы DOS - я проверил по документации), а бинарный обработчик читает весь файл, и `fscanf("%[^ ]", name[17])` не ограничивает длину и пишет в 17-байтовый буфер что угодно до пробела. После разметки стекового кадра дизассемблером (name на 18 байт ниже BP, адрес возврата на 20-м байте) и снятия BP/SS (программа сама напечатала их через одно-байтовый патч) мы переполняем адрес возврата адресом существующего `retf`-гаджета и делаем far-прыжок в позиционно-независимый 8086-шеллкод на стеке, который через INT 21h копирует FLAG.TXT в OUTPUT.TXT. Локально проверено на синтетическом флаге (плюс негативный контроль), затем тот же payload вернул флаг с реального инстанса.

## Уроки

1. Читай исходник прежде всего: `CHALL.CPP` ~50 строк, оба бага видны глазами (два разных режима fopen и fscanf без лимита).
2. Если функция открывает файл в разных режимах - это подозрительно. Текстовый режим DOS останавливается на 0x1A, бинарный нет - классический обход валидатора. Проверяй по документации, не полагайся на память.
3. Прежде чем строить payload, проверь эмпирически, какие байты доходят: один эксперимент с NUL и LF сэкономил часы.
4. Стековый кадр размечается дизассемблером: найди `lea` с отрицательным смещением от BP - это адрес локальной переменной; дальше смещения считаются арифметикой.
5. Нет отладчика - заставь программу напечатать свои регистры: одно-байтовый патч `push` превращает существующий fprintf в принтер регистров.
6. В Borland-программах рантайм сам переключает стек в сегмент данных (SS == DS). Это и открывает far-путь, и закрывает near-путь (16-битный IP не достаёт до высокого стека).
7. Near-`ret` не выходит за свой сегмент кода; для прыжка в другой сегмент нужен `retf`. Готовые `retf`-инструкции ищутся в бинаре по байту CB.
8. Позиционно-независимый код (call/pop для самоадресации) избавляет от необходимости знать адрес загрузки заранее.
9. В payload нельзя ни одного пробела, если чтение идёт через `%[^ ]`. Сканируй payload скриптом перед отправкой.
10. Негативный контроль обязателен: без FLAG.TXT вывод пуст - значит, результат не фантом.
