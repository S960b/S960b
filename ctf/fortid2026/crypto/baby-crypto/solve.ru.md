# Baby Crypto - разбор (AES-CTR с nonce = plaintext[:8], переиспользование keystream)

## Знакомство с задачей

В раздатке исходник (`chall.py`) и удалённый сервис. Сервис - «безопасный сейф»: при старте в него кладётся флаг, а игроку доступны два пункта меню:

1. `Safely Store a Secret Value` - положить свой секрет в сейф;
2. `Export Vault Data` - выгрузить весь сейф в JSON.

Задача: вытащить флаг, имея только эти две операции и исходник.

Первое, что я всегда делаю в криптозадаче с исходником: читаю его целиком и смотрю, откуда берётся случайность. Флаг защищён AES, значит интересны ключ и nonce.

## Как я читал код (на что смотреть)

- `chall.py` - это весь сервис, реверс не нужен.
- Я искал: где генерируется ключ, где генерируется nonce, переиспользуется ли nonce, влияет ли открытый текст на nonce.
- Интересная функция - класс `Cipher`:

```python
class Cipher:
    def __init__(self):
        self.key = get_random_bytes(16)

    def encrypt(self, plaintext):
        cipher = AES.new(self.key, AES.MODE_CTR, nonce=plaintext[:8])
        return cipher.encrypt(plaintext)
```

Три факта, и все три важны:

1. **Nonce - это `plaintext[:8]`** - первые 8 байт самого открытого текста, а не CSPRNG. То есть nonce выбирает вызывающий (мы, когда кладём секрет).
2. **Ключ генерируется один раз на соединение** (`Cipher()` создаётся в `Vault.__init__`) и не меняется между вставками.
3. **При старте флаг уже вставлен**: `vault.insert(FLAG)`, значит `Secret #0` в выгрузке - это шифротекст флага.

## Математика атаки (почему CTR это позволяет)

AES-CTR - потоковый режим: он генерирует keystream `KS = AES(key, nonce || counter)` и вычисляет `C = P XOR KS`. Keystream зависит только от `(key, nonce)` - **не** от открытого текста.

Если два сообщения зашифрованы одним ключом И одним nonce, keystream совпадает, и XOR двух шифротекстов уничтожает keystream:

```text
C_flag XOR C_mine = (FLAG XOR KS) XOR (MINE XOR KS) = FLAG XOR MINE
```

Значит, если заставить сервер зашифровать наше сообщение с тем же nonce, что и флаг, мы узнаём `FLAG XOR MINE`. А если мы знаем `MINE`, то восстанавливаем `FLAG = C_flag XOR C_mine XOR MINE`.

## Первые 8 байт флага

Nonce - это `plaintext[:8]`, поэтому «тот же nonce» значит: наш открытый текст должен начинаться с тех же 8 байт, что и флаг:

```python
assert FLAG.startswith("FortID{") and FLAG.endswith("}")
```

Assert в `main()` даёт первые 7 байт точно: `FortID{`. Значит, неизвестен **один** байт - `FLAG[7]`. Для каждого кандидата `g` из печатного ASCII строим:

```text
MINE = "FortID{" + chr(g) + "B" * (len(FLAG) - 8)
```

Заполнитель (`"B"` повторённый) просто выравнивает длину, чтобы шифротекст имел ту же длину, что у флага. Длина флага известна из длины `Secret #0` (CTR не добавляет паддинг).

## Как отличить попадание без угадывания

Приятная часть: критерий попадания точный, никакой эвристики «похоже на флаг» не нужно.

- Если `MINE[:8] = FLAG[:8]`, keystream'ы совпадают, значит `C_flag XOR C_mine = FLAG XOR MINE` - а так как первые 8 байт `FLAG` и `MINE` одинаковы, первые 8 байт этого XOR - **нули**.
- Если `g != FLAG[7]`, nonce разные, keystream'ы разные, и первые 8 байт XOR (почти наверняка) ненулевые.

```text
критерий: (C_flag XOR C_mine)[:8] = b"\x00" * 8   значит   g = FLAG[7]
```

После того как верный `g` найден, полный флаг:

```text
FLAG = C_flag XOR C_mine XOR MINE
```

Проверка на печатность (`flag.startswith("FortID{") ... flag.isprintable()`) - лишь санитарная проверка сверху, не основной признак.

## Ловушки (что ломает наивный скрипт)

1. **`signal.alarm(15)`** в `main()` - на всю сессию 15 секунд. Спрашивать сервер по одному кандидату (пара round-trip'ов на кандидата, ~95 кандидатов) не укладывается. Поэтому эксплойт **пайплайнит**: отправляет все команды `1\n<secret>\n` одним пакетом, затем `2\n3\n`, и разбирает финальную выгрузку один раз.

2. **`input().strip()`** обрезает секрет по краям. Кандидаты начинаются с `F`, а внутренние символы (включая возможный пробел при `g = 0x20`) не на краях - ничего не теряется. Команды всё равно надо слать построчно.

3. **TLS** (`ncat --ssl`) - скрипт оборачивает сокет в `ssl` и отключает проверку сертификата.

4. **Выгрузка JSON склеена с приглашением.** Подсказки меню печатаются **без** перевода строки, поэтому JSON склеен с `> ` в одну строку: `...Enter secret: > {"Secret #0": "..."}`. Построчный парсер молча ломается; эксплойт вытаскивает последнее совпадение `{"Secret #0":...}` регуляркой.

5. **После `3` (выход) сервер рвёт соединение**, поэтому «последний JSON в выводе» - это финальное состояние сейфа.

## Эксплойт

`scripts/solve.py` делает ровно эту цепочку:

1. Коннект по TLS, чтение баннера.
2. Отправка `2` (export), разбор `Secret #0` - шифротекста флага, получение длины `n`.
3. Построение 95 кандидатов `"FortID{" + chr(g) + "B"*(n-8)` для `g` из `32..126` (печатный ASCII).
4. Пайплайн всех вставок + export + exit одним пакетом.
5. Разбор последнего JSON сейфа.
6. Для каждого кандидата: XOR с шифротекстом флага; если первые 8 байт нулевые - nonce совпал; восстановить флаг и вывести.

Скрипт полностью параметризован (`host`, `port`, `--timeout`) и возвращает 0 при успехе. Черновик с зашитым хостом инстанса намеренно не входит в репозиторий.

## Проверка

Инстанс выдаётся платформой на время соревнования, поэтому нужен свежий хост:

```bash

```

## Тупики (что я рассматривал и отверг)

1. **Брутфорс всего флага.** Не нужен: 7 из первых 8 байт nonce известны, так что перебирается 1 байт.
2. **Bit-flipping в стиле CBC или padding oracle.** У сервиса нет расшифровки и нет паддинга; в CTR паддинга нет вообще. Оракулить нечем.
3. **Восстановление ключа.** Переиспользование nonce/keystream даёт XOR открытых текстов, а не ключ. Ключ и не нужен - нужен один переиспользованный keystream, а структура открытого текста (`FortID{...}`) даёт его напрямую.

## Версия в один абзац

Сейф шифрует каждый вставленный секрет через AES-CTR, где nonce - первые 8 байт открытого текста, а ключ фиксирован на соединение. Флаг вставлен при старте, и его первые 7 байт известны (`FortID{`). Вставив 95 кандидатов, различающихся только байтом 7, ровно один переиспользует nonce/keystream флага; точное попадание определяется как `(C_flag XOR C_mine)[:8] = 0`, а флаг вычисляется как `C_flag XOR C_mine XOR MINE`. 15-секундный alarm вынуждает один пайплайненный запрос вместо round-trip'а на кандидата.

## Уроки

1. В потоковых шифрах keystream зависит только от (key, nonce) и никогда от открытого текста - значит nonce, зависимый от plaintext, это прямой примитив переиспользования keystream.
2. Когда префикс флага закреплён assert'ом, это не флейвор-текст - он говорит, сколько байт nonce ты уже знаешь.
3. Известный префикс плюс один неизвестный байт превращает «восстановить ключ» в «восстановить один байт»; проверка нулевого XOR делает попадание точным.
4. Таймауты сервиса - часть задачи: пайплайнь запросы вместо round-trip'а на кандидата.
5. Никогда не подмешивай пользовательский открытый текст в nonce. Nonce должен браться из CSPRNG и никогда не повторяться под тем же ключом.
