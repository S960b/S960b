# Flacksafety: пять уничтоженных уровней резервирования, шестой остался

[English](solve.md)

## 0. Что за задача и почему она оказалась длинной

Условие: запись камеры наблюдения сохранилась в нескольких уровнях резервного копирования, в сеть утекли IP рабочего компьютера и `/etc/shadow` сотрудника. Нужно добиться, чтобы запись нельзя было восстановить **ни из одного backup tier**. Статус проверяет отдельный дашборд.

Это не задача «найти один файл с флагом». Здесь пришлось последовательно разбираться с Linux, паролем из Argon2id, управлением заданиями root, restic, S3 Object Lock, rclone REST, отдельными контейнерами Kubernetes, приватными репозиториями и сетевыми границами.

**Итог, подтверждённый живым дашбордом: 5 из 6 уровней уничтожены. Governance-флаг получен и принят; шестой уровень Old Rclone Remote оставался intact, второй флаг не получен.** Формулировка честная: частично решённая задача с реальным первым флагом и существенно исследованной шестой стадией.

Краткая схема инфраструктуры:

```text
                  [employee workstation]
                      SSH, resticprofile
                         |       \
                  root cron        \ backup clients
                         |          \
                         v           v
                  [backups-server]    [backups-checker]
                  S3 7070              dashboard 8080
                  REST 8000              GET /main.rs
                  offsite 8001
                  internal SFTP 2200 (loopback only)
                  /data/rclone/{workstation,workstation-legacy}
```

Адреса и действующие реквизиты конкретного инстанса в публичном тексте скрыты. Все названия файлов, пути, API и наблюдавшиеся HTTP-коды взяты из сохранённых технических журналов сеанса.

## 1. Точка входа: shadow.txt → SSH employee

Из раздатки доступен только `shadow.txt`, около 128 байт. Это **не** Docker-образ приложения и не исходники серверной инфраструктуры. Сотрудник представлен Unix-хэшем Argon2id. В ходе решения пароль был восстановлен офлайн, после чего был проверен вход `employee` по SSH на `backups-workstation`.

```text
file: fullpwn.flacksafety.zip
content: shadow.txt
hash type: Argon2id
credential: employee:<redacted>
transport: SSH on CTF workstation
```

В рабочем окружении пароль был известен и подтверждён логами. Здесь он намеренно не публикуется: дальнейшая цепочка не зависит от его буквального значения.

Важное следствие: мы получили оболочку **employee на workstation**, но не на backups-server, и не учётную запись Kubernetes-администратора.

## 2. Где появились права root: resticprofile и supercronic

На workstation найден конфигурационный файл `/etc/resticprofile/profiles.yaml` с разрешениями `rw-rw-rw-`. Это означает, что **employee может изменить файл**, который читается привилегированным планировщиком.

В профиле использовался хук `run-before`, выполняемый перед запуском резервирования. В списке задач supercronic от root было:

```text
* * * * * resticprofile root.backup
```

Схема получения root-контекста:

1. От имени employee изменить `profiles.yaml`, добавив к `base.backup` команду `run-before`.
2. Дождаться очередного запуска supercronic.
3. Команда hook выполнится от root и оставит результаты в доступном нам временном файле.
4. Проверить права на результаты и фактические значения окружения, необходимые для управления архивами.

Для диагностики в записи сохранён такой **фрагмент выполненного root hook** (без реквизитов):

```yaml
run-before:
  - 'sh -c "rm -rf /backups/* 2>/dev/null; env | sort > /tmp/rootenv; chmod 644 /tmp/rootenv; chmod -R a+rX /backups 2>/dev/null; true"'
```

Это одновременно объясняет, почему пользовательский доступ превратился в root-права и почему одну из локальных копий удалось уничтожить. Напрямую `sudo` у employee не было; уязвимость именно в **границе доверия между изменяемым YAML и root scheduler**.

## 3. Что нашли в окружении root

Содержимое `/tmp/rootenv` открыло используемые сервисами реквизиты: S3 access/secret key, `RESTIC_REST_USERNAME`, `RESTIC_REST_PASSWORD` и `RESTIC_PASSWORD`. Литеральные значения в публичный репозиторий не попадают.

На workstation находился `~/backups.txt` со схемой расположения сервисов. После этого стало понятно, что нельзя просто удалить `security_footage.mp4` с диска: за кадром есть несколько независимо проверяемых репозиториев.

Эти файлы — реальные следы локального этапа, из сохранённого технического журнала. В приложенной раздатке их **не было**; они были прочитаны с действующего CTF-стенда.

## 4. Исходник checker: шесть разных критериев успеха

Дашборд на `backups-checker:8080` предоставлял HTML и собственный Rust-исходник `GET /main.rs` (6692 байта). Это важный поворот: появилась возможность изучать **точное условие**, а не гадать, что считает «удалённой копией» интерфейс.

| № | Уровень | Проверка |
|---|---|---|
| 1 | User Local Backup | `restic` через SFTP к `/home/employee/backups` на workstation |
| 2 | Root Local Backup | `restic` через SFTP к `/backups` на workstation |
| 3 | Offsite Replica | `restic` в `/data/offsite/footage` на сервере |
| 4 | S3 Governance | версии объектов в bucket `footage` с Object Lock |
| 5 | Rclone Remote 1 | `restic` в `/data/rclone/workstation/footage` |
| 6 | Old Rclone Remote | рекурсивный `has_files("/data/rclone/workstation-legacy")` |

Для обычного restic-уровня проверка искала `security_footage.mp4` в архивах. Для S3 имело значение не только отсутствие файла в актуальной версии, но и оставшиеся **непоследние версии** объектов. Для шестого уровня проверка вообще не спрашивала пароль репозитория: там нужно физически убрать все файлы из заданного каталога.

```rust
fn has_files(dir: &Path) -> io::Result<bool> {
    for entry in fs::read_dir(dir)? {
        let entry = entry?;
        if !entry.file_type()?.is_dir() || has_files(&entry.path())? {
            return Ok(true);
        }
    }
    // ... false for empty subtree
}
```

`Ok(true)` означало `Intact`. `Ok(false)` или `NotFound` приводили к `Destroyed`. Ошибки других видов давали `Unknown`, а не `Destroyed`. Поэтому недоступность каталога или отказ в чтении не помогали выполнить цель.

## 5. Как закрыли первые пять уровней

Согласно сохранённому протоколу выполнения, были выполнены следующие действия:

- удалена исходная `~/footage/security_footage.mp4`;
- очищены/прунены доступные локальные архивы пользователя и root;
- обработана offsite-копия, где retention запускался каждые 60 секунд;
- через S3 API удалены неактуальные версии объектов с `--bypass-governance-retention`;
- очищен обычный rclone/restic репозиторий пользователя `workstation`.

Из `entrypoint.sh` сервера позже стало известно, что S3 действительно был VersityGW с включённым Object Lock в режиме `GOVERNANCE` и правилом хранения на 3650 дней. Владение соответствующими S3-реквизитами и право bypass-governance объясняют, как удалось убрать исторические версии. Простое удаление «текущего объекта» при S3 versioning не удовлетворило бы такую проверку.

После операций дашборд явно показывал:

```text
User Local Backup       Destroyed
Root Local Backup       Destroyed
Offsite Replica         Destroyed
S3 Governance           Destroyed
Rclone Remote 1         Destroyed
Old Rclone Remote       Intact
```

На этом состоянии появился **первый флаг, посвящённый governance**, и платформа его приняла. Второй флаг за полное уничтожение всех шести уровней не появился.

Нужно честно отметить ограничение архива: последовательность отдельных команд очистки 1–5 сохранена не целиком. Но их состояние **проверено дашбордом**, а технические причины — исходником чекера и конфигурацией сервисов.

## 6. Что было на backups-server: HTTP, rclone и SFTP

С workstation были доступны три сервиса сервера:

- `7070` — S3-совместимый VersityGW;
- `8000` — `rclone serve restic`, режим `--private-repos`;
- `8001` — ещё один `rclone serve restic` для offsite, `--append-only`.

Позже через обнаруженный file-read примитив удалось прочитать `/entrypoint.sh` самого сервера. В нём подтверждены:

```sh
install -d -o rclonebk /data/rclone
htpasswd -cbB /etc/htpasswd workstation <redacted>
htpasswd -bB /etc/htpasswd workstation-legacy "$LEGACY_REST_PASSWORD"

/usr/sbin/sshd -f /dev/null \
  -o ListenAddress=127.0.0.1:2200 \
  -o AllowUsers=rclonebk \
  -o 'Subsystem sftp internal-sftp'

rclone serve restic ":sftp,host=127.0.0.1,port=2200,user=rclonebk,pass=<redacted>:/data/rclone" \
  --addr :8000 --htpasswd /etc/htpasswd --private-repos --cache-objects=false

rclone serve restic /data/offsite \
  --addr :8001 --htpasswd /etc/htpasswd --append-only --cache-objects=false
```

Это был не `local` backend, как первоначально предполагалось, а **SFTP backend, указывающий в `/data/rclone`**, причём SFTP доступен только на loopback самого pod. Внешний `backups-server:2200` не слушал.

Имена пользователей `workstation` и `workstation-legacy` — отдельные области приватного REST-сервера. Обычные реквизиты первого аккаунта не дают права напрямую обращаться к путям второго.

## 7. Подтверждённый обход путей в rclone 1.74.3

При исследовании проверена известный path traversal в версии `rclone v1.74.3` (в журнале обозначен `CVE-2026-59733`). Это была не одна попытка, а серия проверок с уточнением модели.

Сначала Kali-среда не разрешала hostname `backups-server`. Позже выяснилось, что имена сервисов работают внутри CTF workstation; проверки перенесли туда по SSH. В HTTP-запросах использовались:

```sh
curl --path-as-is \
  -u '<workstation-user>:<password>' \
  -H 'Restic-Version: 2' \
  -H 'Accept: vnd.x.restic.rest.v2' \
  'http://backups-server:8000/workstation/../workstation-legacy/footage/'
```

`--path-as-is` важен: без него HTTP-клиент может схлопнуть `..` ещё до отправки и изменить смысл теста.

Первый ложный вывод: `GET` каталога legacy отвечал `200 []`, и это сперва было принято за признак пустого репозитория. Контрольные тесты опровергли гипотезу: `200 []` также возвращался для очевидно несуществующих репозиториев. **Пустой HTTP-список нельзя было приравнивать к пустому каталогу на диске.**

Затем проверили не вывод списка, а операции над **собственными тестовыми файлами** с фиксированными именами. Результаты оказались однозначны:

| Запрос | Наблюдение |
|---|---|
| `POST /workstation/__ctf_probe_.../marker` | 200 |
| `GET` того же пути | 200, записанный marker |
| `POST /workstation/../__ctf_probe_sibling_.../marker` | 200 |
| `GET` того же sibling пути | 200, ожидаемый marker |
| `GET` sibling через обычный путь внутри workstation | 404 |
| `DELETE` sibling marker через `../` | 200; следующий GET 404 |
| `DELETE` самого каталога | 404 |

Значит, **переход по `..` действительно выводил файловые операции из пользовательского дерева**. Контрольные объекты после проверки удалялись. Более поздний запрос:

```text
GET /workstation/../workstation-legacy/footage/config
Restic-Version: 2
Accept: vnd.x.restic.rest.v2

HTTP 200
Content-Length: 155
```

доказал наличие restic config в приватной области legacy. Это уже не косвенная догадка по HTTP-коду каталога, а чтение настоящего файла по известному имени.

## 8. Почему file read/write/delete не дали шестой флаг

В этом месте основная техническая ловушка. Мы можем прочитать, записать и удалить **конкретный файл, если знаем его путь**. Но условие `has_files` требует, чтобы в `/data/rclone/workstation-legacy` вообще не осталось файлов. У restic имена объектов в `keys/`, `data/`, `index/`, `snapshots/` похожи на длинные хэши.

Для их удаления нужен **листинг**, а он не работал через обход приватного префикса.

Обычные GET-листинги через `workstation/../workstation-legacy/` возвращали `200 []`. Без завершающего слеша иногда был `500`. Причина была изучена по реализации SFTP/rclone:

```go
// backend sftp: путь нормализуется
root := path.Join(f.absRoot, dir)
remote := path.Join(dir, info.Name())
```

Слой REST/filter сравнивал **сырое** имя вида `workstation/../workstation-legacy/footage` с уже нормализованным remote `workstation-legacy/footage/config`. Элементы реально находились backend'ом, но отсеивались фильтром списка. Отсюда `[]` для существующего каталога.

Вход напрямую в `/workstation-legacy/footage/` отклонял `checkPrivate` с `403`, потому что авторизованный пользователь — `workstation`. Рабочий `../` даёт путь к файлу, но не полноценный API перечисления соседнего дерева.

Именно это различие между **точечными файловыми операциями** и **обходом directory listing** не позволило сделать шестой уровень `Destroyed`.

## 9. Дополнительные проверки, которые не сработали

### 9.1 Полноширинные точки

Проверяли Unicode-путь с U+FF0E U+FF0E (в URL `%EF%BC%8E%EF%BC%8E`). Для `config` получали `404`, для списков — `[]`. Это не превратилось в корректный путь к соседнему каталогу. Гипотезу закрыли.

### 9.2 .rclonelink

Создали собственный файл-ссылку с суффиксом `.rclonelink` и попытались открыть alias. POST создания отвечал `200`, но обращение к alias возвращало `404`, листинг через него — `[]`. В конфигурации сервера не было `--links`. Тестовые объекты удалены.

### 9.3 HTTP-методы и удаление каталога

`PUT` возвращал `405`, `DELETE` каталога — `404`, `OPTIONS` часто `403`, `HEAD` — `500`. `POST`/`GET`/`DELETE` обычного файла были рабочими, но API рекурсивного удаления каталога не обнаружили.

### 9.4 Offsite и S3

На `8001` не нашлось копии legacy. Через VersityGW виден только bucket `footage`, а не `workstation-legacy`. Доступа к отдельному репозиторию через эти сервисы не было.

### 9.5 Получение пароля legacy

В `/entrypoint.sh` пароль пользователю `workstation-legacy` передаётся как `$LEGACY_REST_PASSWORD`. В `/etc/htpasswd` сохранён bcrypt, не открытый пароль. У известного `RESTIC_PASSWORD` другое назначение: это пароль шифрования **содержимого** restic-репозитория, а не Basic Auth для приватного REST-аккаунта.

Проверяли пароли из рабочей среды, тематические комбинации, а также `rockyou.txt` (~14,3 млн слов), с отрицательным результатом. В одном из сообщений уточняется, что `restic` не находил ключ через traversal не только из-за пароля, но и потому, что `keys/` нельзя было перечислить. Подбор остановили, поскольку он не устранял основной блокер.

### 9.6 Kubernetes и /proc

В workstation не было `kubectl`, `docker`, `crictl`, `ctr`, `sudo`, service-account токена или полезных томов. В backups-server через файловое чтение проверили `/var/run/secrets/kubernetes.io/serviceaccount/{token,namespace,ca.crt}` — `404`, а `/root/.kube/config` — отказ в чтении.

Чтение `/etc/passwd` показало пользователя `rclonebk` (uid 1000), от которого выполнялся rclone. Динамические `/proc/*/cmdline` и `/proc/mounts` возвращали 0 байт, `/proc/*/environ` отсутствовали/были недоступны. Это исключило прямую выдачу переменной окружения с legacy-паролем через найденный file read.

### 9.7 Попытка изменить htpasswd

Контрольный POST **идентичной копии** `/etc/htpasswd` возвращал `500`, контрольная хэш-сумма файла оставалась прежней. Процесс uid 1000 не имел права перезаписать этот файл. Способ авторизоваться как `workstation-legacy` не появился.

## 10. Новое чтение за пределами backend root

Следующей гипотезой было использовать несколько `../` и узнать, может ли сервер прочитать собственную файловую систему. Сработало:

```text
/workstation/../../../etc/hostname          -> 200
/workstation/../../../etc/passwd            -> 200
/workstation/../../../etc/hosts             -> 200
/workstation/../../../etc/resolv.conf       -> 200
/workstation/../../../data/rclone/workstation-legacy/footage/config -> 200
```

Так было доказано **произвольное чтение файлов rootfs контейнера в пределах полномочий uid 1000**, но не вывод содержимого `/root`. Это позволило прочитать `/entrypoint.sh` и уточнить реальную архитектуру. Однако API listing оставался сломанным на тех же правилах сравнения путей. Ещё один примитив чтения не дал имена тысяч потенциальных объектов.

## 11. Состояние и прекращение работы

Последняя достоверная проверка дашборда продолжала показывать:

```text
5 destroyed / 1 intact
Old Rclone Remote: Intact
FLAG_2: not issued
```

Когда был подготовлен следующий read-only тест, перестали отвечать SSH workstation, REST-сервисы сервера, checker и VPN gateway. Это зафиксировано как **недоступность CTF-стенда**, а не новый вывод о его безопасности.

Важно не смешивать результаты:

- Governance-флаг: **получен и принят**.
- Пять первых стадий: **подтверждены как Destroyed**.
- Файловый path traversal: **подтверждён** для GET/POST/DELETE известных файлов; чтение rootfs в рамках прав сервиса подтверждено.
- Directory listing соседнего приватного репозитория: **не удалось**.
- Старый REST-пароль: **не найден**.
- Шестая стадия и второй флаг: **не закрыты**.

## 12. Практические выводы и защита

1. Всемирно записываемая конфигурация root scheduler равнозначна возможности исполнять команды с root-правами. `profiles.yaml` должен быть доступен на изменение только доверенному владельцу.
2. Экспорт root-окружения может раскрыть ключи ко всем уровням резервирования. Секреты должны быть изолированы по задачам и сервисам, а не сконцентрированы в одном процессе.
3. При включённом S3 versioning и Object Lock нужно контролировать удаление старых версий и права `bypass-governance` отдельно от обычного `DeleteObject`.
4. Защитное `--private-repos` бесполезно, если обработка `..` различается между авторизацией, SFTP backend и файловыми операциями. Путь нужно нормализовать **до** проверки доступа и везде использовать одно каноническое представление.
5. Успешный ответ `200 []` не доказывает пустоту каталога; всегда необходим контроль на заведомо существующем и заведомо несуществующем объекте.
6. Каталог, считающийся «уничтоженным» лишь при `has_files==false`, имеет совершенно другой критерий, чем `restic find`. Нельзя механически переносить успешный способ с уровней 1–5 на уровень 6.

## 13. Источники и статус воспроизведения
