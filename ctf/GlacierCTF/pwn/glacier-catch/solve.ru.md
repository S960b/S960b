# Glacier Catch — технический райтап

[English version](solve.md)

## 1. Что было в задаче

В оригинальном `glacier-catch.tar.gz` находились статический PIE-бинарник `chip8` для x86-64, Flask-приложение `src/app.py`, Docker-конфигурация, штатная ROM и файл флага-заглушки. Сервис работал в Alpine с SDL2 и Xvfb. Заголовок веб-страницы: **Glacier Arcade · CHIP-8**.

Через `POST /api/start` можно загрузить свой ROM размером до `0xE00`, через `POST /api/keys` передать нажатия, через `GET /api/status` узнать состояние эмулятора, а через `GET /stream` получить MJPEG-кадры 64×32. Флаг лежал в контейнере в `/flag.txt`.

Это эксплуатация нативного CHIP-8-интерпретатора, а не Flask. Полный оригинальный текст задачи и автор в архиве не записаны.

## 2. Баг: выход за пределы виртуальной памяти

У CHIP-8 всего 4096 байт виртуальной RAM. Однако инструкции `FX65` (чтение в регистры V0..VX) и `FX55` (запись регистров) в данном эмуляторе допускали обращение по 16-битному `I` **за пределами RAM**.

В нативной структуре:

```text
Cpu RAM       = Cpu + 0x866
Cpu.renderer  = Cpu + 0x1868
```

Чтобы записать по `Cpu+0x1868`, достаточно задать `I=0x1868-0x866=0x1002`. Значит, ROM умеет читать нативные указатели и повреждать внутренние поля эмулятора. Кадр SDL используется как канал вывода утечек: восьмибитные значения переводятся в пиксели, а Python-клиент считывает их по яркости. В обратном направлении данные доставляются через пары клавиш-«нибблов» и сохраняются в RAM инструкцией `FX55`.

## 3. Утечки и обход PIE

Оригинальный эксплойт исходил из неверного предположения о расстоянии между `Cpu` и `SDL_Renderer`. На сервере ROM-сканер обнаружил:

```text
renderer - Cpu = 0x58f0
```

Локально встречались другие значения: `0x1930`, `0x2be0`, `0x12fb0`. Поэтому чужой `delta` нельзя хардкодить без проверки на конкретном окружении.

Три утечки в одном процессе раскрывали:
1. `SDL_Renderer*`, хранящийся по `Cpu+0x1868`.
2. Указатель на magic/fn для вычисления базы PIE.
3. Колбэк `SDL_RenderPresent` по `renderer+0xb0`.

Контрольные соотношения:

```python
pie = magic - 0x484e44
assert pie & 0xfff == 0
assert callback == pie + 0x6c88f
```

Это защищало от неверного чтения JPEG/зависших кадров. При получении совпадающих утечек известные офсеты функций и ROP-гаджетов превращались в полноценные адреса с учётом ASLR.

## 4. Почему первые эксплойты падали

Первоначально поля **живого** `SDL_Renderer` изменялись непосредственно, затем ROM вызывал перерисовку и предполагалось попасть через `_longjmp` в ROP. На сервере почти всегда происходил краш (HTTP 409 на `/stream`).

Проверки постепенно исключили транспортную проблему:

- `payload integrity`: **536 байт** доставлены и размещены точно, **2144 события клавиш**, 8/8 проверочных кадров.
- `checkpoints`: сами записи отдельных полей ещё не убивали процесс; падение происходило на нативном переходе/в цепочке.
- `fastpatch` с `--pad 1,33,65,97,129,161,193,225`: падения не исчезли; гипотеза о фазе redraw не подтвердилась.
- Локальные и удалённые раскладки памяти заметно различались; ROM с жёсткой дельтой был ненадёжен.

Вероятное объяснение: SDL успевала использовать частично изменённые рабочие колбэки. Однако точная инструкция падения не сохранилась — это **гипотеза, а не доказанный root cause**.

## 5. Финальный метод: клонируем SDL_Renderer

Рабочий `glacier_catch_clone_renderer_patched.py` вместо порчи настоящего рендерера создаёт его копию:

1. `FX65` читает **0x300 байт** из настоящего `SDL_Renderer` по 8 байт за раз.
2. `FX55` складывает копию в виртуальную память `0x800..0xaff` (три страницы по 256 байт).
3. В копии меняются поля `+0x30`, `+0x38`, `+0x68`, `+0xb0`, `+0x284`, `+0x2cc`; колбэк в `+0xb0` указывает на `_longjmp`.
4. Только после окончания подготовки ROM единственной OOB-записью с `I=0x1002` заменяет `Cpu.renderer` на адрес копии.
5. Инструкция `00E0` вызывает отрисовку через клон → `_longjmp` → ROP.

**Ключевой порядок:** копирование → изменение неактивной копии → одна подмена указателя → вызов. Настоящий SDL-объект не трогается до перехвата.

## 6. ROP, восстановление рендерера и возврат к ROM

Из сохранённого рабочего исходника:

```text
_longjmp                 PIE+0x312f90
memcpy                   PIE+0x318891
open                     PIE+0x307c67
read                     PIE+0x31beaf
Cpu::run                 PIE+0x27e0c
pop rdi / rsi / rdx      PIE+0x25278 / +0x24f18 / +0x23ae97
xchg eax,edi; ret        PIE+0x10b2b7
```

Payload имеет размер **536 байт**: 216-байтовый заголовок по VM-адресу `0x400` и 320-байтовый ROP-блок по `0xe02`. Нативный адрес поддельного стека — `Cpu+0x866+0xe02`.

Эксплойт разделили на два режима:

- `marker`: ROP вызывает `memcpy`, копирует `ROP_OK!!` в RAM по `0x600`, восстанавливает исходный `Cpu.renderer` и возвращается в `Cpu::run`. Успешный удалённый вывод: `[+] STAGE PASSED: ROP_OK!!`. Это доказывает, что нативный переход и возврат работают.
- `read-dynamic`: `open('/flag.txt', 0)`, перенос результата `open` из EAX в EDI через `xchg eax,edi; ret`, `read(fd, VM+0x600, 128)`, восстановление исходного указателя рендерера через `memcpy`, повторный вход в `Cpu::run`.

Номер файлового дескриптора не угадывается. Root, shell и выход из контейнера не требуются: процесс уже может читать `/flag.txt`.

ROM после возврата отрисовывает байты из RAM на экране 64×32 в виде полосок по 8 пикселей на байт. В финальной версии использованы **восемь блоков по 15 байт и девятый на 8 байт**, что позволяет показать до 128 байт. Первая версия читала 64 байта и потому обрезала **68-байтовый флаг**.

## 7. Подтверждение успеха

В консоли успешного marker-прогона было:

```text
[FAKE] mode=marker ... ROP=18 qwords
[keys] 2144/2144 events
[+] STAGE PASSED: ROP_OK!!
```

На отдельном свежем инстансе `read-dynamic` вывел полный флаг на экран. Агент декодировал скриншот `flag128.png`. В архиве есть `FLAG.txt` с расшифрованным значением. Пользователь **подтвердил принятие флага платформой**.

Полный флаг в публичном GitHub по договорённости маскируем как `gctf{...}`. Сырой текст консоли финального успешного прогона отдельно не сохранился, зато есть скриншоты, исходный код и отчёт. Не выдаём цитату отчёта за новый повторный запуск.

## 8. Воспроизводимость

Все данные лежат в пользовательском архиве `glacierctf_glacier_catch_materials.zip`:

```text
glacierctf_glacier_catch/
  REPORT.md
  FLAG.txt
  assets/glacier-catch.tar.gz
  scripts/working/glacier_catch_clone_renderer_patched.py
  scripts/working/glacier_catch_standalone_proxyfixed.py
  evidence/screenshots/flag128.png
  evidence/roms/
  evidence/payloads/
```

Финальный файл импортирует `glacier_catch_standalone`, а соответствующий базовый файл из архива называется `glacier_catch_standalone_proxyfixed.py`. Для **частной** локальной репродукции базовый файл следует переименовать в `glacier_catch_standalone.py`. Подробности: [scripts/README.md](scripts/README.md).

Исторические команды (для ныне недоступных инстансов, **при публикации не выполнялись**):

```sh
python3 glacier_catch_clone_renderer.py --url 'https://<instance>.glacier-catch.web.glacierctf.com' --delta 0x58f0 --mode marker
python3 glacier_catch_clone_renderer.py --url 'https://<instance>.glacier-catch.web.glacierctf.com' --delta 0x58f0 --mode read-dynamic
```

Второй режим запускали на новом инстансе. `delta=0x58f0` был измерен в конкретном окружении и не обязан совпадать на другой машине. Для чтения сохранённых картинок можно использовать [scripts/decode_frame.py](scripts/decode_frame.py).

## 9. Выводы

- Проверять границы доступа `I + X` к 4096 байтам виртуальной RAM критически необходимо.
- Управляемая ROM может превратиться в запись по нативным адресам C++-процесса.
- Утечки указателей обходят PIE/ASLR, если офсеты функций известны.
- Изменение неактивной копии объекта с последующей единственной подменой указателя надёжнее, чем изменение живых колбэков.
- Сначала нужно доказать доставку payload и marker-цепочку, затем выполнять чтение файла.
- Размер буфера чтения должен учитывать длину **всего** флага.

Для написания этого райтапа ни исходный бинарник, ни удалённый сервис повторно не запускались.
