# VoteMe: ход решения

## 0. Общий план

Хендаут - бандл: исходники Ruby-сервиса голосования (`record.rb`, `gateway.rb`,
TLS с собственным ECDH на клиенте и сервере, PLONK-схема доказательства и zkey) и PCAP
прогона «кампании» - все секретные голоса, которые логирует сервер, плюс 1000
опубликованных бюллетеней. Цель - восстановить секретные голоса: они кодируют флаг в
троичной системе (420 голосов = 70 байт).

Цепочка замыкает шесть независимых слабостей, каждая по отдельности маленькая:

1. Порядок кастомной кривой делится на 2^16, поэтому 2-адическая атака по подгруппе
   восстанавливает младшие 16 бит каждого приватного ECDH-скаляра из публичной точки.
2. Все приватные скаляры приходят из одного Ruby `Random.new` (MT19937). Младшие биты
   дают линейную систему над GF(2); решив её, определяем последний TLS-скаляр.
3. С этим скаляром и ClientKeyExchange выводим premaster, TLS AES-256-GCM
   расшифровывается (GCM-тег сходится), и JSON `/votes` с 1000 бюллетеней - открытый
   текст.
4. Каждый бюллетень выдаёт V8 `Math.random()` через баг `@lukeed/uuid` v2; линейная
   алгебра восстанавливает состояние xorshift128+ (64 кандидата), следующие выходы
   предсказуемы.
5. PLONK blinding-скаляры тоже из `Math.random()`; пересчитав обязательство `A` для
   голосов 0,1,2, подбираем правильный голос для каждого бюллетеня.
6. Декодируем первые 420 голосов по 6 тритов в байт в ASCII.

## 1. Раскладка задачи

Зачем этот шаг: понять, какие данные существуют и где, до того как трогать крипту.

- `record.rb` проводит кампанию и пишет `traffic.pcap`: 420 секретных голосов
  (серверные записи), затем `populate(1000-used)` - каждый «голос» это отдельное
  TLS-соединение (в перехвате 1741 исходящий SYN), потом один `GET /votes`.
- Кастомный TLS использует кривую из `curve.rb` (`Curve::ORDER`, `Curve::G`);
  серверные ECDH-скаляры генерируются `Random.new(...).bytes(32)`.
- Каждый бюллетень - PLONK-доказательство из браузера: circom-схема, ключ
  `vote_plonk.zkey` и `@lukeed/uuid` 2.0.1 для бета-идентификаторов.

PCAP плюс исходники сервиса - это всё; живого сервера задачи нет, решение полностью
офлайн.

## 2. Младшие биты ECDH-скаляров

Зачем этот шаг: чётный `ORDER` позволяет делить многократно; маленькая 2-подгруппа
делает дискретный лог тривиальным.

`Curve::ORDER` делится на 2^16, и `G` имеет ненулевую компоненту в 2^16-подгруппе
кручения. Для каждой публичной точки сервера в каждом TLS ServerKeyExchange:

```text
P = k*G;  k mod 2^16 = dlog по 2^16-подгруппе от P
```

2-адическая лестница стоит порядка 2^16 операций подгруппы, но с правильным базисом
гораздо дешевле; сохранённые наблюдения (`observed_lowbits.txt`) - 1741 значение
`scalar % 65536`.

## 3. Взлом общего MT19937

Зачем этот шаг: сервер использует один RNG для всех скаляров, поэтому «случайность» -
это детерминированная последовательность битов.

`Random#bytes(32)` съедает 8 подряд 32-битных выходов MT19937; младшие 16 бит скаляра
равны младшим 16 битам первого слова (множитель 2^16 в порядке их сохраняет). 1741
наблюдение дают 27856 линейных уравнений на 19968-битное состояние MT19937; исключение
Гаусса над GF(2) оставляет 15 свободных бит в неиспользуемой части одного слова и точно
предсказывает последний скаляр. Предсказание проверяется по последней публичной точке
(сходится).

## 4. Расшифровка TLS

Зачем этот шаг: с последним ECDH-скаляром и клиентским key exchange сообщением ключи
сессии следуют из стандартного TLS PRF.

Считаем premaster = `client_pub ^ server_priv` (на кастомной кривой), запускаем
TLS PRF (SHA-384), выводим ключи/IV AES-256-GCM и расшифровываем каждый рекорд. GCM-тег
аутентифицирует данные; открытый текст - JSON `/votes`: 1000 бюллетеней, каждый
`{proof, pubSignals, ...}`.

## 5. Восстановление состояния V8 RNG

Зачем этот шаг: идентификаторы бюллетеней сделаны сломанной UUID-библиотекой,
утекающей рандом.

`@lukeed/uuid` 2.0.1 использует `Math.random()` и публикует ~122 бита из 128-битного
состояния xorshift128+ - примерно 6 неизвестных бит на состояние плюс кеш из 64
пре-сгенерированных выходов, которые хранит V8 RNG. Бета-идентификаторы бюллетеня дают
16 подряд выходов `Math.random()`. Линейная алгебра по ним восстанавливает состояние с
точностью до 6 свободных бит; перебор 64 кандидатов даёт следующий выход. Скрипт
`v8_uuid.py` реализует восстановление состояния.

## 6. Выбор голоса через PLONK

Зачем этот шаг: значение голоса спрятано внутри доказательства; RNG делает его
проверяемым без валидатора.

snarkjs в браузере использует fallback `ffjavascript`, который сидирует ChaCha20 через
`Math.random()` вместо CSPRNG. Из восстановленного состояния V8 следуют 32 байта
сида ChaCha20, а из них - первые два PLONK blinding-скаляра для обязательства `A`. Для
каждого из 64 кандидатов состояния и каждого голоса в {0,1,2} пересчитываем `A`
(используя `vote_plonk.zkey`, секцию Powers of Tau и Lagrange IFFT). Ровно одна
комбинация из 64x3 совпадает с оригинальным обязательством каждого бюллетеня - эта
комбинация и опознаёт голос.

## 7. Чтение флага

Зачем этот шаг: секретные голоса - это открытый текст; группируем 6 тритов в байт.

Первые 420 восстановленных значений - триты в {0,1,2}; группируем по 6:
`byte = sum(trit[j] * 3^(5-j))`. Полученные 70 байт - ASCII-флаг. Голоса 420..425
воспроизводят известный тестовый цикл 1,0,2,1,0,2 - контрольная проверка того, что вся
цепочка верна.

`quick_verify.py` проверяет всё это офлайн: SHA-256 хендаута, 1000 голосов, 426
уникальных строк, шесть тестовых голосов и точный 70-байтовый флаг.

## 8. Воспроизведение

Зачем этот шаг: результатом должна быть работа из оригинального PCAP, а не из
сохранённых выводов.

```bash
python3 quick_verify.py          # офлайн-проверка сохранённых доказательств -> флаг
bash run_reproduce.sh            # полная цепочка из оригинального tar.gz (нужны python3, cryptography, ruby, g++, libgmp-dev)
```

Полное воспроизведение тяжёлое (система GF(2) `27856 x 19968` плюс пересчёт PLONK
обязательств), но офлайн и не требует сервера задачи.

## 9. Тупики (не повторять)

- **Атака на полный дискретный лог кривой.** Не нужно: утекают только младшие 16 бит,
  и этого достаточно для уравнений на RNG.
- **Брутфорс выходов MT19937.** 19968 бит далеко за пределом перебора; правильный
  инструмент - линейная система.
- **Угадывание сидов UUID.** Кеш из 64 пре-сгенерированных выходов ломал наивный поиск
  сида; линейно-алгебраическое восстановление состояния решает это.
- **Доверие `votes.json` до расшифровки.** Файл доверяется только после проверки GCM
  тега внутри TLS-рекордов; всё остальное не аутентично.

## Короткая версия

Кастомная кривая слаба 2-адически и утекает младшие биты скаляров; серверный RNG - один
MT19937 с одним сидом, поэтому 1741 младшебитовых сэмплов решают финальный TLS-скаляр;
трафик AES-GCM расшифровывается; идентификаторы бюллетеней утекают V8 `Math.random()` и
восстанавливают xorshift128+; PLONK-случайность - тот же RNG, поэтому голос каждого
бюллетеня находится сопоставлением пересчитанных обязательств; 420 голосов в троичной
системе декодируются во флаг.

## Выводы

- Составные порядки подгрупп заслуживают 2-адической проверки до использования;
  утечка 16 бит на ключ превращает «случайный» генератор ключей в полностью
  предсказуемый.
- Повторное использование одного сида RNG в разных протоколах (TLS-ключи и
  случайность доказательств) схлопывает их в одну систему уравнений.
- Когда случайность системы доказательств воспроизводима, обязательства становятся
  верификаторами: сопоставление `A` по множеству кандидатов голоса решает скрытый вход.
