# El Clásico — подделка Groth16 через исключительный случай GLV

[English version](solve.md)

## 1. Условие и схема

Организатор выдал `challenge.go`, ключ доказывания `pk.hex`, ключ проверки `vk.hex` и Go-модуль с **gnark v0.16.4**, **gnark-crypto v0.21.1-0.20260913224755-1409fe592052**. Groth16 построен над BN254, а арифметика точек/скаляров **BLS12-381 G1 эмулируется** внутри схемы.

`GET /challenge` возвращает мишень `A=(a,b)`. В `POST /submit` передаются десятичные `s`, `p_x`, `p_y` и шестнадцатеричная сериализация доказательства `proof_hex`. Сервер требует `0<s<r` и **`s % 9 != 0`**, проверяет witness и использует исходный Groth16 verifying key.

Суть исходника `challenge.go`:

```go
curve.AssertIsOnCurve(&c.P)
curve.AssertIsInSubgroup(&c.P)
q := curve.ScalarMul(&c.P, &c.S)
dx := fp.Sub(&q.X, &c.A.X)
dy := fp.Add(&q.Y, &c.A.Y)
fp.AssertIsDifferent(&q.X, &c.A.X)
fp.AssertIsEqual(fp.Mul(fp.Mul(dx, dx), dx), fp.Mul(dy, dy))
```

Нужно доказать, что при `Q=[s]P`:

```text
Q.x ≠ a
(Q.x-a)^3 = (Q.y+b)^2 (mod p)
```

Честный результат умножения — точка группы; задача задумана как невозможная для честной модели.

## 2. Причина: несостоятельная classic GLV реализация

Исследование исходников библиотеки установило, что `Curve.ScalarMul` в этом случае идёт в **`scalarMulGLV`**, а не в `scalarMulGLVAndFakeGLV`. В классическом пути результат не проверяется отдельно на принадлежность кривой и подгруппе.

GLV раскладывает скаляр на две короткие части:

```text
[s]P = [s1]P + [s2]Φ(P)
Φ(x,y) = (ωx,y)
s1 + λ*s2 ≡ s (mod r)
λ²+λ+1 ≡ 0 (mod r)
```

Хинт разложения возвращает два числа примерно по 128 бит и знаки. В схеме проверяются их разрядность и линейное соотношение, но **не требуется каноническое разложение**. В итоге доказывающий может выбрать другое допустимое `s1,s2`.

Внутри `scalarMulGLV` используются неполные формулы `add`, `double`, `doubleAndAdd`, `triple` с `ratioHint` для наклона хорды. При совпадении двух точек числитель и знаменатель отношения становятся нулями. Ограничение превращается в:

```text
0 * slope = 0
```

Оно разрешает **любой slope**. Поддельный наклон выводит `Q` с кривой, но не нарушает ограничений схемы.

## 3. Что первоначально оказалось неверным

В прежнем диалоге ChatGPT предложил `s1=2λ+9`, `s2=5`. Агент проверил эту гипотезу на точной модели и **не обнаружил `0/0`**. Эта пара не является решением.

При построении симулятора нашли ещё две ошибки:

- неправильный знак в `doubleAndAdd`: требуется `y3=l2*(x3-x1)-y1`;
- ошибочный инвариант аккумулятора перед последним окном; после исправления коэффициенты **`4u+2`** и **`4v+2`**, где `u=s1>>3`, `v=s2>>3`.

Простая проверка `ccs.Solve` падала из-за placeholder для commitment. Поэтому создана отдельная `CheckCircuit` с полноценными Groth16 Setup/Prove/Verify и трассой `ratioHint`. Симулятор сверили со **140 вызовами ratioHint** реального gnark и несколькими обычными разложениями `(s1,s2)`, включая `(12345,6789)`.

## 4. Создание коллизии через решётку

Определяем решётку:

```text
L = {(x,y): x+λy ≡ 0 (mod r)}
```

В последнем объединённом окне `i=2` пусть `u=s1>>3`, `v=s2>>3`. После удвоения аккумулятор равен линейной комбинации `(4u+2,4v+2)` в базисе `P,Φ(P)`. Табличная точка задаётся коэффициентами `(d_Q,d_Φ)` из `{-3,-1,1,3}`.

Совпадение при `doubleAndAdd` получается, если

```text
(4u+2-d_Q) + λ*(4v+2-d_Φ) ≡ 0 (mod r)
```

То есть нужен короткий вектор этой решётки. Поиск через редукцию Гаусса нашёл особенно простой вариант:

```text
(x,y) = (λ,-1)
λ = 228988810152649578064853576960394133503
d_Q=-1, d_Φ=3
u=57247202538162394516213394240098533375
v=0
s1=457977620305299156129707153920788267003 = 2λ-3
s2=7
sign1=sign2=0
s=2060899291373846202583682192643547201524
s%9=6
```

`s1` имеет 129 бит, `s2` — 3 бита, и оба проходят диапазоны проверок. Также `s1+λ*s2≡s (mod r)`. В последнем окне складываемые точки совпадают — возникает свободный наклон `0/0`.

## 5. Подбираем наклон под заданную мишень

Для точки коллизии `(x0,y0)` обозначим `z=m²-3x0`. Координаты поддельной `Q` выражаются через свободный наклон `m`:

```text
x3=NX/z²
NX=4*m*y0*z+4*y0²+x0*z²
y3=NY/z³
NY=(m*z+2*y0)*(4*m*y0*z+4*y0²)-y0*z³
```

Чтобы выполнить проверку `(Q.x-a)^3=(Q.y+b)^2`, умножаем на знаменатели:

```text
(NX-a*z²)^3-(NY+b*z³)^2 ≡ 0 (mod p)
```

Получается многочлен **12-й степени**. Для мишени удалённого сервиса поиск нашёл **пять корней**. Подходящий наклон:

```text
m=3779855849564975014954687576048500261310875051983363318127962126203533956438461724178333382126496049625088006452104
```

Полученная `Q` **не лежит на BLS12-381**, но проходит `Q.x!=a` и кубическое сравнение по модулю `p`; второй знаменатель `z≠0`, поэтому дальнейшая арифметика остаётся определённой.

## 6. Как создано доказательство

Сохранённый успешный Go-файл `scripts/solver_main.go` из архива агента использовался как `solver/main.go` в модуле организатора. Он меняет реализации только **двух хинтов**, не меняя исходную схему, proving key и verifying key:

| Хинт | ID | Вывод |
| --- | ---: | --- |
| `decomposeScalarG1` | `1139094758` | `s1=2λ-3`, `s2=7`, знаки 0 |
| `ratioHint` | `3763044065` | при `num=den=0` вернуть выбранный `m`, иначе честно делить |

Солвер сначала сравнивает `GET /challenge` с сохранённой мишенью. Затем `frontend.Compile` → загрузка `pk.hex/vk.hex` → witness → `groth16.Prove` с `solver.OverrideHint(...)` → **локальный `groth16.Verify`** → `POST /submit`.

В фактическом журнале:

```text
nbConstraints=192987
hint ids: decomp=1139094758 ratio=3763044065
local Groth16 verify OK
HTTP 200: Flag is: gctf{...}
```

То есть сервер принял доказательство и вернул флаг. Полный флаг сохранён в частных `FLAG.txt` и `evidence/solve_run.log`, а в GitHub маскируется.

## 7. Материалы и независимые проверки

В `glacierctf_el-clasico_materials.zip` лежат оригинальный **46 348 852-байтовый** архив задания, `REPORT.md`, реальный `solver_main.go`, поиск GLV на Python, симулятор и трасса, `params.json`, тело настоящего запроса `submit_request.json`, расчёты и лог успешной сессии.

[scripts/verify_parameters.py](scripts/verify_parameters.py) проверяет математическую согласованность сохранённых параметров и поддельной `Q` без подключения к сети. Это **не** самостоятельная проверка Groth16 proof: настоящая криптографическая проверка выполнялась при историческом запуске.

В предыдущем чате были только исходная идея и пересылка задания через git-мост. Финальный архив агента исправляет ошибочные параметры, содержит рабочий солвер и успешный ответ сервиса. Это разные этапы одного исследования.

## 8. Вывод

Даже при корректном Groth16 verifier схема может быть **несостоятельной**, если хинтам доверяют больше, чем разрешают ограничения. Здесь сочетание свободного разложения GLV и неполной формулы сложения дало недоопределённую переменную, поддельную точку вне кривой и принятое доказательство.
